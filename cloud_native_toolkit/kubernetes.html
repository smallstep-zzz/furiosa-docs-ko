Kubernetes 플러그인#

Kubernetes 지원#

다음 Kubernetes 및 CRI 런타임 버전을 지원합니다:

  • Kubernetes: v1.24.0 이상

  • helm v3.0.0 이상

  • CRI 런타임: containerd 또는 CRI-O

참고

Docker는 Kubernetes에서 공식적으로 컨테이너 런타임으로 사용이 중단되었습니다. containerd 또는 CRI-O를 컨테이너 런타임으로 사용하는 것이 권장됩니다. 그렇지 않으면 NPU 플러그인과 관련된 예기치 않은 문제가 발생할 수 있습니다. 자세한 내용은 [여기에](링크) 참조하십시오.

NPU 플러그인 배포 가이드#

관리자로서, 당신은 설치해야 전제 조건 driver, firmware와 같은 NPU 노드. 사전 예약이 설치되지 않은 경우 NPU 플러그인은 오류를 반환합니다.

NPU 플러그인을 Helm 차트를 사용하여 배포하는 것을 권장합니다. 각 플러그인을 개별적으로 제어하기 어렵기 때문입니다. NPU 플러그인이 NPU 노드 외의 노드에 배포되면 플러그인이 지원되지 않는 오류를 반환하고, Pod는 CrashLoopBackOff 상태로 유지됩니다.

Helm 차트는 기본적으로 Node Feature Discovery (NFD)를 배포합니다. NFD가 배포되면 NPU 노드는 자동으로 PCI ID 및 기능을 사용하여 레이블이 지정됩니다. NPU 노드에 추가되는 레이블의 예시는 다음과 같습니다:

feature.node.kubernetes.io/pci-1200_1ed2.present: "true"
feature.node.kubernetes.io/pci-1200_1ed2.sriov.capable: "true"

NPU 플러그인 Helm 차트를 사용하여 NPU 노드에만 플러그인 배포를 제어하도록 nodeAffinity 설정을 다음과 같이 구성합니다.

affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: feature.node.kubernetes.io/pci-1200_1ed2.present
          operator: In
          values:
            - "true"

참고

이미 클러스터에 NFD가 배포되어 있는 경우, Helm 차트 설정을 통해 NFD 배포를 건너뛸 수 있습니다. 하지만 NFD가 기본 레이블 정책을 갖도록 해야 합니다. 기본 레이블 정책에는 PCI 클래스 및 Vendor ID 필드가 포함됩니다.

feature.node.kubernetes.io/pci_<CLASS_ID>_<VENDOR_ID>.present

일부 경우, NFD는 레이블에 PCI 클래스 필드를 생략하도록 구성될 수 있습니다.

feature.node.kubernetes.io/pci_<VENDOR_ID>.present

이 문제를 해결하는 방법은 다음과 같습니다. * 클러스터에 서로 다른 레이블 정책을 가진 두 개의 NFD 인스턴스를 배포하고, taint 및 toleration을 사용하여 관리합니다. * NPU 플러그인 Helm 차트를 수정하여 올바른 레이블을 사용하도록 합니다.

각 플러그인의 자세한 정보 및 구성은 다음 링크를 참조하십시오:

  • Furiosa Feature Discovery 설치
  • Furiosa 장치 플러그인 설치
  • Furiosa DRA 드라이버 설치
  • Furiosa 메트릭스 익스포터 설치
  • Furiosa NPU 운영자 설치

NPU 플러그인을 설치한 후, 클러스터는 Furiosa NPUs를 스케줄 가능한 리소스로 노출합니다 (예: furiosa.ai/rngd).

노드가 준비되었는지 확인하려면 v1.node 객체의 Capacity 및/또는 Allocatable 필드를 검사할 수 있습니다. 다음은 2개의 RNGD NPUs를 가진 노드의 예입니다:

...
status:
  ...
  allocatable:
    cpu: "20"
    ephemeral-storage: "1770585791219"
    furiosa.ai/rngd: "2"
    hugepages-1Gi: "0"
    hugepages-2Mi: "0"
    memory: 527727860Ki
    pods: "110"
  capacity:
    cpu: "20"
    ephemeral-storage: 1921208544Ki
    furiosa.ai/rngd: "2"
    hugepages-1Gi: "0"
    hugepages-2Mi: "0"
    memory: 527830260Ki
    pods: "110"
...

다음 명령은 Kubernetes 클러스터의 각 노드의 Capacity 필드를 표시해야 합니다.

kubectl get nodes -o json | jq -r '.items[] | .metadata.name as $name | .status.capacity | to_entries | map("    \(.key): \(.value)") | $name + ":\n  capacity:\n" + join("\n")'

NPU 요청#

Pod 내의 컨테이너에서 NPU 리소스를 요청하여 NPU를 사용할 수 있습니다. 이는 CPU 또는 메모리를 요청하는 것과 동일한 방식입니다.

그러나 NPU는 사용자 정의 리소스로 노출되므로 NPU 리소스를 요청할 때 몇 가지 제한 사항을 고려해야 합니다:

  • NPU를 지정할 수 있습니다 limits 명시하지 않고 requestskubernetes가 요청이 지정되지 않은 경우 요청으로 제한을 사용할 수 있기 때문에.

  • 제한(limits)과 요청(requests) 모두에서 NPU를 지정할 수 있지만, 두 값은 반드시 동일해야 합니다. (NPU는 "Neural Processing Unit"의 약자입니다.)

  • 요청(requests)에 NPU를 지정하려면, 반드시 제한(limits)을 지정해야 합니다.

2개의 RNGD NPU를 요청하는 Pod에 대한 예시 Manifest는 다음과 같습니다:

apiVersion: v1
kind: Pod
metadata:
  name: example-npu-request
spec:
  containers:
  - name: furiosa
    image: furiosaai/furiosa-smi:latest
    imagePullPolicy: IfNotPresent
    command: ["sleep"]
    args: ["120"]
    resources:
      limits:
        furiosa.ai/rngd: 2

특정 요구 사항을 가진 NPU 워크로드를 스케줄링하기#

특정 하드웨어 또는 소프트웨어 요구 사항(예: 특정 드라이버 버전)을 충족하는 노드에 NPU 워크로드를 스케줄링해야 하는 경우가 있습니다. Furiosa Feature Discovery가 클러스터에 배포된 경우, 노드는 하드웨어 및 소프트웨어 구성(드라이버 버전 포함)에 따라 자동으로 레이블이 지정됩니다. 이를 통해 사용자는 특정 요구 사항을 충족하는 노드에 Pod를 스케줄링할 수 있습니다.

다음 예시는 특정 드라이버 버전을 요청하는 2개의 RNGD NPU를 가진 Pod를 스케줄링하기 위해 Affinity를 사용하는 방법을 보여줍니다:

apiVersion: v1
kind: Pod
metadata:
  name: example-npu-scheduling-with-affinity
spec:
  containers:
  - name: furiosa
    image: furiosaai/furiosa-smi:latest
    imagePullPolicy: IfNotPresent
    command: ["sleep"]
    args: ["120"]
    resources:
      limits:
        furiosa.ai/rngd: 2
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: furiosa.ai/driver-version
            operator: In
            values:
            - "1.0.12"

알려진 문제점#

  • 외부 장치(예: NPU)를 사용하는 Pod은 노드가 재시작될 때 재시작되는 Pod에 외부 리소스를 할당하는 과정에서 kubelet의 경쟁 조건으로 인해 재시작되지 않고 예기치 않은 AdmissionError가 발생할 수 있습니다. 이 문제는 kubernetes/kubernetes#128043에서 추적되고 있습니다.
