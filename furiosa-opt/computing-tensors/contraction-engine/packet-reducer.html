패킷 축약기(Packet Reducer)

패킷 축약기(Packet Reducer)는 각 레인(lane)의 축약 트리(reduction tree)를 사용해, 패킷(Packet) 하나 안의 가장 안쪽 수축 축(contracted axis)을 따라 값을 더해 축약(reduce-add)합니다.

인터페이스(Interface)

.contract_packet()은 패킷 축약기(Packet Reducer)를 호출합니다. 각 레인(lane)은 외적 단계(Outer)의 OutPacket에서 이어받은 32 B 또는 64 B 패킷을 받으며, 원소 타입은 i4, i8, f8, bf16 중 하나입니다. 수식으로는 \text{output}[i] = \sum_{j} \text{input}[i, j]를 계산합니다. 여기서 i는 남아 있는 출력 축(output axis)을, j는 Packet 안에서 수축하는 축을 순회합니다.

rust
impl<
    'l,
    D: Scalar,
    Storage: ContractionCast<Output = D>,
    Chip: M,
    Cluster: M,
    Slice: M,
    Lane: M,
    Time: M,
    Packet: M,
    B: Backend,
> ContractOuterTensor<'l, { Tu::Main }, D, Storage, Chip, Cluster, Slice, Lane, Time, Packet, B>
{
    /// `Packet` 내부의 공간 축약(spatial reduction)입니다. `contract_lane`의 결합 접기(fused fold)가 수행할
    /// `Packet` 안의 수축 축(contracted axis)에 대한 합산 축약(reduce-add)를 검증합니다. `D`는 지연 전달 객체(deferred carrier)가
    /// 기준으로 삼는 확장된 누산기(accumulator) 타입이며, DPE 입력 패킷의 크기는 계속 `Storage` 바이트로 계산합니다.
    ///
    /// main 문맥(context)에서만 사용할 수 있습니다.
    #[primitive(ContractOuterTensor::contract_packet)]
    pub fn contract_packet<OutPacket: M>(
        self,
    ) -> ContractPacketTensor<'l, { Tu::Main }, D, Chip, Cluster, Slice, Lane, Time, OutPacket, B> {
        verify_contract_packet(ContractPacketInput {
            in_packet: Packet::to_value(),
            out_packet: OutPacket::to_value(),
            element_bits: Storage::BITS,
        });
        // 지연된 피연산자(deferred operand)를 아직 축약하지 않고 전달합니다. `contract_lane`의 결합 수축(fused contraction)이
        // 이 Packet 축약도 수행합니다. 이 단계에서는 전달 객체(carrier)의 타입만 `OutPacket`으로 바꿉니다.
        ContractPacketTensor::new(self.device, self.inner)
    }
}

아래 커널(kernel)은 8개 레인(lane)을 모두 병렬로 사용합니다. 깊이(depth) 5의 트리가 B의 bf16 원소 32개를 더하여, A의 각 위치(position)마다 f32 하나를 만듭니다.

rust
axes![A = 32, B = 32, C = 8];

fn matmul<'l>(
    input: CollectTensor<'l, { Tu::Main }, bf16, m![1], m![1 # 2], m![1 # 256], m![A, B / 16], m![B % 16]>,
    trf: &TrfTensor<bf16, m![1], m![1 # 2], m![1 # 256], m![C], m![B]>,
) -> ContractTensor<'l, { Tu::Main }, f32, m![1], m![1 # 2], m![1 # 256], m![A], m![C]> {
    //
    // 공간 축약(spatial reduction): 깊이 5의 트리가 B의 bf16 원소 32개를 합쳐 f32를 만듭니다.
    // 출력(Interleaved): Time = [A], Packet = [C]
    input.contract_outer::<m![A], m![B], _, _, _>(&trf)
         .contract_packet::<m![1]>()
         .contract_time::<m![A]>()
         .contract_lane::<m![A], m![C]>(LaneMode::Interleaved)
}

구조(Architecture)

text
ReducePacket = Packet / 2^d        for 0 ≤ d ≤ log2(Packet::SIZE)
OutPacket    = ReducePacket, outermost padding removed
               (size ≤ 32; when ReducePacket::SIZE > 32 only the innermost 32 survive)

패킷 축약기(Packet Reducer)는 먼저 레인(lane)마다 독립된 축약 트리(reduction tree)를 실행합니다. 깊이(depth) 0의 리프(leaf)는 입력 패킷(Packet)의 원소를 보유합니다. 다음 깊이로 갈 때마다 두 값씩 더하여 원소 수를 절반으로 줄입니다. 최대 트리 깊이는 log2(Packet::SIZE)입니다. 따라서 i4는 7(Packet::SIZE = 128), i8 / f8는 6(64), bf16은 5(32)입니다. 컴파일러(compiler)는 사용자가 지정한 OutPacket에서 트리 깊이 d를 도출합니다. 트리는 가장 안쪽의 2^d개 원소를 소비하여 ReducePacket을 만듭니다.

이후 패킷 축약기(Packet Reducer)는 ReducePacket을 OutPacket 크기로 잘라냅니다(trim). 후단 시간 축약기(Time Reducer)의 레인별 누산기(per-lane accumulator)에는 열(column)이 32개뿐이므로 출력은 최대 32개 원소입니다. ReducePacket::SIZE > 32이면 바깥쪽 더미(dummy)를 제거하고 가장 안쪽 32개 원소만 유지합니다. 예를 들어 i4는 128개 원소의 패킷으로 들어오므로 d ∈ {0, 1}이면 128개 또는 64개 원소의 ReducePacket이 만들어집니다. 둘 다 OutPacket::SIZE = 32로 잘라냅니다.

ReducePacket에는 가장 바깥쪽 패딩(padding), 즉 패딩된 패킷 축(packet axis)이 있을 수도 있습니다. 패킷 축약기(Packet Reducer)는 실제 값이 있는 열(live column)만 남기고 이 패딩을 제거합니다. 예를 들어 [A # 16]인 ReducePacket은 실제 A개 열을 16개 열까지 패딩한 것이며, OutPacket = [A]로 줄어듭니다. 따라서 OutPacket은 패딩을 포함한 [A # 16]으로 선언해도, 제거한 [A]로 선언해도 됩니다. 두 표현은 같은 결과를 가리킵니다.

성능(Performance)

지연(latency)은 트리 깊이(tree depth)에 따라 달라집니다. i4는 7사이클(cycle), i8/f8는 6사이클, bf16은 5사이클입니다. 원소 타입(element type)이 넓을수록 패킷(Packet)에 들어가는 원소가 적어 깊이가 줄어듭니다. 덧셈 트리(adder tree)는 완전히 파이프라인화되어 있으므로 깊이는 첫 출력까지의 지연만 늘리고, 정상 상태 처리량(steady-state throughput)은 줄이지 않습니다. 파이프라인을 채우고 나면 매 사이클 패킷 하나가 들어가고 축약된 출력 하나가 나옵니다.

Lane < 8이면 비활성 레인(inactive lane)의 축약 트리(reduction tree)는 쉬게 됩니다. 따라서 사이클당 처리량(per-cycle throughput)은 Lane::SIZE / 8에 비례하여 줄어듭니다.
