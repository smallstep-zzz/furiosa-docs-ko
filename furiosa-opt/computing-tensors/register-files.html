레지스터 파일(Register Files)

원문 대조 메모 · 번역자 설명

원문은 정수 저장 시 i8 → i9 승격을 설명한 직후, i8가 원래 8비트를 유지한다고도 서술합니다. 두 설명을 모두 원문대로 번역했습니다. 저장 비트 폭을 확정해야 할 때에는 사용 중인 버전의 실제 자료형과 API 구현을 함께 확인해야 합니다.

수집 엔진(Collect Engine)은 수축 연산기(Contraction Engine)와 벡터 엔진(Vector Engine)에 스트림(stream)을 보냅니다. 두 엔진은 슬라이스(slice)마다 하나씩 있는 레지스터 파일(register file)에서도 입력을 받습니다. 텐서 레지스터 파일(Tensor Register File, TRF)은 수축 연산기에, 벡터 레지스터 파일(Vector Register File, VRF)은 벡터 엔진에 값을 공급합니다. 이를 소비하는 엔진이 실행되기 전에 레지스터 파일에 데이터를 채워야 합니다.

텐서 레지스터 파일(Tensor Register File)

인터페이스(Interface)

TrfTensor는 TRF에 저장된 텐서(tensor)입니다.

rust
/// 텐서 레지스터 파일(tensor register file)에 저장된 텐서(tensor).
#[primitive(TrfTensor)]
#[derive(Debug)]
pub struct TrfTensor<D: Scalar, Chip: M, Cluster: M, Slice: M, Lane: M, Element: M, B: Backend = CurrentBackend> {
    pub(crate) inner: Tensor<D, Pair<Chip, Pair<Cluster, Pair<Slice, Pair<Lane, Element>>>>, B>,
    _marker: PhantomData<(D, Chip, Cluster, Slice, Lane, Element)>,
}

Chip / Cluster / Slice는 원본에서 그대로 이어집니다. Lane은 공간 병렬성(spatial parallelism)을 인덱싱하며, 활성 레인(active lane)은 1, 2, 4, 8개 중 하나입니다. Element는 레인별 배치(per-lane layout)를 담습니다.

수집 엔진에서 적재하기(From Collect Engine)

CollectTensor의 .to_trf::<Lane, Element>()는 TrfTensor를 만듭니다. 레지스터 파일(register file)의 어느 위치에 저장할지는 컴파일러(compiler)가 결정하므로, 호출에서 영역(region)을 지정하지 않습니다.

rust
impl<'l, P: CanApplyToTrf, D: Scalar, Chip: M, Cluster: M, Slice: M, Time: M, Packet: M, B: Backend>
    TuTensor<'l, { Tu::Sub }, P, D, Chip, Cluster, Slice, Time, Packet, B>
{
    /// 텐서 레지스터 파일(tensor register file)에 저장합니다.
    #[primitive(TuTensor::to_trf)]
    pub fn to_trf<Lane: M, Element: M>(self) -> TrfTensor<D, Chip, Cluster, Slice, Lane, Element, B> {
        verify_to_trf::<D, Lane, Time, Packet, Element>();
        TrfTensor::new(self.inner.transpose(false))
    }
}

impl<'l, P: CanApplyToTrf, D: Scalar, Chip: M, Cluster: M, Slice: M, Time: M, Packet: M, B: Backend>
    TuTensor<'l, { Tu::Main }, P, D, Chip, Cluster, Slice, Time, Packet, B>
{
    /// 쓰기에 사용하는 sub 문맥(context)을 점유하면서 텐서 레지스터 파일(tensor register file)에 저장합니다.
    ///
    /// 빌림(borrow)은 문장(statement)이 끝날 때까지 유지됩니다. 컴파일러(compiler)가 레지스터 할당(register allocation)을 별도로 관리하므로,
    /// 반환한 [`TrfTensor`]는 문맥 빌림(context borrow)을 보유하지 않습니다.
    #[primitive(TuTensor::to_trf_from_main)]
    pub fn to_trf<Lane: M, Element: M>(
        self,
        _sub: &mut TuContext<{ Tu::Sub }>,
    ) -> TrfTensor<D, Chip, Cluster, Slice, Lane, Element, B> {
        verify_to_trf::<D, Lane, Time, Packet, Element>();
        TrfTensor::new(self.inner.transpose(false))
    }
}

저장(store) 메서드는 문맥(context)별로 시그니처(signature)가 하나씩 있으며, 여기의 예제는 sub 문맥의 시그니처를 사용합니다. 쓰기 레지스터(write register)가 sub 문맥의 레지스터 맵(register map)에 있으므로, main 문맥에서 저장할 때는 device.sub를 인수(argument)로 받습니다. 저장이 점유하는 문맥(Which context a store occupies)을 참고하세요.

.to_trf는 스트림(stream)의 Time / Packet을 Lane / Element로 재구성(reshape)합니다.

text
Lane    = Time / FlitsPerLane
Element = [Time % FlitsPerLane, Packet]

여기서 FlitsPerLane은 컴파일러(compiler)가 Lane과 Time으로부터 도출합니다. 각 레인(lane)은 연속된 FlitsPerLane개의 플릿(flit)으로 채워집니다.

다음의 간단한 예는 TRF 전체를 사용합니다.

rust
axes![B = 32];

fn load_trf<'l>(
    input: CollectTensor<'l, { Tu::Sub }, i8, m![1], m![1 # 2], m![1 # 256], m![1], m![B]>,
) -> TrfTensor<i8, m![1], m![1 # 2], m![1 # 256], m![1], m![B]> {
    input.to_trf()
}

예를 들어 행렬곱(matmul) 커널(kernel)에서는 Lane이 출력 채널(output channel)을, Element가 수축 축(contracted axis)을 담습니다.

rust
axes![V = 32, M = 32, N = 8, K = 32];

type Chip    = m![1];
type Cluster = m![V / 16];
type Slice   = m![V % 16 # 256];
type Lane    = m![N];

/// 행렬곱(matmul) 가중치(weight)를 TRF에 저장하여 아래 예제의 `bmatmul`이 사용하게 합니다.
/// [수축 연산기: 배치 행렬곱 예제(Contraction Engine: Example: Batched MatMul)](./contraction-engine/index.md#example-batched-matmul).
fn store_bmatmul_trf<'l>(
    input: CollectTensor<'l, { Tu::Sub }, bf16, Chip, Cluster, Slice, m![N, K / 16], m![K % 16]>,
) -> TrfTensor<bf16, Chip, Cluster, Slice, Lane, m![K]> {
    input.to_trf()
}

벡터 엔진에서 적재하기(From the Vector Engine)

저장(store)을 반드시 collect 직후에 수행할 필요는 없습니다. main 문맥(context)의 스트림(stream)이 먼저 벡터 엔진(Vector Engine)을 실행하고, 그 처리 결과를 저장할 수도 있습니다.

rust
axes![B = 64];

fn store_pass(device: &mut Device) -> VrfTensor<f32, m![1], m![1 # 2], m![1 # 256], m![B]> {
    let dm: DmTensor<f32, m![1], m![1 # 2], m![1 # 256], m![B]> = DmTensor::new();
    device.main
        .begin(dm.view())
        .fetch::<m![1], m![B]>()
        .collect::<m![B / 8], m![B % 8]>()
        .vector_init()
        .vector_intra_slice_tag(TagMode::Zero)
        .vector_narrow_split::<m![B / 8, B % 8 / 4 % 2], m![B % 4]>()
        .vector_fp_unary(FpUnaryOp::Sqrt)
        .vector_widen_concat::<m![B / 8], m![B % 8]>()
        .vector_final()
        .to_vrf(&mut device.sub)
}

두 위치는 같은 연산의 다른 표기가 아니라 서로 다른 데이터 경로(data path)입니다. collect 직후에서는 읽기 네트워크(Fetch Network)가 플릿(flit)을 레지스터 파일(register file)로 넘기며, 사이에 다른 엔진은 실행되지 않습니다. vector_final 직후에서는 벡터 엔진(Vector Engine) 자체의 쓰기 포트(write port)에서 처리가 끝납니다. 따라서 레지스터에 들어가는 것은 그 처리에서 계산한 값입니다. Element2는 *처리 후(post-pass)*의 Time / Packet을 평탄화(flatten)합니다. 이 둘은 중간의 축약(reduce)나 확장(widen)에 의해 이미 재구성되었을 수 있습니다.

계산한 값(computed value)이 VRF에 도달할 수 있는 경로는 이것뿐입니다. DM 직접 저장(DM-direct)과 collect 위치에서의 저장은 모두 데이터 메모리(Data Memory)를 읽기 때문입니다. 같은 명령(command)에서 벡터 엔진(Vector Engine) 뒤의 다른 단계는 실행할 수 없으므로, 저장을 형 변환(cast), 전치(transpose), 쓰기(commit)와 결합할 수 없습니다.

저장이 점유하는 문맥(Which context a store occupies)

main 문맥(context)에서 발행한 저장(store)은 어떤 레지스터 파일(register file)을 대상으로 하든, 위의 두 위치 중 어디에서 수행하든 sub 문맥을 통해 씁니다. 따라서 두 문맥을 모두 점유하며 &mut device.sub도 받습니다. 스케줄러(scheduler)는 명령(command)에 두 문맥을 모두 예약하므로, 어떤 sub 문맥 연산도 이 명령과 겹치지 않습니다. device.main과 device.sub는 서로 다른 필드(field)이므로 &mut Device를 보유한 커널(kernel)은 위의 예제처럼 두 필드를 동시에 빌릴 수 있습니다(borrow).

빌림(borrow)은 해당 문장(statement)이 끝날 때까지 유지되며, 문맥의 점유 범위도 같습니다. 명령(command)이 완료(retire)되면 sub 문맥(context)을 다시 사용할 수 있습니다. 레지스터(register) 자체를 얼마나 오래 점유하는지는 별개입니다. 이는 피연산자(operand)를 마지막으로 읽을 때까지이며, 컴파일러(compiler)의 할당(allocation)이 결정합니다. 그래서 반환되는 VrfTensor에는 빌림이 붙지 않습니다.

sub 문맥(context)에서 발행한 저장(store)은 이미 그 문맥을 보유하므로 별도의 인수(argument)가 필요 없습니다.

데이터 메모리에서 적재하기(From Data Memory)

입력 접근(input access)이 완전히 연속적이고 빈틈이나 순서 변경이 없다면, TRF는 *짧은 명령(short command)*인 StoTRF를 지원합니다. 이 작은 하드웨어 명령은 전체 Fetch → Switch → Collect → to_trf() 파이프라인을 우회하여 데이터 메모리(Data Memory)에서 TRF로 직접 적재합니다(load). 임의의 배치(arbitrary layout)를 지원하지 않는 대신 준비 오버헤드(setup overhead)가 줄어드는 경로입니다.

수축 연산기로 읽어 보내기(To Contraction Engine)

한 번 읽을 때 8개 레인(lane) × 뱅크(bank) 1개 또는 2개 × 행(row) 1개 × 뱅크당 320비트를 처리합니다. 좁은 읽기(narrow read, 뱅크 하나)는 레인당 사이클(cycle)마다 320비트, 넓은 읽기(wide read, 두 뱅크)는 640비트를 만듭니다. 모든 활성 레인은 같은 행의 한 뱅크 또는 두 뱅크에 병렬 접근합니다. 8개 레인을 합치면 슬라이스(slice)당 좁은 읽기는 320바이트/사이클, 넓은 읽기는 640바이트/사이클입니다. 행과 브로드캐스트(broadcast)를 따라 시퀀서(sequencer)가 읽기를 반복하는 방식은 TRF 시퀀서(TRF Sequencer)를 참고하세요.

구조(Architecture)

TRF는 뱅크로 나뉜 SRAM(banked SRAM)이며, 8개 레인(lane) × 2개 뱅크(bank) × 128개 행(row) × 320비트 구조로 슬라이스(slice)당 80 KB를 제공합니다. 8개 레인은 병렬 동작하며, 한 번 접근할 때 활성화하는 레인 수는 1, 2, 4, 8개입니다.

320비트 행(row) 하나에 넣을 수 있는 원소(element) 수는 데이터 타입(data type)에 따라 달라집니다.

타입(Type) 저장하는 원소 크기(Element size stored) 행당 원소 수(Elements per row)
i4 → i5(하드웨어 동작이지만 아직 연결되지 않아, 현재 i4 가중치(weight)는 i4로 유지됩니다.) 5비트(bits) 64
i8 → i9 9비트(bits, 근삿값이며 320비트 행에 맞도록 올림) 32
i8 / f8 8비트(bits) 32개(행당 40바이트)
bf16 16비트(bits) 16개(행당 32바이트)

저장 시 승격(promote)하는 것은 정수(integer)뿐입니다. i4 → i5(5비트), i8 → i9(9비트)로 확장하면 읽기 어댑터(fetch adapter)의 선택적인 영점 빼기(zero-point subtraction)를 위한 공간이 생깁니다. 이 연산은 정수 가중치(weight)를 한 비트 확장합니다. i8 / f8와 bf16은 각각 원래의 8비트, 16비트 너비(native width)를 유지합니다. 320비트 행(row)은 8비트 또는 16비트로 빈틈없이 넣는 경우보다 여유 공간(slack)을 두어, 모든 타입이 같은 물리적 행 너비(physical row width)를 사용하게 합니다.

활성 레인(active lane)이 8개보다 적으면 각 활성 레인에서 더 많은 행(row)을 사용할 수 있습니다. 행 수가 늘어난 것처럼 동작합니다. 활성 수를 절반으로 줄이면 활성 레인당 행 수가 두 배가 됩니다. 예를 들어 활성 레인이 4개이면 뱅크(bank)당 256행, 1개이면 1024행입니다.

이중 버퍼링(Double Buffering)

TRF는 각 뱅크(bank)를 두 절반으로 나누어 이중 버퍼링(double-buffering)을 지원합니다. TRF 시퀀서(TRF Sequencer)가 한쪽 절반에서 읽는 동안 저장(store)은 다른 절반을 채웁니다. 반복(iteration) 사이에 두 절반의 역할을 바꿀 수 있습니다. 영역(region)을 지정하는 주소 모드(address mode)는 세 가지이며, 스케줄러(scheduler)가 저장 시 선택합니다. Full은 뱅크당 128행 전체, FirstHalf는 0~63행, SecondHalf는 64~127행을 사용합니다. 절반 모드의 용량(capacity)은 슬라이스(slice)당 40 KB로 제한됩니다.

main과 sub 문맥(context)에 걸쳐 두 절반을 활용하는 튜닝 패턴(tuning pattern)은 스케줄링과 튜닝: 이중 버퍼링(Scheduling and Tuning: Double Buffering)을 참고하세요.

두 절반은 같은 뱅크(bank)를 공유하므로 서로 다른 행(row)을 대상으로 하더라도 읽기(read)와 쓰기(write)가 뱅크 수준에서 경합(contend)합니다. 같은 사이클(cycle)에 둘 다 같은 뱅크를 요청하면 읽기가 우선합니다. 수축 파이프라인(contraction pipeline)은 그 사이클에 데이터가 필요하지만, 저장(store)은 기다릴 수 있기 때문입니다.

TRF는 읽기 캐시(read cache)와 뱅크 교대(bank alternation)로 이 경합(contention)을 완화합니다.

TRF 읽기(read)는 재사용(reuse)이 많습니다. 같은 데이터를 여러 사이클(cycle)에 걸쳐 브로드캐스트(broadcast)하는 경우가 일반적이므로, 뱅크(bank) 앞에 직접 사상 읽기 캐시(direct-mapped read cache)를 둡니다. 크기는 8개 레인 × 2개 뱅크 × 4개 행 × 320비트 = 2.5 KB이며, 반복 읽기를 흡수합니다. 캐시는 동시 저장(concurrent store)과의 경합도 완화합니다. 적중(hit)하면 뱅크를 읽지 않으므로 그 사이클에 저장이 뱅크를 사용할 수 있습니다. 미스(miss)가 나면 뱅크에서 캐시를 다시 채우므로 해당 사이클에는 뱅크를 점유합니다.

좁은 읽기(narrow read, ≤ 32바이트)에서는 뱅크 교대(bank alternation)가 경합을 한 번 더 줄여 줍니다. 읽기가 뱅크(bank) 하나만 사용하므로 두 뱅크를 32바이트 단위(granularity)로 번갈아 사용할 수 있습니다. 그러면 연속된 사이클(cycle)에서 읽기와 쓰기가 서로 다른 뱅크를 사용해, 캐시 미스(cache miss) 때도 경합을 피할 수 있습니다. 넓은 읽기(wide read, 64바이트)는 매 사이클 두 뱅크를 모두 차지하므로 캐시 미스가 날 때마다 동시 저장(concurrent store)을 막습니다. 좁은 읽기는 캐시 미스 때도 절반 대역폭(half-bandwidth) 단위의 교대를 유지합니다.

벡터 레지스터 파일(Vector Register File)

VRF에는 수집 엔진(Collect Engine)에서 쓰거나 데이터 메모리(Data Memory)에서 직접 쓰며, 벡터 엔진(Vector Engine)이 읽습니다.

인터페이스(Interface)

VrfTensor는 VRF에 저장된 텐서(tensor)입니다.

rust
/// 벡터 레지스터 파일(vector register file, VRF)에 저장된 텐서(tensor).
#[primitive(VrfTensor)]
#[derive(Debug, Clone)]
pub struct VrfTensor<D: VeScalar, Chip: M, Cluster: M, Slice: M, Element: M, B: Backend = CurrentBackend> {
    pub(crate) inner: Tensor<D, Pair<Chip, Pair<Cluster, Pair<Slice, Element>>>, B>,
    _marker: PhantomData<(D, Chip, Cluster, Slice, Element)>,
}

Chip / Cluster / Slice는 원본에서 그대로 이어집니다. Element는 슬라이스별 배치(per-slice layout)를 담습니다.

벡터 엔진(Vector Engine)의 연산(op)은 이 세 차원으로 피연산자(operand)의 일치 여부를 확인합니다. 따라서 피연산자의 분할(partition)이 공급 대상 스트림(stream)의 분할과 다르면 다른 슬라이스(slice)의 데이터를 읽는 대신 컴파일 오류(compile error)가 발생합니다(피연산자(Operands) 참고). .reshape::<Chip2, Cluster2, Slice2, Element2>()는 같은 슬라이스들을 다른 방식으로 분할하여 다시 표현합니다. 이 방법으로 익명 브로드캐스트(anonymous broadcast, m![256])에 복제된 피연산자를 이름 있는 축(named axis)으로 분할한 스트림에 공급할 수 있습니다. 데이터는 움직이지 않고 매핑(mapping)의 이름만 바꾸므로, DmTensor::reshape와 같은 이유로 unsafe입니다. 각 물리적 위치(physical position)에 새 매핑이 주장하는 값이 이미 있어야 합니다. 축을 다시 묶거나 브로드캐스트 분배 축(distribution axis)에 이름을 붙이는 두 형태는 이 조건을 만족합니다. VrfTensor::reshape의 # Safety 절에 두 경우가 설명되어 있습니다.

수집 엔진에서 적재하기(From Collect Engine)

CollectTensor의 .to_vrf::<Element2>()는 플릿(flit)을 VRF에 저장하고 VrfTensor를 만듭니다. 레지스터 파일(register file)의 어느 위치에 저장할지는 컴파일러(compiler)가 결정하므로, 호출에서 주소(address)를 지정하지 않습니다.

rust
impl<'l, P: CanApplyToVrf, D: VeScalar, Chip: M, Cluster: M, Slice: M, Time: M, Packet: M, B: Backend>
    TuTensor<'l, { Tu::Sub }, P, D, Chip, Cluster, Slice, Time, Packet, B>
{
    /// 벡터 레지스터 파일(vector register file)에 저장합니다.
    #[primitive(TuTensor::to_vrf)]
    pub fn to_vrf<Element: M>(self) -> VrfTensor<D, Chip, Cluster, Slice, Element, B> {
        verify_to_vrf::<D, Time, Packet, Element>();
        VrfTensor::new(self.inner.transpose(false))
    }
}

impl<'l, P: CanApplyToVrf, D: VeScalar, Chip: M, Cluster: M, Slice: M, Time: M, Packet: M, B: Backend>
    TuTensor<'l, { Tu::Main }, P, D, Chip, Cluster, Slice, Time, Packet, B>
{
    /// 쓰기에 사용하는 sub 문맥(context)을 점유하면서 벡터 레지스터 파일(vector register file)에 저장합니다.
    ///
    /// 빌림(borrow)은 문장(statement)이 끝날 때까지 유지됩니다. *레지스터(register)*를 점유하는 기간은 컴파일러(compiler)의
    /// 할당(allocation)이 결정하므로 반환한 [`VrfTensor`]는 빌림(borrow)을 보유하지 않습니다.
    #[primitive(TuTensor::to_vrf_from_main)]
    pub fn to_vrf<Element: M>(
        self,
        _sub: &mut TuContext<{ Tu::Sub }>,
    ) -> VrfTensor<D, Chip, Cluster, Slice, Element, B> {
        verify_to_vrf::<D, Time, Packet, Element>();
        VrfTensor::new(self.inner.transpose(false))
    }
}

.to_vrf는 스트림(stream)의 Time / Packet을 Element2로 평탄화(flatten)합니다.

text
Element2 = [Time, Packet]

사용자가 Element2를 선택합니다.

rust
axes![B = 64];

fn store_vrf<'l>(
    input: CollectTensor<'l, { Tu::Sub }, i32, m![1], m![1 # 2], m![1 # 256], m![B / 8], m![B % 8]>,
) -> VrfTensor<i32, m![1], m![1 # 2], m![1 # 256], m![B]> {
    input.to_vrf()
}

저장(store) 메서드는 문맥(context)별로 시그니처(signature)가 하나씩 있으며, 위 예제는 sub 문맥의 것을 사용합니다. 쓰기 레지스터(write register)가 sub 문맥의 레지스터 맵(register map)에 있으므로 main 문맥의 저장은 device.sub를 인수(argument)로 받습니다. 저장이 점유하는 문맥(Which context a store occupies)을 참고하세요.

데이터 메모리에서 적재하기(From Data Memory)

입력 접근(input access)이 완전히 연속적이고 빈틈이나 순서 변경이 없다면 VRF는 *짧은 명령(short command)*인 StoVRF를 지원합니다. 이 작은 하드웨어 명령은 전체 Fetch → Switch → Collect → to_vrf() 파이프라인을 우회하여 데이터 메모리(Data Memory)에서 VRF로 직접 적재합니다(load). 임의의 배치(arbitrary layout)를 지원하지 않는 대신 준비 오버헤드(setup overhead)를 줄이는 경로입니다.
