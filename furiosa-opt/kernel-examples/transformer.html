사례 연구: 트랜스포머(Transformer)

이 트랜스포머(Transformer) 문서는 Qwen3-0.6B를 구체적인 학습 사례로 삼아 모델의 동작을 이해할 틀(mental model)을 설명합니다. 호스트(host)가 준비한 임베딩(embedding)에서 패딩된 어휘 로짓(padded vocabulary logits)까지 디코더 토큰(decoder token) 하나의 흐름을 따라갑니다. 각 경계(boundary)는 이식 가능한 호스트 정답 기준(portable host oracle)과 재현 가능한 스케줄 산출물(schedule artifact)로 검사합니다. 예제를 수정할 때도 호스트가 준비하는 이 경계들을 유지하세요.

이 모델은 28개 층(layer)을 가진 디코더 전용 트랜스포머(decoder-only transformer)입니다. 각 층은 한 번에 토큰(token) 하나의 현재 은닉 벡터(hidden vector)를 변환합니다.

text
token id
   |
   v
[Embedding lookup]
   |
   v
+-----------------------------+
| Decoder layer × 28          |
| RMSNorm → Q/K/V projection  |
| QK-Norm → RoPE → Attention  |
| Output projection + residual|
| RMSNorm → SwiGLU MLP        |
| + residual                  |
+-----------------------------+
   |
   v
[Final RMSNorm] → [LM head] → logits

모델의 은닉 크기(hidden size)는 1024, 질의 헤드(query head)는 16개, 키·값 헤드(key/value head)는 8개, 헤드 차원(head dimension)은 128, 중간 크기(intermediate size)는 3072입니다. 그룹 질의 어텐션(grouped-query attention)은 키·값 헤드 하나를 질의 헤드 두 개가 공유합니다. RoPE의 theta는 1,000,000이며, 모델 설계에서는 임베딩 가중치(embedding weight)와 출력 가중치(output weight)를 공유합니다(tied weights).

구성 요소(Component) 형태 또는 개수(Shape or count)
디코더 층(Decoder layers) 28
어휘 집합(Vocabulary) 토큰(token) 151,936개
임베딩과 가중치를 공유하는 LM 헤드(Embedding and tied LM head) 151,936 × 1,024
층별 어텐션 투영(Attention projections per layer) 매개변수(parameter) 6,291,456개
층별 SwiGLU MLP 매개변수(parameter) 9,437,184개
전체 모델(Total model) 약 5억 9,600만 개의 매개변수(parameter)

이 사례 연구는 RMSNorm, RoPE, 어텐션(attention), KV 캐시(KV-cache), SwiGLU, 잔차(residual), 출력 투영(output projection)의 설계 결정을 요약합니다. 실제 구현은 로컬 트랜스포머(transformer) 예제에 있습니다.

이 예제는 **디코딩 전용(decode-only)이며 단일 토큰(single-token)**을 처리합니다. 프리필(prefill), 샘플링(sampling), 장치 내 토큰 조회(device-side token lookup)는 구현하지 않습니다. 실행 가능한 소스는 트랜스포머 예제에 있습니다. 이 사례 연구는 구현을 복사하는 대신 설계 결정을 설명하고 소스와 테스트로 연결합니다.

실행 가능한 디코더 흐름(Runnable decoder flow)

로컬 furiosa-opt-examples/src/transformer/mod.rs는 다음 장치 실행(device launch) 진입점을 제공합니다.

  • embedding
  • projection
  • attention_forward_first
  • attention_forward
  • decoder
  • final_layer

이 로컬 실행 구성(launch map)이 이 사례 연구의 기준 실행 인터페이스(canonical execution surface)입니다. vISA와 API 규칙(contract)은 각 참조 문서(reference chapter)에서 다룹니다.

작업의 의미(Workload semantics)

이 작업(workload)은 디코더(decoder)의 한 단계입니다.

text
host-prepared embedding → 28 decoder layers → final RMSNorm and LM head → logits [Wp]

현재 예제는 층(layer) 28개, 은닉 크기(hidden size) 1024인 Qwen3-0.6B를 설명합니다. 각 디코더 층(decoder layer)에는 다음 경계(boundary)가 있습니다.

  1. projection: 입력 RMSNorm, Q/K/V 투영(projection), Q/K RMSNorm, RoPE, KV 캐시 쓰기(KV-cache writes)를 수행합니다.
  2. attention_forward_first 또는 attention_forward: 온라인 소프트맥스(online softmax)를 사용하는 어텐션 청크(attention chunk) 하나를 처리합니다.
  3. decoder: 출력 투영(output projection), 잔차(residual), 어텐션 이후 RMSNorm, MLP, 잔차를 수행합니다.

final_layer는 최종 RMSNorm을 적용하고 패딩된 어휘 형태(padded vocabulary shape)의 로짓(logit)을 계산합니다. 정확한 축 크기(axis size)와 텐서 자료형(tensor type)은 axes.rs에 정의되어 있습니다.

설계 결정 따라가기(Decision trace)

이 사례 연구는 문서의 다른 장과 같은 순서로 설명합니다.

  1. 작업의 의미(workload semantics): 토큰(token) 하나와 점점 커지는 KV 캐시(cache)가 데이터 이동(data movement)을 결정합니다.
  2. 필수 제약(hard constraints): 모든 커널(kernel)에는 자료형이 명시된 공개 입출력 경계(typed public boundary)가 있습니다. 어휘 출력(vocabulary output)은 Wp를 사용하지만 모델의 실제 어휘는 W입니다.
  3. 커널 경계(kernel boundaries): Rust 모듈은 embedding, projection, attention_forward_first, attention_forward, decoder, final_layer를 별도의 장치 진입점(device entry point)으로 제공합니다.
  4. 매핑과 이동(mapping and movement): 소스는 호스트(host)가 준비한 텐서(tensor)를 HBM과 DM을 거쳐 옮기며, 각 엔진이 요구하는 표현(representation)을 사용합니다. 해당 규칙은 텐서 매핑(Mapping Tensors)과 텐서 이동(Moving Tensors)을 참고하세요.
  5. 엔진 선택(engine choices): 투영(projection)과 LM 헤드의 수축(contraction)은 수축 연산기(Contraction Engine)를 사용합니다. RMSNorm과 원소별 단계(elementwise stage)는 벡터 엔진(Vector Engine)을 사용하고, 전송(transfer)은 DMA와 Fetch/Commit 경로를 사용합니다. 해당 규칙은 텐서 연산(Computing Tensors)을 참고하세요.
  6. 검사(checks): 호스트 정답 기준 테스트(host-oracle test)가 값의 정확성을 확인하며, 덤프한 스케줄(dumped schedule)이 정적 실행 계획(static execution plan)을 기록합니다. 스케줄링과 튜닝(Scheduling and Tuning)을 참고하세요.

따라서 이 사례 연구는 여러 설계 선택(choice)이 어떻게 결합되는지 보여 줍니다. 개별 엔진 API를 새로 정의하지는 않습니다.

호스트가 준비하는 임베딩(Host-prepared embedding)

embedding 진입점(entry point)은 호스트(host)가 준비한 데이터를 HBM에서 복사합니다. HbmTensor<bf16, ..., m![H]>를 받아 to_hbm_view로 그 뷰(view)를 출력 HBM 텐서에 복사합니다. 토큰 ID(token ID)를 받아 장치에서 조회하는 연산이 아니므로 그렇게 설명해서는 안 됩니다.

현재 소스는 이 단계를 ops::embedding으로 구현합니다. 기본 동작 검사(smoke test)는 test_embedding입니다.

디코더 단계(Decoder step)

projection은 은닉 벡터(hidden vector) 하나, 투영(projection) 및 RMSNorm 가중치, 위치에 따른 cos·sin 벡터, 수정 가능한 K/V 캐시(mutable cache)를 받습니다. Q를 HBM에 쓰고 캐시를 갱신합니다. 첫 어텐션 청크(attention chunk)는 attention_forward_first로 처리하고, 이후 청크들은 attention_forward로 온라인 축약 상태(online reduction state)를 이어 갑니다.

decoder는 어텐션 출력(attention output)과 축약 상태(reduction state)를 받아 잔차 스트림(residual stream)을 HBM에 다시 쓰고, 출력 투영(output projection), 잔차 경로, RMSNorm, MLP, 최종 잔차 경로를 적용합니다. 함수 시그니처(function signature)가 필요한 입력과 출력을 정의합니다. 구현 세부사항은 furiosa-opt-examples/src/transformer/mod.rs에 있습니다.

경계 테스트(boundary test) test_decoder_step_wires_kernel_boundaries는 가중치를 0으로 두고, 호스트(host)가 준비한 입력을 투영(projection), 어텐션 청크(attention chunk) 하나, 디코더(decoder)에 차례로 통과시킵니다. 스칼라 정답 기준 테스트(scalar-oracle test)는 투영, 청크 단위 어텐션(chunked attention), 디코더 산술 연산을 각각 별도로 검사합니다.

최종 층과 패딩된 로짓(Final layer and padded logits)

final_layer는 잔차 스트림(residual stream)을 받아 RMSNorm을 적용하고, 모델 어휘 가중치 뷰(vocabulary weight view)를 패딩된 출력 표현(padded output representation)에 맞게 재구성(reshape)한 뒤 m![Wp]에 로짓(logit)을 씁니다. 소스는 별도의 lm_head_weight를 받습니다. 이 예제 자체는 임베딩 가중치 공유(tied embedding)를 보장하지 않습니다.

결정적 테스트(deterministic test) test_final_layer_matches_scalar_reference는 유효한 W 로짓(logit)을 호스트(host)의 RMSNorm·내적(dot product) 정답 기준(oracle)과 비교합니다. 패딩(padding)은 텐서에 요구되는 형태(shape)와 저장 동작의 일부입니다. 패딩된 항목을 어떻게 해석할지는 호출자(caller)의 몫입니다.

검증하고 살펴보기(Verify and inspect)

저장소(repository)의 일반 명령으로 트랜스포머 테스트 대상(transformer test target)을 실행합니다.

bash
cargo furiosa-opt test --test transformer_tests

테스트는 시드(seed)를 고정한 작은 입력 데이터(fixture)를 사용하고, 지원하는 각 경계를 호스트 수식(host equation)과 비교합니다. 모델 파일이나 샘플링 루프(sampling loop)는 필요 없습니다. 선택한 장치 진입점(device entry point)을 --dump-schedule로 컴파일하여 스케줄 데이터(schedule data)를 생성하세요. 스케줄 뷰어(Schedule Viewer)로 결과를 살펴보고 스케줄링과 튜닝(Scheduling and Tuning)의 비교 절차를 따르세요.

변경은 일정한 절차로 진행하세요. 먼저 정답 기준(oracle)을 만들고 기준 스케줄(baseline schedule)을 기록합니다. 그다음 매핑(mapping)·이동(movement)·엔진(engine)·형태(shape) 중 한 가지 선택만 바꾸어 같은 산출물(artifact)을 비교합니다. 정답 기준이나 소스 코드의 작성 순서만으로 처리량(throughput)을 추정하지 마세요.
