공간 차원과 시간 차원(Spatial and Temporal Dimensions)

HostTensor<D, E>는 하나의 매핑(mapping)으로 물리적 표현(physical representation) 전체를 나타냅니다. 장치 텐서(device tensor)는 매핑을 다음과 같은 여러 전용 차원(dedicated dimension)에 나누어 배치합니다.

  • 공간 차원(Spatial dimensions): Chip, Cluster, Slice는 하드웨어 계층(hardware hierarchy)에 걸쳐 데이터를 분산합니다. SpmTensor는 스크래치패드(scratchpad)를 배치할 때 Slice 대신 Pe를 사용합니다. 스트림 텐서(stream tensor)에서는 Packet이 각 시간 반복(temporal iteration) 안에서 병렬로 전달할 양을 추가로 정합니다.
  • 시간 차원(Temporal dimension): Time은 스트림 텐서(stream tensor)의 데이터 전달 반복을 순서대로 진행시킵니다.

공간 차원(Spatial Dimensions)

하드웨어 계층(hardware hierarchy)의 각 공간 단계(spatial level)는 텐서 타입(tensor type)에 별도의 타입 매개변수(type parameter)를 가지며, 이를 통해 공간 병렬 처리(spatial parallelism)가 가능합니다. 같은 단계의 모든 유닛(unit)은 동일한 매핑(mapping)을 공유한다고 가정합니다.

아래 표기는 물리적 차원(physical dimension)의 이름을 보여 주기 위한 것이며 공개 타입(public type)이나 생성자(constructor)가 아닙니다. 공개 텐서 API(tensor API)와 뷰(view)는 저장소 모듈(storage module)의 문서에서 설명합니다.

rust
// 이 페이지 전체에서 가정하는 선언.
axes![A = 8, B = 512];

// HBM 텐서(tensor)
struct HbmTensor<D: Scalar, Chip: M, Element: M> {
    /* ... */
}

// SRAM 텐서(tensor)
// DM(데이터 메모리, Data Memory), TRF(텐서 레지스터 파일, Tensor Register File), VRF(벡터 레지스터 파일, Vector Register File)
struct DmTensor<D: Scalar, Chip: M, Cluster: M, Slice: M, Element: M> {
    /* ... */
}
struct TrfTensor<D: Scalar, Chip: M, Cluster: M, Slice: M, Lane: M, Element: M> {
    /* ... */
}
struct VrfTensor<D: Scalar, Chip: M, Cluster: M, Slice: M, Element: M> {
    /* ... */
}
struct SpmTensor<D: Scalar, Chip: M, Cluster: M, Pe: M, Element: M> {
    /* ... */
}

HBM 텐서(tensor)는 공간 병렬 처리(spatial parallelism)를 위해 데이터를 여러 칩(chip)에 분산합니다. 각 칩은 자신이 맡은 데이터를 동시에 처리합니다. 예를 들어 HbmTensor<bf16, m![A], m![B]>는 8 × 512 = 4096개의 원소를 칩 8개에 분배하며, 각 칩에 원소 512개를 둡니다. i번째 칩의 j번째 원소에는 텐서 인덱스(tensor index) i![A: i, B: j]에 해당하는 값이 저장됩니다.

SRAM 텐서 타입(tensor type)은 더 세밀한 병렬 처리를 위해 Cluster, Slice 차원(dimension)을 추가합니다. SpmTensor는 결합된 PE(fused-PE) 환경에서 스크래치패드(scratchpad) 데이터를 배치하는 데 Pe를 사용합니다. m![4]는 모든 PE에 데이터(payload)를 복제하고, m![1 # 4]는 PE 0에만 두며, m![X % 4]는 네 PE에 분할합니다. by_positions는 SPM 인덱스(index) 전체가 PE 0에 있어야 하며, PE가 네 개인 클러스터(cluster)에서는 이를 Pe = m![1 # 4]로 표현합니다. Gather와 Scatter를 참고하세요. TrfTensor에는 TRF 데이터를 슬라이스(slice)당 레인(lane) 여덟 개에 분산하는 Lane 차원도 있습니다. 자세한 내용은 수축 엔진(Contraction Engine)을 참고하세요.

HBM 텐서(tensor)는 구체적인 주소(address)를 가집니다. DM·SPM·TRF·VRF 텐서는 백엔드(backend)로부터 주소를 배정받을 수 있습니다. 호스트 텐서(host tensor)는 호스트 측 값으로 남습니다. 매핑 매개변수(mapping parameter)는 물리적 표현(physical representation)을 결정하고, 주소는 저장소(storage)가 별도로 관리합니다.

제약(Constraints)

  • Chip, Cluster, Slice, Pe의 크기(size): 하드웨어의 개수와 정확히 같아야 합니다.

    유닛(Unit) 개수(Count) 제약(Constraint) 패딩 예시(Padding Example)
    Chip 시스템에 따라 다름 Chip::SIZE == NUM_CHIPS m![1 # NUM_CHIPS]
    Cluster 칩(Chip)당 2개 Cluster::SIZE == 2 m![1 # 2]
    Slice 클러스터(Cluster)당 256개 Slice::SIZE == 256 m![X / N # 256]
    Pe 클러스터(Cluster)당 4개 Pe::SIZE == 4 m![1 # 4]

    PE 하나는 슬라이스(slice) 64개를 담당합니다. 따라서 DM ↔ SPM 전송에는 Pe::SIZE == Slice::SIZE / 64라는 추가 조건이 필요하며, 이 조건이 맞으면 양쪽이 같은 슬라이스들을 가리킵니다.

    커널(kernel)이 하드웨어가 제공하는 것보다 적은 유닛(unit)을 사용한다면 어느 차원(dimension)이든 #로 패딩(padding)할 수 있습니다. 예를 들어 type Cluster = m![1 # 2]는 활성 클러스터(active cluster) 하나와 패딩만 있는 클러스터 하나를 사용하여, 칩(chip)당 클러스터 2개라는 하드웨어 요구 조건을 만족합니다.

    참고(Note) 런타임(runtime)은 칩 단위(chip granularity, #[device(chip = N)])로 동작하므로, 칩이나 클러스터(cluster)의 일부만 사용하는 방식은 아직 지원하지 않습니다. 이 제한은 향후 릴리스(release)에서 완화될 수 있습니다.

  • Element 크기(size): Element::SIZE * size_of::<D>()는 유닛(unit)당 SRAM 용량을 초과하면 안 됩니다. 용량은 텐서 타입(tensor type)에 따라 다음과 같이 다릅니다.

    종류(Type) 유닛(Unit) 제약(Constraint)
    DmTensor 슬라이스(Slice)당 512KB Element::SIZE * size_of::<D>() <= 512KB
    SpmTensor PE당 4KB Element::SIZE * size_of::<D>() <= 4KB
    TrfTensor 레인(Lane)당 8KB Lane::SIZE <= 8, Element::SIZE * size_of::<D>() <= 8KB
    VrfTensor 슬라이스(Slice)당 8KB Element::SIZE * size_of::<D>() <= 8KB

  • Element 정렬(alignment): 장치 저장소 API(device storage API)는 주소(address)에 정렬 제약을 둡니다. 모든 텐서(tensor)에 동일한 주소 규칙이 적용된다고 가정하지 말고, 각 메모리 계층(tier)의 생성자(constructor)와 백엔드(backend) 검사를 확인하세요.

시간 차원(Temporal Dimension)

TuTensor는 텐서 유닛(Tensor Unit)을 따라 흐르는 텐서 데이터를 스트림(stream)으로 나타냅니다. SRAM 타입(type)과 같은 Chip, Cluster, Slice 차원(dimension)을 유지하고, 스트리밍(streaming)을 위한 Time과 Packet을 추가합니다. Time은 시간 차원(temporal dimension)으로, 데이터 전달의 반복 순서를 정합니다. 공간 차원(spatial dimension)과 달리 Time에는 하드웨어가 정한 크기 한계가 없으며, 처리할 데이터의 양에 따라 커집니다. Packet은 추가 공간 차원으로, 시간 반복(temporal iteration) 한 번마다 각 슬라이스(slice)가 받는 원소 수를 정합니다.

rust
axes![N = 4, C = 64, H = 32, W = 32];

/// 파이프라인 단계(pipeline stage).
/// `Vector`는 의도적으로 빠져 있음. 벡터 엔진(Vector Engine)은 분기(branch), ALU 등의 전용 상태를 추적하는
/// 별도 타입 상태(typestate)인 `VectorBranchTensor`와 관련 타입을 사용하기 때문.
/// `Commit`도 의도적으로 빠져 있음. 쓰기 엔진(Commit Engine)이 결과를 DM에 기록하면
/// 데이터는 이동을 멈추고 저장된 상태(at rest)가 되어 타입(type)이 `TuTensor` 대신 `DmTensor`가 되기 때문.
enum Position {
    Begin,       // 파이프라인(pipeline)을 시작한 뒤
    Fetch,       // 읽기 엔진(Fetch Engine)을 지난 뒤
    Switch,      // 교환 엔진(Switch Engine)을 지난 뒤
    Collect,     // 수집 엔진(Collect Engine)을 지난 뒤
    Contraction, // 수축 엔진(Contraction Engine)을 지난 뒤
    Reduce,      // 축약 엔진(Reduce Engine)을 지난 뒤
    Cast,        // 형변환 엔진(Cast Engine)을 지난 뒤
    Transpose,   // 전치 엔진(Transpose Engine)을 지난 뒤
}

struct TuTensor<
    'l,                // 텐서 유닛(Tensor Unit) 컨텍스트(context)에 연결된 수명(lifetime)
    const P: Position,
    D: Scalar,
    Chip: M,
    Cluster: M,
    Slice: M,
    Time: M,
    Packet: M,
> {
    /* ... */
}

type T<'l> = TuTensor<
    'l,
    { Position::Fetch }, // 읽기 엔진(Fetch Engine)의 출력
    bf16,
    m![1],           // Chip: 칩(chip) 하나
    m![1],           // Cluster: 클러스터(cluster) 하나
    m![C / 2],       // Slice: 채널(channel) 64개를 슬라이스(slice) 32개에 분배
    m![N, H, W],     // Time: 배치(batch, N)와 공간(spatial, H, W) 차원(dimension)을 반복
    m![C % 2],       // Packet: 사이클(cycle)당 채널(channel) 2개
>;

타입(type) T는 전체 형상(shape)이 \\{N=4, C=64, H=32, W=32\\}인 텐서(tensor)를 슬라이스(slice) 32개에 걸쳐 스트리밍(streaming)합니다(Slice::SIZE = m![C / 2]::SIZE = 32). Time 차원(dimension)인 m![N, H, W]의 크기는 4 * 32 * 32 = 4096이므로 시간 반복(temporal iteration)은 4,096번입니다. 각 시간 반복에서 Packet 차원 m![C % 2]는 각 슬라이스에 채널(channel) 두 개를 전달합니다. 슬라이스 32개가 병렬로 동작하므로 시간 반복 한 번에 처리하는 채널의 총수는 32 * 2 = 64개입니다.

NCHW 표현 추적(NCHW Representation Trace)

NCHW 예제에서는 배치(batch)를 칩(chip) 네 개에 분산하는 HBM 표현(representation)에서 시작해 표현이 바뀌는 과정을 추적할 수 있습니다.

rust
type Hbm = HbmTensor<bf16, m![N], m![C, H, W]>;

활성 칩(active chip) 하나를 사용하고 채널(channel) 두 개마다 하나의 슬라이스(slice)를 배정하여 DM으로 옮깁니다.

rust
type Dm = DmTensor<bf16, m![1], m![1], m![C / 2], m![N, H, W, C % 2]>;

위의 스트림 타입(stream type) T는 같은 채널 분할(channel split)을 사용하지만, N, H, W는 Time에, 각 슬라이스(slice)의 채널 두 개는 Packet에 배치합니다.

Index (N=1, C=17, H=3, W=5)를 추적해 보겠습니다.

  • HBM에서는 칩(chip) 1이 선택되고, 원소 오프셋(element offset)은 17 * 32 * 32 + 3 * 32 + 5 = 17,509입니다.
  • DM에서는 슬라이스(slice) 17 / 2 = 8이 선택됩니다. 원소 매핑(element mapping)은 N=1, H=3, W=5와 패킷 위치(packet position) 17 % 2 = 1을 선택합니다.
  • 스트림(stream)에서는 슬라이스(slice) 8에서 Time = 1 * 32 * 32 + 3 * 32 + 5 = 1,125, Packet = 1을 선택합니다.

각 단계(stage)에서 값의 물리적 좌표(physical coordinate)는 바뀌지만 Index는 (1, 17, 3, 5)로 유지됩니다. 이것이 매핑(mapping)에서 표현(representation)으로 이어지는 경로입니다. 텐서(tensor)가 값을 담는다는 의미는 텐서 의미론(Tensor Semantics)에서 정의합니다.
