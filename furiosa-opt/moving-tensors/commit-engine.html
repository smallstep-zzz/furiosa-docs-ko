쓰기 엔진(Commit Engine)

쓰기 엔진(Commit Engine)은 어댑터(adapter)가 최종 원소 타입(element type)과 배치(layout)를 선택한 뒤 텐서 유닛(Tensor Unit)의 스트림 패킷(stream packet)을 DM에 기록합니다. 읽기 엔진(Fetch Engine)의 반대 동작입니다. 이는 커밋 시퀀서(Commit Sequencer)로, 각 슬라이스(slice)에서 독립적으로 실행되어 자신의 로컬 DM 구획(local DM partition)에 쓰는 수학적 텐서 이동(mathematical tensor move)입니다.

계산된 텐서 유닛 스트림(Tensor Unit stream)을 의도한 Element 배치(layout)의 DM 텐서(tensor)로 만들어야 한다면 Commit을 선택하세요.

인터페이스(Interface)

텐서 유닛 파이프라인(Tensor Unit pipeline)의 끝에서 TuTensor는 Chip, Cluster, Slice, Time, Packet 차원(dimension)을 가집니다. Time은 계산이 시간에 걸쳐 펼쳐진 방식(temporal unrolling)을 나타내고, Packet은 출력 스트림(output stream)의 원소 배치(element layout)입니다.

.commit()은 스트림(stream)을 DM의 DmTensor에 기록합니다.

rust
impl<'l, const T: Tu, P: CanApplyCommit, D: Scalar, Chip: M, Cluster: M, Slice: M, Time: M, Packet: M, B: Backend>
    TuTensor<'l, T, P, D, Chip, Cluster, Slice, Time, Packet, B>
{
    /// 데이터 메모리(data memory)에 기록(commit).
    #[primitive(TuTensor::commit)]
    pub fn commit<Element: M>(self) -> DmTensor<D, Chip, Cluster, Slice, Element, B> {
        verify_commit::<D, Time, Packet, Element>();
        DmTensor::from_parts(self.inner.transpose(false))
    }

    /// 데이터 메모리(data memory)의 변경 가능한 텐서 뷰(mutable tensor view)에 기록(commit).
    #[primitive(TuTensor::commit_view)]
    pub fn commit_view<DstSlice: M, Element: M>(
        self,
        mut dst: DmTensorViewMut<'l, D, Chip, Cluster, DstSlice, Element, B>,
    ) {
        constraints::assert_slice_preserved::<Slice, DstSlice>();
        verify_commit::<D, Time, Packet, Element>();
        dst.inner.transpose(self.inner.view(), false);
    }
}

각 슬라이스(slice)가 자신의 DM 구획(partition)에 독립적으로 기록하므로 .commit()은 Chip, Cluster, Slice 차원(dimension)을 그대로 유지합니다. 출력의 Element 매핑(mapping)은 Time, Packet을 대신하여 스트림(stream)을 DM에 어떻게 배치할지 정의합니다. Element는 커밋 시퀀서(Commit Sequencer)와 쓰기 어댑터(Commit Adapter)를 모두 구성합니다. 입력 스트림에 비해 Time 축(axis)의 순서를 바꿀 수도 있으므로 commit 중 전치(transpose)를 수행할 수 있습니다. Element 매핑이 성능에 미치는 영향은 최적화(Optimizations)를 참고하세요.

다음 예제는 형변환(cast)한 누산 결과(accumulation result)를 bf16으로 DM에 기록(commit)합니다. 출력 DmTensor는 슬라이스(slice) 256개에 걸쳐 시간 단계(time step) 16개 × bf16 원소 8개를 저장합니다. 여기서 D = bf16, Element = m![M, N # 16]입니다.

rust
axes![P = 256, M = 16, N = 8];

fn cast_commit<'l, const T: Tu>(
    input: ContractTensor<'l, T, f32, m![1], m![1 # 2], m![P], m![M], m![N]>,
) -> DmTensor<bf16, m![1], m![1 # 2], m![P], m![M, N # 16]> {
    // f32를 bf16으로 형변환(cast, Cast Engine)한 뒤 DM에 기록(commit, Commit Engine).
    // 입력: M = 시간 단계(time step) 16개, N = 패킷(packet)당 f32 원소 8개(32바이트).
    // 형변환(cast) 후: N = bf16 원소 8개를 16개로 패딩(padding, 32바이트).
    // 자르기(trim) 후: N # 16을 N = 8로 줄임.
    // 시퀀서(sequencer)는 P = 256개 슬라이스(slice)에 걸쳐 기록.
    input.cast::<bf16, m![N # 16]>().commit_trim::<m![N]>().commit()
}

제약(Constraints)

  • 하드웨어 차원(Hardware dimensions): Chip::SIZE, Cluster::SIZE, Slice::SIZE는 하드웨어 구성(hardware configuration)과 일치해야 합니다(공간 차원과 시간 차원(Spatial and Temporal Dimensions) 참고).
  • 주소 정렬(Address alignment): 모든 시퀀서 스트라이드(sequencer stride)는 8바이트의 배수여야 합니다.
  • 쓰기 단위 정렬(Write unit alignment): D[valid_size]는 8·16·24·32바이트 중 하나여야 합니다(커밋 어댑터의 자르기(Trimming) 단계 참고).

여러 번 쓰는 패킷(Multi-Write Packet)

패킷(packet)의 축(axis)이 DM에서 연속되지 않을 수 있으므로, 패킷 하나를 쓰는 데 하드웨어 쓰기(hardware write)가 여러 번 필요할 수 있습니다. 컴파일러(compiler)는 write_size = gcd(valid_size, access_size)를 구합니다. valid_size는 쓰기 어댑터(Commit Adapter)가, access_size는 시퀀서(Sequencer)가 제공합니다. sub 컨텍스트(sub-context)에서는 D[write_size]가 8바이트로 고정됩니다. 총 사이클(cycle) 수는 Time::SIZE * (valid_size / write_size)입니다. 이 나눗셈은 항상 나누어떨어집니다. main 컨텍스트에서는 valid_size == write_size이므로 패킷 하나를 한 사이클에 기록(commit)합니다. sub 컨텍스트에서는 write_size가 8바이트로 고정되고 자르기 제약(trimming constraint)에 따라 valid_size가 8·16·24·32바이트 중 하나이므로, valid_size / write_size는 항상 1·2·3·4 중 하나입니다.

rust
axes![M = 4, K = 2, W = 8, N = 16, L = 32];

// 컴파일러(compiler)가 생성한 구성(configuration): [
//   M -> 4 : 64,  (64 == 2 * 32,  연속(contiguous))
//   K -> 2 : 32,   (32  == 32 * 1,  연속(contiguous))
//   M -> 32 : 1    (패킷 차원(packet dimension), 연속(contiguous))
// ] : 8
// access_size = 64; valid_size = 8; write_size = gcd(64, 8) = 8; 패킷(packet)당 쓰기 횟수 = 1
fn no_transpose<'l, const T: Tu>(
    input: CastTensor<'l, T, i8, m![1], m![1 # 2], m![1 # 256], m![M, K], m![L]>,
) -> DmTensor<i8, m![1], m![1 # 2], m![1 # 256], m![M, K, L]> {
    input.commit_trim::<m![L]>().commit()
}

// 컴파일러(compiler)가 생성한 구성(configuration): [
//   M -> 4 : 8,   (8  != 2 * 32, 비연속(non-contiguous))
//   K -> 2 : 32,  (32 != 8 * 1,  비연속(non-contiguous))
//   W -> 8 : 1    (패킷 차원(packet dimension), 연속(contiguous))
// ] : 32
// access_size = 8; valid_size = 8; write_size = gcd(8, 8) = 8; 패킷(packet)당 쓰기 횟수 = 1
fn transpose<'l, const T: Tu>(
    input: ContractTensor<'l, T, f32, m![1], m![1 # 2], m![1 # 256], m![M, K], m![W]>,
) -> DmTensor<f32, m![1], m![1 # 2], m![1 # 256], m![K, M, W]> {
    input.commit_trim::<m![W]>().commit()
}

// 컴파일러(compiler)가 생성한 구성(configuration): [
//   M -> 4 : 8,   (8  != 2 * 32, 비연속(non-contiguous))
//   K -> 2 : 32,  (32 != 8 * 1,  비연속(non-contiguous))
//   N -> 8 : 1    (자른 패킷 차원(trimmed packet dimension), 연속(contiguous))
// ] : 16
// access_size = 8; valid_size = 8(16에서 자름(trim)); write_size = gcd(8, 8) = 8; 패킷(packet)당 쓰기 횟수 = 1
fn transpose_with_trimming<'l, const T: Tu>(
    input: CastTensor<'l, T, i8, m![1], m![1 # 2], m![1 # 256], m![M, K], m![N # 32]>,
) -> DmTensor<i8, m![1], m![1 # 2], m![1 # 256], m![K, M, N]> {
    input.commit_trim::<m![N]>().commit()
}

최적화(Optimizations)

커밋 시퀀서(Commit Sequencer)의 처리량(throughput)은 세 가지 요인이 결정합니다.

  • 연속 주소(Sequential Addresses): 각 슬라이스(slice)에서 연속된 DM 주소(address)에 쓰면 병렬 뱅크 접근(parallel bank access)이 가능해집니다(DMN당 128 B/cycle, DMN 인터리빙(interleaving) 사용 시 256 B/cycle). 같은 뱅크(bank)를 연속 64회 이상 접근하는 패턴(pattern)은 DM 뱅크 기아(DM Bank Starvation)를 일으킵니다.
  • 공간 병렬 처리(Spatial parallelism): 모든 활성 슬라이스(active slice)에 쓰기를 분산하면 처리량(throughput)을 최대화할 수 있습니다.
  • 정렬된 쓰기(Aligned writes, 불변 조건(invariant)): 쓰기 주소(write address)와 쓰기 단위(write unit)가 항상 8바이트에 정렬되어 있으므로 부분 뱅크 쓰기(partial bank write)는 발생하지 않습니다. 시퀀서 스트라이드(sequencer stride)는 8바이트의 배수이고(제약(Constraints) 참고), 커밋 어댑터의 자르기(Trimming) 단계는 D[valid_size]를 8바이트의 배수로 유지합니다.
