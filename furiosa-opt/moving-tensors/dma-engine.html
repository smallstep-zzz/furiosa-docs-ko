DMA 엔진(DMA Engine)

원문 대조 메모 · 번역자 설명

첫 예제의 원문에는 “슬라이스당 256개 원소”와 “슬라이스당 8개 원소”라는 설명이 함께 있습니다. 제시된 A = 2048, A / 8, A % 8을 보면 256 × 8 = 2,048로 읽어야 수가 맞습니다. 번역문은 원문을 보존하며 이 차이를 별도로 알립니다.

DMA 엔진(DMA Engine)은 텐서 유닛 파이프라인(Tensor Unit pipeline)을 거치지 않고 메모리 계층(memory tier) 사이에서 텐서(tensor)를 직접 옮깁니다. 따라서 계산 단계(compute stage)가 필요 없는 저장 위치(residency) 변경이나 배치(layout) 변경에 사용하세요.

Fetch·계산(compute)·Commit 단계가 필요 없는 HBM↔HBM, HBM↔DM, DM↔DM, DM↔SPM 이동에는 DMA를 선택하세요. 인터페이스(Interface) 예제는 원본 텐서(source tensor), 목적지 매핑(destination mapping), tdma 또는 pdma 컨텍스트(context)를 어떻게 조합하는지 보여 줍니다. 각 전송(transfer)은 서로 맞물려 동작하는 두 단계를 짝짓습니다.

  • 읽기 시퀀서(Read Sequencer): 원본 메모리 계층(source tier)에서 읽습니다.
  • 쓰기 시퀀서(Write Sequencer): 필요하면 배치 변환(layout transformation)을 적용하여 목적지 메모리 계층(destination tier)에 기록합니다.

DMA 전송(transfer)은 수학적 텐서 이동(mathematical tensor move)입니다. 배치(layout)가 달라도 출력은 입력과 같은 수학적 텐서(tensor)를 담습니다. 텐서 DMA(Tensor DMA)는 DMN·클러스터(cluster)·칩(chip) 사이의 전송을 지원하며, 칩 ID(chip ID)는 시스템 전체에서 일관되게 정해집니다.

전송 처리량(transfer throughput)을 고려할 때는 최적화(Optimizations)를 참고하세요.

인터페이스(Interface)

DMA 전송(transfer)은 한 메모리 계층(memory tier)의 텐서(tensor)를 받아 다른 계층 또는 같은 계층에 새 텐서를 만듭니다. 커널(kernel) 작성자는 원본 텐서(source tensor)의 .to_dm(), .to_hbm() 또는 관련 메서드(method)를 호출하며 DmaContext를 전달합니다.

  • Device::tdma: 칩 내부 전송(on-chip transfer)을 위한 텐서 DMA 컨텍스트(Tensor DMA context). HBM ↔ HBM, HBM ↔ DM, DM ↔ DM, DM ↔ SPM을 처리합니다.
  • Device::pdma: 호스트(host) ↔ HBM 전송을 위한 PCIe DMA 컨텍스트(context). PCIe DMA를 참고하세요.
rust
impl<D: Scalar, Chip: M, Element: M, B: Backend> HbmTensor<D, Chip, Element, B> {
    /// `self`를 소비(consume)하여 같은 HBM 주소(address)에서 텐서(tensor)를 다른 매핑(mapping)으로 재해석(reshape).
    /// [`DmTensor::reshape`](crate::tensor::memory::DmTensor::reshape)의 HBM 대응 메서드이며, 둘 다 [`Tensor::reshape`]에 처리를 위임(delegate).
    ///
    /// # 안전성(Safety)
    ///
    /// 각 계층(level)의 크기(`Chip::SIZE == Chip2::SIZE`, `Element`)는 아래에서 컴파일 시점(compile time)에 검사함.
    /// [`constraints::assert_hbm_reshape_dimension_preserved`] 참고. 실제 전제 조건(precondition)은
    /// [`Tensor::reshape`]와 같음. 기존 매핑(mapping)과 새 매핑은 원소를 동일한 물리적 순서(physical order),
    /// 즉 전송 순서(wire order)로 배치해야 하며, 이름 변경(relabel)은 데이터를 옮기지 않아야 함. 축(axis)의 재그룹화(병합/분할, merge/split)는 전송 순서를 보존하므로
    /// 유효하지만 순열(permutation)은 그렇지 않으므로 전치(transpose)를 사용해야 함. 크기가 같다는 사실만으로는 이를 보장하지 않음.
    /// `self`를 소비(consume)하는 것은 안전성 규칙(safety contract)을 명시한 것임. 이전 형상의 핸들(handle)이 남아서
    /// 충돌하는 매핑(mapping)으로 같은 HBM 바이트를 중복 참조(alias)할 수 없어야 함.
    #[primitive(HbmTensor::reshape)]
    pub unsafe fn reshape<Chip2: M, Element2: M>(self) -> HbmTensor<D, Chip2, Element2, B> {
        constraints::assert_hbm_reshape_dimension_preserved::<Chip, Chip2, Element, Element2>();
        HbmTensor::from_buffer(self.buffer)
    }
}

컴파일러(compiler)는 원본과 목적지 텐서 타입(tensor type)에서 읽기·쓰기 시퀀서 구성(sequencer configuration)을 도출합니다. HBM→DM 전송은 HBM의 Chip 차원(dimension)을 유지하면서 목적지의 Cluster, Slice, Element 차원을 지정합니다. DM→DM 전송은 새로운 Chip, Cluster, Slice, Element 차원을 지정할 수 있으며, 목적지가 HBM이면 Chip, Element를 지정합니다.

아래 예제는 두 번의 HBM→HBM 전송(transfer)으로 텐서(tensor)를 [A, B, C]에서 [C, A, B]로 전치(transpose)합니다.

rust
axes![A = 8, B = 16, C = 32];

fn transpose_simple(
    device: &mut Device,
    input: &HbmTensor<f32, m![1], m![A, B, C]>,
) -> HbmTensor<f32, m![1], m![C, A, B]> {
    // 1단계(step): [A, B, C] → [A, C, B]
    let intermediate: HbmTensor<f32, m![1], m![A, C, B]> = input.to_hbm(&mut device.tdma);

    // 2단계(step): [A, C, B] → [C, A, B]
    intermediate.to_hbm(&mut device.tdma)
}

메모리 계층(tier)을 넘는 전송도 목적지 타입(destination type)의 매핑(mapping)을 통해 배치 변환(layout transformation)을 적용합니다. HBM→DM 전송에서는 목적지 DM 텐서(tensor)에 Cluster, Slice 축(axis)을 추가하여 하드웨어 구획(hardware partition)에 텐서를 분산하고 브로드캐스트(broadcast)합니다.

rust
axes![A = 2048];

fn hbm_to_dm(
    device: &mut Device,
    input: &HbmTensor<i8, m![1], m![A]>,
) -> DmTensor<i8, m![1], m![1 # 2], m![A / 8], m![A % 8]> {
    input.to_dm::<m![1 # 2], m![A / 8], m![A % 8]>(&mut device.tdma)
}

여기서는 원소 2,048개짜리 벡터(vector)를 슬라이스(slice)당 256개 원소(Slice = m![A / 8])로 분산하고, 슬라이스당 원소 8개(Element = m![A % 8])씩 두 클러스터(cluster)에 걸쳐 배치합니다.

아키텍처(Architecture)

각 RNGD 칩(chip)에는 DMN 두 개당 하나씩 DMA 엔진(DMA Engine)이 총 8개 있으며, 최대 8개의 독립 전송(independent transfer)을 병렬로 실행합니다. DMA 엔진 하나는 짝지어진 읽기·쓰기 시퀀서(sequencer)를 실행하고, 텐서 이동(tensor move)은 집합 실행(aggregate)을 통해 여러 엔진에 분산됩니다. 아래 하위 절에서는 정적 구조(static structure), 시퀀서 표현(representation), 동적 동작(dynamic behavior), 컴파일러 도출 과정(compiler derivation), 집합 연산(aggregate operation)을 설명합니다.

참고(Note) 텐서 유닛(Tensor Unit)은 Fetch·Commit 엔진을 이용하는 SRAM→SRAM 전송에서 DMA보다 효율적인 경우가 많습니다. DMA가 SRAM 슬라이스(slice)의 대역폭(bandwidth)을 충분히 활용하지 못할 수 있기 때문입니다. 다만 실제로는 HBM 대역폭이 병목(bottleneck)인 경우가 많아 HBM ↔ DM 전송에서는 이 차이가 덜 중요합니다.

정적 구조(Static Structure)

Chip, Cluster, Slice는 하드웨어 공간 병렬 처리(spatial parallelism)의 차원(dimension)입니다. 칩(chip)당 DMA 엔진(DMA Engine) 8개는 서로 다른 메모리 구성 요소(memory component) 사이의 전송을 병렬로 수행합니다. 예를 들어 엔진 #0은 HBM ↔ DM을, 엔진 #1은 DM ↔ DM을 처리할 수 있습니다.

각 DMA 엔진(DMA Engine)은 읽기 시퀀서(read sequencer)와 쓰기 시퀀서(write sequencer)를 서로 보조를 맞추며(lockstep) 실행합니다. 읽기 시퀀서는 원본 주소(source address)를, 쓰기 시퀀서는 목적지 주소(destination address)를 순회합니다. 두 시퀀서는 루프 횟수(loop count)가 같지만 스트라이드(stride)와 기준 주소(base address)는 다릅니다. 배치 변환(layout transformation)이 동일한 논리 원소(logical element)를 원본과 목적지 메모리에서 서로 다른 순서로 배치하기 때문입니다. 컴파일러(compiler)는 읽기·쓰기 횟수가 같다는 점을 이용해, 각 루프 항목(loop entry)에 읽기·쓰기 스트라이드 쌍을 둔 하나의 시퀀서로 간결하게 표현합니다.

컴파일러(compiler)는 텐서 이동(tensor move) 하나를 사용 가능한 DMA 엔진(DMA Engine)에 분산합니다. 칩(chip)·클러스터(cluster)·슬라이스(slice) 차원(dimension)으로 작업을 분할하고 각 구획(partition)을 DMA 엔진에 배정합니다. 어느 DMA 엔진이든 모든 전송을 처리할 수 있습니다. 로컬 DMN 접근(local access)이 다른 DMN을 가로지르는 접근(cross-DMN access)보다 빠르므로, 기본적으로 컴파일러는 원본 DM에 가까운 DMA 엔진을 선택합니다. 커널(kernel) 작성자가 엔진을 명시적으로 지정할 수도 있습니다.

동종 집합 실행(homogeneous aggregate)은 참여하는 모든 DMA 엔진(DMA Engine)에 매개변수(parameter)를 달리 적용하는 하나의 서술자 템플릿(descriptor template)을 사용합니다. 이종 집합 실행(heterogeneous aggregate)은 각 DMN을 전용 서술자(descriptor)와 연결하는 HashMap<DmnIndex, DmaDescriptor>를 사용합니다. DM 텐서 명세(tensor specification)는 정확한 메모리 위치(memory location)를 식별하도록 매핑 표현식(mapping expression)에 칩(chip)·클러스터(cluster)·슬라이스(slice)를 포함해야 합니다.

동적 동작(Dynamic Behavior)

DmaSequencer의 각 루프(loop)는 행 우선 순서(row-major order)로 카운터(counter)를 진행시키고, 스트라이드 쌍(paired stride)에서 읽기·쓰기 주소(address)를 구합니다. 아래 시퀀서(sequencer)의 base = (0, 256³)인 경우를 보겠습니다.

text
[
  A -> 256 : (65,536, 256),
  B -> 256 : (256, 65,536),
  C -> 256 : (1, 1),
] : 256
반복(iteration) i 카운터(counters) 읽기 주소(read addr) 쓰기 주소(write addr)
0 (0, 0, 0) 0 write_base
1 (0, 0, 1) 1 1 + write_base
... ... ... ...
255 (0, 0, 255) 255 255 + write_base
256 (0, 1, 0) 256 65,536 + write_base
i = a·256² + b·256 + c (a, b, c) i 256·a + 256²·b + c + write_base

stride0 = 256이면 하드웨어는 반복(iteration)마다 256바이트를 읽고 씁니다. 따라서 반복 0에서는 (A, B, C) = (0, 0, 0..255)의 모든 값을 패킷(packet) 하나로 처리합니다. 전송은 약 500사이클(cycle)의 시작 지연(startup latency)과 256 × 256사이클의 데이터 전송 시간 후 완료됩니다.

컴파일러의 도출 과정(Compiler Derivation)

원본·목적지 텐서 매핑(tensor mapping) In, Out과 스트림 형상(stream shape) Stream이 주어지면, 컴파일러(compiler)는 읽기·쓰기 시퀀서(sequencer)를 도출합니다.

  • 읽기 시퀀서(Read sequencer): In을 스트림 형상(stream shape)에 사영(project)하여 원본 메모리 계층(source tier)의 루프별 스트라이드(per-loop stride)를 만듭니다.
  • 쓰기 시퀀서(Write sequencer): Out을 스트림 형상(stream shape)에 사영(project)하여 목적지 메모리 계층(destination tier)의 루프별 스트라이드(per-loop stride)를 만듭니다.
  • 통합 시퀀서(Unified sequencer): 각 항목(entry)에 읽기·쓰기 스트라이드(stride)가 쌍으로 들어가도록 두 시퀀서를 합칩니다.
  • 패킷 크기(Packet size): 연속 읽기·쓰기 양(consecutive read/write volume)에서 stride0을 추론합니다. 읽기와 쓰기 모두 연속된 256바이트를 접근하면 최적의 stride0은 256입니다.

A=B=C=256일 때 m![A, B, C] → m![B, A, C]의 스트림(stream)은 m![A, B, C]입니다. 컴파일러(compiler)는 아래 관계식으로 각 선형 인덱스(linear index)를 A·B·C에 대응시킨 뒤 스트라이드 쌍(paired stride)을 도출합니다.

관계식은 m![A, B, C]::map(i) = i![A: i / 65,536, B: (i % 65,536) / 256, C: i % 256]입니다. 표기법은 매핑 표현식(Mapping Expressions)을 참고하세요.

text
read_sequencer  = [
  A -> 256 : 65,536,
  B -> 256 : 256,
  C -> 256 : 1,
] : 256, HBM @ 0
write_sequencer = [
  A -> 256 : 256,
  B -> 256 : 65,536,
  C -> 256 : 1,
] : 256, HBM @ 256³

이 결과들은 항목(entry)마다 스트라이드 쌍(paired stride)을 가진 하나의 DmaSequencer로 합쳐집니다. 통합 DmaSequencer의 읽기 또는 쓰기 한쪽을 보여 줄 때는 가독성을 위해 쌍을 나타내는 대괄호를 생략하고, 해당 방향의 단일 스트라이드 시퀀서(single-stride sequencer)로 표시할 수 있습니다.

집합 연산(Aggregate Operations)

텐서 형상(tensor shape)이 여러 DMN에 균등하게 나누어지는지에 따라 집합 실행(aggregate)은 두 형태 중 하나를 사용합니다.

형상(shape)이 균등하게 나누어지면 참여하는 모든 엔진(engine)은 동종(homogeneous) 집합 실행(aggregate)을 수행합니다. 모든 DMA 엔진은 동일한 매개변수화 스트림 환경(parametric stream environment) Stream = { chip, cluster, slice, time, packet }을 사용하고, 기준 주소(base address)만 다릅니다.

형상(shape)이 균등하게 나누어지지 않으면 컴파일러(compiler)는 이종(heterogeneous) 집합 실행(aggregate)으로 전환합니다. 각 DMN은 StreamFn(chip, cluster, slice)를 통해 자신의 스트림 환경(stream environment)을 받습니다. 경계에 걸친 DMN은 유효 영역(valid region) 바깥에 쓰지 않도록 작업을 여러 DMA 명령(command)으로 나눕니다. 입력·출력 매핑 환경(mapping environment) In, Out은 동종 실행과 구조적으로 같으므로 전체 논리적 텐서 이동(logical tensor move)은 명확하게 정의됩니다.

두 형태 모두 정확성 불변 조건(correctness invariant) 두 가지를 지켜야 합니다.

  • 동일한 매체 종류(Same media types): 참여하는 모든 DMA 엔진(DMA Engine)은 같은 원본·목적지 메모리 매체(source/destination media)를 사용해야 합니다.
  • 하나의 통합 매핑(Single unified mapping): 입력 텐서 매핑(input tensor mapping) 하나와 출력 텐서 매핑(output tensor mapping) 하나가 전송 전체를 정의합니다.

명령(command)마다 별도의 시작 지연(startup latency)이 발생합니다. 따라서 여러 DMN에 균등하게 나누어지는 텐서 형상(tensor shape)을 선택하여 집합 실행(aggregate)을 동종(homogeneous)으로 유지하는 편이 좋습니다.

제약(Constraints)

DMA 엔진(DMA Engine)은 하드웨어 수준(hardware-level)의 정렬(alignment)·패킷 크기(packet-size) 규칙을 강제합니다. 이를 어기면 단순한 성능 저하가 아니라 정확성 오류(correctness error)나 하드웨어 예외(hardware exception)가 발생합니다.

  • 주소 정렬(Address alignment):

    계층(Tier) 읽기(Read) 쓰기(Write)
    HBM 1바이트 1바이트
    DM (SRAM) 1바이트 8바이트
    SPM 1바이트 1바이트

    HBM ↔ DM 전송(transfer)에서는 위 표와 별개로 읽기 주소(read address)·쓰기 주소(write address)·패킷 크기(packet size)가 모두 8바이트에 정렬되어야 합니다. DM의 비대칭 규칙(asymmetric rule)은 SRAM 하드웨어의 비대칭성을 반영합니다. 읽기 포트(read port)는 바이트 선택 로직(byte-select logic)으로 임의의 바이트 범위를 추출하지만, 쓰기 포트(write port)는 뱅크 폭(bank width) 전체인 8바이트 단위로 동작합니다. 따라서 정렬되지 않은 DM 쓰기(misaligned DM write)는 읽기·수정·쓰기(Read-Modify-Write)를 일으켜 쓰기 시간이 세 배가 되고, 해당 뱅크의 다른 연산도 막습니다.

    컴파일러(compiler)는 이 제약들을 하드웨어 불변 조건(hardware invariant)으로 강제합니다.

  • 패킷 크기(Packet size): 최대 크기는 4,096바이트입니다. 이는 트랜잭션(transaction)이 전송 256회(beat) × 16바이트 데이터 폭(data width)을 넘을 수 없다는 AXI 프로토콜(protocol) 제약에서 정해집니다.

최적화(Optimizations)

DMA 처리량(throughput)은 메모리 대역폭(memory bandwidth), 채널(channel)·DMN 인터리빙(interleaving), 패킷 분할(packet splitting)에 수반되는 시작 지연(startup latency)의 세 요인이 결정합니다.

메모리 대역폭(Memory Bandwidth)

각 메모리 계층(tier)의 최대 대역폭(peak bandwidth)은 달성 가능한 처리량(throughput)의 상한이 됩니다. 실제 속도는 스트리밍 경로(streaming path)에서 가장 느린 구성 요소(component)에 제한됩니다.

계층(Tier) 최대 대역폭(Peak bandwidth)
HBM 칩(chip)당 1.5 TB/s(32채널(channel) × 0.75 GHz에서 채널당 48 GB/s)
DM 클러스터(cluster)당 256 B/cycle(DMN 인터리빙(interleaving) 사용 시, DMN당 128 B/cycle)
SPM 클러스터(cluster)당 128 B/cycle(같은 칩(chip)에서만)
PCIe 읽기·쓰기 모두 30 B/cycle(PCIe DMA 참고)

각 DMA 엔진(DMA Engine)은 자체적으로 최대 256 B/cycle을 이동시킬 수 있습니다. HBM 대역폭(bandwidth)은 HBM 데이터를 전송하는 모든 엔진이 공유합니다. 따라서 HBM 대역폭을 모두 사용하는 집합 실행(aggregate)의 상한은 엔진별 수치의 합이 아니라 HBM 최대치인 1.5 TB/s입니다.

같은 클러스터(cluster) 안의 DM→DM 전송(transfer)은 읽기와 쓰기를 직렬화(serialize)합니다. 두 단계가 같은 DM 뱅크 접근(bank access)을 두고 경쟁하기 때문입니다. HBM ↔ DM처럼 계층(tier)을 넘는 전송은 읽기·쓰기 단계를 파이프라인(pipeline)으로 겹쳐 처리합니다.

참고(Note) 텐서 유닛(Tensor Unit)은 Fetch·Commit 엔진을 이용하는 SRAM→SRAM 전송에서 DMA보다 효율적인 경우가 많습니다. DMA가 SRAM 슬라이스(slice)의 대역폭(bandwidth)을 충분히 활용하지 못할 수 있기 때문입니다. 다만 실제로는 HBM 대역폭이 병목(bottleneck)인 경우가 많아 HBM ↔ DM 전송에서는 이 차이가 덜 중요합니다.

채널과 DMN 인터리빙(Channel and DMN Interleaving)

최대 대역폭(peak bandwidth)을 유지하려면 하부 메모리 구획(memory partition)들에 걸쳐 접근 패턴(access pattern)을 인터리빙(interleaving)해야 합니다.

HBM 채널(channel) 선택에는 주소 비트(address bit) 9–28이 사용되며, 주소 비트 8은 스택 비트(stack bit)입니다. 32개 채널 모두에 요청(request)을 분산하려면 접근 패턴(access pattern)이 이 비트들을 모두 변화시켜야 합니다. 스택 비트인 주소 비트 8만 빠져도 요청이 32개 중 16개 채널에만 전달되어 유효 대역폭(effective bandwidth)이 절반으로 줄어듭니다. 같은 HBM 뱅크(bank)에 반복 접근할 때 행 주소 비트(row-address bit) 21 이상이 변할 수 있습니다. 충돌(conflict)마다 약 40사이클(cycle)의 비용이 발생하며, 대역폭이 약 10분의 1 수준으로 줄어들 수 있습니다. FR-FCFS 메모리 스케줄링(memory scheduling)이 처리량(throughput)을 일부 회복시키지만 근본적인 비용은 여전히 큽니다.

DM 대역폭(bandwidth)을 충분히 쓰려면 각각 128 B/cycle인 두 DMN을 번갈아 접근해야 합니다. 따라서 하나의 DMN만 접근하는 패턴(pattern)은 DM 대역폭을 절반으로 줄입니다.

시작 지연과 패킷 분할(Startup Latency and Packet Splitting)

각 DMA 명령(command)은 데이터 전송 전에 약 500사이클(cycle)의 고정 시작 지연(fixed startup latency)이 있습니다. 여러 전송을 더 적은 명령으로 합치면 이 비용을 분산(amortize)할 수 있습니다. 이종 집합 실행(heterogeneous aggregate)은 DMN별 명령으로 나뉘므로 각 명령마다 지연 비용을 부담합니다.

하나의 명령(command) 안에서 하드웨어는 각 패킷(packet)을 256바이트 단위로 나눕니다. 따라서 n바이트 패킷은 ceil(n / 256)개의 AXI 요청(request)이 됩니다. 4,095바이트 패킷은 요청 16개가 들지만, 4,096바이트 한계를 조금 넘는 소수 길이(prime length) 4,099바이트 패킷은 여러 명령으로 나누어야 합니다. 가장 안쪽 루프의 스트라이드(innermost-loop stride) stride0은 패킷 정렬(alignment)을 결정합니다. stride0이 256바이트에 정렬되어 있으면 사이클(cycle) 수는 ceil(stride0 / 256)입니다. stride0이 정렬되어 있지 않으면 HBM 쓰기는 일부만 쓰는 256바이트 블록(block)에 대해 읽기·수정·쓰기(Read-Modify-Write) 비용을 추가로 부담합니다. HBM 읽기는 ceil에 따른 추가 비용만 발생하며, DM 연산은 이런 종류의 정렬 불일치에 대체로 영향을 받지 않습니다.

DMA는 DM 뱅크 접근(bank-access) 우선순위(priority)가 가장 낮습니다. 따라서 Fetch 또는 Commit 엔진(engine)이 같은 뱅크를 연속 64회 이상 접근하면 DMA에 기아(starvation)가 생겨 NoC 타임아웃(timeout)을 유발할 수 있습니다. 자세한 내용은 DM 뱅크 기아(DM Bank Starvation)를 참고하세요.

상세 예제(Detailed Examples)

아래 예제들은 대표적인 전송 패턴(transfer pattern)의 구체적인 시퀀서 구성(sequencer configuration)과 예상 사이클(cycle) 수를 제시합니다. 예제 1–3은 각 메모리 계층 쌍(tier pair)에서 잘 조정된 단일 엔진(single-engine) 경우를 다룹니다. 예제 4–5는 성능이 10배 이상 떨어지는 병적인 접근 패턴(pathological access pattern)을 대조합니다. 예제 6은 형상(shape)이 DMN에 균등하게 나누어지지 않을 때 이종 분할(heterogeneous segmentation)이 어떻게 이뤄지는지 보여 줍니다.

시퀀서 구성(sequencer configuration)은 주소 스트라이드(address stride)를 나타내는 기호 두 개를 사용합니다.

  • slice_stride: 슬라이스(slice) 내부 DM 구획(partition) 하나가 차지하는 가상 주소 범위(virtual address span, 4 MB).
  • DMN_stride: 같은 클러스터(cluster) 안에서 두 DMN 사이의 주소 간격(address span).

예제 1: HBM ↔ HBM 배치 변환(Layout Transformation)

인수(Arguments):

  • axes![A = 8, B = 8, C = 256]
  • dtype = i8
  • 원본(source): 오프셋(offset) 0의 HBM, 매핑(mapping) m![A, B, C]
  • 목적지(destination): 오프셋(offset) 16,384의 HBM, 매핑(mapping) m![B, A, C]
  • 스트림(stream): 시간(time) m![A, B], 패킷(packet) m![C]

생성된 시퀀서(sequencer):

text
read = [
  A -> 8   : 2,048,
  B -> 8   : 256,
  C -> 256 : 1,
] : 256, HBM @ 0

write = [
  A -> 8   : 256,
  B -> 8   : 2,048,
  C -> 256 : 1,
] : 256, HBM @ 16,384

가장 안쪽이 아닌 스트라이드(stride) 256과 2,048은 HBM 주소 비트(address bit) 8(스택, stack)과 11(채널, channel)을 변화시켜 요청(request)을 서로 다른 HBM 채널에 분산하고 병렬 실행합니다. 단일 256바이트 전송은 0.75 GHz에서 채널당 4사이클(cycle)이지만, 채널에 병렬 분산하면 최대치에 가까운 대역폭(bandwidth)을 유지합니다. 총 시간은 1 GHz 기준 읽기 요청 64개 + 쓰기 요청 64개에 시작 지연(startup) 500사이클을 더한 약 628사이클입니다.

DMA 엔진(DMA Engine) 4개가 HBM ↔ HBM 트래픽(traffic)을 공유하면, 읽기 대역폭(read bandwidth) 0.75 TB/s 중 각 엔진에는 약 0.1875 TB/s가 배정됩니다. 이렇게 나눈 대역폭에서는 stride0 = 256이어도 엔진 하나가 매 사이클(cycle) 요청(request) 하나를 완료할 수는 없습니다.

예제 2: 최대 대역폭의 HBM → DM(Full Bandwidth)

이 계층 간 전송(cross-tier transfer)은 HBM 채널(channel)과 두 DMN에 걸쳐 인터리빙(interleaving)하여 읽기·쓰기를 파이프라인(pipeline)으로 처리합니다.

인수(Arguments):

  • axes![A = 256, B = 256, C = 256]
  • dtype = i8
  • 원본(source): 칩(chip) 0의 HBM, 매핑(mapping) m![B, A, C]
  • 목적지(destination): 칩(chip) 0·클러스터(cluster) 0·슬라이스(slice) 0의 DM. 슬라이스 매핑(mapping) m![A / 4], 원소 매핑 m![A % 4, B, C]
  • 스트림(stream): 시간(time) m![B, A % 4, A / 4 % 32, A / 128], 패킷(packet) m![C]

생성된 시퀀서(sequencer):

text
read = [
  B      -> 256 : 65,536,
  A%4    -> 4   : 256,
  A/4%32 -> 32  : 1,024,
  A/128  -> 2   : 32,768,
  C      -> 256 : 1,
] : 256, HBM @ 0

write = [
  B      -> 256 : 256,
  A%4    -> 4   : 65,536,
  A/4%32 -> 32  : slice_stride,
  A/128  -> 2   : DMN_stride,
  C      -> 256 : 1,
] : 256, DM @ 0

HBM 측에서는 A/128=2의 스트라이드(stride) 32,768이 채널(channel) 사이의 접근을 인터리빙(interleaving)하고, 하드웨어 명령 큐(command queue)가 총 65,536개 요청(request, 256 × 4 × 32 × 2)의 흐름을 유지합니다. DM 측에서는 slice_stride, DMN_stride가 연속된 256바이트 쓰기를 두 DMN에 교차 배치하여 각 DMN이 사이클(cycle)당 요청 하나를 처리하게 합니다. 읽기·쓰기는 계층(tier)을 넘어 파이프라인(pipeline)으로 겹치므로, 총 시간은 max(읽기 65,536사이클, 쓰기 65,536사이클) + 시작 지연(startup) 500 ≈ 66,036사이클입니다.

예제 3: 한 클러스터 내 DM → DM(Within One Cluster)

같은 클러스터(cluster) 안의 DM→DM 전송(transfer)은 읽기·쓰기가 동일한 DM 뱅크 접근(bank access)을 놓고 경쟁하므로 두 단계를 직렬화(serialize)합니다.

인수(Arguments):

  • axes![A = 256, B = 256, C = 256]
  • dtype = i8
  • 원본(source): 칩(chip) 0·클러스터(cluster) 0·슬라이스(slice) 0의 DM, 원소 오프셋(element offset) 0. 슬라이스 매핑(mapping) m![A / 4], 원소 매핑 m![A % 4, B, C]
  • 목적지(destination): 칩(chip) 0·클러스터(cluster) 0·슬라이스(slice) 0의 DM, 원소 오프셋(element offset) 4·256·256. 슬라이스 매핑(mapping) m![A / 4], 원소 매핑 m![B, A % 4, C]
  • 스트림(stream): 시간(time) m![B, A % 4, A / 4 % 32, A / 128], 패킷(packet) m![C]

생성된 시퀀서(sequencer):

text
read = [
  B      -> 256 : 1,
  A%4    -> 4   : 65,536,
  A/4%32 -> 32  : slice_stride,
  A/128  -> 2   : DMN_stride,
  C      -> 256 : 1,
] : 256, DM @ 0

write = [
  B      -> 256 : 1,024,
  A%4    -> 4   : 256,
  A/4%32 -> 32  : slice_stride,
  A/128  -> 2   : DMN_stride,
  C      -> 256 : 1,
] : 256, DM @ (4·256·256)

DMN과 슬라이스(slice)를 인터리빙(interleaving)하면 각 단계에서 최대 256 B/cycle을 사용할 수 있지만, 두 단계는 직렬로 실행됩니다. 총 시간은 약 131,072사이클(cycle, 읽기 65,536 + 쓰기 65,536)에 시작 지연(startup) 500사이클을 더한 값입니다.

참고(Note) 가능하면 C를 256의 배수로 선택하세요. C = 256n + r, 0 < r < 256이면 전체 데이터 양은 조금만 바뀌어도 각 접근이 더 많은 요청(request)으로 나뉘어 사이클(cycle) 수가 n+1배로 늘어납니다.

예제 4: HBM 뱅크 충돌의 병적 사례(Bank-Conflict Pathology)

여기서는 DM 인터리빙(interleaving)은 적절하지만, 병적인 HBM 접근 패턴(pathological access pattern)으로 인해 잘 조정된 경우보다 약 10배의 사이클(cycle)이 듭니다.

인수(Arguments):

  • 칩(chip) 1개(DMN 8개)
  • axes![A = 64, B = 2,048, C = 1,024]
  • dtype = i8
  • 원본(source): HBM. 클러스터 매핑(cluster mapping) m![B / 1024], 슬라이스 매핑(slice mapping) m![B / 256 % 4, A], 원소 매핑(element mapping) m![B % 256, C]
  • 목적지(destination): DM. 슬라이스 매핑(slice mapping) m![A / 4], 원소 매핑(element mapping) m![B, A % 4, C]
  • 스트림(stream): 클러스터(cluster) m![B / 1024], 슬라이스(slice) m![B / 256 % 4], 시간(time) m![B % 256, C / 256, A % 32, A / 32], 패킷(packet) m![C % 256]

각 (cluster_i, dmn_j)에 대해 생성된 시퀀서(sequencer):

text
read = [
  B%256 -> 256 : 1,024,
  C/256 -> 4   : 256,
  A%32  -> 32  : 2²¹,
  A/32  -> 2   : 2²⁶,
  C%256 -> 256 : 1,
] : 256, HBM @ (i·2²⁰ + j·2¹⁸)

write = [
  B%256 -> 256 : 1,024,
  C/256 -> 4   : 256,
  A%32  -> 32  : slice_stride,
  A/32  -> 2   : DMN_stride,
  C%256 -> 256 : 1,
] : 256, DM @ (cluster_i, dmn_j, 0)

A%32, A/32의 스트라이드(stride)는 HBM 뱅크(bank) 내부의 행(row)을 선택하는 주소 비트(address bit) 21, 26을 변화시킵니다. 따라서 각 채널(channel)의 연속 접근은 거의 모든 요청(request)에서 한 행을 닫고 다음 행을 열어야 하며, 접근마다 약 40사이클(cycle)을 지불합니다. C / 256 = 4(스트라이드 256)를 통한 채널 인터리빙(interleaving)은 요청을 32개 채널 모두에 분산하지만, 각 채널 내부의 행 충돌(row-conflict) 비용을 가릴 수는 없습니다.

성능 내역(Performance breakdown):

  • HBM 읽기(read): 총 요청(request) 524,288개 ÷ 32채널(channel) = 채널당 16,384개 × 약 40사이클(cycle) ≈ 655,360사이클.
  • DM 쓰기(write): DMN당 요청(request) 65,536개를 사이클(cycle)당 하나씩 처리하며, 이 시간은 읽기 지연(read latency)에 가려집니다.

총 시간은 약 655,360사이클(cycle) + 시작 지연(startup) 500 ≈ 655,860사이클입니다. FR-FCFS 스케줄링(scheduling)이 처리량(throughput)을 일부 회복시키지만 약 10배 수준의 비용 증가는 남습니다.

예제 5: 스택 비트 누락의 병적 사례(Missing Stack Bit Pathology)

이 접근 패턴(access pattern)은 HBM의 스택 차원(stack dimension, 주소 비트(address bit) 8)에 걸쳐 인터리빙(interleaving)하지 못해 모든 트래픽(traffic)을 절반의 채널(channel)로 보내며, 유효 대역폭(effective bandwidth)을 절반으로 줄입니다.

인수(Arguments):

  • 칩(chip) 1개(DMN 8개)
  • axes![A = 8, B = 64, C = 8, D = 512]
  • dtype = i8
  • 원본(source): HBM, 매핑(mapping) m![A, B, C, D]
  • 목적지(destination): DM. 클러스터 매핑(cluster mapping) m![A / 4], 슬라이스 매핑(slice mapping) m![A % 4, B], 원소 매핑(element mapping) m![C, D % 256]
  • 스트림(stream): 클러스터(cluster) m![A / 4], 슬라이스(slice) m![A % 4], 시간(time) m![C, B % 32, B / 32], 패킷(packet) m![D % 256]

각 (cluster_i, dmn_j)에 대해 생성된 시퀀서(sequencer):

text
read = [
  C     -> 8   : 512,
  B%32  -> 32  : 4,096,
  B/32  -> 2   : 131,072,
  D%256 -> 256 : 1,
] : 256, HBM @ (i·2²⁰ + j·2¹⁸)

write = [
  C     -> 8   : 256,
  B%32  -> 32  : slice_stride,
  B/32  -> 2   : DMN_stride,
  D%256 -> 256 : 1,
] : 256, DM @ (cluster_i, dmn_j, 0)

C의 스트라이드(stride) 512는 HBM 주소 비트(address bit) 8인 스택 비트(stack bit)를 전혀 바꾸지 않으므로, DMN 여덟 개의 접근이 HBM 채널(channel) 32개 중 16개에 집중됩니다.

성능 내역(Performance breakdown):

  • HBM 읽기(read, 병목(bottleneck)): 총 요청(request) 4,096개 ÷ 16채널(channel) = 채널당 256개 × 1 GHz에서 요청당 약 5.3사이클(cycle) ≈ 1,357사이클.
  • DM 쓰기(write): DMN당 요청(request) 512개이며 읽기와 파이프라인(pipeline)으로 겹쳐 처리됩니다.

총 시간은 약 1,357사이클(cycle) + 시작 지연(startup) 500 ≈ 1,857사이클입니다. 스택 비트 인터리빙(stack-bit interleaving)을 복구해 32개 채널(channel) 모두를 사용하면 HBM 사이클 수가 절반이 됩니다.

예제 6: 이종 DMN 분할(Heterogeneous DMN Segmentation)

텐서 형상(tensor shape)이 여러 DMN에 균등하게 나누어지지 않으면 컴파일러(compiler)는 경계 DMN의 작업을 여러 명령(command)으로 분할하며, 각 명령마다 시작 지연(startup latency)이 발생합니다.

인수(Arguments):

  • 칩(chip) 4개
  • axes![A = 15, B = 32, C = 256, D = 8]
  • dtype = i8
  • 원본(source): DM. A' = A + 1#로 표기할 때 칩 매핑(chip mapping) m![D / 2], 클러스터 매핑(cluster mapping) m![D % 2], 슬라이스 매핑(slice mapping) m![A' / 4, A' / 2 % 2, B], 원소 매핑(element mapping) m![A' % 2, C]
  • 목적지(destination): HBM. 칩 매핑(chip mapping) m![D / 2], 원소 매핑(element mapping) m![D % 2, B, A, C]
  • 스트림(stream, DMN별로 StreamFn(chip_i, cluster_j, slice_k)로 표현):
text
StreamFn(chip_i, cluster_j, slice_k) = let A' = A + 1# in
  { chip: m![(D / 2) @ i = 1], cluster: m![(D % 2) @ j = 1],
    slice: m![(A' / 4) @ k = 1],
    time: (k == 0,1,2): m![A' % 2, B, A' / 2 % 2, C]
          (k == 3, exec #0): m![A' % 2, B, A' / 2 = 1, C]
          (k == 3, exec #1): m![A' = 1, B, A' / 2 % 2 @ 1, C],
    packet: m![C] }

차원(dimension) A = 15는 DMN 4개에 균등하게 나누어지지 않습니다(15 = 3·4 + 3). 따라서 DMN 0–2는 각각 원소 4개를 처리하고 DMN 3은 3개만 처리합니다. DMN 3에서 서술자(descriptor) 하나를 사용하면 네 번째 원소가 유효 영역(valid region) 밖에 기록되므로, 컴파일러(compiler)는 DMN 3의 작업을 합쳐서 정확히 원소 3개를 다루는 명령(command) 두 개로 나눕니다.

성능 내역(Performance breakdown):

  • DMN 0–2(각 명령(command) 한 개): 약 256사이클(cycle) + 시작 지연(startup) 500 ≈ 756사이클.
  • DMN 3(명령(command) 두 개): 데이터 처리 약 192사이클(cycle) + 시작 지연(startup) 1,000(각 500) ≈ 1,192사이클.

총 시간은 DMN 3에 의해 결정되며 약 1,192사이클(cycle)입니다. 이러한 분할(segmentation) 비용을 피하려면 여러 DMN에 균등하게 나누어지는 텐서 형상(tensor shape)을 선택하세요.

재분배 연산(Redistribution Operations)

SRAM 재분배(redistribution)는 DmTensor 또는 DmTensorView에서 재분배 계획(redistribution plan)을 만들고 to_dm이나 to_dm_view로 실행합니다. 마지막 메서드(terminal method) 이전의 모든 단계(stage)는 하나의 DMA 연산(operation)으로 융합(fuse)됩니다. 이 연산들은 칩(chip) 또는 클러스터(cluster) 사이로 부분 값(partial value)을 전달하고 각 대상(target)에 필요한 분할 조각(shard)을 선택합니다. 이 연산으로 부분 값을 전달하고 선택하는 완전한 축약 예제(reduction example)는 칩과 클러스터 축약(Chip and Cluster Reduction)을 참고하세요.

인터페이스 요약(Interface Summary)

원본(source)이나 선택할 Element 좌표(coordinate)를 제공하는 차원(dimension)에 따라 연산(operation)을 고르세요.

API 의미(Meaning) 형상에 미치는 영향(Shape effect) 실행(Execution)
source.chip_shuffle(sources) 대상 칩(target chip)마다 원본 칩(source chip) 하나를 선택 없음 지연 실행 텐서 DMA(Deferred Tensor DMA)
source.cluster_swap() 각 칩(chip) 내부에서 원본 클러스터(source cluster) 0과 1을 교환 없음 지연 실행 텐서 DMA(Deferred Tensor DMA)
source.chip_slice::<Axis, Output>(indices) 대상 칩(target chip)마다 Axis 좌표(coordinate) 하나를 선택 Element를 Output으로 변경 지연 실행 텐서 DMA(Deferred Tensor DMA)
source.cluster_slice::<Axis, Output>(indices) 대상 클러스터(target cluster)마다 Axis 좌표(coordinate) 하나를 선택 Element를 Output으로 변경 지연 실행 텐서 DMA(Deferred Tensor DMA)
tensor.asymmetric_chip_slice::<Axis, Output>(...) 각 칩(chip)에서 로컬(local) Axis 좌표(coordinate) 하나를 선택 Element에서 Axis 제거 sub 컨텍스트(sub-context)에서 즉시 병렬 복사(parallel copy)
tensor.asymmetric_cluster_slice::<Axis, Output>(...) 각 클러스터(cluster)에서 로컬(local) Axis 좌표(coordinate) 하나를 선택 Element에서 Axis 제거 sub 컨텍스트(sub-context)에서 즉시 병렬 복사(parallel copy)
source.hbm_chip_shuffle(dma, sources) 대상 HBM 칩(target HBM chip)마다 원본 칩(source chip) 하나를 선택 없음 즉시 HBM DMA 실행

이 표의 source는 텐서(tensor) 또는 뷰(view)일 수 있습니다. SRAM 뷰에는 Element 타일(tile)이 들어갈 수 있지만, Chip·Cluster 타일은 재분배(redistribution) 입력으로 지원하지 않습니다. 네 SRAM 메서드(method)는 지연 실행 재분배 계획(deferred redistribution plan)을 반환하므로 마지막 호출(terminal call) 전까지 이어 붙일 수 있습니다. to_dm은 계획을 실행해 새로운 목적지 텐서(destination tensor)를 만들고, to_dm_view는 동일한 논리적 결과(logical result)를 타일 같은 기존 목적지 뷰에 기록합니다. 축 순열(axis permutation)은 목적지 매핑(destination mapping)에서 정해지며 어느 마지막 메서드를 쓰는지와 무관합니다. 결과 매핑은 목적지 배치(destination layout)를 설명하지만, 각 값이 어느 원본 배치(source placement)나 선택 좌표(slice coordinate)에서 왔는지는 기록하지 않습니다. 이 값의 의미(value semantics)는 재분배 단계와 그 배열(array)을 읽어 확인하세요. 컴파일러(compiler)는 완성된 계획에서 동기화(synchronization)를 도출합니다. 원본 칩이 바뀌면 ChipSync, 원본 클러스터가 바뀌면 ClusterSync를 삽입하고, 둘 다 있으면 둘 다 삽입합니다. 로컬 데이터(local data)의 일부만 선택(slice)하는 계획은 어느 동기화도 삽입하지 않습니다.

텐서 DMA 의미론(Tensor DMA Semantics)

아래 예제는 칩(chip) 네 개, 클러스터(cluster) 두 개, 슬라이스(slice) 256개와 로컬 원소 형상(local element shape) [B, C, D]를 사용합니다.

rust
axes![ChipAxis = 4, ClusterAxis = 2, B = 4, C = 8, D = 8];

표의 in[p, k, b, c, d]는 원본 칩(source chip) p, 원본 클러스터(source cluster) k의 로컬 Element 좌표(coordinate) [b, c, d]에 있는 입력값입니다. 결과 이름은 out이며, 모든 행은 동일한 유효 슬라이스(live slice)를 가리킵니다.

칩 셔플(Chip Shuffle)

chip_shuffle(sources)는 각 대상 칩(target chip)에 대해 sources의 같은 위치에 지정된 원본 칩(source chip)에서 데이터를 전달합니다. 아래 패턴(pattern)은 대상 칩 0·1·2·3이 각각 원본 칩 1·2·3·0에서 읽는다는 뜻입니다. 텐서 형상(tensor shape)을 바꾸지 않고 각 값을 공급하는 칩을 바꿉니다.

각 대상 클러스터(target cluster) k와 모든 로컬 좌표(local coordinate) [b, c, d]에 대해:

대상 칩(Target chip) 대상 클러스터(Target cluster) 출력 원소(Output element) 원본 칩(Source chip) 원본 클러스터(Source cluster) 원본 원소(Source element) 출력값(Output value)
0 k [b, c, d] 1 k [b, c, d] out[0, k, b, c, d] = in[1, k, b, c, d]
1 k [b, c, d] 2 k [b, c, d] out[1, k, b, c, d] = in[2, k, b, c, d]
2 k [b, c, d] 3 k [b, c, d] out[2, k, b, c, d] = in[3, k, b, c, d]
3 k [b, c, d] 0 k [b, c, d] out[3, k, b, c, d] = in[0, k, b, c, d]
rust
fn chip_shuffle(
    device: &mut Device,
    dm: &DmTensor<i32, m![ChipAxis], m![ClusterAxis], m![1 # 256], m![B, C, D]>,
) -> DmTensor<i32, m![ChipAxis], m![ClusterAxis], m![1 # 256], m![B, C, D]> {
    dm.chip_shuffle([1, 2, 3, 0]).to_dm(&mut device.tdma)
}

HBM 칩 셔플(HBM Chip Shuffle)

HbmTensor::hbm_chip_shuffle, HbmTensorView::hbm_chip_shuffle은 sources가 선택한 원본 칩(source chip)에서 각 대상 칩 슬롯(target chip slot)으로 복사하고, Chip·Element 매핑(mapping)이 같은 새로운 HbmTensor를 반환합니다. 원본 목록(source list)은 sources[target_chip] = source_chip을 따르며 Chip의 모든 위치에 대한 순열(permutation)이어야 합니다. 칩 간 셔플(inter-chip shuffle)은 시스템 전체의 전역 칩 ID(global chip ID)를 사용합니다.

모든 원소 좌표(element coordinate) e에서 [1, 2, 3, 0] 패턴(pattern)은 다음과 같은 값의 의미(value semantics)를 가집니다. 여기서 in[p, e]는 원본 칩(source chip) p의 입력이고, out[t, e]는 대상 칩(target chip) t의 결과입니다.

대상 칩(Target chip) 원본 칩(Source chip) 출력값(Output value)
0 1 out[0, e] = in[1, e]
1 2 out[1, e] = in[2, e]
2 3 out[2, e] = in[3, e]
3 0 out[3, e] = in[0, e]
rust
axes![HbmChip = 4, HbmElement = 256];

fn hbm_chip_shuffle(
    device: &mut Device,
    hbm: &HbmTensor<i32, m![HbmChip], m![HbmElement]>,
) -> HbmTensor<i32, m![HbmChip], m![HbmElement]> {
    hbm.hbm_chip_shuffle(&mut device.tdma, &[1, 2, 3, 0])
}

두 엔진(engine) 모두 HBM→HBM 전송을 지원하므로 DMA 인수(argument)는 tdma, pdma 어느 것이든 사용할 수 있습니다.

클러스터 교환(Cluster Swap)

cluster_swap()은 모든 칩(chip) 내부에서 원본 클러스터(source cluster) 0과 1을 교환합니다. 텐서 형상(tensor shape)을 바꾸지 않고 각 값을 공급하는 클러스터를 바꿉니다.

모든 대상 칩(target chip) p와 로컬 좌표(local coordinate) [b, c, d]에 대해:

대상 칩(Target chip) 대상 클러스터(Target cluster) 출력 원소(Output element) 원본 칩(Source chip) 원본 클러스터(Source cluster) 원본 원소(Source element) 출력값(Output value)
p 0 [b, c, d] p 1 [b, c, d] out[p, 0, b, c, d] = in[p, 1, b, c, d]
p 1 [b, c, d] p 0 [b, c, d] out[p, 1, b, c, d] = in[p, 0, b, c, d]

chip_slice::<Axis, Output>(indices)는 대상 칩(target chip)마다 유효한 Axis 위치(live position) 하나를 선택하고, 남은 Element 매핑(mapping)을 Output으로 선언합니다. [0, 1, 2, 3]이면 대상 칩 t는 B의 위치 t를 남기며, 결과의 Element에서 B가 제거됩니다.

각 대상 클러스터(target cluster) k와 모든 결과 좌표(result coordinate) [c, d]에 대해:

대상 칩(Target chip) 대상 클러스터(Target cluster) 출력 원소(Output element) 원본 칩(Source chip) 원본 클러스터(Source cluster) 원본 원소(Source element) 출력값(Output value)
0 k [c, d] 0 k [0, c, d] out[0, k, c, d] = in[0, k, 0, c, d]
1 k [c, d] 1 k [1, c, d] out[1, k, c, d] = in[1, k, 1, c, d]
2 k [c, d] 2 k [2, c, d] out[2, k, c, d] = in[2, k, 2, c, d]
3 k [c, d] 3 k [3, c, d] out[3, k, c, d] = in[3, k, 3, c, d]
rust
fn chip_slice(
    device: &mut Device,
    dm: &DmTensor<i32, m![ChipAxis], m![ClusterAxis], m![1 # 256], m![B, C, D]>,

}

클러스터별 부분 선택(Cluster Slice)

cluster_slice::<Axis, Output>(indices)는 대상 클러스터(target cluster)마다 유효한 Axis 위치(live position) 하나를 선택하고, 남은 Element 매핑(mapping)을 Output으로 선언합니다. [1, 0]이면 대상 클러스터 0·1은 각각 B의 위치 1·0을 남기며, 결과의 Element에서 B가 제거됩니다.

p 0 [c, d] p 0 [1, c, d] out[p, 0, c, d] = in[p, 0, 1, c, d]
p 1 [c, d] p 1 [0, c, d] out[p, 1, c, d] = in[p, 1, 0, c, d]

단계 결합(Combining Stages)

재분배 단계(redistribution stage)는 물리적 순서(physical order)를 따릅니다. 선택적인 칩 셔플(chip shuffle), 선택적인 클러스터 교환(cluster swap), 0회 이상의 칩별 부분 선택(chip slice), 0회 이상의 클러스터별 부분 선택(cluster slice) 순서입니다. 두 마지막 메서드(terminal) 모두 완성된 계획을 하나의 DMA 연산(operation)으로 결합합니다. to_dm은 새 목적지 텐서(destination tensor)를 만들고, to_dm_view는 제공된 목적지 뷰(view)에 씁니다. slice 메서드를 여러 번 호출하면 같은 DMA 안에서 여러 축(axis)을 제거합니다.

아래의 융합 예제(fused example)는 남은 모든 d에 대해 다음 배치(placement)와 원소 좌표 매핑(element-coordinate mapping)을 만듭니다.

각 연산(operation)은 Chip이나 Cluster 차원(dimension)을 따라 데이터를 이동하지 않고 병렬 복사(parallel copy)로 축(axis) 하나를 선택합니다.

재분배 제약(Redistribution Constraints)

cluster_swap()은 클러스터(cluster)가 정확히 두 개여야 합니다. 원본 칩 목록(source chip list)은 순열(permutation)이어야 하며, 유효한 대상(live target)은 유효한 원본 칩 또는 클러스터 인덱스(source index)를 읽어야 합니다. 부분 선택 배열(slice array)은 대상 칩 또는 클러스터마다 유효한 인덱스 하나를 가져야 합니다. 융합 계획(fused plan)은 사용 가능한 동기화 프로토콜(synchronization protocol)에 맞게 목적지 칩마다 원본 칩 하나, 목적지 클러스터마다 원본 클러스터 하나를 선택해야 합니다. chip_slice::<m![B, C]>는 m![B, C]를 하나의 선형 인덱스(linear index)를 가진 연속 매핑(contiguous mapping)으로 다룹니다. 떨어져 있는 축(axis)을 따로 선택하려면 축마다 메서드(method) 호출 하나를 이어 붙이세요.

성능(Performance)

SRAM 재분배(redistribution)는 DMA의 정렬·패킷 제약(alignment and packet constraints)을 따릅니다. 일반적인 지침으로, DM 쓰기가 정렬(aligned)되고 긴 연속 구간(contiguous run)을 갖도록 Element 매핑(mapping)을 선택하면 컴파일러(compiler)가 효율적인 패킷(packet)을 만들 수 있습니다. 로컬 축(local axis) 하나를 선택할 때는 sub 컨텍스트 부분 선택(sub-context slice)을 사용하세요. 부분 선택을 셔플(shuffle)과 융합(fuse)하거나 여러 축을 하나의 DMA에서 선택해야 하면 DmTensorView 호출 연결(chain)을 사용하세요.

모아 읽기와 흩어 쓰기(Gather and Scatter)

모아 읽기(gather)는 인덱스 목록(index list)이 가리키는 위치의 HBM 값을 읽고, 흩어 쓰기(scatter)는 그 위치에 HBM 값을 씁니다. 아래 예제의 I는 인덱싱 대상 축(indexed axis), D는 인덱스가 정의된 정의역(domain), P는 함께 이동하는 데이터(payload)입니다. 소문자 d, p는 각각 D, P의 위치(position)이고, position[d]는 I의 위치입니다.

각 행(row)은 인덱스(index)가 가리키는 HBM 텐서(tensor)부터 시작해 호출 연결(chain)이 피연산자(operand)를 받는 순서대로 나열합니다.

연산(Operation) 피연산자(Operands) 의미(Meaning)
모아 읽기(Gather) 테이블(table) [I,P], 인덱스(index) [D], 결과(result) [D,P] result[d, p] = table[position[d], p], position[d]의 범위는 0..I::SIZE
흩어 쓰기(Scatter) 목적지(destination) [I,P], 인덱스(index) [D], 갱신값(updates) [D,P] destination[position[d], p] = updates[d, p], position[d]의 범위는 0..I::SIZE

by_positions는 SPM 인덱스(index)에서 이 위치(position)를 직접 가져옵니다. by_byte_offsets는 위치에 I의 바이트 스트라이드(byte stride)를 곱한 값을 담는 HBM 인덱스를 받습니다. 이 오프셋(offset)은 테이블(table) 또는 목적지 HBM 뷰(destination HBM view)의 기준 위치(base)에 대한 상대값이며, 반드시 스트라이드의 정수 배여야 합니다. 원소가 bf16이고 P = 128인 [I,P]에서는 스트라이드가 256바이트이므로 위치 3은 바이트 오프셋 768입니다.

인덱스(index)는 position: D -> I라는 사상(map)이며, 타입 매개변수(type parameter)는 그 구성 부분을 가리킵니다. 정의역(domain)은 인덱스가 정의된 범위이고, IndexedAxis는 인덱스 값이 가리키는 곳이며, Payload는 인덱스가 건드리지 않는 위치들을 따라 함께 이동합니다.

모아 읽기(gather)에서 IndexedAxis는 테이블(table)의 I, Payload는 P를 가리킵니다. D는 인덱스(index) 자체의 매핑(mapping)이므로 따로 선언하지 않습니다. 흩어 쓰기(scatter)에서도 같은 두 매개변수를 목적지(destination)에 선언하며 IndexedAxis가 I를 가리킵니다. 여기서도 Domain은 인덱스 자체의 매핑입니다. 두 호출 연결(chain)은 모두 인덱스가 가리키는 텐서(tensor)에서 시작하므로 값이 공급되기 전에 인덱스의 단위(unit)가 정해집니다. gather는 테이블을 읽고, scatter는 목적지에 씁니다.

연산(Operation) 인덱스 출처(Index source) API 호출 연결(API chain)
모아 읽기(Gather) HBM 바이트 오프셋(byte offsets) gather::<IndexedAxis, Payload>().by_byte_offsets::<Domain>(...).to_dm(...)
모아 읽기(Gather) SPM 위치(positions) gather::<IndexedAxis, Payload>().by_positions::<Domain>(...).to_dm(...)
흩어 쓰기(Scatter) HBM 바이트 오프셋(byte offsets) scatter::<IndexedAxis, Payload>().by_byte_offsets::<Domain>(...).from_dm(...)
흩어 쓰기(Scatter) SPM 위치(positions) scatter::<IndexedAxis, Payload>().by_positions::<Domain>(...).from_dm(...)

매핑 요구 사항(Mapping requirements)

세 요소를 구별하는 규칙은 하나입니다. IndexedAxis는 하나의 연속 영역(consecutive region)이어야 합니다. Domain, Payload에는 그런 제약이 없으며 서로 끼워 배치(interleave)할 수도 있습니다.

IndexedAxis는 하나의 연속 영역(consecutive region)을 가리킵니다. 이 영역은 여러 선언된 축(axis)으로 구성될 수 있습니다. gather 예제에서는 m![I], scatter 예제에서는 m![I, F]입니다. 이 영역을 제거하면 패딩(padding)을 포함한 Payload가 남습니다. m![I, F]의 인덱스 값(index value) 범위는 0..(I::SIZE * F::SIZE)입니다. 한 단계는 payload 하나의 크기에 해당합니다. 이는 하드웨어 규칙(hardware rule)입니다. 서술자(descriptor)는 인덱싱 대상 축(indexed axis)을 하나의 스트라이드(stride)로 전진시키므로, 그 영역이 조각나 있으면 전진할 단일 스트라이드가 없습니다.

Domain, Payload에는 그런 규칙이 없습니다. 시퀀서(sequencer)는 값을 가져오거나 보내는 텐서(tensor) 안에 둘을 배치합니다. 어느 쪽이든 다른 쪽이 사이에 끼어 있는 여러 구간(run)으로 나뉠 수 있고, 텐서의 Cluster, Slice, Element에 걸쳐 있을 수도 있습니다.

두 종류의 인덱스 목록(index list) 모두 패딩(padding)을 포함할 수 없습니다. 모든 정의역 위치(domain position)에 값이 있어야 합니다.

HBM 인덱스에서 얻는 gather의 정의역(domain)

인덱스(index)는 Cluster, Slice가 없는 HbmTensor<i32, Chip, Domain>입니다. 이 텐서의 원소 매핑(element mapping)이 정의역(domain)입니다. by_byte_offsets는 인덱스로부터 Domain을 추론하며 타입 표기(annotation)로 지정할 수도 있습니다. 이 표기는 인덱스 자체의 타입(type)을 가리키므로 인덱스에 쓰인 것과 같은 형태로 적어야 합니다.

SPM 인덱스에서 얻는 gather의 정의역(domain)

인덱스(index)는 SpmTensor<i32, Chip, IdxCluster, IdxPe, IdxElement>입니다. 이 중 두 매핑(mapping)이 정의역(domain)을 구성합니다. IdxCluster의 이름 있는 축(axis)이 앞에 오고, IdxElement는 클러스터(cluster) 하나가 가진 목록(list)을 제공합니다. 목록은 반드시 PE 0에 있어야 하며 m![1 # 4]로 표현되므로 IdxPe는 정의역에 참여하지 않습니다.

결과 전체를 나타내는 단일 타입(type)은 없습니다. by_positions::<Domain>에서 이를 선언하고, 그 선언을 검증합니다.

위의 gather_spm은 SpmTensor<i32, m![1], m![CL], m![1 # 4], m![D]>를 읽습니다. IdxCluster = m![CL]은 CL을 제공하고, IdxPe = m![1 # 4]는 아무 축(axis)도 제공하지 않으며, IdxElement = m![D]가 목록(list)을 제공하므로 정의역(domain)은 m![CL, D]입니다. IdxCluster = m![2] 또는 m![1 # 2]는 이름 있는 축을 가지지 않습니다. 이 경우 각 클러스터(cluster)가 같은 목록을 가지고 정의역은 m![D]입니다.

같은 정의역(domain)을 다른 배치(placement)에서 만들 수도 있습니다. SpmTensor<i32, m![1], m![2], m![1 # 4], m![CL, D]>는 목록(list) 하나를 모든 클러스터(cluster)에 브로드캐스트(broadcast)하고 CL을 원소 매핑(element mapping)에 둡니다. 여전히 by_positions::<m![CL, D]>가 정의역을 지정합니다. 두 경우는 목록의 저장 위치가 다를 뿐, 항목(entry)이 어떤 좌표를 키(key)로 삼는지는 같습니다.

gather의 DM 출력에 담겨야 하는 값

HBM 텐서(tensor)에는 Slice가 없으므로 payload는 테이블(table)의 Element에서만 나옵니다. 이후 to_dm 출력은 Cluster, Slice, Element를 합쳐 검사합니다. 출력은 각 정의역 위치(domain position)마다 payload를 한 번씩 담기만 하면 되며, 정의역과 payload를 모두 분할하거나 재배열할 수 있습니다. 예제 출력은 D를 Slice = m![D / 2]와 Element = m![D % 2, P]에 나눠 배치합니다.

scatter의 DM 갱신값(updates)에 담겨야 하는 값

갱신값(updates)은 gather 출력과 같은 역할을 맡으며 같은 규칙을 따릅니다. Payload를 선언하면 갱신값은 Cluster, Slice, Element를 합쳐 검사됩니다. 각 정의역 위치(domain position)마다 payload를 한 번씩 담기만 하면 되며, 둘 다 분할하거나 재배열할 수 있습니다.

위의 scatter_split_domain은 갱신값(updates)을 DmTensor<bf16, m![1], m![1 # 2], m![D / 2], m![F, D % 2, P]>로 담습니다. Slice가 m![D / 2], Element가 m![F, D % 2, P]이므로 정의역(domain) m![D]는 첫째·셋째 구간(run), payload m![F, P]는 둘째·넷째 구간을 차지합니다. 정의역은 DM 텐서(tensor)의 Cluster까지 확장될 수도 있습니다. DmTensor<bf16, m![1], m![CL], m![D / 2], m![D % 2, P]>는 정의역 m![CL, D]를 세 배치 매핑(placement mapping) 전체에 걸쳐 담고, 클러스터(cluster)마다 인덱스 목록(index list) 하나를 가집니다.

희소 모아 읽기(Sparse gather)

바이트 오프셋 gather(byte-offset gather)는 sparse_prefix(valid_length)를 호출해 인덱스 목록(index list)의 앞부분(prefix)만 런타임(runtime)에 실행할 수 있습니다. 이 앞부분 길이는 인덱스 텐서(index tensor) 자체의 매핑(mapping)인 Domain의 위치(position)를 셉니다. Domain에 축(axis)이 여러 개면 원래 인덱스 매핑 순서로 하나의 목록으로 펼친(flatten) 뒤 valid_length가 그 항목 수를 셉니다. IndexedAxis는 각 인덱스 값이 가리키는 테이블 영역(table region)이며, valid_length는 그 값들이 가리킬 수 있는 위치를 제한하지 않습니다. 인덱스 목록 전체 길이가 용량(capacity)입니다. 런타임 i32 길이는 0..=capacity 범위로 제한(clamp)되며, 제한된 길이를 requested라고 부르겠습니다.

장치는 requested보다 거친 경계(coarser boundary)에서 멈추므로 최소한 그만큼의 위치(position)를 실행하고, 실제로는 더 많이 실행하는 경우가 많습니다. 추가 실행량은 하위 표현 변환(lowering)이 해당 배치(placement)에서 찾은 건너뛰기 단위(skip unit)에 따라 달라지며, 커널(kernel)이 미리 예측할 수 없습니다. 커널을 컴파일해야 이것이 결정됩니다.

여기서 두 가지 규칙이 나오며, 어느 규칙도 그 구체적인 단위 값을 알 필요는 없습니다. 장치가 어느 항목이든 읽을 수 있으므로 requested에 포함되는지와 무관하게 인덱스 목록(index list)의 모든 위치에 유효한 바이트 오프셋(byte offset)이 있어야 합니다. 결과는 requested까지 정의됩니다. 그 이후 실제 실행 길이(executed length)까지는 값이 지정되지 않으며(unspecified), 그 뒤는 0입니다. requested가 0이면 아무것도 실행하지 않고 인덱스도 읽지 않습니다.

여기서 IndexedAxis는 m![I], Domain은 m![D]입니다. 호스트(host)는 D를 따라 처음 다섯 인덱스 항목(index entry)을 요청하며, 각 항목은 payload m![P] 전체를 동반합니다. 다만 인덱스 위치(index position) 512개는 모두 초기화합니다. 테이블(table)에 첫 행(row)이 있다면 0은 유효한 바이트 오프셋(byte offset)입니다.

rust
async fn gather_first_five(
    device: &mut Device,
    table: &HbmTensor<bf16, m![1], m![I, P]>,
    index: &HbmTensor<i32, m![1], m![D]>,
) -> Result<DmTensor<bf16, m![1], m![1 # 2], m![D / 2], m![D % 2, P]>, Error> {
    let valid_length = HbmScalar::<i32>::from_host(5, &mut device.pdma).await?;
    let valid_length = valid_length.to_spm(&mut device.tdma);
    Ok(table
        .gather::<m![I], m![P]>()
        .by_byte_offsets::<m![D]>(index)
        .sparse_prefix(valid_length)
        .to_dm(&mut device.tdma))
}

장치는 배치(placement)의 한 축(axis)을 따라 인덱스 목록(index list)을 줄이므로, to_dm 배치가 진행 간격(stepping)을 얼마나 거칠게 할지 결정합니다. 런타임 길이(runtime length)는 인덱스 목록이 차지한 연속 축(consecutive axis) 중 가장 바깥 축을 단위로 진행합니다. 그 아래의 축들은 통째로 함께 움직이며, 그 크기가 건너뛰기 단위(skip unit)입니다.

다만 Slice에 놓인 축의 분할 성분(digit)은 원래 크기를 유지하지 않습니다. DMA 컴파일(compilation)은 슬라이스 축(slice axis)을 DMN 단위로 자르며, 이 과정에서 인덱스 목록(index list)이 여러 서술자(descriptor)에 나뉘어 단위(unit)가 더 거칠어집니다.

A = 512를 분할 성분(digit) A / 2, A % 2로 나누고, payload는 QP × QD라고 해 보겠습니다. A / 2가 바깥 성분이므로 두 배치(placement) 모두에서 길이를 조정하는 축(stepped axis)이 되며, 위 규칙에 따라 그 아래에는 512 / 256 = 2가 남습니다. 기본 단일 칩(chip) 8PE 구성(configuration)에서는 다음과 같습니다.

Slice Element 규칙상(By the rule) 컴파일 결과(Compiled)
m![A % 2] m![A / 2, QP, QD] 2 2
m![A / 2] m![A % 2, QP, QD] 2 64

A / 2를 Slice에 둔 배치(placement)만 분할(cut) 비용을 부담합니다. 그 배치에서만 길이를 조정하는 축(stepped axis)이 분할되기 때문입니다.

현재 도구는 컴파일된 단위(compiled unit)를 보고하지 않습니다. 빌드(build)가 성공해도 어느 단위가 선택되었는지 알 수 없으며, 이를 드러내는 도구(tooling)는 아직 제공될 예정입니다.

PCIe DMA

PCIe DMA(Device::pdma)는 호스트 시스템 메모리(host system memory)와 장치 HBM(device HBM) 사이에서 텐서(tensor)를 옮깁니다. 칩 내부 텐서 DMA(on-chip Tensor DMA)와는 별도의 물리 엔진(physical engine)입니다. PCIe DMA는 호스트 ↔ HBM만 처리하고 텐서 DMA는 모든 칩 내부 전송(on-chip transfer)을 처리합니다.

커널(kernel) 작성자는 HostTensor의 .to_hbm()(호스트→장치, host → device) 또는 HbmTensor의 .to_host()(장치→호스트, device → host)를 호출합니다. 둘 다 비동기 연산(async operation)입니다.

rust
axes![A = 8, B = 512];

async fn upload_and_download(device: &mut Device) -> Result<(), Error> {
    let mut rng = SmallRng::seed_from_u64(0);
    let host: HostTensor<i8, m![A, B]> = HostTensor::rand(&mut rng);

    // 호스트(host) → HBM(할당기(allocator)가 지정한 주소)
    let hbm: HbmTensor<i8, m![A], m![B]> = host.to_hbm(&mut device.pdma).await?;

    // HBM → 호스트(host, 시스템 메모리로 복귀)
    let _round_tripped: HostTensor<i8, m![A, B]> = hbm.to_host(&mut device.pdma).await?;

    Ok(())
}

호스트 메모리(host memory)는 칩(chip)·클러스터(cluster)·슬라이스(slice)로 나뉘지 않으므로 HostTensor에는 Element 매핑(mapping)만 있습니다. 목적지 HbmTensor는 여러 칩에 분산하기 위해 Chip 축(axis)을 추가합니다. to_hbm이 새로운 Chip, Element 타입 매개변수(type parameter)를 받으므로 HBM의 목적지 원소 배치(destination element layout)는 호스트 배치와 달라도 됩니다.

PCIe DMA의 대역폭(bandwidth)은 30 B/cycle로, 칩 내부 텐서 DMA(on-chip Tensor DMA)의 256 B/cycle보다 대략 10배 느립니다. 알고리즘(algorithm)은 데이터를 한 번 업로드(upload)한 뒤 여러 칩 내부 연산(on-chip operation)에서 재사용하여 호스트 ↔ 장치 트래픽(traffic)을 최소화해야 합니다.
