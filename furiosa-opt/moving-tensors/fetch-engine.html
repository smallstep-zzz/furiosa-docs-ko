읽기 엔진(Fetch Engine)

읽기 엔진(Fetch Engine)은 DM 텐서(tensor)를 읽어 텐서 유닛(Tensor Unit)에 전달할 패킷 스트림(packet stream)을 만듭니다. OutTime, OutPacket이 이후 단계(stage)에서 소비할 스트림을 정합니다.

DM 데이터를 특정 시간 순서(temporal order)와 패킷 순서(packet order)로 텐서 유닛 스트림(Tensor Unit stream)에 넣어야 한다면 Fetch를 선택하세요.

인터페이스(Interface)

BeginTensor는 텐서 유닛 파이프라인(Tensor Unit pipeline)의 입구에서 DM에 저장된 텐서(tensor)를 나타냅니다. Time은 m![1]이며, 이는 파이프라인이 시작되기 전에는 시간 반복(temporal iteration)이 없다는 뜻입니다. Packet은 DM의 원소 배치(element layout)입니다.

BeginTensor::fetch()는 시퀀서(sequencer)를 실행하여 FetchTensor 패킷 스트림(packet stream)을 만듭니다. 이 스트림은 읽기 어댑터(Fetch Adapter), 교환 엔진(Switch Engine), 수집 엔진(Collect Engine)에 공급할 수 있습니다. assert_eq! 호출은 Cluster::SIZE, Slice::SIZE, 패킷 정렬(packet alignment)의 하드웨어 제약(hardware constraint)을 강제합니다(제약(Constraints) 참고).

rust
impl<'l, const T: Tu, P: CanApplyFetch, D: Scalar, Chip: M, Cluster: M, Slice: M, Time: M, Packet: M, B: Backend>
    TuTensor<'l, T, P, D, Chip, Cluster, Slice, Time, Packet, B>
{
    /// 페치 시퀀서(Fetch Sequencer)를 실행.
    #[primitive(TuTensor::fetch)]
    pub fn fetch<OutTime: M, OutPacket: M>(self) -> FetchTensor<'l, T, D, Chip, Cluster, Slice, OutTime, OutPacket, B> {
        verify_fetch::<Cluster, Slice, Time, Packet, OutTime, OutPacket>();
        FetchTensor::new(self.device, self.inner.transpose(true))
    }
}

텐서 매핑(Mapping Tensors)에서 소개했듯이 Chip, Cluster, Slice, Time, Packet 매핑(mapping)은 데이터를 공간과 시간에 분산합니다. 각 슬라이스(slice)가 자신의 DM 구획(partition)을 독립적으로 읽으므로 .fetch()는 입력의 Chip, Cluster, Slice 차원(dimension)을 그대로 보존합니다. 이후 교환 엔진(Switch Engine)은 슬라이스 사이에서 데이터를 옮겨 Slice 매핑을 바꿉니다. 축 끌어올리기(Axis lifting)는 선택한 차원에 따라 서로 다른 DM 읽기 오프셋(read offset)을 사용하여, 데이터 전송 없이 Chip, Cluster, Slice를 바꿉니다.

fetch()는 페치 시퀀서(Fetch Sequencer)를 구성하는 타입 매개변수(type parameter) OutTime, OutPacket을 받습니다. OutTime은 출력 스트림(output stream)의 시간 단계(time step) 수를, OutPacket은 각 패킷(packet) 내부의 원소 배치(element layout)를 정합니다. OutPacket 선택이 성능에 미치는 영향은 최적화(Optimizations)를 참고하세요.

다음 예제는 DM의 i8 행렬(matrix)을 i8 패킷 스트림(packet stream)으로 가져옵니다(fetch). 출력 FetchTensor는 512개 시간 단계(time step)를 스트리밍(streaming)하며, 각 단계는 i8 원소 32개짜리 패킷(packet, 32바이트)입니다. 여기서 OutTime = m![A], OutPacket = m![B]입니다.

rust
axes![CH = 4, CL = 2, S = 256, A = 512, B = 32];

fn fetch_matrix_example<'l, const T: Tu>(
    input: BeginTensor<'l, T, i8, m![CH], m![CL], m![S], m![1], m![A, B]>,
) -> FetchTensor<'l, T, i8, m![CH], m![CL], m![S], m![A], m![B]> {
    input.fetch::<m![A], m![B]>()
}

Chip, Cluster, Slice는 하드웨어 공간 병렬 처리(spatial parallelism)의 차원(dimension)입니다. 모든 슬라이스(slice)에서 페치 시퀀서(Fetch Sequencer)가 독립적으로 실행되며, 각각 자신의 로컬 DM 구획(local DM partition)에서 동작합니다. 이 예제의 CH = 4, CL = 2, S = 256은 칩(chip) 4개, 칩당 클러스터(cluster) 2개, 클러스터당 슬라이스 256개인 시스템을 나타냅니다. 각 슬라이스는 자신의 A×B 부분 텐서(sub-tensor)에 대해 같은 시퀀서를 실행합니다.

축 끌어올리기(Axis Lifting)

fetch_chip_lift, fetch_cluster_lift, fetch_slice_lift는 축(axis)을 Time에서 Chip, Cluster, Slice로 옮깁니다. 일반 fetch는 모든 칩(chip)·클러스터(cluster)·슬라이스(slice)에서 같은 DM 오프셋(offset)으로 시작해 Time의 축들을 순회합니다. 끌어올리기(lift)는 각 칩·클러스터·슬라이스에 서로 다른 읽기 *기준 위치(base)*를 주므로, 끌어올린 축은 병렬로 읽히고 Time에서는 제거됩니다.

읽기 기준 위치(read base)는 시작 오프셋(starting offset)만 바꾸므로, 끌어올리기(lift)를 하려면 선택한 차원(dimension)에 걸쳐 원본 영역(source region)이 복제되어 있어야 합니다. DM 배치(placement)는 이 복제를 브로드캐스트(broadcast)로 표현하며, lift는 그 자리를 끌어올린 축(axis)으로 바꿉니다.

Slice의 경우 슬라이스(slice) 사이에서 데이터를 옮기거나 Slice에서 Time으로 옮겨야 하면 InterTranspose를 사용하세요. Chip, Cluster에서는 원본 영역(source region)이 복제되어 있지 않을 때 DMA를 대안으로 사용합니다.

단계(Stage) 차원(Dimension) 기준 위치의 출처(Where the base comes from)
fetch_chip_lift Chip 읽기 명령(read command)에 정적 기준 위치(static base)가 인코딩되므로 lift에 별도 설정 연산(setup operation)이 추가되지 않음
fetch_cluster_lift Cluster 읽기 명령(read command)에 정적 기준 위치(static base)가 인코딩되므로 lift에 별도 설정 연산(setup operation)이 추가되지 않음
fetch_slice_lift Slice 컴파일러(compiler)가 DMA, fetch 실행 컨텍스트(execution context) 안의 덧셈(add), SFR 저장(store)을 사용하여 슬라이스(slice)별 런타임 기준 위치(runtime base)를 생성함

슬라이스 기준 위치(slice base)는 원본 텐서(source tensor)의 런타임 주소(runtime address)에 의존하므로 정적 명령 필드(static command field)로 인코딩할 수 없습니다. 컴파일러(compiler)는 상대 오프셋(relative offset) 상수들을 DRAM에서 SRAM으로 복사하고, fetch의 실행 컨텍스트(execution context)에서 원본 주소를 더한 뒤, 결과를 슬라이스별 기준 위치 SFR(per-slice base SFR)에 저장합니다. Fetch는 이 설정(setup)이 끝날 때까지 기다립니다. 이 설정은 교환 엔진(Switch Engine)의 사용자 정의 비트맵(custom bitmap)과 같은 SFR 저장 방식을 사용합니다.

sub 컨텍스트(sub-context)의 fetch에서는 설정을 위한 저장(setup store)이 fetch 자체에 필요한 SFR을 덮어씁니다. 컴파일러(compiler)는 기준 위치(base)를 기록한 뒤 이 매개변수(parameter)를 복원합니다. 두 컨텍스트(context) 모두 모든 lift 변형(variant)을 지원합니다.

예제: Q를 Slice로 끌어올리기(Lifting)

rust
axes![A = 128, Q = 4, V = 16];

fn fetch_halves_per_slice<'l, const T: Tu>(
    input: BeginTensor<'l, T, bf16, m![1], m![1 # 2], m![A, 2], m![1], m![Q, V]>,
) -> FetchSliceLiftTensor<'l, T, bf16, m![1], m![1 # 2], m![A, Q / 2], m![Q % 2], m![V]> {
    input
        .fetch::<m![Q], m![V]>()
        .fetch_slice_lift::<m![A, Q / 2], m![Q % 2]>()
}

A = 128일 때 Slice 배치(placement) m![A, 2]는 슬라이스(slice) 128쌍을 나타냅니다. 각 쌍의 두 슬라이스는 같은 m![Q, V] 데이터를 담습니다. 일반 fetch는 두 슬라이스 모두에서 Q 값 네 개를 전부 읽습니다. 끌어올리기(lift)는 브로드캐스트(broadcast) 2를 Q / 2로 바꾸고 Time에는 Q % 2를 남깁니다. 첫 슬라이스는 기준 위치(base) 0에서 Q = 0, 1을, 두 번째 슬라이스는 원소 32개 위치(bf16 64바이트)에서 Q = 2, 3을 읽습니다.

배치(placement) 기준 위치(base) 읽는 값(reads) 시간 단계(time steps)
fetch, 어느 슬라이스(slice)든 동일 m![A, 2] 0 Q = 0, 1, 2, 3 4
lift, 첫 슬라이스(slice) m![A, Q / 2] 0 Q = 0, 1 2
lift, 두 번째 슬라이스(slice) m![A, Q / 2] 원소 32개 Q = 2, 3 2

각 칩(chip)·클러스터(cluster)·슬라이스(slice)의 기준 위치(base)는 끌어올린 각 축(axis)의 값에 원래 DM 스트라이드(stride)를 곱한 값들을 더해 구합니다. 여기서는 두 번째 슬라이스의 Q / 2 = 1이므로 기준 위치는 원소 1 × (Q % 2) × V = 32개에 해당합니다.

요구 사항(Requirements)

끌어올리기(lift)는 다음 조건을 모두 만족해야 합니다.

  • 선택한 차원(dimension)의 입력 크기와 출력 크기가 같아야 합니다.
  • 브로드캐스트(broadcast)만 변경할 수 있습니다. 검증기(verifier)는 매핑(mapping)을 크기 2짜리 묶음(group)으로 비교합니다. 변경되는 브로드캐스트 2는 크기가 2인 축 구성 요소(axis component)로 바뀌어야 합니다. 브로드캐스트를 패딩(padding)으로 바꾸려면 DM 배치(placement)를 reshape하고 해당 패딩은 읽지 않도록 하세요. 한 번의 lift에서 여러 묶음을 바꿀 수 있지만, 기존 축(axis)이나 크기 3인 브로드캐스트는 바꿀 수 없습니다.
  • 끌어올린 축(lifted axis)은 OutTime에서 제거해야 합니다. OutPacket은 그대로 유지합니다.
  • Lift 메서드(method)는 Chip, Cluster, Slice 순서로 호출해야 하며, 각 차원(dimension)당 최대 한 번만 호출할 수 있습니다.
  • 계산된 모든 기준 위치(base)는 8바이트의 배수여야 합니다.
  • 안전하지 않은 reshape(unsafe reshape)로 브로드캐스트(broadcast)를 도입한다면 데이터가 이미 복제되어 있어야 합니다. reshape는 원소 순서(element order)를 검사할 뿐 복제 여부는 검사하지 않습니다. 이 요구 사항을 어기면 하드웨어와 CPU에서 결과가 달라질 수 있습니다.
rust
axes![A = 128, H = 2, V = 16, Rep = 2, G = 2];

// 유효: DMA가 `[H, V]`를 `Rep`에 걸쳐 복제하고, reshape가 `Rep`를 브로드캐스트(broadcast)로 드러냄.
fn named_broadcast(
    device: &mut Device,
    input: &HbmTensor<bf16, m![1], m![A, H, V]>,
) -> DmTensor<bf16, m![1], m![1 # 2], m![A, H], m![V]> {
    let written: DmTensor<bf16, m![1], m![1 # 2], m![A, Rep], m![H, V]> =
        input.to_dm::<m![1 # 2], m![A, Rep], m![H, V]>(&mut device.tdma);
    let dm: DmTensor<bf16, m![1], m![1 # 2], m![A, 2], m![H, V]> = unsafe { written.reshape() };

    device.main
        .begin(dm.view())
        .fetch::<m![H], m![V]>()
        .fetch_slice_lift::<m![A, H], m![1]>()
        .collect::<m![1], m![V]>()
        .commit_trim::<m![V]>()
        .commit()
}

// lift에 부적합: `G`에 서로 다른 값이 있는데 reshape가 이를 브로드캐스트(broadcast)로 이름 붙임.
fn without_broadcast(
    device: &mut Device,
    input: &HbmTensor<bf16, m![1], m![A, G, H, V]>,
) -> DmTensor<bf16, m![1], m![1 # 2], m![A, H], m![V]> {
    let written: DmTensor<bf16, m![1], m![1 # 2], m![A, G], m![H, V]> =
        input.to_dm::<m![1 # 2], m![A, G], m![H, V]>(&mut device.tdma);
    let dm: DmTensor<bf16, m![1], m![1 # 2], m![A, 2], m![H, V]> = unsafe { written.reshape() };

    device.main
        .begin(dm.view())
        .fetch::<m![H], m![V]>()
        .fetch_slice_lift::<m![A, H], m![1]>()
        .collect::<m![1], m![V]>()
        .commit_trim::<m![V]>()
        .commit()
}

제약(Constraints)

  • 하드웨어 차원(Hardware dimensions): Chip::SIZE, Cluster::SIZE, Slice::SIZE는 하드웨어 구성(hardware configuration)과 일치해야 합니다(공간 차원과 시간 차원(Spatial and Temporal Dimensions) 참고).

여러 번 읽는 패킷(Multi-Read Packet)

패킷(packet)의 축(axis)이 DM에서 연속되지 않을 수 있고 하드웨어가 한 번에 읽을 수 있는 양도 최대 32바이트이므로, 패킷 하나를 준비하는 데 여러 번의 하드웨어 읽기(hardware read)가 필요할 수 있습니다. main 컨텍스트(main-context)에서 read_size는 max_access_size의 약수 중 D[read_size]가 1·2·4·8·16·32바이트가 되는 가장 큰 값입니다. max_access_size는 시퀀서 아키텍처(Sequencer Architecture)를 참고하세요. sub 컨텍스트(sub-context)에서는 read_size가 8바이트로 고정됩니다. 컴파일러(compiler)는 입력 원소 타입(element type)과 읽기 어댑터(Fetch Adapter)의 형변환(cast)을 바탕으로 read_size를 결정하며, 사용자가 직접 설정하지 않습니다. Packet::SIZE > read_size이면 다중 읽기(multi-read)가 발생합니다. 예를 들어 main 컨텍스트의 24바이트 패킷은 read_size = 8이 되어 패킷당 읽기 3회가 필요합니다. 총 사이클(cycle) 수는 Time::SIZE * (Packet::SIZE / read_size)입니다.

다음 예제들은 같은 i4 텐서(tensor), 형상(shape) m![N, C, H, W](N=4, C=3, H=4, W=16)를 서로 다른 네 가지 OutPacket 선택으로 가져옵니다(fetch).

rust
axes![N = 4, C = 3, H = 4, W = 16];

/// 시퀀서 구성(sequencer config): [N = 4 : 192, C = 3 : 64, H = 4 : 16, W = 16 : 1].
/// max_access_size = 16; read_size = 16(8바이트); 패킷(packet)당 읽기 횟수 = 1; 사이클(cycle) 수 = 48
fn fetch_batch_1<'l, const T: Tu>(
    input: BeginTensor<'l, T, i4, m![1], m![1 # 2], m![1 # 256], m![1], m![N, C, H, W]>,
) -> FetchTensor<'l, T, i4, m![1], m![1 # 2], m![1 # 256], m![N, C, H], m![W]> {
    input.fetch()
}

/// 시퀀서 구성(sequencer config): [N = 4 : 192, C = 3 : 64, H / 2 = 2 : 32, H % 2 = 2 : 16, W = 16 : 1].
/// max_access_size = 32; read_size = 32(16바이트); 패킷(packet)당 읽기 횟수 = 1; 사이클(cycle) 수 = 24
fn fetch_batch_2<'l, const T: Tu>(
    input: BeginTensor<'l, T, i4, m![1], m![1 # 2], m![1 # 256], m![1], m![N, C, H, W]>,
) -> FetchTensor<'l, T, i4, m![1], m![1 # 2], m![1 # 256], m![N, C, H / 2], m![H % 2, W]> {
    input.fetch()
}

/// 시퀀서 구성(sequencer config): [N = 4 : 192, C = 3 : 64, H = 4 : 16, W = 16 : 1].
/// max_access_size = 64; read_size = 64(32바이트); 패킷(packet)당 읽기 횟수 = 1; 사이클(cycle) 수 = 12
fn fetch_batch_3<'l, const T: Tu>(
    input: BeginTensor<'l, T, i4, m![1], m![1 # 2], m![1 # 256], m![1], m![N, C, H, W]>,
) -> FetchTensor<'l, T, i4, m![1], m![1 # 2], m![1 # 256], m![N, C], m![H, W]> {
    input.fetch()
}

/// 시퀀서 구성(sequencer config): [N = 4 : 192, C = 3 : 64, H = 4 : 16, W = 16 : 1].
/// max_access_size = 192; read_size = 64(32바이트); 패킷(packet)당 읽기 횟수 = 3; 사이클(cycle) 수 = 12
fn fetch_batch_4<'l, const T: Tu>(
    input: BeginTensor<'l, T, i4, m![1], m![1 # 2], m![1 # 256], m![1], m![N, C, H, W]>,
) -> FetchTensor<'l, T, i4, m![1], m![1 # 2], m![1 # 256], m![N], m![C, H, W]> {
    input.fetch()
}

인터리빙(Interleaving)

인터리빙(interleaving)은 매핑(mapping)이 같은 두 텐서(tensor)를 하나의 시퀀서(sequencer) 연산으로 결합합니다. 같은 계산에 두 텐서가 모두 필요할 때 부가 비용(overhead)을 줄입니다. 명시적인 Time 축(axis)이 두 텐서를 번갈아 읽는 순서를 표현합니다.

다음 예제에서 main 컨텍스트(main-context)는 begin_interleaved()로 인터리빙된 텐서(interleaved tensor)를 만듭니다. 첫 시간 반복(temporal iteration)은 lhs, 두 번째는 rhs, 세 번째는 다시 lhs에서 가져오는(fetch) 식으로 진행됩니다. 한 번의 fetch 연산에는 최대 두 텐서를 인터리빙할 수 있습니다.

rust
axes![A = 16, B = 32, I = 2];

/// 입력 텐서(tensor) 두 개를 하나의 패킷 스트림(packet stream)으로 인터리빙(interleaving).
/// 벡터 엔진(Vector Engine)의 'input1 + input2' 같은 연산(operation)에 유용.
/// 인터리빙된(interleaved) BeginTensor는 Tu.begin_interleaved()로 생성.
/// Time의 `I = 2` 축(axis)은 두 텐서(tensor)를 번갈아 처리하는 순서를 표현.
fn fetch_interleaved<'l>(
    device: &'l mut Device,
    lhs: &'l DmTensor<i8, m![1], m![1 # 2], m![1 # 256], m![A, B]>,
    rhs: &'l DmTensor<i8, m![1], m![1 # 2], m![1 # 256], m![A, B]>,
) -> FetchTensor<'l, { Tu::Main }, i8, m![1], m![1 # 2], m![1 # 256], m![A, I], m![B]> {
    device.main.begin_interleaved::<I, _, _, _, _, _>(lhs.view(), rhs.view()).fetch()
}

최적화(Optimizations)

페치 시퀀서(Fetch Sequencer)의 처리량(throughput)은 세 가지 요인이 결정합니다.

  • 입력 대역폭(Input bandwidth): read_size는 DM에서 축(axis)의 연속성(contiguity)과 패킷 크기(packet size)에 제한됩니다. 이웃하지 않은 축들은 max_access_size를 줄이며, 결과적으로 read_size도 줄입니다(비연속 패킷(Non-Contiguous Packets) 참고). 패킷이 연속 구간(contiguous run)보다 작아도 read_size가 제한됩니다. 더 큰 2의 거듭제곱 크기로 패딩(padding)하면 이를 늘릴 수 있습니다(패킷 패딩(Packet padding) 참고).

    같은 뱅크(bank)에 반복해서 접근하면 우선순위(priority)가 낮은 쓰기 엔진(Commit Engine)과 DMA 엔진(DMA Engine)이 자원을 배정받지 못하는 기아(starvation)가 발생할 수 있습니다. 한계는 연속 접근 64회이며, 이를 넘으면 NoC 타임아웃(timeout)이 발생할 수 있습니다.

    자세한 내용은 메모리 성능(Memory Performance)을 참고하세요.

  • 출력 대역폭(Output bandwidth): 뒤쪽 수집 엔진(Collect Engine)은 Fetch의 패킷(packet)을 32바이트 *플릿(flit)*으로 바꾸므로, 패킷 크기가 32바이트 단위에 맞지 않으면 대역폭이 낭비됩니다. 20바이트 패킷은 플릿 하나에 12바이트의 0 패딩(zero-padding)을 추가하므로 12 / 32 = 37.5%를 낭비합니다. 40바이트 패킷은 플릿 두 개(총 64바이트)에 걸치며 두 번째 플릿의 마지막 24바이트를 0으로 채우므로 24 / 64 = 37.5%를 낭비합니다.

  • 공간 병렬 처리(Spatial parallelism): fetch를 여러 슬라이스(slice)에 분산하면 처리량(throughput)을 최대화할 수 있습니다.

예제: 패킷 패딩(Packet padding)

OutPacket의 원소 수를 더 큰 2의 거듭제곱으로 패딩(padding)하면 read_size가 커질 수 있습니다. 다음 세 예제는 패킷(packet)을 2→16→32바이트로 키워 같은 30바이트 텐서(tensor)를 각각 15·3·1사이클(cycle)에 가져옵니다(fetch).

rust
axes![A = 3, B = 5, C = 2];

/// 가장 작은 패킷(packet): C 차원(dimension)만 8바이트로 패딩(padding). 15사이클(cycle)이 걸림.
fn fetch_packet_C<'l, const T: Tu>(
    input: BeginTensor<'l, T, f8e4m3, m![1], m![1 # 2], m![1 # 256], m![1], m![A, B, C]>,
) -> FetchTensor<'l, T, f8e4m3, m![1], m![1 # 2], m![1 # 256], m![A, B], m![C # 8]> {
    input.fetch()
}

/// 중간 크기 패킷(packet): B와 C 차원(dimension)을 16바이트로 패딩(padding). 3사이클(cycle)이 걸림.
fn fetch_packet_BC<'l, const T: Tu>(
    input: BeginTensor<'l, T, f8e4m3, m![1], m![1 # 2], m![1 # 256], m![1], m![A, B, C]>,
) -> FetchTensor<'l, T, f8e4m3, m![1], m![1 # 2], m![1 # 256], m![A], m![[B, C] # 16]> {
    input.fetch()
}

/// 가장 큰 패킷(packet): 모든 차원(dimension)을 32바이트로 패딩(padding). 1사이클(cycle)이 걸림.
fn fetch_packet_ABC<'l, const T: Tu>(
    input: BeginTensor<'l, T, f8e4m3, m![1], m![1 # 2], m![1 # 256], m![1], m![A, B, C]>,
) -> FetchTensor<'l, T, f8e4m3, m![1], m![1 # 2], m![1 # 256], m![1], m![[A, B, C] # 32]> {
    input.fetch()
}

이 예제에서는 패딩(padding) 때문에 실제 데이터 뒤의 영역까지 읽지만, 패딩 값이 계산에 영향을 주지 않으므로 안전합니다. 패딩 전략(strategy)에 따라 다른 FetchTensor 매핑(mapping)이 생기며, 이는 이후 구성 요소(downstream component)에 영향을 줄 수 있습니다.

동일한 A = 3, B = 5, C = 2의 f8e4m3 텐서(tensor)에 다음 패킷 매핑(packet mapping)을 사용할 수 있습니다.

함수(Function) Fetch의 Time Fetch의 Packet Fetch 작업량(work) Collect의 패딩(padding)
fetch_packet_c A, B C # 8 8바이트 패킷(packet) 15개 패킷(packet)마다 24바이트.
fetch_packet_bc A [B, C] # 16 16바이트 패킷(packet) 3개 패킷(packet)마다 16바이트.
fetch_packet_abc 1 [A, B, C] # 32 32바이트 패킷(packet) 1개 없음.

8바이트·16바이트 후보(candidate)는 Collect가 각 패킷(packet)을 32바이트 플릿(flit)으로 패딩(padding)해야 합니다. 32바이트 후보는 꽉 찬 플릿 하나로 Collect에 도달하지만, 늘어난 물리적 용량(physical capacity) 때문에 DM 사용량이 증가할 수 있습니다. 같은 작업(workload)을 고정한 스케줄(schedule) 비교를 통해, fetch 횟수 감소의 이득이 패딩과 후속 배치(downstream layout)의 비용보다 큰지 판단합니다.
