텐서 이동(Moving Tensors)

읽기 도움말 · 번역자 설명

코드에서 텐서(tensor)의 이름이 같아 보여도, 저장 위치와 데이터를 읽는 순서는 다를 수 있습니다. 먼저 출발지와 목적지를 찾고, 그 사이를 담당하는 엔진(engine)과 수명(lifetime)을 확인하면 예제를 따라가기 쉽습니다.

Furiosa-opt 커널(kernel)은 Furiosa NPU용으로 컴파일되는 Rust 함수입니다. 이 장은 커널이 호스트 메모리(host memory), HBM, DM, SPM, 텐서 유닛(Tensor Unit) 사이에서 텐서 데이터(tensor data)를 전송하는 방법을 설명합니다. 빠른 시작의 커널 설계는 완전한 커널 안에서 이 메모리 계층(tier)들을 소개합니다. 전송 예제를 읽기 전에 이동 경로 표에서 출발지(source)와 목적지(destination)를 선택하세요. 시퀀서(Sequencer)는 공통 루프 모델(loop model)을 설명하며, 각 엔진(engine) 페이지는 구체적인 경계를 다룹니다.

이동 경로 선택하기(Choose a movement route)

이동 경로 표(movement table)는 현재 값(current value)을 목적지(destination)로 옮기는 연산(operation)을 선택하게 해 줍니다. 공개 API로 드러나는 각 경계(public boundary)에서 사용할 연산과 컨텍스트(context)를 제시합니다.

현재 값(Current value) 목적지(Destination) 연산과 컨텍스트(Operation and context)
HostTensor HbmTensor Device::pdma를 사용하는 HostTensor::to_hbm(비동기, async). DMA 엔진(DMA Engine) 참고
HbmTensor HostTensor Device::pdma를 사용하는 HbmTensor::to_host(비동기, async). DMA 엔진(DMA Engine) 참고
HbmTensor DmTensor Device::tdma를 사용하는 HbmTensor::to_dm. DMA 엔진(DMA Engine) 참고
DmTensor HbmTensor Device::tdma를 사용하는 DmTensor::to_hbm. DMA 엔진(DMA Engine) 참고
HbmTensor HbmTensor 호출에 필요한 DMA 컨텍스트(context)를 사용하는 HbmTensor::to_hbm. DMA 엔진(DMA Engine) 참고
DmTensor DmTensor Device::tdma를 사용하는 DmTensor::to_dm, 또는 텐서 유닛(Tensor Unit)을 거치는 fetch/commit 왕복 처리(round trip). DMA 엔진(DMA Engine)과 쓰기 엔진(Commit Engine) 참고
DmTensor SpmTensor Device::tdma를 사용하는 DmTensor::to_spm. DMA 엔진(DMA Engine) 참고
SpmTensor DmTensor Device::tdma를 사용하는 SpmTensor::to_dm. DMA 엔진(DMA Engine) 참고
DmTensorView 텐서 유닛 스트림(Tensor Unit stream) TuContext::begin 후 fetch
텐서 유닛 스트림(Tensor Unit stream) DmTensor commit, 또는 기존의 변경 가능한 뷰(mutable view)에 쓰는 commit_view

복사해서 사용할 수 있는 전체 전송 예제(Copyable end-to-end transfer)

이 페이지는 데이터 이동 경계(movement boundary), 컨텍스트 소유권(context ownership), 수명 규칙(lifetime rule)을 정의합니다. 예제는 HBM 텐서(tensor)의 데이터 타입 폭을 넓히고 순서를 바꾼 뒤 HBM으로 돌려보냅니다. 장치 함수(device function)는 HBM 데이터를 DM에 임시 적재하고, 스트림(stream)을 가져와(fetch) 형변환(cast)·수집(collect)한 뒤 DM에 기록(commit)하고 결과를 HBM으로 전송합니다. 호스트 테스트(host test)는 호스트→HBM과 HBM→호스트 입출력(I/O)만 기다리고(await), 순서가 바뀐 결과를 확인합니다.

전송 예제는 다음 순서로 읽고 수정하세요.

단계(Step) 선언한 선택 사항(Declared choice)
입력(Input) A = 4096, B = 8, 입력 원소 타입(input element type)은 i8, 입력 HBM 매핑(mapping)은 m![1], m![A, B]입니다.
HBM→DM DM의 Cluster는 m![1 # 2], Slice는 m![A / 16], Element는 m![A / 8 % 2, A % 8, B]입니다.
가져오기(Fetch) OutTime은 m![A / 8 % 2], OutPacket은 m![A % 8, B]입니다.
계산과 수집(Compute and Collect) 스트림(stream)은 i8을 i32로 형변환(cast)합니다. 이후 수집(Collect)은 Time에 m![A / 8 % 2, A % 8], Packet에 m![B]를 사용합니다.
Commit→DM→HBM commit_trim::<m![B]>()은 DM 텐서(tensor)를 m![A, B]로 기록합니다. 이어서 to_hbm은 DMA 재배치(relayout)를 거쳐 HbmTensor<i32, m![1], m![B, A]>를 반환합니다.

소스(source)의 정렬 단언(alignment assertion)을 유지하면서 여기 선언된 축(axis), 매핑(mapping), 원소 타입(element type)만 바꾸세요. 호스트 테스트(host test)는 pdma를 통한 to_hbm, to_host를 기다린(await) 뒤 예상한 B-major 결과인지 검사합니다.

rust
#![expect(clippy::type_complexity)]

use furiosa_opt_std::prelude::*;

axes![A = 4096, B = 8];

type Chip = m![1];
type Cluster = m![1 # 2];

#[device(chip = 1)]
pub fn fetch_commit_simple(
    device: &mut Device,
    input: &HbmTensor<i8, m![1], m![A, B]>,
) -> HbmTensor<i32, m![1], m![B, A]> {
    // Element의 가장 안쪽 축(axis)은 원본의 가장 안쪽 축(B, 스트라이드(stride) 1)과 같아야 함. 그래야
    // DMA 꼬리(tail)가 B축 전체(8 × i8 = 8바이트)를 포함하여 min_align = 8을 만족함.
    let input_dm = input.to_dm::<Cluster, m![A / 16], m![A / 8 % 2, A % 8, B]>(&mut device.tdma);

    let fetch_and_commit_tensor: DmTensor<i32, Chip, Cluster, m![A / 16], m![A / 8 % 2, A % 8, B]> = device
        .main
        .begin(input_dm.view())
        .fetch::<m![A / 8 % 2], m![A % 8, B]>()
        .fetch_cast::<i32>()
        .collect::<m![A / 8 % 2, A % 8], m![B]>()
        .commit_trim::<m![B]>()
        .commit();

    fetch_and_commit_tensor.to_hbm(&mut device.tdma)
}
rust
use furiosa_opt_examples::fetch_commit::fetch_commit_simple;
use furiosa_opt_std::prelude::*;

#[tokio::test]
async fn test_fetch_commit_simple_host() -> eyre::Result<()> {
    use furiosa_opt_examples::fetch_commit::{A, B};

    let mut device = Device::new(fetch_commit_simple.topology())?;

    // 형상(shape)이 (A=4096)(B=8)인 입력 텐서(tensor)를 생성.
    let input = HostTensor::<i8, m![A, B]>::from_vec((0..32768).map(|x| x as i8).collect::<Vec<_>>())
        .to_hbm::<m![1], m![A, B]>(&mut device.pdma)
        .await?;

    // 장치 함수(device function)를 호출.
    let output = launch(fetch_commit_simple, (&mut device, &input)).await?;

    let mut expected = vec![0i32; 4096 * 8];
    let mut idx = 0;
    for b in 0..8 {
        for a in 0..4096 {
            expected[idx] = ((a * 8 + b) as i8) as i32;
            idx += 1;
        }
    }

    assert_eq!(
        output.to_host::<m![B, A]>(&mut device.pdma).await?.into_inner(),
        Tensor::<_, m![B, A], CurrentBackend>::from_vec(expected)
    );

    Ok(())
}

포함된 소스(source)는 아래의 실행 순서(ordering)와 수명(lifetime) 규칙을 보여 주는 완전한 예제입니다. 이 장은 해당 전송을 HBM↔DM과 수명을 이해하기 위한 읽기 쉬운 튜토리얼로 다룹니다. 패킷(packet)과 성능의 자세한 비교는 링크된 텐서 유닛 입출력(Tensor Unit I/O) 패턴에서 다룹니다.

타입 수준(type-level)의 Chip, Cluster, Slice, Time, Element 매핑(mapping)은 각 값의 저장(storage) 및 스트림(stream) 동작을 정의합니다. DMA 호출은 타입 매개변수(type parameter)로 지정한 매핑을 가진 목적지(destination)를 생성하며, 원본(source)을 수정하지 않습니다. Fetch와 commit은 텐서 유닛 파이프라인(Tensor Unit pipeline)으로 들어가고 나오는 인계 지점(hand-off point)입니다.

첫 파이프라인(pipeline)에서는 HBM 입력을 DM에 임시 적재하고, begin(...).fetch(...)를 호출하여 계산 단계(compute stage)를 수행한 뒤, 스트림(stream)을 DM에 기록(commit)하고 결과를 HBM으로 전송하세요. 사례 연구: 텐서 유닛 입출력(Tensor Unit I/O)은 구체적인 매핑(mapping)과 소스 코드(source code)로 이 순서를 보여 줍니다.

전송 순서 유지하기(Keep transfers ordered)

Device::new(Topology { chips, pes })는 칩(chip)을 열며 실행 요청(launch)이 사용할 장치를 만듭니다. 이 장치는 독립적인 main, sub 텐서 유닛 컨텍스트(Tensor Unit context)와 tdma, pdma DMA 컨텍스트를 가집니다. 각 연산(operation)에 맞는 변경 가능한 컨텍스트(mutable context)를 전달하세요. Rust의 빌림(borrow)은 텐서 유닛 스트림이 원본 뷰(source view)의 수명을 유지하도록 강제합니다. begin은 DmTensorView를 빌리며, 스트림 수명(stream lifetime)은 그 뷰보다 길 수 없습니다. Fetch는 BeginTensor를 소비(consume)하고 스트림을 만듭니다. fetch_cast, collect 같은 어댑터(adapter)는 이전 단계를 소비하고 다음 단계 값을 반환합니다. Commit은 마지막 스트림을 소비하며, 제공된 DmTensorViewMut에 쓰면서 소비할 수도 있습니다.

호스트 전송(host transfer) to_hbm, to_host는 비동기 입출력(async I/O)이므로 반드시 await로 기다려야 합니다. 커널 측(kernel-side) to_dm, to_hbm, fetch, commit 연산은 선택한 컨텍스트(context)의 큐(queue)에 장치 명령(device command)을 넣습니다. 이들을 감싸는 커널(kernel)이나 백엔드 제출(backend submission)이 완료될 때까지 원본과 목적지 핸들(handle)의 수명을 유지하세요. 목적지 영역(destination region)을 의도적으로 덮어쓸 때만 변경 가능한 뷰(mutable view)를 사용하세요. 데이터를 만드는 전송이나 commit이 끝나기 전에 목적지를 읽지 말고, 순서 관계(ordering edge) 없이 동일한 영역을 참조하는 뷰(aliased view)에 대한 쓰기를 겹치지 마세요.

엔진 경계(Engine boundaries)

  • **Fetch**는 슬라이스(slice)별 시퀀서(sequencer) 하나로 DM을 읽고 텐서 유닛(Tensor Unit)에 패킷 스트림(packet stream)을 내보냅니다. 출력 매핑(output mapping)이 스트림의 Time, Packet 축(axis)을 선택합니다. 선택한 차원(dimension)에 브로드캐스트(broadcast)가 있으면 축 끌어올리기(Axis lifting)로 축을 Time에서 Chip, Cluster, Slice로 옮길 수도 있습니다.
  • **Commit**은 텐서 유닛 스트림(Tensor Unit stream)을 DM에 기록합니다. Element 매핑(mapping)은 목적지 배치(destination layout)를 선택하며, 쓰는 동안 스트림 축(stream axis)을 전치(transpose)할 수 있습니다.
  • **DMA**는 읽기·쓰기 시퀀서(sequencer)를 짝지어 메모리 간 이동(memory-to-memory movement)을 수행합니다. 공개 API가 지원하는 경로는 HBM→HBM, HBM→DM, DM→HBM, DM→DM, DM→SPM, SPM→DM입니다. 간접 gather/scatter API(indirect gather/scatter API)는 인덱스(index)를 받는 호출 이름에 인덱스의 단위를 표시합니다. 두 연산 모두 by_byte_offsets는 HBM에 있는 바이트 오프셋(byte offset)을, by_positions는 SpmTensor<i32>의 위치(position)를 받습니다.

따라서 텐서 유닛 파이프라인(Tensor Unit pipeline)은 다음과 같습니다.

Collect는 수축(Contraction) 또는 벡터(Vector) 계산을 위해 스트림 피연산자(stream operand)를 TRF나 VRF 레지스터 파일(register file)에 저장할 수 있습니다. 이 계산 경계(compute boundary)는 텐서 계산(Computing Tensors)에서 다룹니다.

이동 성능 조정하기(Tune movement)

모든 데이터 이동은 수학적 텐서 이동(mathematical tensor move)입니다. 목적지 매핑(destination mapping)이 바뀌어도 논리적 값(logical value)은 보존됩니다. 컴파일러(compiler)는 양쪽 매핑에서 시퀀서 스트라이드(sequencer stride)를 도출합니다. 성능을 조정하기 전에 엔진 제약(engine constraint)을 지키세요. DM의 Cluster는 1 또는 2, Slice는 64·128·256 중 하나여야 하며, DMA 패킷 꼬리(packet tail)는 API가 검사하는 원소 크기 정렬(element-size alignment)을 만족해야 합니다. Fetch와 commit도 매핑에 따른 시퀀서 규칙을 검증합니다. 유효하지 않은 매핑은 컴파일이나 명령 검증(command verification)에서 실패합니다.

패킷(packet)을 연속 배치하고, 클러스터(cluster)·슬라이스(slice)·DM 뱅크(bank)·HBM 채널(channel)에 트래픽(traffic)을 분산하는 매핑(mapping)을 우선하세요. 작거나 간격이 벌어진 패킷(strided packet)은 시퀀서(sequencer)의 접근 횟수를 늘립니다. DM 뱅크 충돌(bank conflict)이 반복되는 패턴은 DMA가 자원을 배정받지 못하는 기아(starvation)를 일으킬 수 있습니다. 뱅크 기아 규칙, HBM 인터리빙(interleaving), 패킷 크기의 절충 관계(trade-off)는 메모리 성능(Memory Performance)을 참고하세요.

전체 데이터 이동 패턴은 사례 연구: 텐서 유닛 입출력(Tensor Unit I/O)을 참고하세요. 간접 HBM 행 이동(indirect HBM row movement)은 DMA gather와 scatter를 참고하세요.

함께 보기(See also)

릴리스 API(release API)는 furiosa-opt-std rustdoc에 설명되어 있습니다. 연산별 동작 규칙(operation-specific contract)은 위의 엔진(engine) 페이지를, 올바른 이동 계획(movement plan)에 대한 겹침(overlap) 측정이나 위험 상황(hazard) 진단이 필요하면 스케줄링과 튜닝(Scheduling and Tuning)을 참고하세요.
