시퀀서(Sequencer)

시퀀서(sequencer)는 메모리 버퍼(memory buffer)를 패킷 스트림(packet stream)으로 읽고, 패킷 스트림을 다시 메모리에 씁니다. 커널 작성자는 매핑(mapping)과 패킷 크기(packet size)로 이 동작을 제어합니다.

시퀀서(sequencer)의 동작 원리는 Fetch·Commit·DMA가 공통으로 사용하는 루프(loop), 스트라이드(stride), 접근 크기(access size), 수명(lifetime)을 설명합니다. 의사 타입(pseudo-type) 예제는 모델을 소개하고, 접근 크기와 아키텍처(Architecture) 절은 실제 엔진(engine) 동작을 설명합니다. Fetch와 Commit 엔진은 각각 시퀀서 하나로 DM 주소를 지정합니다. DMA 엔진은 읽기 시퀀서와 쓰기 시퀀서를 연결하여 중간 버퍼(intermediate buffer) 없이 DM과 HBM 사이에서 데이터를 옮깁니다.

인터페이스(Interface)

MemTensor, StreamTensor는 학습용 의사 타입(pseudo type)입니다. 버퍼(buffer)와 스트림(stream) 사이의 변환 패턴만 분리해, 모든 엔진 타입(engine type)을 소개하지 않고도 시퀀서(sequencer) 원리를 설명할 수 있게 합니다. 실제 엔진 API는 DmTensor, HbmTensor, TuTensor 등 서로 다른 타입을 사용하지만, 각각의 구체적인 타입 쌍은 아래의 동일한 MemTensor → StreamTensor 형태에 대응합니다.

MemTensor는 어떤 메모리 매핑(memory mapping) Buf에 데이터를 담습니다. 공개 API(public API)에서는 DM·SPM·HBM 텐서(tensor)가 이 역할을 맡습니다.

DMA 엔진(engine)은 읽기 시퀀서(read sequencer)와 쓰기 시퀀서(write sequencer)를 연결하여 중간 버퍼(intermediate buffer) 없이 DM·SPM·HBM 사이에서 데이터를 옮깁니다.

rust
/// 버퍼(buffer)에 저장되는 범용 텐서(generic tensor).
/// 메모리 `Buf`에 데이터를 담고 스트림(stream)으로 읽거나 쓸 수 있는 대상.
#[derive(Debug)]
pub struct MemTensor<D: Scalar, Buf: M> {
    inner: Tensor<D, Buf>,
}

StreamTensor는 이동 중인 텐서(tensor in flight)입니다. 수명(lifetime) 'l은 스트림(stream)을 원본 버퍼(source buffer)에 연결하므로, 스트림이 데이터보다 오래 존재할 수 없습니다. Time은 시간 매핑(temporal mapping), 즉 시간에 따른 반복이며, Packet은 공간 매핑(spatial mapping), 즉 패킷 하나의 내용입니다.

rust
/// 이동 중인 텐서(tensor in flight)를 스트림(stream)으로 보는 뷰(view).
/// `Packet`은 사이클(cycle) 하나의 형상(shape), `Time`은 여러 사이클에 걸친 형상.
#[derive(Debug)]
pub struct StreamTensor<'l, D: Scalar, Time: M, Packet: M> {
    inner: Tensor<D, Pair<Time, Packet>>,
    _marker: PhantomData<&'l ()>,
}

read는 MemTensor를 StreamTensor로 바꾸고, write는 반대로 바꿉니다. 둘 다 값을 보존합니다. 각 엔진(engine)의 전체 API는 여기에 공간 차원(spatial dimension) Chip, Cluster, Slice를 추가하며, 이는 각 엔진 페이지에서 설명합니다.

rust
impl<D: Scalar, Buf: M> MemTensor<D, Buf> {
    /// 주어진 `Time`, `Packet` 매핑(mapping)으로 이 버퍼(buffer)에서 스트림(stream)을 읽음.
    /// `(Time, Packet)`은 `Buf`의 브로드캐스트(broadcast)일 수 있음(Fetch / Switch / DMA-read 동작과 일치).
    pub fn read<'l, Time: M, Packet: M>(&'l self) -> StreamTensor<'l, D, Time, Packet> {
        StreamTensor {
            inner: self.inner.transpose(true),
            _marker: PhantomData,
        }
    }

    /// 스트림(stream)을 이 버퍼(buffer)에 다시 기록.
    /// 브로드캐스트(broadcast)는 허용하지 않음. 각 `Buf` 슬롯(slot)에 대응하는 `(Time, Packet)`의 원본 위치(source position)는 정확히 하나여야 함(Commit 동작과 일치).
    pub fn write<'l, Time: M, Packet: M>(&mut self, stream: StreamTensor<'l, D, Time, Packet>) {
        self.inner = stream.inner.transpose(false);
    }
}

어떤 MemTensor에도 유효한 Time·Packet 조합이 여럿 있을 수 있으며, 각 조합은 다른 StreamTensor를 만듭니다. 유효한 선택지 중에서는 Packet 크기가 클수록 대역폭 활용률(bandwidth utilization)이 좋아집니다. 구체적인 절충 관계(trade-off)는 메모리 성능(Memory Performance)에서 설명합니다.

예제(Examples)

다음 예제들은 위의 핵심 API로 흔히 쓰는 읽기·쓰기 패턴(pattern)을 보여 줍니다. 아래 아키텍처(Architecture)에서는 컴파일러(compiler)가 각 패턴의 하드웨어 구성(hardware configuration)을 도출하는 방법을 설명합니다.

rust
axes![A = 8, B = 512, N = 4, C = 3, H = 8, W = 8, T = 4, P = 4];

/// 스트라이드 접근(strided access): 8×512 텐서(tensor)를 원소 32개짜리 패킷(packet) 128개로 읽음.
/// Time = m![A, B / 32]는 8 * 16 = 128개의 시간 단계(time step)를 생성.
/// Packet = m![B % 32]는 패킷(packet)마다 연속 원소(consecutive element) 32개를 전달.
fn strided_read<'l>(
    buf: &'l MemTensor<bf16, m![A, B]>,
) -> StreamTensor<'l, bf16, m![A, B / 32], m![B % 32]> {
    buf.read()  // 자동 타입 추론(automatic type inference)
}

/// 스트라이드 쓰기(strided write): 원소 32개짜리 패킷(packet) 128개를 8×512 텐서(tensor)에 다시 기록.
fn strided_write(
    buf: &mut MemTensor<bf16, m![A, B]>,
    stream: StreamTensor<bf16, m![A, B / 32], m![B % 32]>,
) {
    buf.write(stream)
}

/// 축 순서를 바꾸는 읽기(axis reordering read): 순회(traversal)를 [N, C, H, W]에서 [W, H, C, N]으로 변경.
/// Time = m![W, H, C, N]은 축(axis)의 역순으로 반복.
/// Packet = m![1]은 원소 하나짜리 패킷(packet)을 전달.
fn axis_reordering_read<'l>(
    buf: &'l MemTensor<bf16, m![N, C, H, W]>,
) -> StreamTensor<'l, bf16, m![W, H, C, N], m![1]> {
    buf.read()
}

/// 축 순서를 바꾸는 쓰기(axis reordering write): [W, H, C, N] 스트림(stream)을 [N, C, H, W] 버퍼(buffer)에 다시 기록.
fn axis_reordering_write(
    buf: &mut MemTensor<bf16, m![N, C, H, W]>,
    stream: StreamTensor<bf16, m![W, H, C, N], m![1]>,
) {
    buf.write(stream)
}

/// 타일링 읽기(tiling read): 캐시 효율(cache efficiency)을 위해 축(axis)을 하위 블록(sub-block)으로 분할.
/// Time = m![A % 2, B % 4, A / 2, B / 4]는 A를 2 × 4, B를 4 × 128 블록(block)으로 타일링(tiling).
/// Packet = m![C # 32]는 C를 패킷(packet)당 원소 32개로 패딩(padding).
fn tiling_read<'l>(
    buf: &'l MemTensor<i8, m![A, B, C # 8]>,
) -> StreamTensor<'l, i8, m![A % 2, B % 4, A / 2, B / 4], m![C # 32]> {
    buf.read()
}

/// 타일링 쓰기(tiling write): 타일로 나뉜 스트림(tiled stream)을 버퍼(buffer)에 다시 기록.
fn tiling_write(
    buf: &mut MemTensor<i8, m![A, B, C # 8]>,
    stream: StreamTensor<i8, m![A % 2, B % 4, A / 2, B / 4], m![C # 32]>,
) {
    buf.write(stream)
}

/// 브로드캐스트 읽기(broadcasting read): `Buf`에 없는 축에 대해 원소를 복제.
/// Time = m![T, A]는 T를 시간 방향으로 브로드캐스트(broadcast, 같은 데이터를 T번 반복).
/// Packet = m![P]는 P를 공간 방향으로 브로드캐스트(broadcast, 같은 원소로 패킷(packet)을 채움).
fn broadcasting_read<'l>(
    buf: &'l MemTensor<i8, m![A]>,
) -> StreamTensor<'l, i8, m![T, A], m![P]> {
    buf.read()
}

/// 브로드캐스트 쓰기(broadcasting write): 브로드캐스트된 스트림(stream)을 버퍼(buffer)에 다시 기록.
/// 각 `Buf` 슬롯(slot)에 대응하는 `(Time, Packet)`의 원본 위치(source position)는 정확히 하나여야 하므로 이 동작은 거부됨.
/// 이 코드는 실행 시 패닉(panic)을 일으킴.
fn broadcasting_write(
    buf: &mut MemTensor<i8, m![A]>,
    stream: StreamTensor<i8, m![T, A], m![P]>,
) {
    buf.write(stream)
}

아키텍처(Architecture)

각 시퀀서(sequencer) 호출은 입력·출력 텐서(tensor)의 매핑(mapping)에서 중첩 루프 구성(nested-loop configuration)으로 컴파일되며, 시퀀서 하드웨어가 이 구성을 실행합니다. 구성 형태는 [size_0 : stride_0, size_1 : stride_1, ...] : packet_size이며, 첨자 0이 가장 바깥 루프(loop)입니다.

rust
struct Config {
    /// 각 항목(entry)은 중첩 루프(nested loop)의 한 단계를 정의.
    entries: Vec<Entry>,
    /// 패킷(packet)당 원소 수.
    packet_size: usize,
}

struct Entry {
    /// 이 루프 단계(loop level)의 반복 횟수.
    size: usize,
    /// 반복(iteration) 후 건너뛸 메모리 주소 간격(memory address distance, 원소 단위).
    stride: isize,
}

각 항목(entry)은 텐서 순회(tensor traversal)의 한 차원(dimension)을 표현합니다. size 필드는 해당 루프(loop)의 반복 횟수를, stride 필드는 연속한 반복 사이의 메모리 오프셋(memory offset)을 정합니다.

접근 크기(Access Size)

max_access_size = gcd(Packet::SIZE, contiguous_run)은 하드웨어 접근(hardware access) 한 번에 처리하는 원소 수입니다.

여기서 contiguous_run은 Config 항목(entry)의 가장 안쪽부터 이어지는 물리적으로 연속된 구간(physically contiguous run)의 원소 수입니다. max_access_size가 클수록 패킷(packet)당 접근 횟수는 줄어듭니다. 다음은 Config에서 max_access_size를 계산하는 방법입니다.

rust
impl Config {
    fn contiguous_run(&self) -> usize {
        // 가장 안쪽부터 바깥쪽으로 항목 쌍(pair)을 확인하고, 처음 비연속(non-contiguous) 쌍을 만나면 중단.
        // 이웃한 두 항목(entry) (n_outer : s_outer), (n_inner : s_inner)는
        // s_outer == n_inner * s_inner일 때 연속(contiguous)임.
        let mut contiguous_run = self.entries.last().map_or(1, |e| e.size);
        for w in self.entries.windows(2).rev() {
            if w[0].stride == w[1].size as isize * w[1].stride {
                contiguous_run *= w[0].size;
            } else {
                break;
            }
        }
        contiguous_run
    }

    fn max_access_size(&self) -> usize {
        gcd(self.packet_size, self.contiguous_run())
    }
}

대부분의 경우 패킷 배치(packet layout)는 DM에서 완전히 연속(contiguous)이므로 max_access_size == Packet::SIZE입니다. max_access_size < Packet::SIZE인 경우는 비연속 패킷(Non-Contiguous Packets)을 참고하세요.

동작 원리(How It Works)

m![N, C, H, W] → m![W, H, C, N]의 Config에는 스트림(stream)의 각 축(axis)마다 항목(entry) 하나가 들어갑니다. 각 스트라이드(stride)는 원본 버퍼(source buffer)에서 그 축의 한 단계에 해당하는 간격입니다. Packet = m![1]이므로 Packet::SIZE = max_access_size = 1이며, 시퀀서(sequencer)는 루프(loop)를 한 번 반복할 때마다 DM 접근을 한 번 수행합니다.

rust
axes![N = 4, C = 3, H = 8, W = 8];

fn read_nchw_whcn(buf: &MemTensor<bf16, m![N, C, H, W]>) ->
                     StreamTensor<bf16, m![W, H, C, N], m![1]> {
    // 컴파일러(compiler)가 생성한 구성(configuration): [8 : 1, 8 : 8, 3 : 64, 4 : 192] : 1
    let config = Config {
        entries: vec![
            Entry { size: 8, stride: 1 },   // W
            Entry { size: 8, stride: 8 },   // H
            Entry { size: 3, stride: 64 },  // C
            Entry { size: 4, stride: 192 }, // N
        ],
        packet_size: 1,
    };

    // 하드웨어는 구성을 중첩 루프(nested loop)로 실행:
    for w in 0..8 {
        for h in 0..8 {
            for c in 0..3 {
                for n in 0..4 {
                    // 각 주소(address)를 읽음
                    let addr = 1 * w + 8 * h + 64 * c + 192 * n;
                    // yield buf[addr];
                }
            }
        }
    }

    buf.read()
}

fn write_whcn_nchw(buf: &mut MemTensor<bf16, m![N, C, H, W]>,
                  stream: StreamTensor<bf16, m![W, H, C, N], m![1]>) {
    // 컴파일러(compiler)는 쓰기에도 같은 구성(config)을 생성
    // 하드웨어는 구성을 중첩 루프(nested loop)로 실행:
    for w in 0..8 {
        for h in 0..8 {
            for c in 0..3 {
                for n in 0..4 {
                    // 각 주소(address)에 기록
                    let addr = 1 * w + 8 * h + 64 * c + 192 * n;
                    // buf[addr] = stream.next();
                }
            }
        }
    }
}

구성(Configurations)

다음 패턴(pattern)들은 커널(kernel) 작성자가 만나게 될 대부분의 구성(configuration)을 다룹니다.

축 전치(Transposing Axes)

축(axis)을 전치(transpose)하면 스트림(stream)이 버퍼(buffer)와 다른 순서로 축을 순회할 수 있습니다. 컴파일러(compiler)는 그 순서대로 메모리를 순회하는 데 필요한 스트라이드(stride)를 계산합니다.

rust
axes![A = 8, B = 8, C = 8];

fn read_rearranging<'l>(
    buf: &'l MemTensor<i8, m![A, B, C # 32]>,  // Buf
) -> StreamTensor<'l, i8, m![B, A], m![C # 16]> {  // Time, Packet
    buf.read()
}

컴파일러(compiler)는 합쳐진 매핑(mapping) m![B, A, C # 16]을 항(term)별로 처리하면서 구성 항목(configuration entry)을 만들고, 그 과정에서 Buf를 변환합니다. 각 항목의 크기는 해당 항의 크기이고, 스트라이드(stride)는 현재 Buf에서 그 항의 한 단계가 차지하는 범위(volume)입니다. 항 하나를 처리하면 그 축(axis)을 소비했다는 사실을 반영하여 Buf를 갱신합니다.

항(Term) 항목(Entry) 스트라이드의 근거(Stride Source) 처리 후 Buf
B 8 : 32 m![C # 32]::SIZE m![A, 1 # 8, C # 32]
A 8 : 256 m![1 # 8, C # 32]::SIZE m![1 # 64, C # 32]
C # 16 16 : 1 연속(contiguous, Packet 차원) 1 # 2048

Packet::SIZE = max_access_size = 16입니다. 가장 안쪽 항목(entry) 16 : 1은 연속(contiguous)이므로 하드웨어는 접근 한 번으로 패킷(packet) 전체를 전송합니다.

축 분할(Splitting Axes)

타일링(tiling)은 캐시 효율(cache efficiency)을 높이거나 텐서 유닛(Tensor Unit)의 버퍼 크기에 맞추기 위해 논리 축(logical axis)을 하위 블록(sub-block)으로 나눕니다. 컴파일러(compiler)는 축을 여러 항목(entry)으로 나누어 이를 구현합니다.

rust
axes![A = 8, B = 8, C = 4];

fn read_splitting<'l>(
    buf: &'l MemTensor<i8, m![A, B, C # 8]>,  // Buf
) -> StreamTensor<'l, i8, m![A % 2, B % 4, A / 2, B / 4], m![C # 32]> {  // Time, Packet
    buf.read()
}

A % 2, A / 2 같은 표현식(expression)은 A축(axis)을 별도의 항목(entry)으로 나눕니다. 컴파일러(compiler)는 m![A % 2, B % 4, A / 2, B / 4, C # 32]를 항(term)별로 처리합니다.

항(Term) 항목(Entry) 스트라이드의 근거(Stride Source) 처리 후 Buf
A % 2 2 : 64 m![B, C # 8]::SIZE m![A / 2, 1 # 2, B, C # 8]
B % 4 4 : 8 m![C # 8]::SIZE m![A / 2, 1 # 2, B / 4, 1 # 4, C # 8]
A / 2 4 : 128 m![1 # 2, B / 4, 1 # 4, C # 8]::SIZE m![1 # 8, B / 4, 1 # 4, C # 8]
B / 4 2 : 32 m![1 # 4, C # 8]::SIZE m![1 # 64, C # 8]
C # 32 32 : 1 연속(contiguous, Packet 차원) 1 # 512

Packet::SIZE = max_access_size = 32.

축의 일부 선택(Slicing Axes)

슬라이싱(slicing)은 메모리 배치(memory layout)에서 인덱스(index)의 일부 범위만 읽습니다. 인덱스를 지정한 뷰(indexed view)가 원본 텐서(tensor)의 부분집합을 선택할 때 이런 조건이 생깁니다.

rust
axes![A = 16, B = 8, C = 8];

fn read_slicing<'l>(
    buf: &'l MemTensor<i8, m![A, B, C]>,  // Buf
) -> StreamTensor<'l, i8, m![A / 4, A % 4 = 3, B / 4, B % 4 = 2], m![C]> {  // Time, Packet
    buf.read()
}

= 3 표기는 A % 4의 반복 횟수를 4회 대신 3회로 제한하여 하드웨어가 텐서(tensor)의 일부 영역(sub-region)만 다루게 합니다. 컴파일러(compiler)는 m![A / 4, A % 4 = 3, B / 4, B % 4 = 2, C]를 항(term)별로 처리합니다.

항(Term) 항목(Entry) 스트라이드의 근거(Stride Source) 처리 후 Buf
A / 4 4 : 256 m![A % 4, B, C]::SIZE m![1 # 4, A % 4, B, C]
A % 4 = 3 3 : 64 m![B, C]::SIZE(범위를 3으로 제한) m![1 # 16, B, C]
B / 4 2 : 32 m![B % 4, C]::SIZE m![1 # 32, B % 4, C]
B % 4 = 2 2 : 8 m![C]::SIZE(범위를 2로 제한) m![1 # 128, C]
C 8 : 1 연속(contiguous, Packet 차원) 1 # 1024

Packet::SIZE = max_access_size = 8.

축 브로드캐스트(Broadcasting Axes)

브로드캐스트(broadcasting)는 스트림(stream)이 Buf에 없는 축(axis)을 순회할 때 하나의 원소를 여러 패킷(packet)이나 시간 단계(time step)에 걸쳐 반복합니다. 축 전체나 N / 512 같은 축의 일부가 Time 또는 Packet에는 있지만 Buf에는 없을 수 있습니다. 그러면 시퀀서(sequencer)는 브로드캐스트 항목(entry) : 0을 만들어 같은 주소(address)에 다시 접근합니다.

rust
axes![A = 16, T = 4, P = 4];

fn read_broadcasting<'l>(
    buf: &'l MemTensor<i8, m![A]>,  // Buf
) -> StreamTensor<'l, i8, m![T, A], m![P]> {  // Time, Packet
    buf.read()
}

컴파일러(compiler)는 m![T, A, P]를 항(term)별로 처리합니다.

항(Term) 항목(Entry) 스트라이드의 근거(Stride Source) 처리 후 Buf
T 4 : 0 Buf에 없음(브로드캐스트, broadcast) m![A]
A 16 : 1 m![A] 안의 A 1 # 16
P 4 : 0 Buf에 없음(브로드캐스트, broadcast) 1 # 16

Packet::SIZE = max_access_size = 4입니다. P가 브로드캐스트(broadcast)되므로 패킷(packet) 전체에 같은 원소가 복제됩니다(공간 브로드캐스트, spatial broadcast). T가 브로드캐스트되므로 여러 시간 단계(time step)에 같은 데이터가 반복됩니다(시간 브로드캐스트, temporal broadcast).

Time이나 Packet이 Buf에 없는 축(axis)의 일부를 참조하는 경우에도 같은 규칙이 적용됩니다. 예를 들어 m![N % 512] 버퍼(buffer)를 StreamTensor<m![N / 512], m![N % 512]>로 읽으면 N / 512 시간 항목(time entry)에서 브로드캐스트(broadcast)가 일어납니다. 버퍼의 원소 512개가 바깥쪽 N / 512 반복마다 재사용됩니다.

항목 병합(Merging Entries)

하드웨어는 구성(configuration) 하나당 최대 항목(entry) 8개를 지원합니다. 변환 결과가 이보다 많으면 컴파일러(compiler)는 이웃한 항목들을 병합(merge)하여 한계에 맞춥니다. 이웃한 (n1 : s1), (n2 : s2)가 s1 == n2 * s2를 만족해 물리적으로 연속(physically contiguous)이면 (n1 * n2 : s2)로 병합됩니다.

rust
axes![N = 8, C = 8, H = 8, W = 32];

fn read_merging<'l>(
    buf: &'l MemTensor<i8, m![N, C, H, W]>,  // Buf
) -> StreamTensor<'l, i8, m![W / 16, H % 2, H / 2, C / 2, C % 2, N / 2, N % 2, W / 8 % 2], m![W % 8]> {  // Time, Packet
    buf.read()
}

컴파일러(compiler)는 m![W / 16, H % 2, H / 2, C / 2, C % 2, N / 2, N % 2, W / 8 % 2, W % 8]를 항(term)별로 처리하여 처음에 항목(entry) 9개를 만듭니다.

항(Term) 항목(Entry) 스트라이드의 근거(Stride Source)
W / 16 2 : 16 m![W % 16]::SIZE
H % 2 2 : 32 m![W]::SIZE
H / 2 4 : 64 m![H % 2, W]::SIZE
C / 2 4 : 512 m![C % 2, H, W]::SIZE
C % 2 2 : 256 m![H, W]::SIZE
N / 2 4 : 4096 m![N % 2, C, H, W]::SIZE
N % 2 2 : 2048 m![C, H, W]::SIZE
W / 8 % 2 2 : 8 m![W % 8]::SIZE
W % 8 8 : 1 연속(contiguous, 패킷 차원(packet dimension))

항목(entry) 9개는 하드웨어 한계인 8개를 넘으므로 컴파일러(compiler)는 s1 == n2 * s2인 연속 항목 쌍(contiguous pair)을 병합합니다. H % 2 -> (2 : 32)와 H / 2 -> (4 : 64)는 물리적으로 연속이 아니므로 병합되지 않습니다(s_1 \neq n_2 \times s_2 \iff 32 \neq 4 \times 64). 최종 구성(configuration)은 항목 6개를 가집니다. 마지막 병합은 시간/패킷 경계(time/packet boundary)를 가로지릅니다. W/8%2 (2:8)과 W%8 (8:1)이 W%16 (16:1)로 병합됩니다.

항(Term) 항목(Entry) 병합된 항목(Merged Entries)
W / 16 2 : 16
H % 2 2 : 32
H / 2 4 : 64
C 8 : 256 C / 2 (4 : 512),
C % 2 (2 : 256)
N 8 : 2048 N / 2 (4 : 4096),
N % 2 (2 : 2048)
W % 16 16 : 1 W / 8 % 2 (2 : 8),
W % 8 (8 : 1)

Packet::SIZE = max_access_size = 8.

비연속 패킷(Non-Contiguous Packets)

패킷(packet)이 차지하는 범위 안에서 DM 배치(layout)의 스트라이드(stride)가 불연속이면 max_access_size < Packet::SIZE입니다. 이때 하드웨어는 패킷당 한 번이 아니라 연속된 하위 블록(contiguous sub-block)마다 한 번씩 접근합니다. 다음 예제는 원소 32개짜리 패킷 m![A, B]를 DM에서 각 B행(row)을 16칸(slot)으로 패딩(padding)한 버퍼(buffer)에 씁니다. A의 스트라이드가 8이 아닌 16이므로 패킷 범위가 연속되지 않아 하드웨어는 접근을 1회 대신 4회 수행합니다.

rust
axes![A = 4, B = 8];

fn write_padded(
    buf: &mut MemTensor<i8, m![A, B # 16]>,
    stream: StreamTensor<i8, m![1], m![A, B]>,
) {
    // 컴파일러(compiler)가 생성한 구성(configuration): [
    //   A -> 4 : 16,   (16 != 8 * 1, 비연속(non-contiguous) — 각 B행 뒤에 패딩 간격(padding gap))
    //   B -> 8 : 1,    (연속된 패킷 하위 블록(contiguous packet sub-block))
    // ] : 32
    buf.write(stream)
}

Packet::SIZE = 32, contiguous_run = 8, max_access_size = 8.

Packet에 원본 배치(source layout)에서 이웃하지 않은 축(axis)이 들어가도 비연속 스트라이드(non-contiguous stride)가 생깁니다. 다음 예제는 같은 m![N, C, H, W] 버퍼(buffer)를 서로 다른 Packet 선택으로 읽습니다. 가장 안쪽 축 W만 Packet에 넣으면 max_access_size = Packet::SIZE = 8이 되어 패킷당 한 번 접근합니다. m![N, H, W]를 Packet에 넣으면 C를 건너뛰므로 원본에서 N의 스트라이드(96)가 H×W(32)와 같지 않습니다. 따라서 contiguous_run = 32, max_access_size = 32이고 하드웨어는 패킷당 접근을 1회 대신 4회 수행합니다.

rust
axes![N = 4, C = 3, H = 4, W = 8];

// 컴파일러(compiler)가 생성한 구성(configuration): [
//   N -> 4 : 96,   (96 == 3 × 32, 연속(contiguous))
//   C -> 3 : 32,   (32 == 4 × 8,  연속(contiguous))
//   H -> 4 : 8,    (8  == 8 × 1,  연속(contiguous))
//   W -> 8 : 1,    (패킷 차원(packet dimension))
// ] : 8
// contiguous_run = 8 (W); ×4 (H): 8==8×1 ✓; ×3 (C): 32==4×8 ✓; ×4 (N): 96==3×32 ✓; 모든 축(axis)이 연속(contiguous)
// max_access_size = gcd(packet_size, contiguous_run) = packet_size = 8
fn read_contiguous<'l>(
    buf: &'l MemTensor<i8, m![N, C, H, W]>,
) -> StreamTensor<'l, i8, m![N, C, H], m![W]> {
    buf.read()
}

// 컴파일러(compiler)가 생성한 구성(configuration): [
//   C -> 3 : 32,   (시간 차원(time dimension))
//   N -> 4 : 96,   (96 != 4 × 8 = 32, 비연속(non-contiguous) — C축이 사이에 끼어 있음)
//   H -> 4 : 8,    (8  == 8 × 1, 연속(contiguous))
//   W -> 8 : 1,    (패킷 차원(packet dimension))
// ] : 128
// contiguous_run = 8 (W); ×4 (H): 8==8×1 ✓ → 32; ×4 (N): 96!=4×8 ✗ 중단 → 32
// max_access_size = gcd(128, 32) = 32; 하드웨어는 패킷(packet)당 128/32 = 4회 접근
fn read_non_contiguous<'l>(
    buf: &'l MemTensor<i8, m![N, C, H, W]>,
) -> StreamTensor<'l, i8, m![C], m![N, H, W]> {
    buf.read()
}

제약(Constraints)

RNGD에서는 다음 하드웨어 한계(hardware limit) 중 하나라도 넘으면 컴파일 오류(compilation error)가 발생합니다.

  • 항목 수 한계(Entry limit): 최대 항목(entry) 8개이므로, 컴파일러(compiler)는 가능한 경우 이웃한 항목들을 병합합니다(구성 절의 항목 병합(Merging Entries) 참고).
  • 반복 횟수 한계(Iteration limit): 항목(entry)당 size <= 65,536.
  • 패킷 크기(Packet size): 1·2·4·8·16·32바이트 중 하나여야 합니다.
  • 패킷 가져오기(Packet fetch): 가장 안쪽 항목(entry) n : s는 다음 중 하나를 만족해야 합니다.
    • 연속 접근(contiguous access, 이웃 원소): (s == 0 || s == 1) && n % packet_size == 0
    • 불연속 접근(discrete access, 단일 원소 패킷): packet_size == 1

병합(merging)이 실패하거나 한계를 넘으면 텐서 매핑(tensor mapping)을 다시 설계하거나 연산(operation)을 여러 시퀀서(sequencer) 호출로 나누세요.

호환되는 축 분해(Compatible Axis Decompositions)

Buf와 스트림(stream) 양쪽에 이름이 나오는 각 축(axis)은 같은 분해(decomposition)를 사용해야 합니다. 컴파일러(compiler)는 스트림을 항(term)별로 순회하며 Buf에서 축을 소비합니다(아키텍처(Architecture) 참고). Buf와 스트림이 한 축을 서로 다른 방식으로 나누고, 두 분할을 함께 표현할 더 세밀한 공통 분할(common refinement)도 없다면 어떤 순회 순서(traversal order)도 성립하지 않습니다. 양쪽의 총 원소 수가 같아도 이 구성(configuration)은 거부됩니다.

rust
axes![A = 15];

fn read_incompatible<'l>(
    buf: &'l MemTensor<i8, m![A % 5, A / 5]>,  // Buf
) -> StreamTensor<'l, i8, m![1], m![A % 3, A / 3]> {  // Time, Packet
    buf.read() // 컴파일 오류(compilation error): 호환되지 않는 분해(incompatible decomposition)
}

Buf는 A를 5 × 3으로, 스트림(stream)은 3 × 5로 분해합니다. gcd(5, 3) = 1이므로 어느 쪽도 다른 쪽을 더 세분한 분해(refinement)가 아닙니다. 컴파일러(compiler)는 이미 5블록 분할을 정한 Buf에서 A % 3을 소비할 수 없습니다.
