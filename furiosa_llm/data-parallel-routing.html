Data-Parallel 라우팅#

언제 data_parallel_size 1보다 큰 Furiosa-LLM는 동일한 모델의 여러 data-parallel (DP) 복제를 실행합니다. DP 라우터는 복제가 각 새로운 요청을받습니다.

Furiosa-LLM는 기본적으로 scoring-based DP 여정을 사용합니다. 이미 큰 token 워크로드를 가지고있는 복제를 피하면서 유용한 prefix-cache 상태 근처에 요청을 유지하도록 설계되었습니다.

점수를 얻는 방법#

각 살아있는 DP 복제를 위해, 대패는 2개의 신호를 보상합니다:

  • 전두환 지역: prompt 길이의 분수로 복제의 접두사 캐시가 얼마나 새로운 prompt의 일치합니다.

  • 로드 압력: 해당 복제에 이미 활성 컨텍스트 토큰의 수입니다. Prompt 토큰은 요청이 처리될 때 청구되며, 생성된 토큰은 요청이 완료될 때까지 청구됩니다.

라우터는 더 높은 부하 점수로 낮은 부하 압력을 정상화, prefix-locality 점수와 결합, 가장 높은 최종 점수와 복제에 대한 요청을 보냅니다. 정확한 동점은 첫 라이브 DP 복제를 유지합니다.

final_score = prefix_weight * prefix_score + load_weight * load_score

prefix-locality 신호는 각 DP 복제의 KV-cache 사건을 추적하는 경량 가상 접두사 캐시에 근거를 둡니다. 그것은 복제 사이 KV cache를 이동하지 않습니다. 접두사 캐시가 DP-local이기 때문에 나중에 요청이 캐시를 얻을 수 있는 경우에 따라 복제 요청을 라우팅하십시오.

라우팅 정책#

Use --data-parallel-routing-policy 경로 정책을 선택합니다:

정책

행동

scoring

과태. 균형 접두사 지방성 및 token-load 압력.

round-robin

순서에 있는 DP 복제에 요청을 보냅니다. 이것은 간단한 벤치마킹을 위해 유용할 수 있습니다 또는 cache-aware 여정이 원하지 않을 때.

점수 프로필#

사용 시 scoring, 사용 --data-parallel-scoring-profile prefix-locality/load 거래 끄기를 조정하려면:

프로파일

Prefix/load 무게

사용할 때

balanced

0.55 / 0.45

기본값. workload 특성이 혼합 또는 알 수없는 경우 대부분의 서빙 작업 부하에 사용.

locality

0.90 / 0.10

반복된 시스템 프롬프트, multi-turn 대화, 또는 RAG-style 문서 접두사로 워크로드를 위해 이것을 준비하십시오.

load

0.10 / 0.90

이 경우 신속하게 드물게 prefixes를 공유, 또는 균형 잡힌 부하가 캐시 지방보다 더 많은 문제. 극단적으로 긴 공유 시스템 프롬프트 또는 문서 접두사는 현지화 될 때 하나의 DP 복제를 오버로드 할 수 있습니다.

prefix caching가 비활성화되면 Furiosa-LLM가 다시 돌아갑니다. load prefix locality가 더 이상 유용한 신호를 제공하지 않기 때문에 단면도. 오래된 prefix-aware 프로파일 이름이 제거되었습니다; 다음을 사용하세요 locality 그 대신

구성#

기본 동작은 scoring-based 라우팅입니다. balanced 프로필:

furiosa-llm serve <model> --data-parallel-size 2

prefix-cache 재사용을 위해 routing:

furiosa-llm serve <model> \
  --data-parallel-size 2 \
  --data-parallel-routing-policy scoring \
  --data-parallel-scoring-profile locality

round-robin 라우팅 사용:

furiosa-llm serve <model> \
  --data-parallel-size 2 \
  --data-parallel-routing-policy round-robin

점수 프로파일은 다음과 같은 영향을 미칩니다. scoring. non-default scoring 단면도를 가진 놓지 마십시오 --data-parallel-routing-policy round-robin.

Python API#

동일한 설정은 통과 할 수 있습니다. SchedulerConfig:

from furiosa_llm import LLM
from furiosa_llm.metadata.config_types import (
    DataParallelRoutingPolicy,
    DataParallelScoringProfile,
    SchedulerConfig,
)

scheduler_config = SchedulerConfig(
    data_parallel_routing_policy=DataParallelRoutingPolicy.SCORING,
    data_parallel_scoring_profile=DataParallelScoringProfile.LOCALITY,
)

with LLM(
    "furiosa-ai/Qwen3-4B-FP8",
    data_parallel_size=2,
    scheduler_config=scheduler_config,
) as llm:
    outputs = llm.generate(["Hello"])

운용기록#

  • DP 라우팅은 하나의 Furiosa-LLM 프로세스 안에 발생합니다. 여러 model-server pods를 통해 라우팅을 위해 llm-d.

  • Scoring-based 라우팅은 prefix caching 활성화를 위해 최선을 다하고 있습니다. 참조 Prefix Caching NPU 기반 캐싱 및 계층적 Prefix Caching (선택 사항) 호스트 캐시 계층에 대해.

  • DP 자체에 대한 배경 정보는 다음을 참조하십시오. 모형 평행성.
