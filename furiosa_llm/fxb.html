C Furiosa 실행 파일 묶음 (FXB)#

Furiosa-LLM는 Furiosa NPU의 자산을 실행하는 Hugging Face 형식과 컴파일된 프로그램에 있는 모델 자산입니다. 모델 자산은 구성, 토큰화기 및 무게를 제공하지만, Furiosa 실행 파일 묶음 (FXB) 컴파일된 커널을 제공합니다. 실행 가능한 배포는 두 부분 모두 필요로 합니다.

Furiosa-LLM는 NPU에서 실행되는 코드가 모델 아키텍처 및 실행 구성에 대해 미리 컴파일되었기 때문에 FXB가 필요합니다. 그 결과 .fxb 파일은 컴파일된 binaries 및 metadata가로드하고 실행해야 하는 단일 아카이브입니다.

모델 자산에서 별도의 컴파일 된 프로그램을 유지하면 몇 가지 이점이 있습니다.

  • 모델은 서빙 호스트에 커널을 컴파일하지 않고 시작할 수 있습니다.

  • FXB는 모델로 복사, 캐시 또는 게시 할 수 있습니다.

  • 호환 모델은 동일한 FXB를 재사용 할 수 있습니다.

FXB는 모델 무게를 포함하지 않으며 Hugging Face 모델 디렉토리를 대체하지 않습니다. Furiosa-LLM는 여전히 구성, 토큰화기 및 그 디렉토리 또는 저장소에서 무게를 읽습니다.

이 페이지는 FXB를 구축하여 모델 자산을 공급하고 호환 모델로 재사용하는 모델 라이프사이클을 따릅니다. 자세한 명령 행동, 번들 메타데이터 및 호환성 규칙은 나중에 섹션에 설명되어 있습니다.

Tip

FuriosaAI는 대중적인 모형을 위한 pre-compiled FXB 뭉치의 세트를 발행합니다 Hugging Face 허브 - FuriosaAI 조직. 이 중 하나를 다운로드하고 아래의 작업 흐름과 호환 모델에 대해 제공합니다.

설치#

FXB은 .fxb 번들 형식과 건물, 배포 및 로딩 번들을위한 프레임 워크. Furiosa-LLM는이 수명주기를 통해 노출 fxb CLI

The fxb CLI는 Furiosa-LLM 패키지로 배송하므로 설치하기에는 추가가 없습니다. Furiosa-LLM를 설치하지 않은 경우 다음을 따르십시오. Furiosa-LLM 설치:

pip install --upgrade pip setuptools wheel uv
uv pip install --upgrade --torch-backend=auto furiosa-llm

CLI가 사용 가능한지 확인하십시오:

fxb --help

The fxb CLI는 전체적인 FXB 수명주기를 포함합니다: 건물, 다운로드, 캐싱, 겸용성 검사 및 검사. 시렁과 검사 subcommands는 동일한 국부적으로 시렁을 이용합니다 furiosa-llm serve 참조

FXB를 특정 모델에 맞게 구성하는 방법#

전제 조건#

FXB를 구축하려면 AArch64 GNU C cross-compiler 및 대상 C 라이브러리 헤더가 필요합니다. Debian 또는 Ubuntu에서 필요한 패키지를 설치하십시오.

sudo apt-get update
sudo apt-get install --no-install-recommends gcc-aarch64-linux-gnu libc6-dev-arm64-cross

참고

건물 FXB는 현재 RHEL 또는 기타 RPM-based 배포판에서 지원되지 않습니다. EPEL cross-compiler는 AArch64 glibc 사용자 공간 sysroot를 제공하지 않습니다. furiosa-tcc.

Use fxb build 모델을 컴파일하여 .fxb 묶음:

fxb build Qwen/Qwen3-8B-FP8 qwen3-8b-fp8

첫 번째 인수는 Hugging Face 모델 ID 또는 로컬 경로 ( 경로가 시작해야 함) . or /). 두번째는 산출 경로입니다; .fxb 확장은 자동으로 none를 가지고 있을 때, 위의 명령을 쓰기 qwen3-8b-fp8.fxb.

해결 된 구성 및 버킷 계획을 사용하여 컴파일하지 않고 미리보기 --dry-run:

fxb build Qwen/Qwen3-8B-FP8 qwen3-8b-fp8 --dry-run

일반적인 옵션:

  • -tp/--tensor-parallel-size - tensor-parallel 그룹 당 PEs의 수 (과태: 모형 미리 설치).

  • -pp/--pipeline-parallel-size — pipeline-parallel 크기 (기본값: 1).

  • --max-model-len — 모델의 최대 컨텍스트 길이를 버킷 선택에 덮어줍니다. 이 모양은 묶어 묶어 버리는 것을 의미합니다. furiosa-llm serve 봉사 시간에만 입장할 수 있는 동일한 이름의 선택권을 가지고 갑니다 (see 컨텍스트 길이 제한).

  • -O/--optim-level — bucket-filtering 최적화 수준: O0 (최소) O1 (반) O2 (제4분기) O3 (전체, 기본).

  • --convert - 주변 건축물과 모델에 대한 작업 override: embed 다시 쓰기 *ForCausalLM → *Model; score/classify → *ForSequenceClassification (전기: auto, i.e. 아키텍처를 유지 config.json).

건물 후에, 캐시에 있는 뭉치를 이렇게 등록하십시오 fxb check and furiosa-llm serve 찾을 수 있습니다:

fxb add ./qwen3-8b-fp8.fxb

생산 빌드 권고를 위해, 참조 가장 좋은 방법.

Furiosa-LLM를 사용하여 실행 가능한 모델#

Furiosa-LLM는 모델 자산과 FXB를 함께로드합니다. 모델 자산은 Hugging Face 허브 디렉토리 형식을 따라야하며 같은 파일을 포함합니다. config.json, Tokenizer 파일 및 모델 무게. 모델은 다음 양식 중 하나에서 배포 또는 호출 할 수 있습니다.

FXB를 포함하는 모델 디렉토리#

호환 가능한 .fxb Hugging Face 모델 디렉토리에 모델 구성, Tokenizer 및 무게와 함께 파일:

my-model/
  config.json
  tokenizer.json
  model-00001-of-00002.safetensors
  model-00002-of-00002.safetensors
  model.safetensors.index.json
  my-model.fxb

디렉토리는 로컬로 저장하거나 Hugging Face 허브에 저장소로 게시 할 수 있습니다. Furiosa-LLM는 번들 FXB를 자동으로 검색합니다.

furiosa-llm serve ./my-model

furiosa-llm serve furiosa-ai/Qwen3-8B-FP8

이 양식은 self-contained 모델 저장소를 배포하는 것이 편리합니다.

직접 FXB를 지정#

모델 자산과 FXB를 별도의 위치에 유지하고 번들을 선택하십시오. --fxb:

furiosa-llm serve Qwen/Qwen3-8B-FP8 --fxb ./qwen3-8b-fp8.fxb

첫 번째 인수는 여전히 Hugging Face 모델 저장소 또는 로컬 디렉토리를 식별합니다. Furiosa-LLM는 구성, Tokenizer 및 무게를로드합니다. --fxb 컴파일된 번들만 선택합니다. 이 형태는 새로 만들어진 FXB를 테스트하는 데 유용합니다. 특정 번들을 피하거나 여러 호환 모델과 함께 FXB를 재사용합니다.

Python API는 동일한 별거를 제공합니다:

from furiosa_llm import LLM

llm = LLM("Qwen/Qwen3-8B-FP8", fxb="./qwen3-8b-fp8.fxb")

로컬 FXB 캐시를 통해 자동 발견을 위해, 참조 호환 캐시 FXB와 모델 제공.

FXB 호환성#

FXB 호환성은 결정됩니다 아키텍처 지문. 지문은 모형 건축술과 포함합니다 config.json 커널 생성에 영향을 미치는 필드는 숨겨진 크기, 관심 구성, mixture-of-experts 설정 및 quantization 형식과 같은 형태입니다. 모델 무게는 지문의 일부가 아닙니다.

결과적으로 기존 FXB는 일반적으로 재사용 될 수 있습니다.

  • 모델은 fine-tuned 구성을 변경하지 않고 fine-tuned입니다.

  • 건축과 지문 분야가 동일하게 남아 있는 동안 무게는 개정됩니다; 또는

  • 다른 모형 저장소에는 동일한 건축 지문이 있습니다.

새로운 FXB는 변경이 컴파일된 커널에 영향을 미칠 때 필요합니다. 예를 들어 아키텍처, 모델 치수, 주의 또는 전문가 구성, quantization 형식 또는 다른 지문 필드를 변경할 수 있습니다. 호환성 일치는 엄격합니다. fine-tuned 모델은 구성이 변경되는 경우 자동으로 호환되지 않습니다.

아키텍처 호환성은 단지 배포 제약이 아닙니다. FXB는 또한 설치 Furiosa 소프트웨어 버전과 의도 된 tensor-parallel 및 context-length 구성에 적합해야합니다. 참조 지문 및 호환성 정확한 일치 규칙 및 호환성 제한을 위해.

호환 캐시 FXB와 모델 제공#

모델 자체 Hugging Face 저장소는 배송되지 않을 수 있습니다 .fxb 자체의. 그 일이 일어날 때, Furiosa-LLM는 여전히 그것을 reusing에 의해 봉사 할 수있다 fingerprint-compatible 로컬 캐시에서 [bundle]를 가져오십시오 (자세한 내용은 다음을 참조) 지문 및 호환성 호환성이 결정되는 방법에 대한). 이 모델 무게가 업데이트 될 때 특히 유용합니다. 또는 지원 모델의 fine-tuned 모델 또는 변형을 제공 할 때 : 건축 지문이 변하지 않는 한, 당신은 기존 FXB 대신 모든 무게 업데이트 또는 변종에 대한 새로운 것을 컴파일 할 수 있습니다. 작업 흐름은 다음과 같습니다.

  1. 호환 FXB를 캐시로 가져 오기 - 허브에서 하나를 다운로드하거나 디스크에 이미 하나 추가하십시오.

  2. 캐시드 번들은 당신이 봉사하고 싶은 모델과 호환됩니다.

  3. 모델을 Serve — Furiosa-LLM는 찾아서 캐시된 번들을 자동으로 사용합니다.

아래 예시는 Qwen/Qwen3-8B-FP8 (FXB를 발송하지 않는) furiosa-ai/Qwen3-8B-FP8 동일한 지문이 있는 번들.

단계 1 — 캐시에 호환 FXB를 가져옵니다#

Hub에서 출판된 번들을 다운로드:

fxb download furiosa-ai/Qwen3-8B-FP8

이것은 모든 것을 가져옵니다. .fxb 저장소에서 캐시 및 인쇄에 각각 저장되었다. 다운로드를 단일 파일로 제한 --file, branch/tag/commit 중 하나를 선택하고, --revision, 그리고 re-fetch는 캐시된 패키지로, --force.

또는, 이전 옵션 또는 설정을 등록합니다. .fxb 당신은 이미 디스크에 있다 — 예를 들어 하나만 내장 (see) FXB를 특정 모델에 맞게 구성하는 방법) 또는 다른 머신에서 복사된 경우:

fxb add ./qwen3-8b-fp8.fxb

add 파일을 캐시로 복사하고 번들의 표현에서 이름을 표준화하므로 베어 out.fxb 다운로드 된 번들로 일관성이됩니다.

✔    furiosa-ai/Qwen3-8B-FP8  4.1 GiB    2026.3.0 (a1b2c3) — match  Qwen3-8B-FP8-<npu>-<rt>-<ts>.fxb

Recommended: /root/.cache/furiosa/llm/fxb/models--furiosa-ai--Qwen3-8B-FP8/snapshots/<sha>/Qwen3-8B-FP8-<npu>-<rt>-<ts>.fxb

표시된 묶음 ✔ 그것은 추천 한쪽. FuriosaIR 열은 build-match 상태에 annotated:

  • — match — 번들의 FuriosaIR (compiler) 개정은 당신의 운영하는 구조 일치합니다. 이 뭉치는 자동적으로 봉사됩니다.

  • — stale — 번들은 fingerprint-compatible이지만 내장되었습니다. 다른 FuriosaIR 버전입니다. 이는 not 자동적으로 제공 (다음 단계 참조).

호환 가능한 묶음이 캐시되지 않은 경우, check non-zero 상태로 메시지 및 출구를 인쇄합니다.

단계 3 — 모델 실행#

평소처럼 대상 모델을 세울 수 있습니다. Furiosa-LLM는 FXB를 해결하여이 주문에서 실행합니다.

  1. 명백한 --fxb <path> (이용된 as-is);

  2. an .fxb 모형의 자신의 저장소 안쪽에 발송하는;

  3. the 로컬 캐시 — 권장 호환 번들, 하지만 그것의 FuriosaIR 개정 실행 빌드 일치 하는 경우에만.

furiosa-llm serve Qwen/Qwen3-8B-FP8

캐시가 사용되면 Furiosa-LLM는 로그 INFO 묶음 묶음을 묶는 선. 동일한 해결책은 Python에 적용합니다 LLM(...) API는, 둘 다 동일한 부호 경로를 통해 갈기 때문에.

경고

캐시가 [데이터 유형]만 포함하고 있다면 낡은 (FuriosaIR-revision-mismatched) 호환 번들, 서빙은 다른 compiler 개정을 위해 건설된 번들을 침묵적으로 적재하는 것보다 실패합니다. 오류는 당신이 1개의 명시적으로 선택할 것을 말합니다:

참고

Tip

몇몇 저장소는 문질러집니다. 다운로드하기 전에 Hugging Face 허브를 허가하고 검사하기 전에, 것과 같이 동일한 방법 (선택) Hugging Face 허브 승인:

지휘자 참조#

캐시를 접촉하는 모든 subcommand는 받아들입니다 --cache-dir (전기: ~/.cache/furiosa/llm/fxb).

fxb build#

모델로부터 FXB 아티팩트를 생성합니다.

fxb build <model> <output_path> [options]

  • model - Hugging Face 모델 ID 또는 로컬 경로 ( 경로가 시작 . or /).

  • output_path — 작성 위치 .fxb (.fxb (필요한 경우 추가)

  • -tp/--tensor-parallel-size N — tensor-parallel 그룹 당 PEs (과태: 모형 미리 설치).

  • -pp/--pipeline-parallel-size N — pipeline-parallel 크기 (기본값: 1).

  • --max-model-len N - 버킷 필터링에 사용되는 최대 컨텍스트 길이.

  • -O/--optim-level {O0,O1,O2,O3} – bucket-filtering 레벨 (기본값: O3).

  • --convert {auto,embed,score,classify} — 작업 덮어쓰기 (기본값: auto).

  • --dry-run — config 및 Buckets를 해결하고 컴파일 없이 빌드 요약을 인쇄합니다.

  • --build-report — 빌드 후 per-kernel 컴파일 타이밍 보고서를 인쇄합니다.

  • --slow-kernel-threshold DURATION - 이 기간을 초과하는 커널을 실행하는 로그는 각 5 초마다 유형, 버킷 및 탈출 된 시간, longest-running 첫째. 몇 초 또는 초에 non-negative 정수를 허용 s, m, or h 후자 (전기: 15m; 0 slow-kernel 보고를 비활성화합니다.

  • --concurrency N - 최대 커널 컴파일을 병렬로 실행 (기본: 1).

  • --dump-tc DIR — 생성 된 TC/DSL 파일을 덤프 DIR 디버깅을 위해

고급 옵션 (당신이 그들을 필요로하지 않는 한 설정 해제):

  • --no-fast-fail - 컴파일 실패 후 나머지 커널을 구축하십시오.

  • --skip-bucket-validation — prefill/decode attention-size 체크 (bring-up 전용)를 건너뛰십시오.

  • --enable-collective-dq — 공동 동적 quantization를 활성화; 선택한 모델만 지원한다.

  • --tokenwise-buckets 1,2,4,8 / --attention-buckets '(1,128,128),(1,1024,1)' — 버킷 계획을 재정의합니다.

성공 시 (non-dry-run) 다음 내용을 출력합니다. Artifact Build Completed.

Slow-kernel 보고는 기본적으로 FXB 빌드 CI를 포함하여 활성화됩니다. 컴파일 시간이 계산된 시간을 제외하고는 concurrency 슬롯을 기다리게 됩니다. 각 업데이트는 빌드가 실행되는 동안 CI 로그에서 볼 수 있는 반 커널을 만들고 터미널 출력 대신 새로운 로그 라인을 추가합니다. 보고는 멈추지 않거나 컴파일 시간을 하지 않습니다. FXB 빌드 CI는 추가 구성 없이 CLI 기본을 사용합니다.

더 짧은 축을 조사하기 위해, 문턱을 낮추십시오:

fxb build Qwen/Qwen3-8B-FP8 qwen3-8b-fp8 \
    --concurrency 8 --slow-kernel-threshold 2m

fxb download#

Hugging Face 저장소에서 FXB 번들을 캐시에 다운로드하십시오.

fxb download <repo_id> [--file F] [--revision R] [--force] [--cache-dir D]

  • repo_id — Hugging Face 저장소 ID.

  • --file F — 다운로드 범위를 단일 항목으로 제한 .fxb 파일 이름으로

  • --revision R - 저장소 개정 (브레이크, 태그, 또는 커밋).

  • --force — re-download는 뭉치가 이미 캐시된 경우에 조차.

fxb add#

로컬을 추가 .fxb 캐시에 저장할 파일 (예: download, 그것은 캐시를 채우고 - 허브에서 디스크에 파일에서. 저장 파일 이름은 각 번의 표현에서 표준화되고, 파일은 복사됩니다 (원래는 장소에서 왼쪽). 여러 경로가 허용됩니다, 그래서 같은 쉘 glob 등 fxb add *.fxb 매칭 번들을 추가합니다. 잘못된 번들은 나머지를 낙태하지 않고 보고되며, 명령은 non-zero를 종료합니다.

fxb add <path>... [--cache-dir D]

fxb check#

Hugging Face 저장소의 모델 구성과 호환되는 캐시 된 FXBs 찾기 (see) 지문 및 호환성 어떻게 호환성이 결정되는지).

fxb check <repo_id> [--cache-dir D]

대상 지문을 인쇄, 호환 캐시 번들 테이블 (표시 된 것을 수정) ✔, 각 번의 FuriosaIR 개정으로 — match or — stale) 및 권장 경로. 호환 번들가 캐시되지 않을 때 non-zero 상태와 출구.

Inspect 및 prune 이미 캐시 된 것. 상단 수준에서 캐시 생활에 추가 (fxb download / fxb add); fxb cache 순수 inventory-management 그룹, subcommands와 ls, rm, 그리고 prune.

fxb cache rm#

캐시된 FXB 번들을 제거하십시오. 적어도 1개의 선별기를 요구합니다 (repo id 또는 .fxb 파일 이름) 또는 --all- 그렇지 않으면 -y/--yes 그것은 확인을 위해 제거되고 신속한 것을 보여줍니다.

fxb cache rm [<selector>...] [--all] [--dry-run] [-y/--yes] [--cache-dir D]

  • selectors ⁇ repo ID 또는 .fxb 파일 이름을 제거해야 합니다.

  • --all — 캐시의 모든 내용을 제거합니다.

  • --dry-run — 아무것도 삭제하지 않고 제거 될 것 이다.

  • -y/--yes — 확인을 위한 prompt가 아닙니다 (Stdin가 대화식이 아닙니다).

fxb cache prune#

FuriosaIR 버전으로 캐시 된 번들을 제거하십시오. 기본적으로 번들을 제거하면 낡은 실행 빌드의 경우 - FuriosaIR (compiler) 개정이 실행 빌드와 일치하지 않습니다, 또는 그 개정은 알 수 없습니다 - 그래서 그들은 자동으로 어쨌든 제공되지 않습니다. --older-than FuriosaIR 버전이 주어진 semantic 버전의 밑에 있는 번들을 제거하십시오. rm, "it" 미리보기 및 안내를 제공합니다, 단 -y/--yes 수요가 주어집니다.

fxb cache prune [--older-than IR_VERSION] [--dry-run] [-y/--yes] [--cache-dir D]

  • --older-than IR_VERSION - FuriosaIR 버전이 이전되는 번들을 제거하십시오. IR_VERSION, e.g. 2026.3.0, <2026.3.0, or <=2026.2.0 (빈 버전은) <). 기록된 FuriosaIR 버전이 없는 뭉치는 지켜집니다. omitted 때, prune는 운영하는 구조의 stale 뭉치를 표합니다.

  • --dry-run — 아무것도 삭제하지 않고 제거 될 것 이다.

  • -y/--yes — 확인을 위한 prompt가 아닙니다 (Stdin가 대화식이 아닙니다).

지문 및 호환성#

FXB의 주요 특징은 다음과 같습니다: 아키텍처 지문 - 값 Furiosa-LLM는 주어진 모델과 호환 여부를 결정하기 위해 사용합니다. 이 표는 모델의 아키텍처와 컴파일된 커널을 결정하는 구성 필드를 기록하며, 지문 일치시 모델과 호환됩니다. 단일 FXB는 그러므로 다시 사용할 수 있습니다 any 같은 지문을 공유하는 Hugging Face 모델은 하나에서 구축되지 않았습니다. 자체 저장소 선박이 아니었던 모델에 대해 가능한 것이 무엇인지 알 수 있습니다. .fxb 로컬 캐시에서 호환 번들을 재사용함으로써.

지문은 모형 건축술에서 더하기 건축됩니다 config.json 커널 생성에 영향을 미치는 필드 - 치수, 관심 및 mixture-of-experts 설정 및 quantization furiosa — 빌드 시 커널 읽기대표적인 예시는 다음과 같습니다. hidden_size, num_attention_heads, sliding_window, MoE 모형을 위한 전문가 조사, 및 quantization format. 다른 커널에 이 컴파일과 다른 두 개의 저장소는 FXB를 공유하지 않아야 합니다; 로드 시간에만 사용되는 필드는 지문의 일부가 아닙니다.

일치하는 것은 엄격한: 두 가지 모델은 건축과 모든 지문 필드가 동일하게 호환됩니다. 사용 fxb check 번들을 재사용하기 전에 일치를 확인합니다.

참고

fingerprint-based 호환성 일치는 입니다 실험적. 지문을 만들 수있는 필드의 정확한 설정, 그들은 비교, 미래 릴리스에서 변경할 수 있습니다. 항상 일치를 확인합니다 fxb check 다른 모델에 대 한 캐시 번에 의존 하기 전에.

가장 좋은 방법#

fxb build runtime 적용 및 결과 번들의 성능에 대한 시간을 거래하십시오. 올바른 옵션은 건물에 따라 다릅니다. 아래의 시나리오는 일반적인 사례를 커버합니다. FuriosaAI의 자체 per-model 생산 구성은 빌드 매트릭스에서 라이브합니다. .github/fxb-artifacts.yaml.

빠른 테스트 구축#

가능한 한 빨리 실행 가능한 번들을 원할 때 - bring-up, 연기 테스트, 또는 모델을 모두 컴파일하는 것을 검사 — 컴파일하고 빌드를 평행시키는 커널 수를 최소화:

  • -O O0 — 최소 버킷 세트, 지금까지 몇 커널이 컴파일됩니다. 이것은 빌드 시간에 하나의 가장 큰 레버입니다.

  • --max-model-len — 작은 몇 가지와 작은 버킷이 생성되는 상황에 맞는 길이를 캡합니다.

  • --concurrency — 기본값보다 높은 수준으로 1 병렬에서 커널을 컴파일하고 빌드 호스트에서 사용할 수 있는 코어를 사용합니다.

  • --dry-run — config 및 Bucket 계획 수정 및 빌드 요약 인쇄 없는 것 컴파일하기 전에 계획을 확인 할 수 있습니다.

# Preview the plan first, then build a minimal bundle quickly
fxb build Qwen/Qwen3-8B-FP8 qwen3-8b-test.fxb --max-model-len 4096 --dry-run
fxb build Qwen/Qwen3-8B-FP8 qwen3-8b-test.fxb -O O0 --max-model-len 4096 --concurrency 8

⁇ 이 만든 -O O0 실행, 하지만 그것은 단지 물통의 최소 세트를 다룹니다; 전체 빌드와 비교된 성능과 적용을 감소 기대. 생산에서 그것을 제공 하지 마십시오.

생산 구축#

번들을 위해 실제로 봉사, 호의 전체 버킷 적용 및 구성을 일치 배포, 더 긴 빌드를 수용:

  • -O O3 - 전체 버킷 세트 (이 기본값입니다; 그대로 그대로 그대로 그대로 그대로 그대로 유지).

  • -tp/--tensor-parallel-size — 서빙 topology (8 PEs 카드 당 - e.g. 8 한 카드만 있으면 32 4개로)

  • --max-model-len — 실제로 봉사하는 최대 상황에 놓으십시오, 그래서 물통은 over-built 보다는 오히려 진짜 워크로드를 위해 치수를 재십시오.

  • --concurrency — 빌드 호스트를 포용하고 (longer) 전체 빌드를 단축합니다.

  • --build-report — per-kernel 컴파일 타이밍을 예기치 않게 느린 커널에 인쇄합니다.

fxb build openai/gpt-oss-120b gpt-oss-120b.fxb \
    -O O3 -tp 32 --max-model-len 32768 --concurrency 24 --build-report

배포 토폴로지#

Tensor 평행은 건축 시간에 조정됩니다, 파이프라인과 자료 평행은 당신이 봉사할 때 놓입니다. 한 묶음 -tp/--tensor-parallel-size 컴파일된 커널을 형성 (각 커널은 tensor-parallel 정도를 위해 sharded), 그래서 FXB의 일부이며 나중에 변경할 수 없습니다 - 빌드 -tp 배포하려는 경우. 대조, 복제 및 단계에 의해 파이프라인 및 데이터 병렬, already-compiled 번들을 다시 컴파일하지 않고, 그래서 그들은 선택 furiosa-llm serve 시간 -pp/--pipeline-parallel-size and -dp/--data-parallel-size:

# Built once for tensor-parallel size 8; deployed with pipeline and data parallelism
furiosa-llm serve Qwen/Qwen3-8B-FP8 --fxb ./qwen3-8b-fp8.fxb -pp 2 -dp 4
