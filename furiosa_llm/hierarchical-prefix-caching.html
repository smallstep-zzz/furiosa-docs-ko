계층적 프리픽스 캐싱#

계층적 prefix caching 확장 Prefix Caching host-memory 캐시 계층과 함께. 그것은 Furiosa-LLM를 허용하여 NPU 메모리에 적합 할 수있는 것보다 더 재사용 가능한 KV cache를 보존 할 수 있습니다, 긴 반복 된 접두사 및 NPU KV cache보다 더 큰 작업 세트.

이 문서는 로컬 두 계층 캐시를 설명합니다:

  • NPU 캐시 (L1)는 가장 낮은 지연 시간을 제공하며, 제한된 용량을 가지며, 활성 요청에도 필요합니다.

  • 호스트 캐시 (L2)는 시스템 메모리에 추가 용량을 제공합니다. 일치하는 호스트 메모리에 있는 프리픽스는 재사용되기 전에 NPU 메모리로 복사됩니다.

각 데이터 병렬 복제본은 Furiosa-LLM 프로세스 내에서 독립적인 NPU 및 호스트 캐시를 소유합니다. 캐시 내용은 영구적이지 않으며 서버 프로세스 간에 공유되지 않습니다.

경고

계층적 사전 캐싱은 실험적인 기능입니다. 따라서 CLI 옵션은 --experimental- 접두사를 사용하며, furiosa-llm serve --help에서 표시되지 않습니다. 옵션 이름과 동작은 향후 릴리스에서 변경될 수 있습니다.

언제 사용하면 좋을까요?#

계층적 사전 캐싱은 다음 조건이 모두 충족될 때 가장 효과적입니다:

  • 요청이 반복적으로 매우 긴, 토큰이 동일한 프리픽스를 사용합니다.

  • 재사용 가능한 프리픽스 작업 세트가 NPU 메모리에 너무 커서 유지할 수 없습니다.

  • 제거된 프리픽스를 다시 계산하는 비용이 호스트 메모리에서 해당 KV 캐시를 복사하는 비용보다 큽니다.

  • 호스트는 구성된 캐시에 필요한 충분한 메모리와 양방향 호스트-NPU 대역폭을 가지고 있어야 합니다.

일반적인 예로는 반복적인 시스템 프롬프트, 다중 턴 대화, 문서 프리픽스를 재사용하는 RAG 요청, 그리고 대규모 프롬프트 템플릿 모음을 사용하는 애플리케이션 등이 있습니다.

프롬프트가 거의 동일한 프리픽스를 공유하지 않거나, 공유 프리픽스가 짧거나, NPU 프리픽스 캐시 용량이 이미 충분한 경우, 큰 이점을 얻기 어려울 수 있습니다. 호스트 캐시 히트는 일반적으로 NPU 캐시 히트보다 느리지만, 긴 프리픽스를 다시 계산하는 것보다 훨씬 저렴할 수 있습니다. 광범위하게 배포하기 전에 대표적인 요청 분포를 사용하여 결과를 측정하십시오.

작동 방식#

Furiosa-LLM은 각 프롬프트의 시작 부분에서 토큰 ID를 기준으로 프리픽스를 계속 일치시킵니다. 계층적 캐싱을 활성화하면 일치하는 프리픽스가 어디에 위치하는지에 영향을 미치지만, 일치 기준은 동일하게 유지됩니다.

개념적으로, 캐시된 프리픽스는 다음과 같은 세 가지 상태 중 하나일 수 있습니다:

  • NPU만 사용 시: 즉시 재사용 가능.

  • 호스트만 사용 시: NPU 메모리 밖에서 보관되며, 다음 요청 시 다시 로드됩니다.

  • NPU와 호스트 모두 사용 시: 호스트 복사본이 NPU 제거에도 살아남아 즉시 재사용 가능합니다.

새로운 요청 시, 스케줄러는 가장 안전한 토큰-정확한 일치 항목을 찾습니다. 해당 항목의 시작 부분은 이미 NPU에 존재할 수 있으며, 이후 부분은 호스트 메모리에 존재할 수 있습니다. Furiosa-LLM은 NPU 부분을 재사용하고, 호스트 부분을 다시 로드하며, 나머지 일치되지 않는 프롬프트 접미사만 계산합니다.

New prompt:       [       matching prefix       ][ new suffix ]
Cache residency:  [ NPU-resident ][ host-only   ][ not cached ]
Request action:   [ reuse         ][ reload     ][ compute    ]

호스트와 NPU 용량은 자동으로 관리됩니다. 활성 요청에 사용되는 항목은 보호됩니다. NPU 메모리 부족 시, 비활성 캐시 항목은 NPU 복사본을 잃을 수 있습니다. 호스트 메모리 부족 시, 오래된 유효한 호스트 항목이 제거되어 더 유용한 캐시 콘텐츠를 위한 공간을 확보합니다.

호스트 보관 정책#

계층적 캐싱은 호스트 복제를 위한 두 가지 보완적인 방법을 제공합니다.

쓰-쓰 방식 (Write-through) 활성화#

쓰-쓰 방식 활성화는 NPU에 존재하는 반복적으로 사용되는 접두사를 식별합니다. 접두사가 구성된 타겟 값에 도달하면 Furiosa-LLM은 해당 접두사를 호스트 메모리로 미리 복사합니다. 이로 인해 접두사는 NPU와 호스트 메모리 모두에 존재하므로, 나중에 NPU에서 제거될 때 호스트 메모리의 복사본을 유지할 수 있습니다.

이것이 기본 정책입니다. 기본 타겟 값은 2이며, 쓰-백 방식은 비활성화됩니다. 따라서, 자주 사용되는 접두사는 호스트 메모리에 유지되지만, 타겟 값에 도달하지 않은 NPU 전용 접두사는 제거 시 삭제될 수 있습니다. 이는 호스트 트래픽과 호스트 캐시 오염을 제한하는 안전한 시작점입니다.

NPU 접두사 캐시에 대한 초기 쓰기는 타겟 값으로 간주되지 않습니다. 따라서, 타겟 값 1은 접두사를 첫 번째 일치하는 요청에서 활성화하고, 기본 타겟 값 2는 두 번째 일치하는 요청에서 활성화합니다.

타겟 값을 높여 더 자주 사용되는 접두사만 활성화합니다. 타겟 값을 0으로 설정하여 쓰-쓰 방식 활성화를 비활성화할 수 있습니다.

참고

0 값을 쓰기-쓰기 임계값으로 지원하는 즉시-승격 모드가 계획 중입니다. 이 모드에서는 Furiosa-LLM이 NPU 프리픽스 캐시에 처음 쓰여질 때, 프리픽스를 호스트 티어로 즉시 복사합니다. 현재 실험 버전에서는 0이 쓰기-쓰기 승격을 비활성화합니다. 즉, 호스트 복사를 요청하지 않습니다.

NPU 제거 시 쓰기-백#

쓰기-백이 활성화되면, Furiosa-LLM은 NPU 메모리 압박으로 인해 제거된 NPU 전용 캐시된 프리픽스를 호스트 메모리로 복사하려고 시도합니다. 이를 통해 쓰기-쓰기 임계값을 충족하지 못한 프리픽스도 포함하여 더 많은 프리픽스를 보존할 수 있습니다.

쓰기-백은 대규모 또는 예측 불가능한 워킹 세트에 대한 재사용성을 향상시킬 수 있지만, NPU-호스트 간의 트래픽을 증가시키고 호스트 캐시를 사용하지 않는 프리픽스로 채울 수 있습니다. NPU 제거 후 재사용이 일반적이고, 추가적인 전송이 가치가 있다는 것을 보여주는 벤치마크 결과가 있는 경우에만 활성화하십시오.

쓰기-백이 활성화된 경우, 쓰기-쓰기 승격이 활성 상태로 유지됩니다. 단, 임계값이 0으로 설정된 경우에만.

구성#

계층적 프리픽스 캐싱은 기본적으로 비활성화되어 있습니다. 두 가지 호스트 용량 옵션 중 하나를 제공하면 활성화됩니다.

CLI 옵션#

옵션

기본값

설명

--experimental-kv-offload-host-memory-gb FLOAT

비활성화

프로세스 전체에 걸쳐 호스트 KV 캐시 예산을 GiB 단위로 설정하여 계층적 캐싱을 활성화합니다. 이 예산은 스케줄러 인스턴스 및 하이브리드 어텐션 모델의 경우 해당 캐시 유형에 분할됩니다.

--experimental-kv-offload-host-memory-ratio FLOAT

비활성화

각 스케줄러 및 캐시 유형에 대한 호스트 용량을 설정하여 계층적 캐싱을 활성화합니다. 이 용량은 NPU KV 블록 수에 비례하여 설정됩니다. 예를 들어, 0.5는 NPU 블록 수의 절반만큼의 호스트 블록을 사용합니다.

--experimental-kv-offload-write-through-threshold INTEGER

2

쓰기-처리(write-through) 활성화 기준에 대한 최소 프리픽스 캐시 히트 횟수. 0은 활성화 기능을 비활성화합니다. 음수 값은 유효하지 않습니다.

--experimental-kv-offload-write-back

비활성화

NPU만 사용하는 캐시된 프리픽스를 호스트 메모리에 보존하며, 호스트 용량에 따라 적용됩니다.

--experimental-kv-offload-overlap-l2-reload

비활성화

Overlaps layerwise L2-to-L1 모델 실행과 전송. host-capacity 옵션과의 필요 --npu-queue-limit 1; 참조 모델 실행을 통한 L2 재로드.

두 개의 호스트 용량 옵션은 상호 배타적입니다. 호스트 메모리 비율이 0이면 계층적 캐싱이 비활성화됩니다. 음수 값은 유효하지 않습니다. GiB 값은 프로세스 예산을 분할한 후 최소한 하나의 사용 가능한 KV 캐시 블록을 저장할 수 있는 양수 값이어야 합니다.

호스트 용량 선택#

대부분의 배포에서는 GiB 옵션을 선호하는 것이 좋습니다. 왜냐하면 이는 프로세스의 호스트 KV 캐시 할당에 대해 예측 가능한 상한을 설정하기 때문입니다:

furiosa-llm serve <model> \
  --experimental-kv-offload-host-memory-gb 16

예산은 전체 Furiosa-LLM 프로세스에 적용됩니다. 데이터 병렬 처리를 사용하는 경우, 이는 데이터 병렬 스케줄러 인스턴스에 분할됩니다. 하이브리드 어텐션 모델의 경우, 각 인스턴스의 할당은 NPU KV 메모리 풋프린트에 따라 글로벌 어텐션 및 슬라이딩 윈도우 캐시 간에 추가로 분할됩니다. 용량은 전체 블록 단위로 할당되므로 실제 할당은 요청된 한계보다 약간 작을 수 있습니다.

비율 옵션은 호스트 용량이 모델의 NPU KV 캐시와 함께 확장되어야 할 때 편리합니다:

furiosa-llm serve <model> \
  --experimental-kv-offload-host-memory-ratio 0.5

비율은 각 스케줄러 인스턴스에 독립적으로 적용됩니다. 따라서 전체 프로세스 호스트 메모리 사용은 data_parallel_size와 함께 증가합니다. 비율 1.0은 각 캐시 유형에서 NPU KV 블록당 하나의 호스트 KV 블록을 요청합니다. 이는 프로세스 전체 메모리 제한이 아닙니다.

설정된 예산은 호스트 KV 캐시 풀에만 적용되며, 모델 가중치, 런타임 상태, 요청 데이터 또는 기타 프로세스 메모리에 적용되지 않습니다. 해당 구성 요소와 운영 체제에 충분한 물리 메모리를 확보하십시오.

CLI 예제#

반복적으로 사용되는 접두사를 기본 프로모션 임계값 및 삭제 시 쓰기 백업 없이 유지합니다:

furiosa-llm serve <model> \
  --experimental-kv-offload-host-memory-gb 16

삭제 시 NPU 전용 캐시 항목을 호스트에 기록하여 더 넓은 작업 집을 유지합니다:

furiosa-llm serve <model> \
  --experimental-kv-offload-host-memory-gb 32 \
  --experimental-kv-offload-write-back

최소 4번의 캐시 히트를 받은 접두사만 허용합니다:

furiosa-llm serve <model> \
  --experimental-kv-offload-host-memory-ratio 0.5 \
  --experimental-kv-offload-write-through-threshold 4

첫 번째 캐시 히트 후 접두사를 프로모트하고, 삭제 시 더 차가운 NPU 전용 항목을 유지합니다:

furiosa-llm serve <model> \
  --experimental-kv-offload-host-memory-gb 32 \
  --experimental-kv-offload-write-through-threshold 1 \
  --experimental-kv-offload-write-back

Python API#

오프라인 Python API는 SchedulerConfig을 통해 동일한 동작을 노출합니다. 다음 예시는 16 GiB의 전역 프로세스 호스트 예산을 사용하고 기본 "핫 프리픽스" 프로모션 정책을 사용합니다:

from furiosa_llm import LLM
from furiosa_llm.metadata.config_types import (
    KVOffloadConfig,
    PrefixCacheConfig,
    SchedulerConfig,
)

scheduler_config = SchedulerConfig(
    prefix_cache_config=PrefixCacheConfig(enabled=True),
    kv_offload_config=KVOffloadConfig(
        enabled=True,
        host_memory_bytes=16 * 1024**3,
        write_through_threshold=2,
        write_back=False,
    ),
)

with LLM(
    "furiosa-ai/Qwen3-8B-FP8",
    scheduler_config=scheduler_config,
) as llm:
    first = llm.generate(
        "A long shared document or instruction prefix...\nQuestion one"
    )
    second = llm.generate(
        "A long shared document or instruction prefix...\nQuestion two"
    )

NPU KV 용량에 따라 호스트 티어를 크기 조정하려면 host_memory_ratio를 host_memory_bytes 대신 설정합니다:

kv_offload_config = KVOffloadConfig(
    enabled=True,
    host_memory_ratio=0.5,
    write_through_threshold=4,
    write_back=True,
)

host_memory_bytes와 양의 host_memory_ratio를 동시에 설정하지 마십시오. Python API에서는 enabled=True를 명시적으로 설정해야 합니다. 용량 필드만 설정하는 것으로는 오프로딩이 활성화되지 않습니다. direct KVOffloadConfig에서 write_through_threshold=None를 사용하여 write-through 프로모션을 비활성화할 수 있습니다. CLI에서도 0을 사용하여 동일한 기능을 수행합니다.

L2 재로드와 모델 실행의 중복#

기본적으로 런타임은 호스트에서 NPU로 KV를 재로드한 후 모델 실행을 수행합니다. 실험적인 레이어별 재로드 경로는 나중에 KV 데이터가 이미 사용 가능한 레이어의 실행과 함께 후반 레이어의 전송을 중복할 수 있습니다:

furiosa-llm serve <model> \
  --experimental-kv-offload-host-memory-gb 16 \
  --experimental-kv-offload-overlap-l2-reload

이 옵션은 기본적으로 비활성화되며 긍정적 인 L2 용량을 필요로합니다. npu_queue_limit=1 (기본값). 그것은 eager 스케줄링과 지원 겹치는 스케줄 윤곽. 그것은 speculative 해독 또는 PD 탈중앙도 결합될 수 없습니다. 그것은 L2-to-L1 재부하에, Mooncake L3 prefetch 아닙니다 적용합니다.

Python API 모델의 경우, 다음 설정을 적용합니다. overlap_l2_reload=True in KVOffloadConfig 옆으로 enabled=True 그리고 호스트 용량. 대표 캐시 놓기 및 컨텍스트 길이 옵션 벤치 마크; 혜택은 얼마나 많은 전송 시간이 오버랩 모델 실행 할 수 있는지에 따라 달라집니다.

기능 간 상호 작용 및 제한 사항#

프리픽스 캐싱#

계층적 캐싱은 일반적인 프리픽스 캐싱을 필요로 합니다. 프리픽스 캐싱은 기본적으로 활성화되어 있으므로 추가 옵션이 필요하지 않습니다. --no-enable-prefix-caching 옵션과 호스트 용량 옵션을 함께 사용하면 서버가 해당 구성에서 계층적 캐싱을 초기화할 수 없습니다.

데이터 병렬 처리#

각 데이터 병렬 복제본은 자체 NPU 및 호스트 프리픽스 캐시를 갖습니다. 캐시 항목은 복제본 간에 복사되지 않습니다. 프로세스 전체의 GiB 용량은 복제본 간에 분할되며, 각 복제본에 비율 기반 용량이 적용되므로 복제본이 추가될 때 전체 호스트 할당이 증가합니다.

Cache-aware 라우팅은 이미 캐시 항목을 소유 한 복제로 관련 프롬프트를 다시 전송하여 재사용을 향상시킬 수 있습니다. 참조 Data-Parallel 라우팅 그리고 locality 큰 공유 접두사에 의해 지배되는 workloads를 위한 득점 단면도.

하이브리드 어텐션#

계층적 캐싱은 글로벌 어텐션과 슬라이딩 윈도우 어텐션을 결합하는 모델을 지원합니다. Furiosa-LLM은 두 유형의 캐시 모두에 호스트 용량을 할당하고, 필요한 슬라이딩 윈도우 상태가 유효한 프리픽스만 다시 로드합니다. 따라서 안전하게 재사용 가능한 프리픽스는 원본 토큰 매치보다 짧을 수 있습니다. "하이브리드 어텐션 모델"에서 매칭 의미와 "하이브리드 KV 캐시 관리"에서 기본 메모리 모델에 대한 정보를 참조하십시오.

기타 제한 사항#

  • 하위 층적 KV 오프로딩은 하위 층적 디코딩과 함께 사용할 수 없습니다.

  • 프리픽스 재사용은 토큰 정확합니다. 공백, 구두점, 챗 템플릿 변경 또는 토크나이저 변경은 재사용을 방지할 수 있습니다.

  • 호스트 캐시 내용은 프로세스가 종료될 때 사라지며, 다른 서버 프로세스와 공유되지 않습니다. (호스트 캐시 내용은 프로세스가 종료될 때 삭제되며, 다른 서버 프로세스와 공유되지 않습니다.)

  • 호스트 캐시는 NPU 용량을 늘리는 것이지, NPU 용량을 늘리는 것이 아닙니다. 호스트에 할당된 프리픽스는 추론을 계속하기 위해 NPU 블록이 필요합니다. (호스트 캐시는 NPU 용량을 늘리는 것이지, NPU 용량을 늘리는 것이 아닙니다. 호스트에 할당된 프리픽스는 추론을 계속하기 위해 NPU 블록이 필요합니다.)

호스트 준비#

엔진이 시작될 때 호스트 KV 캐시 풀이 할당됩니다. 요청된 풀을 할당할 수 없거나, 생성된 프로세스 공유가 너무 작아 유용한 글로벌 어텐션 용량을 제공할 수 없는 경우 엔진 시작이 실패합니다.

Linux에서는 호스트 KV 캐시용 충분한 hugepage를 예약해야 합니다. Furiosa-LLM이 예약된 hugepage 풀이 부족한 경우 일반 4 KiB 페이지로 전환될 수 있지만, 이는 전송 속도를 감소시킬 수 있습니다. 서버는 부족한 예약 수를 포함하는 경고를 출력합니다. 자세한 내용은 "호스트 PCI 최적화 튜닝"을 참조하십시오.

모니터링 및 튜닝#

이 GET /metrics [설명] OpenAI-Compatible Server 모니터링 서버는 다음을 비교하고 계층 캐싱을 활성화 한 후:

  • furiosa_llm_prefix_cache_hits: 누적적으로 재사용된 캐시된 토큰 (cumulative cached tokens reused).

  • furiosa_llm_prefix_cache_queries: 접두사 일치에 대해 고려된 프롬프트 토큰의 누적 수 (cumulative prompt tokens considered for prefix matching).

  • 첫 번째 토큰 생성 시간 (Time to first token, TTFT), 특히 충분한 캐시 교체 후 NPU 캐시 용량을 초과하는 경우.

  • 예상되는 동시성 하에서 호스트 메모리 소비, NPU 활용률, 요청 큐잉, 그리고 엔드 투 엔드 지연.

접두사 캐시 카운터는 NPU 및 호스트에 존재하는 히트 모두를 결합합니다. 현재 이 카운터는 캐시 계층을 식별하지 않습니다. 따라서 높은 결합된 히트 비율이 자체적으로 호스트 오프로드가 지연 시간을 개선했음을 증명하지 않습니다. 따뜻하고 안정적인 워크로드에서 NPU 캐시 교체를 강제하여 TTFT 및 처리량을 비교하십시오.

참고

호스트 및 NPU별 지표를 도입하여, 다양한 워크로드 특성에 따른 계층적 캐싱 문제 해결 및 튜닝을 용이하게 할 예정입니다. (호스트 및 NPU별 지표: 호스트 및 NPU에 특화된 지표)

실질적인 튜닝 순서는 다음과 같습니다:

  1. 먼저, 제한된 GiB 예산을 설정하고, 기본 임계값을 2로 설정하며, 쓰기 백(write-back) 기능을 비활성화합니다.

  2. 워크로드가 반복적으로 긴 프리픽스를 사용하고 있으며, NPU 캐시 교체 후 캐시 재사용이 개선되는지 확인합니다.

  3. 유용한 프리픽스가 여전히 손실되고 호스트에 충분한 메모리가 있는 경우, 호스트 예산을 늘립니다.

  4. 단발성 프리픽스가 호스트 용량 또는 전송 대역폭을 과도하게 소비하는 경우, 프로모션 임계값을 높입니다.

  5. 유용한 프리픽스가 충분히 사용되지 않은 상태에서 쓰기-백(write-back) 테스트를 수행하여, 쓰기-쓰루(write-through)로 승격되기 전에 충분히 사용되지 않은 상태로 유지합니다.

  6. 프로덕션 환경의 동시성을 고려하여 재테스트를 수행합니다. 데이터 부하에 따라 캐시 경쟁 및 캐시 거주 패턴이 변경되기 때문입니다.

문제 해결#

서버 시작 실패#

다음 사항을 확인합니다. 정확히 하나의 긍정적인 호스트 용량 옵션이 설정되어 있는지, 프리픽스 캐싱이 활성화되어 있는지, 데이터 병렬 분할 후 구성된 프로세스 예산이 충분한지, 그리고 충분한 호스트 메모리가 있는지. 비율의 경우, 0보다 큰 값을 사용합니다. 쓰기-쓰루 임계값의 경우, 0 또는 양의 정수를 사용합니다.

높은 히트율이지만, 지연 시간 개선이 제한적임#

게시된 히트율은 NPU와 호스트 히트를 결합한 값입니다. 호스트 히트는 리로드 비용을 포함하며, 짧은 접두사 리로드는 충분한 계산을 수행하여 그 비용을 상쇄하지 못할 수 있습니다. 대신, 긴 접두사 요청을 별도로 비교하고 호스트 메모리 또는 DMA 대역폭 경쟁을 확인하십시오.

낮은 히트율#

완전히 렌더링된 프롬프트가 시작 시 토큰 수준에서 동일한지 확인하십시오. 여기에는 채팅 템플릿과 시스템 메시지가 포함됩니다. 데이터 병렬 처리를 사용할 때, 관련된 요청이 동일한 복제본으로 돌아갈 수 있도록 캐시 기반 라우팅을 사용하십시오. 또한 워드가 캐시를 충분히 가열하고 있으며 호스트 예산이 재사용 가능한 작업 세트에 충분한지 확인하십시오.

호스트 메모리가 예상보다 증가#

비율 옵션은 스케줄러별이며, 프로세스 전체에 적용되지 않습니다. 총 할당은 데이터 병렬 복제본과 각 어텐션 유형의 캐시 요구 사항을 포함합니다. 프로세스 전체 제한이 필요한 경우 GiB 옵션을 사용하고, Furiosa-LLM의 나머지 부분도 호스트 메모리를 소비한다는 점을 기억하십시오.
