계층적 Prefix Caching#

계층적 prefix caching 확장 Prefix Caching host-memory 캐시 계층과 함께. 그것은 Furiosa-LLM를 허용하여 NPU 메모리에 적합 할 수있는 것보다 더 재사용 가능한 KV cache를 보존 할 수 있습니다, 긴 반복 된 접두사 및 NPU KV cache보다 더 큰 작업 세트.

이 문서는 로컬 two-tier 캐시를 설명합니다:

  • NPU 캐시 (L1) lowest-latency 접두사 재사용을 제공하지만 제한된 용량을 가지고 있으며 활성 요청에 의해 필요합니다.

  • 호스트 캐시 (L2) 시스템 메모리에 추가 용량을 제공합니다. host-resident 접두사는 재사용되기 전에 NPU 메모리로 다시 복사됩니다.

각 data-parallel 복제는 Furiosa-LLM 프로세스 내에서 독립적 인 NPU 및 호스트 캐시를 소유합니다. 캐시 내용은 서버 프로세스간에 지속적이거나 공유되지 않습니다.

경고

Hierarchical prefix caching는 실험적입니다. 따라서 CLI 옵션은 사용 --experimental- 접두사를 유지하고 나타나지 않습니다. furiosa-llm serve --help. 옵션 이름과 행동은 향후 릴리스에서 변경할 수 있습니다.

언제 사용 해야 합니까?#

Hierarchical prefix caching는 뒤에 오는 것 전부가 true인 때 가장 효과적입니다:

  • 반복적으로 긴 사용, token-identical 접두사 요청.

  • 재사용 가능한 접두사 작업 세트는 NPU 메모리에 남아있는 너무 크다.

  • evicted 접두사 비용을 호스트 메모리에서 KV cache를 복사하는 것보다 더 많은 비용 절감.

  • 호스트는 충분히 무료 메모리와 양방향 host-NPU 대역폭을 구성한 캐시를 가지고 있습니다.

일반적인 예제에는 반복된 시스템 프롬프트, multi-turn 대화, RAG 요청이 있으며, 대용량 prompt 템플릿 모음과 함께 문서 접두사 및 응용 프로그램을 재사용합니다.

그것은 신속하게 접두사, 공유 접두사 짧은, 또는 NPU prefix-cache 용량이 이미 충분하다 때 약간의 혜택을 제공 할 수 있습니다. 호스트 캐시 히트는 일반적으로 NPU 캐시가 KV 데이터가 다시로드되어야하지만 긴 접두사보다 실질적으로 저렴 할 수 있기 때문에 감소합니다. 배포하기 전에 대표 요청 배포 결과를 측정하십시오.

어떻게 작동 하는 것 입니까?#

Furiosa-LLM는 각각 prompt의 시작부터 token ID에 의해 접두사를 계속합니다. 일치한 접두사는 어떤 경기를 구성하지 않을지도 모르다 곳에 계층화한 조화시키는 hierarchical 캐싱 변화.

개념적으로, 캐시 된 접두사는 3 주 중 하나에있을 수 있습니다 :

  • NPU만: 즉시 재사용 가능.

  • 호스트만: NPU 메모리 밖에 유지하고 다음 히트를 다시로드했습니다.

  • NPU 및 호스트: 즉시 재사용 가능, NPU eviction을 생존 할 수있는 호스트 복사.

새로운 요청의 경우, 스케줄러는 가장 긴 안전한 token-exact 일치를 찾습니다. 그 경기의 시작은 이미 NPU-resident가 될 수 있으며 다음 부분은 host-resident입니다. Furiosa-LLM는 NPU 부분을 재사용하고 호스트 부분을 다시로드하고 나머지는 prompt suffixuffix를 준수합니다.

New prompt:       [       matching prefix       ][ new suffix ]
Cache residency:  [ NPU-resident ][ host-only   ][ not cached ]
Request action:   [ reuse         ][ reload     ][ compute    ]

호스트 및 NPU 용량은 자동으로 관리됩니다. 활성 요청으로 사용 된 항목은 보호됩니다. NPU 메모리 압력에서 비활성 캐시 항목은 NPU 사본을 잃을 수 있습니다. 호스트 메모리에 남아있는 경우 아래 설명 된 유지 정책에 따라 다릅니다. 호스트 메모리 압력에서, 이전 자격 호스트 항목은 더 유용한 캐시 콘텐츠를 위해 방을 만들기 위해 evicted.

호스트 보존 정책#

Hierarchical 캐싱은 호스트 사본을 만들 수있는 두 가지 보완 방법을 제공합니다.

Write-through 프로모션#

Write-through 프로모션은 여전히 NPU-resident 인 동안 반복적으로 재사용 된 접두사를 식별합니다. 접두사는 구성 된 히트 임계값을 도달 할 때 Furiosa-LLM는 활성으로 호스트 메모리에 복사합니다. 접두사는 NPU 및 호스트 사본을 모두 가지고 있으므로 나중에 NPU eviction은 eviction-time 전송없이 호스트 복사를 유지할 수 있습니다.

이것은 기본 정책입니다. 기본 임계 값은 2, 그리고 write-back는 무효합니다. 따라서, 수시로 재사용한 접두사는 지그개선 도중 문턱에 도달하지 않은 NPU 전용 접두사에서 보존됩니다. 이것은 주인 교통과 host-cache 오염을 제한하기 때문에 보존적인 출발점입니다.

초기는 NPU 접두사 캐시가 히트로 계산되지 않습니다. 임계값 1 따라서 첫 번째 연속 일치 요청에 접두사를 촉진하고, 기본 임계 값이 있는 동안 2 2단계에서 이를 활성화합니다.

문턱만 인정할 수 있는 문턱을 증가시킨다. 문턱을 설정한다. 0 write-through 프로모션을 비활성화하기 위해.

참고

write-through 임계값 지원 0 immediate-promotion 모드가 계획되어 있습니다. 그 모드에서 Furiosa-LLM는 NPU 접두사 캐쉬에 처음 쓴 호스트 계층에 접두사를 복사합니다. 현재 실험적인 릴리스에서, 0 write-through 프로모션을 비활성화; 그것은 즉각적인 호스트 복사를 요청하지 않습니다.

Write-back가 NPU에서 발생한 이탈#

write-back가 활성화되면 Furiosa-LLM는 NPU 메모리 압력이 부풀릴 때 NPU 전용 캐쉬드 프리픽을 호스트 메모리에 복사하려고 시도합니다. 이것은 write-through 임계값에 도달하지 않은 접두사를 포함하여 접두사의 더 넓은 세트를 보존합니다.

Write-back는 큰 또는 더 적은 예상할 수 있는 일 세트를 위한 재사용을 개량할 수 있습니다, 그러나 또한 NPU-to-host 트래픽을 증가시키고 결코 다시 사용되지 않는 접두사로 주인 캐시를 채울 수 있습니다. NPU eviction 후에 재사용할 수 있는 것은 일반 적이고 벤치 마크는 추가 이동이 비유하다는 것을 보여줍니다.

Write-through 프로모션은 write-back가 임계값이 설정되지 않는 한 활성화되면 활성화됩니다. 0.

구성#

Hierarchical prefix caching는 기본적으로 비활성화됩니다. 2개의 긍정적인 host-capacity 옵션 중 하나를 공급하면 됩니다.

CLI 옵션#

선택 사항

기본 설정

설명

--experimental-kv-offload-host-memory-gb FLOAT

장애인

GiB의 process-wide 호스트 KV cache 예산과 계층 캐싱을 가능하게합니다. 예산은 스케줄러 인스턴스 중 분할되며 하이브리드주의 모델의 캐시 유형입니다.

--experimental-kv-offload-host-memory-ratio FLOAT

장애인

각 스케줄러 및 캐시 타입의 호스트 용량과 조화를 이루는 것은 NPU KV 블록 카운트의 비율로 크기가 다릅니다. 예를 들어, 0.5 NPU 블록으로 많은 호스트 블록으로 절반을 요청합니다.

--experimental-kv-offload-write-through-threshold INTEGER

2

최소 prefix-cache는 write-through 프로모션에 대한 카운트를 히트. 0 프로모션을 비활성화합니다. 부정적 값은 유효하지 않습니다.

--experimental-kv-offload-write-back

장애인

NPU-only는 NPU eviction가 발생하면 호스트 메모리에서 prefixes를 캐시했습니다.

--experimental-kv-offload-overlap-l2-reload

장애인

Overlaps layerwise L2-to-L1 모델 실행과 전송. host-capacity 옵션과의 필요 --npu-queue-limit 1; 참조 모델 실행을 통한 L2 재로드.

두 host-capacity 옵션은 상호 전용입니다. host-memory 비율 0 무술 캐싱을 해제; 부정적인 비율은 유효하지 않습니다. GiB 값은 공정 예산이 나뉘어 후 적어도 하나의 쓸모 KV 캐시 블록을 보유하는 충분한 긍정적이고 큰이어야한다.

호스트 용량 선택#

대부분의 배포를 위해 GiB 옵션을 선호하기 때문에 프로세스의 호스트 KV cache 할당에 대한 예측 가능한 상단 경계를 설정하기 때문에:

furiosa-llm serve <model> \
  --experimental-kv-offload-host-memory-gb 16

예산은 Furiosa-LLM 프로세스 전체에 적용됩니다. 데이터 병렬화로 인해 data-parallel 스케줄러 인스턴스 중 분할됩니다. hybrid-attention 모델의 경우, 각 인스턴스 공유는 global-attention와 sliding-window 캐시 사이에 NPU KV 메모리 발자국으로 나뉩니다. 용량은 전체 블록으로 할당되므로 실제 할당량은 약간 작을 수 있습니다.

비율 선택권은 주인 수용량이 모형의 NPU KV cache로 가늠자해야 할 때 편리합니다:

furiosa-llm serve <model> \
  --experimental-kv-offload-host-memory-ratio 0.5

비율은 각 스케줄러 인스턴스에 독립적으로 적용됩니다. 따라서 총 공정 host-memory 사용량이 증가합니다. data_parallel_size. 1.0 각 캐시 유형에 있는 각 NPU KV 구획을 위한 대략 1개의 주인 KV 구획을 요구하십시오; 그것은 process-wide 기억 한계가 아닙니다.

구성 예산은 호스트 KV cache 풀, 모델 무게, runtime 상태, 요청 데이터 또는 기타 프로세스 메모리가 아닌 호스트 KV cache 풀을 다룹니다. 그 구성 요소와 운영 체제에 대한 충분한 물리적 메모리를 남겨두십시오.

CLI 예제#

기본 프로모션 임계값과 eviction-time write-back를 사용하여 반복된 결과를 수신하는 예비 고정:

furiosa-llm serve <model> \
  --experimental-kv-offload-host-memory-gb 16

NPU-only 캐시 항목을 작성하여 더 넓은 작업 설정을 보존하십시오.

furiosa-llm serve <model> \
  --experimental-kv-offload-host-memory-gb 32 \
  --experimental-kv-offload-write-back

적어도 4 개의 캐시를 수신 한 유일한 접두사에 대한:

furiosa-llm serve <model> \
  --experimental-kv-offload-host-memory-ratio 0.5 \
  --experimental-kv-offload-write-through-threshold 4

첫 번째 캐시 히트 및 콜드 보존기 NPU-only 항목 후 접두사를 홍보하십시오.

furiosa-llm serve <model> \
  --experimental-kv-offload-host-memory-gb 32 \
  --experimental-kv-offload-write-through-threshold 1 \
  --experimental-kv-offload-write-back

Python API#

오프라인 Python API는 동일한 동작을 통해 노출합니다. SchedulerConfig. 다음 예제는 16 GiB process-wide 호스트 예산과 기본 hot-prefix 프로모션 정책을 사용합니다.

from furiosa_llm import LLM
from furiosa_llm.metadata.config_types import (
    KVOffloadConfig,
    PrefixCacheConfig,
    SchedulerConfig,
)

scheduler_config = SchedulerConfig(
    prefix_cache_config=PrefixCacheConfig(enabled=True),
    kv_offload_config=KVOffloadConfig(
        enabled=True,
        host_memory_bytes=16 * 1024**3,
        write_through_threshold=2,
        write_back=False,
    ),
)

with LLM(
    "furiosa-ai/Qwen3-8B-FP8",
    scheduler_config=scheduler_config,
) as llm:
    first = llm.generate(
        "A long shared document or instruction prefix...\nQuestion one"
    )
    second = llm.generate(
        "A long shared document or instruction prefix...\nQuestion two"
    )

NPU KV 용량과 관련된 호스트 계층을 크기로 설정 host_memory_ratio 그 대신 host_memory_bytes:

kv_offload_config = KVOffloadConfig(
    enabled=True,
    host_memory_ratio=0.5,
    write_through_threshold=4,
    write_back=True,
)

둘 다 설정하지 마세요 host_memory_bytes 그리고 긍정적인 host_memory_ratio. Python API enabled=True 명시적으로 설정해야합니다; 혼자 용량 필드를 설정하면 offloading를 활성화하지 않습니다. 사용 write_through_threshold=None 직접 write-through 프로모션을 비활성화 KVOffloadConfig. CLI의 사용 0 와 동일한 목적으로 사용.

모델 실행을 통한 L2 재로드#

기본적으로 runtime는 모델을 실행하기 전에 host-to-NPU KV 재로드를 완료합니다. 실험적인 layerwise 재로드 경로는 KV 데이터가 이미 사용할 수 있는 레이어의 실행을 가진 나중에 레이어에 대한 오버랩 전송을 할 수 있습니다.

furiosa-llm serve <model> \
  --experimental-kv-offload-host-memory-gb 16 \
  --experimental-kv-offload-overlap-l2-reload

이 옵션은 기본적으로 비활성화되며 긍정적 인 L2 용량을 필요로합니다. npu_queue_limit=1 (기본값). 그것은 eager 스케줄링과 지원 겹치는 스케줄 윤곽. 그것은 speculative 해독 또는 PD 탈중앙도 결합될 수 없습니다. 그것은 L2-to-L1 재부하에, Mooncake L3 prefetch 아닙니다 적용합니다.

Python API 모델의 경우, 다음 설정을 적용합니다. overlap_l2_reload=True in KVOffloadConfig 옆으로 enabled=True 그리고 호스트 용량. 대표 캐시 놓기 및 컨텍스트 길이 옵션 벤치 마크; 혜택은 얼마나 많은 전송 시간이 오버랩 모델 실행 할 수 있는지에 따라 달라집니다.

특징 상호 작용 및 한계#

Prefix caching#

Hierarchical 캐싱은 정규적인 prefix caching를 요구합니다. Prefix caching는 기본적으로 활성화됩니다, 그래서 추가 선택권은 일반적으로 필요합니다. host-capacity 선택권을 가진 결합하지 마십시오 --no-enable-prefix-caching; 서버는 그 구성에서 계층 캐싱을 초기화 할 수 없습니다.

데이터 병렬성#

각 data-parallel 복제에는 자체 NPU 및 호스트 접두사 캐시가 있습니다. 캐시 항목은 복제 사이에 복사되지 않습니다. process-wide GiB 예산은 복제 중 나뉩니다. ratio-based 용량은 각 복제에 적용되며 복제로 총 호스트 할당이 추가됩니다.

Cache-aware 라우팅은 이미 캐시 항목을 소유 한 복제로 관련 프롬프트를 다시 전송하여 재사용을 향상시킬 수 있습니다. 참조 Data-Parallel 라우팅 그리고 locality 큰 공유 접두사에 의해 지배되는 workloads를 위한 득점 단면도.

하이브리드 관심#

Hierarchical 캐싱은 글로벌 관심과 sliding-window주의를 결합하는 모델을 지원합니다. Furiosa-LLM는 캐시 유형 모두에 대한 호스트 용량을 할당하고 필요한 sliding-window 국가가 유효하다는 접두사 만 다시로드합니다. 따라서 안전하게 재사용 가능한 접두사는 token 경기보다 단축 될 수 있습니다. 참조 하이브리드 어텐션 모델 의미론적 정보와 하이브리드 KV Cache 관리 기본 메모리 모델에 대한.

다른 제한#

  • 결정적인 해독은 hierarchical KV offloading와 결합될 수 없습니다.

  • 접두사 재사용은 token-exact입니다. Whitespace, punctuation, chat-template 변경, 또는 Tokenizer 변경은 재사용을 방지할 수 있습니다.

  • 호스트 캐시 내용이 프로세스 종료시 손실되며 다른 서버 프로세스와 공유되지 않습니다.

  • 호스트 캐시는 용량을 증가, NPU 용량이 아닙니다. host-resident 접두사는 여전히 NPU 블록 전에 NPU 블록이 필요합니다.

호스트 준비#

호스트 KV cache 풀은 엔진이 시작될 때 할당됩니다. 요청된 풀이 할당될 수 없거나 결과 프로세스 공유가 너무 작을 경우 엔진 시작이 실패합니다.

Linux에서 호스트 KV cache에 대한 충분한 거대한 페이지를 예약하십시오. Furiosa-LLM는 예약 된 거대한 페이지 풀이 충분할 때 일반 4 KiB 페이지로 돌아갈 수 있지만 throughput로 전송을 줄일 수 있습니다. 서버는 충분한 예약을 감지 할 때 필요한 거대 카운트를 포함하는 경고를 방출합니다. 참조 호스트 PCI 최적화 튜닝 시스템 구성 지침에 대한.

모니터링 및 튜닝#

이 GET /metrics [설명] OpenAI-Compatible Server 모니터링 서버는 다음을 비교하고 계층 캐싱을 활성화 한 후:

  • furiosa_llm_prefix_cache_hits: 누적 캐시된 토큰을 재사용합니다.

  • furiosa_llm_prefix_cache_queries: 접두사 일치에 고려되는 누적 prompt 토큰.

  • 처음 token (TTFT)에 시간, 특히 충분한 캐시 churn 후에 NPU 캐시 용량을 초과하는.

  • 호스트 메모리 소비, NPU 활용, 요청 큐잉, 그리고 예상되는 동시성 하에서 latency.

prefix-cache 카운터는 NPU-resident와 host-resident를 결합합니다; 그들은 현재 캐시 계층을 식별하지 않습니다. 더 높은 결합된 히트률 따라서 호스트 오프로드가 latency 향상을 증명하지 않습니다. 따뜻한 steady-state에 TTFT 및 throughput를 비교하여 NPU 캐시 비션을 강제로 NPU.

참고

Host-와 NPU-specific 메트릭은 다른 워크로드 특성에 대한 문제 해결 및 튜닝 계층 캐싱을 쉽게 만들 계획입니다.

실용적인 튜닝 순서는 다음과 같습니다.

  1. 바인딩 된 GiB 예산으로 시작, 기본 임계 값 2, 그리고 write-back 기능이 비활성화되었습니다.

  2. workload가 긴 접두사를 반복하고 캐시 재사용이 NPU-cache churn 후 개선되었는지 확인하십시오.

  3. 소중한 접두사가 여전히 잃어버린 경우 호스트 예산을 증가시키고 호스트는 충분한 메모리를 가지고 있습니다.

  4. one-off 접두사는 너무 많은 호스트 용량 또는 전송 대역폭을 소비하면 프로모션 임계값을 올릴 수 있습니다.

  5. write-through 프로모션에 충분히 뜨거운되기 전에 유용한 접두사가 evicted 경우에 write-back를 시험하십시오.

  6. 생산 concurrency에서 테스트, 전송 contention 및 캐시 residency 패턴 부하와 변화.

문제 해결#

서버가 시작되지 않았음을 나타냅니다.#

정확히 하나의 긍정적인 host-capacity 옵션 설정 확인, prefix caching 활성화, 구성 프로세스 예산 data-parallel 부서 후 충분히 크다, 충분한 호스트 메모리를 사용할 수 있습니다. 비율에 대 한, 더 큰 가치를 사용 0. write-through 임계값을 위해, 사용 0 또는 양의 정수.

높은 명중율 그러나 제한된 latency 개선#

게시 된 히트 레이트는 NPU와 호스트가 표시됩니다. 호스트는 재로드 비용 및 short-prefix 재로드를 포함하면 비용이 상쇄에 충분한 계산을 저장할 수 없습니다. long-prefix 요청을 별도로 비교하고 host-memory 또는 DMA 대역폭 콘텐츠에 대한 확인을 비교하십시오.

낮은 타격률#

완전히 렌더링 된 프롬프트는 채팅 템플릿과 시스템 메시지를 포함하여 처음부터 token-identical입니다. 데이터 병렬로 인하여 cache-aware 라우팅을 사용하여 동일한 복제로 반품하십시오. 또한 워크로드가 캐시를 따뜻하게하고 호스트 예산이 재사용 가능한 작업 세트에 충분히 크다는 것을 확인합니다.

호스트 메모리는 예상보다 더 많은 성장#

process-wide가 아닌 스케줄러의 비율 옵션이 있습니다. 총 할당량은 data-parallel 복제로 성장하며 각 주의 유형의 캐시 요구 사항을 포함합니다. process-wide 경계가 요구될 때 GiB 옵션을 사용하여 Furiosa-LLM의 나머지는 호스트 메모리를 소비합니다.
