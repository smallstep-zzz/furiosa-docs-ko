겹치기 기획#

겹치기 기획 (또한 비동기 스케줄링) NPU는 현재 배치를 실행하는 동안 CPU에 다음 배치를 준비합니다. 이것은 NPU가 스케줄 작업을 기다리고 있으며 출력 token (TPOT) 당 throughput 및 시간을 향상시킬 수 있습니다.

Tradeoff는 처음 token (TTFT)에 추가 시간입니다: 새로 도착 요청은 이미 준비된 배치에 가입할 수 없습니다. 대부분의 경우, 감소된 TPOT는 TTFT에서 모든 미터 측에 걸쳐 전반적인 개선 된 성능으로 인해 약간 증가한 TTFT를 위해 위로 만듭니다.

Overlap 스케줄링은 기본적으로 비활성화되며 지원된 text-generation 모델에 사용할 수 있습니다.

사용#

CLI#

서버를 시작할 때 overlap 스케줄링을 활성화하십시오:

furiosa-llm serve <model> --enable-overlap-scheduling

eager scheduling로 돌아 가기, 옵션 또는 명시적으로 비활성화 :

furiosa-llm serve <model> --no-enable-overlap-scheduling

Python API#

오프라인 세대의 경우, 스케줄링 루프를 통해 선택하십시오. SchedulerConfig:

from furiosa_llm import LLM
from furiosa_llm.metadata.config_types import SchedulerConfig, SchedulingLoop

with LLM(
    "furiosa-ai/Qwen3-8B-FP8",
    scheduler_config=SchedulerConfig(
        scheduling_loop_type=SchedulingLoop.OVERLAP,
    ),
) as llm:
    outputs = llm.generate([
        "Explain how a transformer generates text.",
        "Describe the difference between prefill and decode.",
    ])

Use SchedulingLoop.EAGER 기본적으로 루프를 선택하기 위해.

어떻게 작동 하는 것 입니까?#

기본 설정 열망 스케줄링 루프는 이전 배치의 결과를 처리 한 후 각 배치를 준비합니다. 이 순차적 의존도는 자연적이며, 다음 배치는 일반적으로 이전 배치의 지속적인 decode 요청에서 샘플 출력이 필요합니다.

그리고 겹치는 것 스케줄링, Furiosa-LLM는 어떤 활성 요청이 추가적인 decode 단계 또는 추가적인 prompt 청크를 필요로 할지 예측한 다음 요청을 선택하고 KV cache 블록을 할당하고 현재 배치가 NPU에서 실행되는 동안 다음 배치의 I/O 버퍼 및 작업을 준비합니다.

Eager scheduling:
CPU: [prepare A]             [prepare B]             [prepare C]
NPU:             [execute A]             [execute B]             [execute C]

Overlap scheduling:
CPU: [prepare A] [prepare B] [prepare C]
NPU:             [execute A] [execute B] [execute C]

이 다이어그램은 개념적이다; 결과 처리 및 동기화는 여전히 특정 경우에 시간이 걸릴 수 있습니다. 준비된 decode 배치를 파견하기 전에 Furiosa-LLM는 사전 처리 배치에서 실제 샘플 토큰을 채웁니다. 그것은 token 값을 추측하는 것보다 더 많은 요청 오염을 기대합니다.

그러나, 오버랩 스케줄링은 요청이 end-of-sequence (EOS) token를 생성하거나 클라이언트가 취소 될 때 추가 오버 헤드를 호출 할 수 있습니다. already-prepared 단계는 여전히 실행 될 수 있지만 출력이 무시됩니다.

언제 사용 해야 합니까?#

Overlap 스케줄링은 NPU 실행 사이의 시간의 의미있는 부분을 위해 CPU 배치 준비 계정이 가장 유용합니다. 지속 된 세대와 많은 decode 침략과 작업 부하는이 오버 헤드를 숨길 수있는 기회를 반복했습니다.

잠재적인 이점은 다음과 같습니다:

  • 더 높은 throughput: 일괄 처리 사이의 NPU idle 시간이 적은 경우 초당 출력 토큰의 수를 늘릴 수 있습니다.

  • 낮은 TPOT: scheduling gaps를 축소하면 생성된 토큰 사이에 평균 간격을 단축할 수 있습니다.

  • NPU의 더 나은 활용: CPU 준비 및 NPU 실행은 동시에 진행할 수 있습니다.

개선은 모델, 일괄 크기, prompt 및 출력 길이, 요청 도착 패턴 및 호스트 성능에 따라 다릅니다. 첫 번째 배치는 여전히 실행하기 전에 준비해야합니다. 짧은 세대는 NPU 계산에 의해 지배되는 몇 가지 기회를 가지고 더 적은 상대적 개선을 볼 수 있습니다. Overlap는 일부 CPU 작업을 숨깁니다. 그것은 그 작업이 더 빠르거나 개별 모델 패스를 만들지 않습니다.

Overlap 스케줄링은 throughput 및 TPOT가 TTFT에서 증가를 초과 할 때 유용한 최적화가 될 수 있습니다.

주의사항 및 호환성#

First-Token Latency#

준비된 배치는 새로 도착 요청 전에 파견됩니다 후속 스케줄 작업에 통합됩니다. 새로운 요청은 prompt가 처리되기 전에 추가 배치를 기다릴 수 있습니다. 이것은 throughput 및 TPOT가 개선 될 때 TTFT를 늘릴 수 있습니다.

추가 지연은 일괄 실행 시간 및로드에 따라 달라집니다. 그것은 밀리 초 또는 총 요청 latency에 상단 경계의 고정 번호가 아닙니다. 응용 프로그램은 빠른 첫 번째 응답을 우선하거나 엄격한 TTFT 대상을 가지고 있다면 예상 요청 부하에서 루프를 비교하십시오.

완료 후 작업 또는 취소#

스케줄러는 이미 준비하고 요청이 완료되거나 취소되었는지 배우게 될 때 다른 단계를 파견 할 수 있습니다. 그 단계는 NPU compute 및 임시 KV cache 공간을 출력하는 것이 허용되지 않는 경우에도 사용할 수 있습니다. Furiosa-LLM는 in-flight 작업이 완료된 후 추가 쓰기 블록을 해제합니다. 이 오버 헤드는 매우 짧은 출력 또는 빈번한 취소로 작업 부하에 대한 이점을 줄일 수 있습니다.

성능 평가#

동일한 모델의 artifact, 장치 구성, concurrency, prompt 및 출력 길이 및 sampling 설정을 사용하여 eager 및 overlap 스케줄링을 비교하십시오. 각 구성을 따뜻하게하고 prefix-cache 조건을 준수하십시오.

throughput와 latency 둘 다 측정:

  • 초당 출력 토큰 수 서비스 용량을 평가하는 데 사용됩니다.

  • TPOT 또는 inter-token 지연 시간 스트리밍 생성 속도를 평가합니다.

  • TTFT, 포함: 꼬리 퍼센트일, 새로운 요구에 비용을 검사하기 위하여.

  • End-to-end의 요청 지연 완전한 사용자 경험을 평가하기 위해.

짧은 긴 요청과 생산 예상 도착률의 혼합을 포함. throughput 또는 generation-speed 개선이 유용하고 first-token latency가 응용 프로그램의 대상 내에서 남아 프리퍼 오버랩 스케줄링. 서버 로그 Overlap scheduler has started 이 루프가 시작될 때, 설정을 확인하는 메시지가 효력을 발생했습니다.
