겹치는 스케줄링 (Overlap Scheduling)#

겹치는 스케줄링 (동시 스케줄링)은 CPU에서 다음 배치 준비를 시작하는 동시에, NPU가 현재 배치를 실행합니다. 이를 통해 NPU가 스케줄링 작업 대기 시간을 줄여 처리량과 1개 토큰당 시간 (TPOT)을 개선할 수 있습니다.

이러한 경우, 첫 번째 토큰 생성 시간 (TTFT)이 증가합니다. 새로운 요청은 이미 준비된 배치에 참여할 수 없습니다. 대부분의 경우, 감소된 TPOT이 약간 증가된 TTFT를 상쇄하여, TTFT를 제외한 모든 지표에서 전반적인 성능이 향상됩니다.

겹치는 스케줄링은 기본적으로 비활성화되어 있으며, 지원되는 텍스트 생성 모델에 대해 활성화할 수 있습니다. (기본적으로 겹치는 스케줄링이 비활성화되어 있으며, 특정 텍스트 생성 모델에 대해 활성화할 수 있습니다.)

사용법#

CLI (명령줄 인터페이스)#

서버를 시작할 때 겹치는 스케줄링을 활성화합니다:

furiosa-llm serve <model> --enable-overlap-scheduling

즉시 스케줄링으로 돌아가려면 옵션을 생략하거나 명시적으로 비활성화합니다:

furiosa-llm serve <model> --no-enable-overlap-scheduling

Python API#

오프라인 생성의 경우, SchedulerConfig를 통해 스케줄링 루프를 선택합니다.

from furiosa_llm import LLM
from furiosa_llm.metadata.config_types import SchedulerConfig, SchedulingLoop

with LLM(
    "furiosa-ai/Qwen3-8B-FP8",
    scheduler_config=SchedulerConfig(
        scheduling_loop_type=SchedulingLoop.OVERLAP,
    ),
) as llm:
    outputs = llm.generate([
        "Explain how a transformer generates text.",
        "Describe the difference between prefill and decode.",
    ])

기본 루프를 명시적으로 선택하려면 SchedulingLoop.EAGER를 사용합니다.

작동 방식#

기본적인 즉시 실행 스케줄링 루프는 이전 배치 처리 결과가 완료된 후 다음 배치를 준비합니다. 이러한 순차적인 의존성은 자연스럽습니다. 왜냐하면 다음 배치는 일반적으로 이전 배치의 진행 중인 디코딩 요청에서 샘플링된 출력을 필요로 하기 때문입니다.

오버랩 스케줄링을 사용하면 Furiosa-LLM은 어떤 활성 요청이 추가적인 디코딩 단계 또는 추가적인 프롬프트 조각을 필요로 할지 예측하고, 요청을 선택하고, KV 캐시 블록을 할당하고, 현재 배치가 NPU에서 실행되는 동안 다음 배치의 I/O 버퍼와 작업을 준비합니다.

Eager scheduling:
CPU: [prepare A]             [prepare B]             [prepare C]
NPU:             [execute A]             [execute B]             [execute C]

Overlap scheduling:
CPU: [prepare A] [prepare B] [prepare C]
NPU:             [execute A] [execute B] [execute C]

이 다이어그램은 개념적인 것이며, 결과 처리 및 동기화에는 여전히 시간이 소요될 수 있습니다. 준비된 디코딩 배치를 전송하기 전에, Furiosa-LLM은 이전 배치의 실제 샘플링된 토큰을 채웁니다. 토큰 값을 추측하는 대신, 요청의 지속성을 예측합니다.

그러나 오버랩 스케줄링은 요청이 시퀀스 종료 (EOS) 토큰을 생성하거나 클라이언트에서 취소될 때 추가적인 오버헤드를 발생시킬 수 있습니다. 이미 준비된 단계는 실행될 수 있지만, 그 출력은 버려집니다.

언제 사용하면 좋을까요?#

오버랩 스케줄링은 CPU 배치 준비가 NPU 실행 사이의 의미 있는 시간을 차지하는 워크로드에서 가장 유용합니다. 지속적인 생성 및 많은 디코딩 반복을 갖는 워크로드에는 이 오버헤드를 숨기는 여러 번의 기회가 있습니다.

잠재적인 이점은 다음과 같습니다:

  • 더 높은 처리량: 배치 간의 NPU 비활성 시간을 줄이면 초당 생성되는 출력 토큰 수가 증가할 수 있습니다.

  • 낮은 평균 토큰 생성 시간 (TPOT): 스케줄링 간격을 줄이면 생성된 토큰 간의 평균 간격이 짧아집니다.

  • 더 나은 NPU 활용률: CPU 준비와 NPU 실행을 동시에 수행하여 효율성을 높일 수 있습니다.

이러한 개선 효과는 모델, 배치 크기, 프롬프트, 출력 길이, 요청 도착 패턴, 호스트 성능에 따라 달라집니다. 첫 번째 배치는 실행되기 전에 준비되어야 합니다. 짧은 생성은 이 효과를 얻을 기회가 적고, NPU 연산에 집중된 워크로드에서는 상대적인 개선 효과가 더 작을 수 있습니다. 겹치는 스케줄링은 일부 CPU 작업을 숨깁니다. 이는 CPU 작업을 제거하거나 개별 모델의 순차적인 연산을 더 빠르게 하는 것이 아닙니다.

겹치는 스케줄링은 TTFT 증가와 비교하여 처리량 및 TPOT 측면에서 이점을 제공할 때 유용한 최적화가 될 수 있습니다.

주의사항 및 호환성#

첫 번째 토큰 지연 시간#

준비된 배치(batch)가 새롭게 도착한 요청(request)이 다음 스케줄링 작업에 통합되기 전에 먼저 전송됩니다. 따라서 새로운 요청은 응답을 처리하기 전에 추가적인 배치(batch)를 기다려야 할 수 있으며, 이는 처리량(throughput)과 총 처리 시간(TPOT)이 향상되더라도 TTFT(첫 번째 토큰 지연 시간)를 증가시킬 수 있습니다.

추가적인 지연 시간은 배치 실행 시간과 부하에 따라 달라지며, 이는 고정된 밀리초 또는 전체 요청 지연 시간의 상한이 아닙니다. 애플리케이션이 빠른 첫 번째 응답을 우선시하거나 엄격한 TTFT 목표를 가지고 있다면, 예상되는 요청 부하 하에서 두 가지 루프를 비교하여 성능을 평가해야 합니다.

완료 또는 취소 후 작업#

스케줄러가 요청이 완료되거나 취소되었음을 알게 되면 이미 다른 단계를 준비하고 전송했을 수 있습니다. 이 단계는 NPU 컴퓨팅 및 임시 KV 캐시 공간을 소비할 수 있으며, 결과는 버려지더라도 그렇습니다. Furiosa-LLM은 실행 중인 작업이 완료된 후 추가적인 쓰기 블록을 해제합니다. 이 오버헤드는 매우 짧은 출력 또는 빈번한 취소로 인해 발생하는 워크로드의 경우 이득을 감소시킬 수 있습니다.

임베딩 및 재랭킹 모델 풀링

지원되지 않음. 이러한 모델에는 디코딩 단계가 없으므로 엔진 시작에 실패합니다. (Decoding phase)

NPU 프리픽스 캐시 (L1)

지원. Overlap 스케줄링은 비활성화가 필요하지 않습니다. Prefix Caching.

호스트 KV 캐시 (L2)

구성된 경우 지원됩니다. 계층적 프리픽스 캐싱 참조.

레이어별 L2-L1 재로드

별도의 실험 재로드 옵션과 호스트 캐시 예산에 지원. 참조 모델 실행을 통한 L2 재로드.

실험적 NPU 샘플링

호환 모델 및 FXB 지원. 참조 실험적인 NPU 샘플링.

실험적 추론 예측

지원되지 않습니다. 즉시 실행(eager) 스케줄링을 사용하십시오.

원격 KV 캐시 (L3, Mooncake)

오버랩 스케줄러가 시작될 때, 설정되어 있더라도 비활성화됩니다. 원격 캐시 재사용에 의존하는 워크로드는 즉시 실행(eager) 스케줄링을 사용하십시오.

npu_queue_limit / --npu-queue-limit

기본값인 1으로 유지해야 합니다. 오버랩 스케줄링은 더 큰 NPU 실행 큐를 필요로 하지 않고, CPU 작업을 미리 준비합니다.

지원되지 않는 모델 또는 디코딩 구성의 경우, --no-enable-overlap-scheduling 또는 SchedulingLoop.EAGER으로 재시작하십시오.

성능 평가#

동일한 모델 아티팩트, 장치 구성, 동시성, 프롬프트 및 출력 길이, 샘플링 설정을 사용하여 즉시 실행(eager) 방식과 겹침(overlap) 방식을 비교합니다. 각 구성에 대해 워밍업을 수행하고, 프리픽스 캐시 조건을 동일하게 유지합니다.

처리량과 지연 시간을 모두 측정합니다:

  • 토큰당 초당 처리량을 측정하여 서비스 용량을 평가합니다.

  • TPOT 또는 토큰 간 지연 시간을 측정하여 스트리밍 생성 속도를 평가합니다.

  • TTFT (Tail Percentile 포함)를 측정하여 새로운 요청에 대한 비용을 확인합니다.

  • 전체 요청 지연 시간을 측정하여 완전한 사용자 경험을 평가합니다.

짧고 긴 요청을 모두 포함하고, 실제 환경에서 예상되는 도착률을 고려합니다. 처리량 또는 생성 속도 향상이 유용하고, 첫 번째 토큰 지연 시간이 애플리케이션의 목표 범위 내에 있도록, 중첩 스케줄링을 선호합니다. 서버 로그에 "Overlap scheduler has started" 메시지가 나타나면, 해당 설정이 적용되었음을 확인할 수 있습니다.
