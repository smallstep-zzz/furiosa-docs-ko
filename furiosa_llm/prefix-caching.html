Prefix Caching#

Prefix caching는 이전에 일반적인 prompt 접두사를 위한 KV cache 입장을 계산한 성과 최적화 기술입니다. 이것은 latency를 크게 감소시키고 동일한 prompt 시작을 공유하는 요구를 위한 계산비를 계산합니다.

개요#

유사한 접두사 (e.g., 시스템 프롬프트, 일반적인 지침, 또는 공유 컨텍스트)와 여러 요청을 처리 할 때 prefix caching는 중복 계산을 제거 :

  1. 저장 KV cache 항목 이전 계산

  2. 일치하는 캐시된 프리픽스와의 새로운 프롬프트 사용

  3. 재사용 관련 캐시 항목 대신 recomputing 그들

  4. 컴퓨터 non-cached의 prompt의 non-cached 부분만

이 시나리오에 대한 성능을 극적으로 향상시킬 수 있습니다 :

  • 여러 사용자 쿼리에 걸쳐 반복된 시스템 프롬프트

  • 일반적인 명령어 템플릿

  • multi-turn 대화에 대한 공유 대화 역사

  • Document-based 질문은 문서 접두사가 일정한 곳에 응답합니다

어떻게 작동 하는 것 입니까?#

자동 관리#

접두사 캐시는 스케줄러에 의해 자동으로 관리됩니다.

  • 캐시 인구: KV cache 항목은 각 전달 패스 후 저장됩니다.

  • 캐시 일치: 새로운 요청은 캐시 트리에 대해 확인됩니다.

  • 캐시 삭제: 최근에 사용 된 Least, non-active 항목은 메모리가 필요할 때 evicted (잎 스프록스에서 시작)

  • 캐시 비효율: 수동으로 유효성 검사를 수행할 필요 없음

Token-레벨 매칭#

Furiosa-LLM의 prefix caching는 token 레벨에서 작동하며 효율적인 접두사 매칭을위한 Radx 나무 데이터 구조를 사용합니다.

Request 1: [S1] + [A]
       │
       │    ┌──────────────┐   ┌──────────────┐
       └──► │ new compute  │ + │ new compute  │
            └──────────────┘   └──────────────┘
       Cache: ROOT ── [S1] ── [A]

Request 2: [S1] + [B]
       │
       │    ┌──────────────┐   ┌──────────────┐
       └──► │  cache hit   │ + │ new compute  │
            └──────────────┘   └──────────────┘
       Cache: ROOT ── [S1] ──┬── [A]
                             └── [B]

표준 radix-cache 흐름 (non-hybrid 관심)에서, Furiosa-LLM:

  • 이 가장 긴 token와 일치하는 접두사 prompt 시작부터

  • 그 접두사에서 모든 일치 KV 블록을 재사용

  • Computes 및 캐시 만 일치 suffix

기존 지점의 중간에 있는 요청이 있는 경우, 캐시는 내부적으로 분기를 나타낼 수 있으므로 향후 요청은 여전히 공유 부분을 정확하게 재사용할 수 있습니다.

하이브리드 어텐션 모델#

Prefix caching는 완전히 세계적인 주의와 sliding-window 주의 둘 다를 사용하는 잡종 주의 모델을 지원합니다. 이 모형을 위해, 접두사는 동일한 일치한 범위를 위해 유효합니다 두 캐시 유형 둘 다 유효할 때 재사용할 수 있습니다:

  • prompt의 시작부터 토큰 일치

  • Global KV cache 항목은 해당 범위에 대한 존재입니다.

  • Sliding-window KV 항목은 현재 위치에 대한 유효한 연속 창으로 유효합니다

token 경기가 계속되더라도 sliding-window 필요조건은 더 이상 만족하지 않습니다, Furiosa-LLM는 가장 긴 안전한 접두사만 재사용하고 나머지를 따릅니다. 이것은 아직도 재사용을 극화하는 동안 결과를 정확한 유지합니다.

연습에서 하이브리드 모델에서 캐시가 짧은 경우 token 오버랩, 특히 recent-window 컨텍스트가 요청에 따라 다르거나 evicted되었습니다.

이러한 동작은 또한 이탈 정책에 영향을 받습니다. 슬라이딩 윈도우 어텐션의 경우, Furiosa-LLM는 전역 블록과 독립적으로 슬라이딩 윈도우 블록이 이탈되도록 의도적으로 허용합니다. 여기에는 중간 (비 잎) 접두사 트리 노드도 포함됩니다. 그 이유는 메모리 효율성 때문입니다. 자주 재사용되는 윈도우 외부의 블록은 오래된 것으로 간주되며 더 유용한 캐시 콘텐츠를 위한 공간을 확보하기 위해 더 일찍 회수할 수 있습니다. 그러나 높은 메모리 압력 하에서는 token-접두사 일치가 더 빨리 종료되는 동안에도 계속될 수 있습니다. 이 경우 Furiosa-LLM는 여전히 유효한 윈도우를 가진 가장 긴 접두사를 안전하게 재사용합니다.

성능상의 이점#

Latency 감소#

Prefix caching는 뜻깊은 latency 개선을 제공할 수 있습니다:

  • 50-90% 감소 time-to-first-token (TTFT)에서 긴 공유 접두사로 요청에 대한

  • 비례적 개선 일치된 접두사의 길이에 따라

  • 영향은 없습니다 생성 품질 또는 정확도를 비교합니다.

예제 시나리오#

시나리오: 1 – 시스템 Prompt 재사용

system_prompt = "You are a helpful assistant specialized in Python programming..."  # 200 tokens

# First request: Full computation
response1 = llm.generate([
    {"role": "system", "content": system_prompt},
    {"role": "user", "content": "How do I read a file?"}
])  # Computes all 200 + N tokens

# Second request: Only user message computed
response2 = llm.generate([
    {"role": "system", "content": system_prompt},
    {"role": "user", "content": "How do I write to a file?"}
])  # Reuses 200 cached tokens, computes only new N tokens

시나리오 2: 문서 품질 보증

long_document = "..."  # 2000 tokens

# Multiple questions about the same document
for question in questions:
    response = llm.generate([
        {"role": "system", "content": f"Answer based on: {long_document}"},
        {"role": "user", "content": question}
    ])  # Document prefix cached after first query

Throughput 영향#

요구에 의하여 계산을 감소시키십시오:

  • 더 높은 throughput 공유 프리픽스를 사용하는 워크로드에 대해

  • 자원 활용 개선 같은 compute에 더 많은 요청을 제공함으로써

  • 메모리 대역폭 감소 사용

구성#

Prefix caching 기본 설정으로 설정 Furiosa-LLM에서 유익한 자연으로 인해. 그러나 특정 벤치 마크 시나리오에서, 그것은 캐시 효과없이 더 일관성있는 성능 측정을 생성하는 데 바람직 할 수있다. 이러한 경우, prefix caching를 비활성화, 설정 --no-enable-prefix-caching Furiosa-LLM 서버 설정 옵션:

furiosa-llm serve --no-enable-prefix-caching ...

메모리 관리#

접두사 캐시는 KV cache 풀과 메모리를 공유합니다. 스케줄러는 자동으로:

  • 사용 가능한 KV cache 메모리에서 캐시 항목 할당

  • 메모리 압력 증가 때 Evicts 캐시 된 접두사

캐쉬 크기 또는 eviction 정책의 수동 조정은 필요하지 않습니다.

호스트 메모리에 재사용 가능한 접두사를 유지하려면 NPU 캐시를 남겨주고, 계층적 Prefix Caching.

가장 좋은 방법#

캐시 히트 최대화#

prefix caching의 가장 혜택을 얻으려면:

  1. 일관된 시스템 프롬프트를 사용하십시오: 요청을 통한 시스템의 신속한 대응

  2. token와 정확히 일치하도록 유지: 작은 변화도 (punctuation, whitespace)는 경기를 깰

  3. 메시지를 일관성 있게 보내십시오.: prompt 시퀀스의 시작부터 캐시 일치

예시 - 일관된 프롬프트 사용:

# Good: Exact same system prompt
system_prompt = "You are a helpful AI assistant."

response1 = llm.generate([{"role": "system", "content": system_prompt}, ...])
response2 = llm.generate([{"role": "system", "content": system_prompt}, ...])
# ✓ Cache hit

# Bad: Slightly different prompts
response3 = llm.generate([{"role": "system", "content": "You are a helpful AI assistant."}, ...])
response4 = llm.generate([{"role": "system", "content": "You are a helpful assistant."}, ...])
# ✗ Cache miss due to difference

모니터링#

prefix caching 효율성을 모니터링하려면 다음을 참조하십시오.

  • 프리픽스 캐시 히트 비율: 높은 비율은 캐시된 접두사의 더 나은 재사용을 나타냅니다. 서버 로그에서 이것을 찾을 수 있습니다.

  • Time-to-First-Token (TTFT): 캐시된 접두사 요청을 감소해야 합니다.

  • 지연 패턴 요청: 유사한 프롬프트를 따르는 요청은 일관된 speedups를 표시해야 합니다.
