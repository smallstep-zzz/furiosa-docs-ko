접두사 캐싱#

접두사 캐싱은 이전 계산된 KV 캐시 항목을 일반 프롬프트 접두사에 재사용하여 성능을 최적화하는 기술입니다. 동일한 프롬프트 시작을 공유하는 요청의 경우, 이는 지연 시간을 크게 줄이고 계산 비용을 절감합니다.

개요#

유사한 접두사를 가진 여러 요청을 처리할 때 (예: 시스템 프롬프트, 일반적인 지침 또는 공유 컨텍스트), 접두사 캐싱은 중복 계산을 제거하여 다음을 수행합니다.

  1. 이전 계산에서 KV 캐시 항목을 저장

  2. 새 프롬프트와 캐시된 접두사를 일치

  3. 일치하는 캐시 항목을 재계산하는 대신 재사용

  4. 프롬프트의 캐시되지 않은 부분만 계산

이는 다음 시나리오에서 성능을 크게 향상시킬 수 있습니다:

  • 여러 사용자 쿼리에서 반복적으로 사용되는 시스템 프롬프트

  • 일반적인 명령어 템플릿

  • 다중 턴 대화에서 공유되는 대화 기록

  • 문서 기반 질문 응답 시스템, 여기서 문서 접두사는 일관됨

작동 방식#

자동 관리#

접두사 캐시는 스케줄러에 의해 자동으로 관리됩니다:

  • 캐시 채우기: 각 순방향 통과 후 KV 캐시 항목이 저장됩니다

  • 캐시 일치: 새로운 요청은 캐시 트리와 비교됩니다

  • 캐시 제거: 메모리가 필요할 때, 가장 최근에 사용되지 않은, 비활성 항목이 제거됩니다 (리프 접미사부터 시작)

  • 캐시 무효화: 수동 무효화 불필요

토큰 수준 일치#

Furiosa-LLM의 토큰 수준 사전 캐싱은 효율적인 토큰 사전 일치에 사용되는 래디스 트리 데이터 구조를 사용하여 작동합니다:

Request 1: [S1] + [A]
       │
       │    ┌──────────────┐   ┌──────────────┐
       └──► │ new compute  │ + │ new compute  │
            └──────────────┘   └──────────────┘
       Cache: ROOT ── [S1] ── [A]

Request 2: [S1] + [B]
       │
       │    ┌──────────────┐   ┌──────────────┐
       └──► │  cache hit   │ + │ new compute  │
            └──────────────┘   └──────────────┘
       Cache: ROOT ── [S1] ──┬── [A]
                             └── [B]

표준 래디스 캐시 흐름(하이브리드 어텐션이 아닌 경우)에서 Furiosa-LLM은:

  • 프롬프트의 시작 부분에서 가장 긴 토큰 정확한 접두사를 찾습니다.

  • 해당 접두사에서 일치하는 모든 KV 블록을 재사용합니다.

  • 일치하지 않는 접미사를 계산하고 캐싱만 수행

요청이 기존 분기를 중간에 분기되는 경우, 캐시는 내부적으로 해당 분기를 분리하여, 향후 요청이 공유된 부분을 정확하게 재사용할 수 있도록 합니다.

하이브리드 어텐션 모델#

프리픽스 캐싱은 글로벌 어텐션과 슬라이딩 윈도우 어텐션을 모두 사용하는 하이브리드 어텐션 모델을 완전히 지원합니다. 이러한 모델의 경우, 프리픽스는 캐시 유형이 동일한 일치 범위 내에서 유효한 경우에만 재사용됩니다:

  • 토큰은 프롬프트의 시작 부분에서 일치

  • 해당 범위에 대한 글로벌 KV 캐시 항목이 존재

  • 슬라이딩 윈도우 KV 항목은 현재 위치에 대해 유효한 연속적인 윈도우로 제공됩니다.

토큰 일치성이 유지되지만 슬라이딩 윈도우 요구 사항이 더 이상 충족되지 않으면, Furiosa-LLM은 가장 안전한 가장 긴 접두사를 재사용하고 나머지 부분은 계산합니다. 이를 통해 결과의 정확성을 유지하면서 재사용을 극대화합니다.

실제로는, 하이브리드 모델에서 캐시 히트가 원시 토큰 오버랩보다 짧을 수 있으며, 특히 최근 윈도우 컨텍스트가 요청 간에 다를 경우 또는 제거된 경우에 그렇습니다.

이러한 동작은 제거 정책에 의해 영향을 받습니다. 슬라이딩 윈도우 어텐션의 경우, Furiosa-LLM은 슬라이딩 윈도우 블록이 전역 블록과 독립적으로 제거되도록 의도적으로 허용합니다. 여기에는 중간 (비 잎) 접두사 트리 노드에서도 포함됩니다. 그 이유는 메모리 효율성 때문입니다. 자주 사용되는 윈도우 외부의 블록은 오래된 것으로 간주되어 더 유용한 캐시 콘텐츠를 위해 더 빨리 확보할 수 있습니다. 그러나 메모리 압박이 높을 경우, 토큰-접두사 일치성이 유지되는 동안 슬라이딩 윈도우 유효성이 더 빨리 종료될 수 있습니다. 이 경우 Furiosa-LLM은 여전히 유효한 윈도우를 가진 가장 긴 접두사를 안전하게 재사용합니다.

성능상의 이점#

지연 시간 감소#

프리픽스 캐싱은 상당한 지연 시간 개선을 제공할 수 있습니다:

  • 긴 공유 프리픽스를 사용하는 요청의 첫 번째 토큰 생성 시간 (TTFT)을 50-90% 단축

  • 일치하는 프리픽스의 길이에 비례하여 개선 효과가 발생

  • 생성 품질 또는 정확성에 영향을 미치지 않음

예시 시나리오#

시나리오 1: 시스템 프롬프트 재사용

system_prompt = "You are a helpful assistant specialized in Python programming..."  # 200 tokens

# First request: Full computation
response1 = llm.generate([
    {"role": "system", "content": system_prompt},
    {"role": "user", "content": "How do I read a file?"}
])  # Computes all 200 + N tokens

# Second request: Only user message computed
response2 = llm.generate([
    {"role": "system", "content": system_prompt},
    {"role": "user", "content": "How do I write to a file?"}
])  # Reuses 200 cached tokens, computes only new N tokens

시나리오 2: 문서 QA

long_document = "..."  # 2000 tokens

# Multiple questions about the same document
for question in questions:
    response = llm.generate([
        {"role": "system", "content": f"Answer based on: {long_document}"},
        {"role": "user", "content": question}
    ])  # Document prefix cached after first query

처리량에 미치는 영향#

요청당 계산량 감소를 통해:

  • 공유 접두사를 사용하는 워크로드에 더 높은 처리량

  • 동일한 컴퓨팅 자원을 사용하여 더 많은 요청을 처리하여 리소스 활용도 향상

  • 메모리 대역폭 사용량 감소

구성#

Furiosa-LLM은 기본적으로 프리픽스 캐싱을 활성화합니다. 이는 일반적으로 유용하지만, 특정 벤치마크 시나리오에서는 캐싱 효과를 제거하여 보다 일관된 성능 측정값을 얻기 위해 비활성화하는 것이 좋습니다. 이 경우, 프리픽스 캐싱을 비활성화하려면 Furiosa-LLM 서버 설정에서 --no-enable-prefix-caching 옵션을 설정합니다:

furiosa-llm serve --no-enable-prefix-caching ...

메모리 관리#

프리픽스 캐시는 KV 캐시 풀과 동일한 메모리를 공유합니다. 스케줄러는 자동으로 다음 작업을 수행합니다:

  • 사용 가능한 KV 캐시 메모리에서 캐시 항목을 할당합니다.

  • 메모리 사용량이 증가하면 캐시된 프리픽스를 제거합니다.

캐시 크기 또는 제거 정책에 대한 수동 튜닝이 필요하지 않습니다.

호스트 메모리에 NPU 캐시에서 빠져나간 재사용 가능한 프리픽스를 유지하려면, 계층적 프리픽스 캐싱을 참조하십시오. (Hierarchical Prefix Caching)

최적 사용법#

캐시 히트율 극대화#

프리픽스 캐싱을 최대한 활용하려면:

  1. 일관된 시스템 프롬프트를 사용하십시오: 모든 요청에서 시스템 프롬프트를 동일하게 유지하십시오.

  2. 토큰 정확한 일치 유지: 작은 변경 사항 (구두점, 공백)도 일치를 깨뜨립니다.

  3. 메시지 순서를 일관되게 유지하십시오: 캐시는 프롬프트 시퀀스의 시작 부분부터 일치합니다.

일관성 있는 프롬프트 사용 예시:

# Good: Exact same system prompt
system_prompt = "You are a helpful AI assistant."

response1 = llm.generate([{"role": "system", "content": system_prompt}, ...])
response2 = llm.generate([{"role": "system", "content": system_prompt}, ...])
# ✓ Cache hit

# Bad: Slightly different prompts
response3 = llm.generate([{"role": "system", "content": "You are a helpful AI assistant."}, ...])
response4 = llm.generate([{"role": "system", "content": "You are a helpful assistant."}, ...])
# ✗ Cache miss due to difference

모니터링#

프롬프트 캐싱 효과를 모니터링하려면 다음 사항을 확인하십시오:

  • 프롬프트 캐시 히트 비율: 높은 비율은 캐시된 프롬프트의 효과적인 재사용을 나타냅니다. 서버 로그에서 확인할 수 있습니다.

  • 첫 번째 토큰 생성 시간 (TTFT): 캐시된 프롬프트가 있는 요청의 경우 감소해야 합니다.

  • 유사한 프롬프트에 대한 요청의 지연 시간 패턴: 유사한 프롬프트에 대한 요청은 일관된 속도 향상을 보여야 합니다.
