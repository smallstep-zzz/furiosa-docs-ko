비전-언어 모델#

Furiosa-LLM은 OpenAI 호환 Chat Completions API 및 Responses API를 통해 텍스트와 이미지를 입력으로 받는 비전-언어 (VL) 모델을 제공합니다. 현재 지원되는 첫 번째 아키텍처는 Qwen3-VL (예: Qwen/Qwen3-VL-32B-Instruct)입니다. 자세한 내용은 "지원되는 모델"을 참조하십시오.

이미지 입력은 리모트로 통과될지도 모릅니다 https:// URL, 베이스64 data: URL, 또는 지역 file:// 경로. 사전 처리 (저장, 패치, prompt-token 확장)는 Hugging Face에 의해 처리됩니다 AutoProcessor 모델에 기본적으로 포함된 구성품.

참고

비디오 입력은 현재 지원되지 않습니다. Furiosa SDK 2026.5.0에서 지원될 예정입니다.

빠른 시작#

FXB와 호환되는 비전-언어 모델을 포함하는 서버를 시작하십시오:

furiosa-llm serve furiosa-ai/Qwen3-VL-32B-Instruct

이미지와 텍스트 프롬프트를 사용하여 챗 컴플리션 요청을 보내기:

curl http://localhost:8000/v1/chat/completions \
    -H "Content-Type: application/json" \
    -d '{
    "model": "Qwen/Qwen3-VL-32B-Instruct",
    "messages": [
        {
            "role": "user",
            "content": [
                {
                    "type": "image_url",
                    "image_url": {
                        "url": "https://developer.furiosa.ai/latest/en/_images/Furiosa_RNGD_image.png"
                    }
                },
                {"type": "text", "text": "Describe this image in one short sentence."}
            ]
        }
    ],
    "max_tokens": 128
    }' \
    | python -m json.tool

(Python 클라이언트 예제는 아래의 Python 예제 섹션을 참조하세요).

이미지 입력 형식#

chat-completion 메시지의 image_url.url 필드는 다음 URL 스킴을 지원합니다:

  1. 원격 URL (http:// / https://) — 서버는 httpx를 사용하여 이미지를 가져옵니다.

    {
  "type": "image_url",
  "image_url": {"url": "https://example.com/photo.png"}
}

  2. Base64 데이터 URL — 인라인 페이로드에 유용합니다:

    {
  "type": "image_url",
  "image_url": {"url": "data:image/png;base64,iVBORw0KGgoAAAANSUh..."}
}

  3. 로컬 파일 (file://) — 기본적으로 비활성화되어 있습니다. --allowed-local-media-path 서버 플래그가 필요합니다 (아래 참조).

    {
  "type": "image_url",
  "image_url": {"url": "file:///srv/media/photo.png"}
}

요청에는 여러 image_url 는 text 부품. 모델의 채팅 템플릿은 이미지 홀더가 prompt로 렌더링되는 방법을 제어합니다.

  • OpenAI 형식의 채팅 템플릿 (일반적인 경우) 반복합니다. content 자체적으로, 그래서 이미지 placeholders 토지는 원래 위치에 자동으로 - 추가 서버 플래그가 필요하지 않습니다.

  • String-format 템플릿 납작한 content 단일 텍스트 문자열로. 기본적으로, 어떤 이미지에 대한 위주자는 prompt에 prepended; 패스 --interleave-mm-strings 대신 자신의 원래 위치에 보관하십시오.

서버 옵션#

다음 furiosa-llm serve 플래그는 멀티모달 동작을 구성합니다. 이러한 규칙을 위반하는 요청은 NPU에 도달하기 전에 HTTP 400 오류로 거부됩니다.

플래그

기본값

설명

--image-limit-per-prompt N

무제한

요청당 생성 가능한 이미지의 최대 개수. 이 제한을 초과하면 HTTP 400 오류가 반환됩니다.

--video-limit-per-prompt N

무제한

요청당 생성 가능한 비디오의 최대 개수. 현재 비디오 입력은 지원되지 않으므로 (위의 참고 사항 참조), 이 플래그는 현재 아무런 효과가 없습니다.

--allowed-local-media-path PATH

비활성화

허락해 file:// 해결된 경로가 아래에 있는 URL PATH. 지역 이미지를 봉사하는 필요; 다른 사람 file:// URL는 거부됩니다.

--allowed-media-domains D [D …]

모든 허용된 도메인

SSRF 보호를 위한 원격 도메인 목록입니다. 설정되면, 목록에 있는 도메인에서만 이미지를 가져오며, 나머지는 HTTP 400 오류를 반환합니다.

--interleave-mm-strings (병렬 처리)

off (끄기)

상단의 이미지 입력 형식 참조. OpenAI 형식의 일반적인 챗 템플릿에는 영향을 미치지 않습니다.

--mm-processor-cache-gb GB (멀티모달 프로세서 캐시 크기)

4.0

멀티모달 전처리 캐시의 크기를 GiB 단위로 설정합니다. 0으로 설정하면 전처리 캐싱을 비활성화합니다. 인코딩된 임베딩은 여전히 재사용할 수 있습니다. UUID를 사용하여 멀티모달 입력 캐싱에 대한 자세한 내용은 "UUID를 사용하여 멀티모달 입력 캐싱" 참조.

--media-io-kwargs JSON (미디어 I/O 매개변수)

{}

기본 이미지 가져오기 옵션, 모달리티별로 지정. 멀티모달 옵션에서 타임아웃 및 요청 오버라이드를 참조하세요.

--mm-processor-kwargs JSON

{}

선택적으로 images_kwargs를 포함한 프로세서 기본 설정. 멀티모달 옵션에서 모델별 제어 및 요청 오버라이드를 참조하세요.

여러 허용된 도메인(nargs="+")을 사용하는 예시:

furiosa-llm serve Qwen/Qwen3-VL-32B-Instruct \
    --fxb /path/to/qwen3-vl-32b.fxb \
    --allowed-media-domains developer.furiosa.ai cdn.example.com

경고

--allowed-local-media-path가 설정되지 않은 경우, 로컬 파일 접근(file://)은 비활성화됩니다. 이를 보안 경계로 사용하세요. 채팅 완료 클라이언트에 노출할 의사가 있는 디렉토리만 지정해야 합니다.

팁

공용 인터넷에서 가져오는 경우(예: 프로덕션 배포), SSRF 및 대역폭 증폭 위험을 줄이기 위해 --allowed-media-domains를 가장 작은 세트로 제한하세요.

다중 모달 옵션#

media_io_kwargs 사용 image 객체 mm_processor_kwargs 프로세서 옵션 및 옵션 허용 images_kwargs. videos_kwargs and audio_kwargs 현재는 이미지 처리가 지원되기 때문에 거부됩니다. CLI와 서버 기본값을 설정하십시오:

furiosa-llm serve furiosa-ai/Qwen3-VL-32B-Instruct \
    --media-io-kwargs '{"image": {"timeout": 10}}' \
    --mm-processor-kwargs '{"min_pixels": 1024}'

챗 컴플리트 및 응답: JSON 요청 본문에 media_io_kwargs 및 mm_processor_kwargs를 사용하여 이러한 기본 설정을 덮어쓸 수 있습니다. OpenAI Python 클라이언트를 사용하여, extra_body를 통해 이러한 필드를 전달합니다.

import os
from openai import OpenAI

client = OpenAI(
    base_url=os.getenv("OPENAI_BASE_URL", "http://localhost:8000/v1"),
    api_key=os.getenv("OPENAI_API_KEY", "EMPTY"),
)
response = client.chat.completions.create(
    model=client.models.list().data[0].id,
    messages=[{
        "role": "user",
        "content": [
            {"type": "image_url", "image_url": {
                "url": "https://developer.furiosa.ai/latest/en/_images/Furiosa_RNGD_image.png"
            }},
            {"type": "text", "text": "Describe this image."},
        ],
    }],
    max_completion_tokens=32,
    extra_body={
        "media_io_kwargs": {"image": {"timeout": 5}},
        "mm_processor_kwargs": {"min_pixels": 4096},
    },
)
print(response.choices[0].message.content)

이러한 덮어쓰기는 해당 요청에만 적용되며 서버 기본 설정을 변경하지 않습니다. 두 개의 딕셔너리를 생략하거나, null로 설정하거나, {}를 전달하면 기본 설정을 유지합니다. 두 딕셔너리는 서로 다른 병합 규칙을 가지며, 아래에 설명되어 있습니다.

이미지 가져오기 옵션#

요청 옵션 키는 각 모달리티 내에서 기본 설정을 덮어씁니다. {"image": {}}를 전달하면 기본 이미지 가져오기 옵션이 유지됩니다.

다음 가져오기 옵션을 지원합니다.

옵션

유효성 검사

기본값

동작

media_io_kwargs.image.timeout

양수 형태의 초 단위 시간 (예: 60초, 1분 30초). 문자열, 불리언, null 값은 허용되지 않습니다. (정수 형태의 시간)

기본 설정 또는 요청에서 누락된 경우, 30초.

HTTP 요청 처리에 사용되며, 이미지 처리 또는 생성과는 관련이 없습니다. 로컬 파일, 인라인 데이터 URL, URL이 없는 참조에는 영향을 미치지 않습니다.

서버의 로컬 경로 및 도메인 제한 사항은 여전히 적용되며, 이 딕셔너리를 통해 변경할 수 없습니다. (local-path, domain restrictions)

(프로세서) 옵션#

요청 키는 일치하는 최상위 프로세서 기본값을 대체하며, 여기에는 중첩된 객체 전체가 포함됩니다. 예를 들어, "size"의 대체는 전체 기본 "size" 객체를 대체하는 것이며, 그 차원을 병합하는 것이 아닙니다.

이미지에 특정한 옵션은 images_kwargs에 제공할 수 있습니다.

{"mm_processor_kwargs": {"min_pixels": 1024, "images_kwargs": {"max_pixels": 200704}}}

이 기능은 두 가지 제어를 모두 사용합니다. 요청의 images_kwargs는 전체 기본 images_kwargs 객체를 대체합니다. {"images_kwargs": {}}는 해당 그룹을 지우고 나머지 최상위 옵션만 유지합니다. 옵션은 최상위 레벨과 images_kwargs 내에 동시에 나타날 수 없습니다. 여기에는 기본값 및 요청 옵션이 결합된 후에도 적용됩니다. 이는 모든 옵션 이름에 적용됩니다.

(이미지 프로세서) 옵션#

카탈로그는 모든 업스트림 프로세서 인수를 나열하는 대신, 권장되는 런타임 제어 목록을 제공합니다. 아래의 일반적인 옵션은 Qwen-VL, EXAONE 4.5, Gemma 4에 적용됩니다. EXAONE은 Qwen 이미지 프로세서를 사용하며, 추가적으로 윈도우 정렬된 리사이징을 수행합니다. 기본값은 로드된 프로세서 구성에서 가져옵니다. 아래 표는 Transformers 5.8 클래스의 기본값 fallback을 보여줍니다. 체크포인트 구성은 이를 덮어쓸 수 있으며, 여기에는 정규화 값도 포함됩니다. 누락된 옵션은 로드된 기본값을 사용합니다. 명시적인 null 값은 그대로 전달되며, 일반적으로 누락과 동일하지 않습니다.

옵션

허용되는 값

기본값

부울 또는 null

true

입력 데이터를 RGB로 변환합니다. EXAONE은 윈도우 정렬된 리사이징 전에 이 작업을 수행합니다.

0부터 5까지의 정수, 또는 null

do_rescale

부울 또는 null

rescale_factor

유한한 숫자 또는 null 값

픽셀 리스케일 멀티플라이어, do_rescale가 활성화된 경우 사용됩니다.

do_normalize

image_mean

image_std

숫자, 숫자 시퀀스 또는 null

Qwen: [0.26862954, 0.26130258, 0.27577711]. Gemma: [1, 1, 1].

스칼라 또는 채널별 표준 편차; 정규화가 활성화된 경우 사용됩니다.

input_data_format

모델별 설정 옵션은 아래에 나열되어 있습니다. 크기 관련 설정이 누락되면 Furiosa가 자동으로 크기를 조정합니다. EXAONE는 항상 윈도우 크기에 맞춰 조정합니다.

정수: 70, 140, 280, 560, 또는 1024

이미지 및 컴파일된 용량에서 자동으로 선택되며, 로드된 프로세서 제한(HF 기본값: 280)부터 시작합니다.

FXB 비전 버킷이 없는 경우, 크기 설정은 로드된 프로세서의 설정을 사용합니다. images와 return_tensors는 런타임에서 제공되며, 사용자가 프로세서 설정을 변경할 수 없습니다.

min_pixels, max_pixels, max_soft_tokens에 대한 문자열, 불리언, 부동 소수점, null 값은 거부됩니다. 기본값, 요청 오버라이드, 그리고 이들의 결합된 결과는 유효성 검사를 거칩니다. 결합된 옵션에 대한 경계 검사는 수행됩니다. 등록되지 않은 옵션은 그대로 통과하며, 로드된 프로세서가 해당 옵션을 지원하는지 확인합니다. 이러한 옵션도 캐시 식별에 참여합니다.

처리 과정은 로드된 FXB의 컴파일된 비전 용량에 따라 진행됩니다. 유효한 옵션 값만으로는 이미지가 적합한지 보장하지 않습니다. 변환기는 로드된 프로세서의 패치 및 병합 기하 정보를 사용하여 용량 확인 및 출력 변환을 수행합니다. 기하 정보 오버라이드는 이에 맞춰야 합니다.

사전 캐시 히트는 이미지 처리를 건너뜁니다. 키는 서버 기본값 및 요청 오버라이드가 병합된 후, images_kwargs가 평탄화된 후 제공된 프로세서 kwargs를 포함합니다. 예를 들어 do_rescale와 같은 제공된 옵션을 변경하면 별도의 캐시 항목이 선택됩니다. 캐시되지 않은 옵셋을 요청할 때 이미지를 다시 제공해야 합니다. UUID는 원래 이미지를 식별합니다.

프로세서 구성의 기본값 및 자동으로 선택된 크기 설정은 사전 캐시에 추가되지 않습니다. 옵션을 생략하고 기본값을 명시적으로 제공하면 다른 항목이 선택될 수 있습니다. Qwen-VL 및 EXAONE 4.5의 기존 min_pixels / max_pixels 검사 또는 Gemma 4의 max_soft_tokens 검사와 같은 항목은 여전히 적용됩니다. 요청 범위를 벗어난 항목은 히트에서 제거되고 다시 처리됩니다. 이러한 검사는 자동으로 크기가 조정된 캐시 결과가 신선한 처리 결과와 일치한다는 것을 보장하지 않습니다.

유효성 검사 오류#

유효하지 않은 요청 옵션은 HTTP 400 또는 422 오류를 반환하며, 유효하지 않은 오프라인 옵션은 ValueError를 발생시킵니다. 잘못된 CLI 옵션 구조 또는 가져오기 옵션은 인자 오류이며, 모델별 프로세서 유효성 검사는 모델을 로드할 때 수행됩니다. 이러한 검사는 이미지 없는 요청에도 적용됩니다.

원시 비전 인코딩 또는 임베딩 재사용이 처리된 이미지 레이아웃과 일치하지 않는 토큰 수를 반환하는 경우, 텍스트 생성 전에 요청이 중단됩니다. Chat Completions 및 Responses는 스트리밍 요청을 포함하여 HTTP 500 InternalServerError를 JSON 형식으로 반환하며, SSE 이벤트를 전송하기 전에 반환합니다. 오프라인 호출자는 MultimodalTokenCountError (RuntimeError)를 받으며, LLMEngine은 step()을 통해 전달하고, AsyncLLMEngine은 generate()를 반복하는 동안 발생시킵니다.

토큰화 관련 동작에 대한 Tokenizer API 및 저장된 대화와 함께 옵션 처리에 대한 Multi-Turn Conversations를 참조하십시오.

UUID를 사용하여 멀티모달 입력 캐싱#

이미지는 내용에 의해 자동적으로 해져지고, 그들의 가공한 결과는 조차 때 아무 때도 시동됩니다 uuid 공급됩니다. 반복 된 이미지는 캐시 된 결과를 재사용 할 수 있으며 pre-processing를 건너 뛸 수 있으며 processor-bound 체크인에 따라 달라질 수 있습니다. 멀티모달 옵션.

캐시된 결과는 프롬프트와 독립적으로 이미지 전처리 출력을 포함합니다. 동일한 이미지를 다른 텍스트 또는 나중에 프롬프트에서 다른 위치에 사용하여 재사용할 수 있습니다. 각 요청은 여전히 이미지 플레이스홀더와 확장된 컨텍스트 길이를 유효성 검사하며, 이미지를 재사용하면 이전 응답이 재사용되지 않습니다.

사전 처리 캐시 미스 발생 시, 서버는 제공된 이미지를 다시 사전 처리한 후, 재사용 가능한 인코딩된 임베딩을 확인합니다. 자동 크기 조정은 요청 내 다른 이미지와 함께 변경될 수 있습니다. 인코딩된 임베딩은 미디어 식별, 제공된 프로세서 옵션, 처리된 픽셀, 레이아웃이 일치할 때만 재사용됩니다. UUID가 있는 경우에도 적용됩니다.

각 이미지를 안정시킬 수 있습니다. uuid 이미지를 다시 보류하지 않고 follow-up 요청에 대한 캐시 된 결과를 참조하십시오. UUIDs는 추가 검색 메커니즘을 제공합니다. UUID가 캐싱을 선택하지 않도록 설정하십시오.

콘텐츠 항목에서 image_url 옆에 uuid를 추가합니다.

{
  "type": "image_url",
  "image_url": {"url": "https://example.com/receipt.png"},
  "uuid": "receipt-2026-05-01-abc"
}

follow-up는 이미지 바이트를 올릴 수 있습니다 ("image_url": null) 및 업로드에 대한 참조 uuid 혼자:

{
  "type": "image_url",
  "image_url": null,
  "uuid": "receipt-2026-05-01-abc"
}

UUID 및 효과적인 프로세서 옵션에 대한 재사용 가능한 항목이 존재하지 않는 경우 (예를 들어, 알 수없는 UUID, 비활성, 변경 옵션 또는 요청된 경계 밖에 항목), 서버 re-runs pre-processing image_url 또한 공급됩니다; 그렇지 않으면 HTTP 400를 반환합니다 unknown multimodal uuid, 그리고 클라이언트는 이미지로 붙어 있어야 합니다. UUID-only 참고는 또한 fetching를 건너갑니다; URL를 아직도 fetches 공급하고 처리 캐시를 검사하기 전에 이미지를 삭제하십시오. 따로 잇기 외침은 사용할 수 있습니다 multi_modal_uuids 는 동일한 재사용 동작 [을 갖습니다 (자세한 내용은 다음 참조)] 오프라인 API 아래와 같다).

캐시 용량은 --mm-processor-cache-gb (기본값: 4.0, 0은 사전 처리 캐싱을 비활성화)로 제어됩니다. 용량은 사전 처리 항목의 픽셀 버퍼 수를 계산합니다. 가장 최근에 사용되지 않은 항목은 캐시가 가득 찼을 때 제거됩니다. 인코딩된 임베딩은 별도의 수명을 가지며, 사전 처리 제거 또는 사전 처리 캐싱이 비활성화된 후에도 재사용될 수 있습니다. UUID만으로 요청하는 경우, 사전 처리 항목이 필요합니다. 단, 유지된 인코딩된 임베딩만으로는 충족할 수 없습니다. 캐시 및 UUID 매핑은 프로세스 수준이며 재시작 시 재설정됩니다.

Python 예제#

Furiosa-LLM 서버에 OpenAI Python 클라이언트를 사용하는 방법:

"""
OpenAI-Compatible Server - Vision-Language Chat Completion Example

Sends a chat-completion request containing an image and a text prompt
to a running Furiosa-LLM server.

The image URL below is hosted on the Furiosa developer documentation
site and is intended to be stable. For other image-input forms (base64
``data:`` URLs and local ``file://`` paths), see the Vision-Language
Models documentation page.
"""

import os

from openai import OpenAI

base_url = os.getenv("OPENAI_BASE_URL", "http://localhost:8000/v1")
api_key = os.getenv("OPENAI_API_KEY", "EMPTY")
client = OpenAI(base_url=base_url, api_key=api_key)

IMAGE_URL = "https://developer.furiosa.ai/latest/en/_images/Furiosa_RNGD_image.png"

response = client.chat.completions.create(
    model=client.models.list().data[0].id,
    messages=[
        {
            "role": "user",
            "content": [
                {"type": "image_url", "image_url": {"url": IMAGE_URL}},
                {"type": "text", "text": "Describe this image in one short sentence."},
            ],
        }
    ],
    max_completion_tokens=32,
    temperature=0.0,
)

print(response.choices[0].message.content)

오프라인 API#

동일한 이미지 입력을 오프라인 LLM / LLMEngine API를 통해 multi_modal_data 필드에 있는 프롬프트 딕셔너리에 전달할 수 있습니다. PIL 이미지를 모다티에 따라 키하여 전달합니다:

from PIL import Image
from furiosa_llm import LLM, SamplingParams

image = Image.open("photo.png")
prompts = [
    {
        "prompt": "<|vision_start|><|image_pad|><|vision_end|>Describe this image.",
        "multi_modal_data": {"image": [image]},
        "mm_processor_kwargs": {"min_pixels": 4096},
    }
]

with LLM(
    "Qwen/Qwen3-VL-32B-Instruct",
    fxb="/path/to/qwen3-vl-32b.fxb",
    mm_processor_kwargs={"min_pixels": 1024},
) as llm:
    outputs = llm.generate(prompts, SamplingParams(max_tokens=64))
    print(outputs[0].outputs[0].text)

LLM(mm_processor_kwargs=...)는 프로세서 기본 설정을 설정합니다. 각 프롬프트의 mm_processor_kwargs는 서버와 동일한 프로세서 병합 규칙을 사용하여 기본 설정을 덮어씁니다. 예제에서는 min_pixels=4096을 사용합니다. 오프라인 호출자는 디코딩된 이미지를 제공하므로 media_io_kwargs는 오프라인 LLM 옵션이 아닙니다.

Caching Multimodal Inputs with UUID에서 설명된 콘텐츠 기반 캐싱 및 UUID 참조도 오프라인 API를 통해 사용할 수 있습니다. multi_modal_data와 함께 multi_modal_uuids를 동일한 순서로 추가합니다. UUID 참조가 필요 없는 항목에는 None을 전달합니다. 이러한 항목도 콘텐츠 기반 캐싱에 참여합니다.

각 모달리티의 UUID 목록은 해당 이미지 목록과 정확히 동일한 개수를 가져야 합니다. 단일 이미지의 경우, 빈 UUID 문자열도 허용됩니다. UUID를 반복하면, 프롬프트 내에서 해당 항목이 반복됩니다. 따라서 동일한 캐시된 결과를 재사용하더라도, 각 UUID에 해당하는 이미지 플레이스홀더를 제공해야 합니다.

예를 들어:

prompts = [
    {
        "prompt": "<|vision_start|><|image_pad|><|vision_end|>Describe this image.",
        "multi_modal_data": {"image": [image]},
        "multi_modal_uuids": {"image": ["receipt-2026-05-01-abc"]},
    }
]

후속 프롬프트는 이미지를 생략하고 UUID만 참조할 수 있습니다. multi_modal_data 슬롯에 None을 전달합니다.

followup = [
    {
        "prompt": "<|vision_start|><|image_pad|><|vision_end|>Translate to Korean.",
        "multi_modal_data": {"image": [None]},
        "multi_modal_uuids": {"image": ["receipt-2026-05-01-abc"]},
    }
]

자세한 내용은 API 참조를 참조하십시오.
