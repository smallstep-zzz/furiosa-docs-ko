Furiosa SDK 릴리즈 2026.2#

우리는의 출시를 발표하게 행복합니다. Furiosa SDK 2026.2.

2026.1에 배치된 기초에 건물, 이 방출은 생산 배치를 더 빠르게 만들기에 집중하고, 형성하게 쉬운, 그리고 더 쉬운 확장합니다. 우리는 개량한 서빙 성과가 있습니다 Qwen3 and 엑소네4, artifact에서 bucket-tuning 행사의 대부분 제거 preset-based 구성독립적인 데이터 병렬 (DP) 라우터 a prefix-aware 변종, 활성화 기본값: prefix caching, 및 첫 번째 단계의 배송 응답 API (/v1/responses).

2026.1에서 업그레이드하는 경우, 또한 읽으십시오 🚨 주요 변경 사항 및 폐기 부문 및 FuriosaAI 소프트웨어 업그레이드.

주요 내용#

Qwen3 및 Exaone4 성능 개선#

RNGD에 가장 자주 배치 된 모델 가족 중 두 가지는 throughput 등급에서 per-request latencies와 함께이 릴리스에서 의미있는 throughput 개선을 볼 수 있습니다. Qwen3 prefill, decode 및 부트 버킷 (Qwen3-32B-FP8에 대한 64k 부트 버킷 포함)를 확장하여 real-world 요청 배포가 well-tuned 커널을 표시하고 엑소네4 더 많은 high-batch와 함께 부드킷을 얻을 하이브리드 KV Cache 관리global-attention 및 sliding-window 풀과 sliding-window 블록을 별도로 분리하는 KV 메모리를 분할하는 KV 메모리는 활성 창 밖에 떨어지기 때문에 long-context 워크로드에서 메모리 낭비 및 리프팅 효과적인 통화를 줄입니다.

입력 길이, 출력 길이 및 concurrency, tokens/second throughput에 의해 개선된의 청소를 건너 평균적으로 2026.1에서 74.9%, 상승하여 84.8% low-concurrency (64 아래 통화)에서 TTFT 및 TPOT는 2026.1 기본 라인과 함께 라인에 남아 있습니다.

Per-Model 버킷 프리셋#

좋은 양동이 구성 - prefill, decode의 세트, 그리고 부동이 크기에 대한 artifact가 컴파일된다 - 제공 성능을위한 highest-leverage 손잡이 중 하나이며, 또한 손으로 조정하는 가장 어려운 중 하나입니다. 2026.2에서, ArtifactBuilder 그 복잡성을 흡수: 모든 지원 모델 배와 함께 per-model 템플릿 설정, Furiosa 팀에 의해 조정 각 모델의 아키텍처에 일치 하 고 전체 최대 컨텍스트를 커버 하 고 빌드 시간에 자동으로 적용.

설계 목표는 간단합니다: 기본 빌드는 일반적인 서빙 작업 부하에 가장 적합한 것을 생성해야합니다.사용자를 요구하지 않고 모든 양동이에 대한 이유 :

# Build an artifact for Qwen3-32B-FP8 and write it to ./Qwen3-32B-FP8
furiosa-llm build Qwen/Qwen3-32B-FP8 -tp 8 ./Qwen3-32B-FP8

Explicit 양동이 인수는 여전히 지원되고 선행을 취합니다. 따라서 workload- 특정 조정은 필요한 사용자에게 사용할 수 있습니다.

Prefix-Aware Routing를 가진 자료 평행한 대패#

2026.2는 first-class를 소개합니다. 데이터 병렬 (DP) 라우터 수평으로 확장 된 배포를 위해. 라우터는 프런트 엔드의 앞에 앉아서 모든 engine-local 스케줄링이 발생하기 전에 DP 복제에 각 요청을 파견, 그래서 클라이언트는 단일 항목 포인트를 참조하면서 각 복제는 독립적으로 자신의 스케줄러를 실행합니다.

두 가지 라우팅 정책이 있습니다. round_robin 복제를 통해 균등하게 요청을 배포합니다. prefix_aware 토큰화 된 접두사를 검사하고 이미 접두사 캐시 항목과 일치하는 복제를 선호한다 - 긴 시스템 프롬프트 또는 RAG 시스템과 같은 공유 주요 토큰과 같은 워크로드에 중요한, 해군 round-robin 사기꾼이 복제를 통해 공유 접두사를 공유하고 캐시 지방을 파괴한다. 정책은 통해 선택됩니다 --data-parallel-routing-policy, 그리고 prefix_aware prefix caching이 활성화된 경우, round_robin 다른 경우:

# Explicitly use prefix-aware routing
furiosa-llm serve <model> --data-parallel-size <N> \
    --data-parallel-routing-policy <policy>

Prefix Caching는 기본적으로 활성화됨#

Prefix caching는 opt-in 플래그 뒤에 2026.1에서 소개되었습니다. 생산 사용 및 여러 교정 및 성능 개선의 출시 후, 지금입니다 기본 설정으로 설정 2026.2에서. 더 이상 어떤 플래그를 필요로하지 않습니다.

기본 플립 외에도 여러 가지 정제를 착륙했습니다.

  • 프리픽스 캐시 히트 지연 in-flight 접두사와 일치하기에 대한 간단한 방어 요청으로 캐시 히트 레이트를 극대화합니다. 대신 신선한 prefill로 킥링합니다.

  • Prefix caching는 디코딩 출력에 적용됩니다. 뿐만 아니라 multi-turn 대화는 계속적인 측에 조차 캐시에서 이익을 얻습니다.

특정 배포를 위해 prefix caching를 비활성화해야 하는 경우 — 예를 들어, 요청을 통해 미리 설정할 수 있는 워크로드 또는 벤치마킹 실행을 위해 cache-hit 가변이 측정을 중단할 경우 — 패스 --no-enable-prefix-caching:

furiosa-llm serve <model> --no-enable-prefix-caching

응답 API (단계 1)#

2026.2는 초기 지원 기능을 추가합니다. 응답 API at /v1/responses. 응답 API는 OpenAI의 더 새로운, 채팅 완료에 더 표현적인 대안이고, 이 방출은 똑바른 request/response 교류를 위해 유용한 표면 지역의 충분히 커버합니다.

이것은 표기되어 있습니다 단계 1 의도적으로: endpoint는 요청을 받아들이고 well-formed 응답을 생성하지만, 고급 행동의 수는 여전히 구출됩니다.

OpenAI Python 클라이언트를 사용하는 최소 예:

from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")

response = client.responses.create(
    model="Qwen/Qwen3-32B-FP8",
    input="Tell me a three-sentence bedtime story about a unicorn.",
)
print(response.output_text)

전체 엔드포인트 목록의 경우 지원되는 매개 변수, multi-turn 대화를 통해 previous_response_id, 스트리밍, 도구 호출, 및 구조 출력, 참조 답변 API.

이 릴리스의 변경의 전체 목록은 아래의 모든 변경 섹션에서 요약됩니다.

모든 변화#

주요 기능 및 개선 사항#

  • 데이터 병렬 (DP) 라우터

    • 독립적으로 DP 복제를 통해 요청을 일정하는 전용 DP 라우터를 도입하여 inference 노동자의 수평 scale-out를 사용하여 fine-grained 제어를 요청 배포합니다.

    • Prefix-aware 라우팅 multi-tenant 배포에서 multi-tenant 캐시 히트 레이트를 극대화하는 프리픽스 캐시 항목에 대한 공유 접두사 요청을 전달합니다.

    • DP 라우터는 engine-local 스케줄링 전에 결정이 발생하기 때문에 frontend의 앞에 배치됩니다. cross-replica 콘텐츠 감소.

  • Prefix Caching는 기본적으로 활성화됩니다.

    • Prefix caching는 이제 모든 배포에 기본적으로 활성화되어 Time-To-First-Token (TTFT)를 박스에서 제공합니다.

    • 추가적인 개선 사항으로는 프리픽스 캐시 히트 지연 prefix caching를 적용하여 출력을 디코딩하고, 하이브리드주의 모델의 안전한 접두사 캐시 삽입을 위한 보조 블록 길이 평형을 보장합니다.

  • 응답 API와 OpenAI 호환 API

    • 응답 API (/v1/responses): 응답 API에 대한 지원이 추가되며, 현명한 상호 작용을 가능하게 합니다.

    • 토큰화 / 역토큰화 API: 추가 /tokenize and /detokenize server-side 토큰화 및 탈 토큰화를위한 엔드 포인트.

    • ``dimensions`` 매개변수를 사용하여 임베딩 생성: 특정 embedding 차원을 요청하는 지원 dimensions 현장

  • 더 넓은 플랫폼 지원

    • ARM64 호스트 (AArch64): Furiosa SDK는 이제 ARM64-based 서버에서 실행되며 호스트 runtime에서 AArch64 SIMD 지원으로 2026.1에서 도입된 벡터화 최적화는 x86-64에서 x86-64에 적용됩니다.

    • Red Hat Enterprise Linux (RHEL): RPM 패키지는 Debian/Ubuntu를 RHEL-based 배포에 Debian/Ubuntu를 넘어 first-class OS 지원을 확장하고 있습니다.

성과 & 효율성 개선#

  • Model-specific 최적화:

    • 확장 및 re-tuned prefill, decode 및 부드킷을위한 Qwen3 and 엑소네4 real-world 요청 배포는 well-tuned 커널을 보았으므로 compiler와 lower-batch 버킷에 최적화되어 있습니다.

  • 최적화된 로짓 복사 I/O:

    • : 샘플러가 실제로 소비하는 슬라이스만 복사하여 sampling 모델 출력 로딩의 메모리 병목 현상을 줄였습니다. 이를 통해 각 decode 단계마다 호스트-장치 전송 볼륨이 줄었습니다.

  • 스케줄러 최적화:

    • 프리픽스 캐시 히트 지연 in-flight 접두사와 일치하기에 대한 간단한 deferring 요청에 의해 cross-request 캐시 히트 레이트를 극대화합니다.

    • 추가적인 최적화는 prefix-aware DP 라우터 매우 긴 공유 접두사를 위해 빠른 여정 결정을 유지하십시오.

API 및 사용성 개선#

  • 서비스 옵션:

    • 추가 --served-model-name OpenAI 호환 API (aliasing 또는 drop-in 교체에 적합)를 통해 노출 된 모델 ID를 사용자 정의 할 수 있습니다.

    • 추가 --chat-template-content-format multi-part 채팅 콘텐츠 렌더링에 대한 인수.

  • Sampling 기본값:

    • 기본 sampling 매개 변수는 이제 모델의 소스가 될 수 있습니다 generation_config.json, 모델의 권장된 기본값으로 서버 동작을 정렬합니다.

  • 사용법 및 관찰:

    • 사용 응답에 추가됨 cached_tokens 그리고 prompt/completion token 세부사항.

    • sampling_done 미터는 지금 per-device 고장을 위한 장치 ID를 포함합니다.

  • CLI:

    • New furiosa-llm version subcommand는 설치된 SDK 버전을 보고합니다.

  • 채팅 완료 API:

    • token 길이는 최대 사용 가능한 KV 블록에 대해 검증되며 빈 캐시에도 적합 할 수없는 요청을 방지합니다.

🚨 주요 변경 사항 및 폐기#

  • –prefill-chunk-size 제거:

    • The --prefill-chunk-size CLI 옵션이 제거되었습니다. Prefill chunking은 이제 스케줄러에 의해 내부적으로 관리됩니다.

    • 이주: 제거 --prefill-chunk-size 시작 스크립트에서; 교체가 필요하지 않습니다.

  • PyTorch 2.10로 업그레이드:

    • PyTorch는 2.7에서 2.10에 융해한 종속성입니다.

    • 이주: 환경을 보장하는 것은 PyTorch 2.10.x를 지원합니다.

  • reasoning_content (더 이상 사용되지 않음):

    • The reasoning_content 채팅 완료 응답의 필드는 이름 reasoning 업스트림 컨벤션과의 일관성을 위해. 두 필드는 2026.2에서 대중화됩니다, 그래서 기존 클라이언트는 변경되지 않는 작업을 계속; reasoning_content 제거하기 전에 적어도 하나의 더 많은 릴리스 사이클 동안 사용할 수 있습니다.

    • 이주: 클라이언트 코드를 업데이트하여 읽도록 reasoning 제거 작업 전에 해당 필드를 설정합니다.

  • guided_decoding는 structured_output로 이름을 변경했습니다:
