Furiosa SDK 릴리스 2026.2#

Furiosa SDK 2026.2 출시를 발표하게 되어 기쁩니다.

2026.1에 구축된 기반을 바탕으로, 이번 릴리스는 프로덕션 배포를 더 빠르고, 구성이 더 쉬워지고, 확장성이 더 용이하도록 집중합니다. Qwen3 및 Exaone4에 대한 서비스 성능을 개선하고, 프리셋 기반 구성으로 아티팩트 빌드에서 대부분의 버킷 튜닝 의식을 제거했으며, 프리픽스 인식 기능을 갖춘 독립적인 데이터 병렬 (DP) 라우터를 도입하고, 기본적으로 프리픽스 캐싱을 활성화했으며, 첫 번째 단계의 응답 API (/v1/responses)를 출시했습니다.

2026.1에서 업그레이드하는 경우, 🚨 Breaking Changes & Deprecations 섹션과 FuriosaAI 소프트웨어 업그레이드를 반드시 읽어보십시오.

주요 기능#

Qwen3 및 Exaone4 성능 개선#

RNGD에서 가장 많이 배포되는 모델 패밀리 2가지에 상당한 처리량 개선이 이루어졌으며, 요청당 지연 시간은 2026.1 수준으로 유지됩니다. Qwen3 아티팩트는 확장된 프리필, 디코딩 및 어펜드 버킷 (64k 어펜드 버킷 포함, Qwen3-32B-FP8용)을 포함하여 실제 요청 분포의 더 많은 부분이 잘 튜닝된 커널에 맞도록 설계되었으며, Exaone4는 하이브리드 KV 캐시 관리를 통해 더 많은 고-배치 및 어펜드 버킷과 함께, KV 메모리를 별도의 글로벌-어텐션 및 슬라이딩-윈도우 풀로 분할하고, 활성 창 밖으로 나가는 슬라이딩-윈도우 블록을 즉시 회수하여 메모리 낭비를 줄이고, 장기 컨텍스트 워크로드에서 효과적인 동시성을 높입니다.

입력 길이, 출력 길이, 동시성 등 다양한 요소를 고려했을 때, 2026.1에 비해 평균적으로 토큰/초 처리량이 74.9% 증가했으며, 특히 낮은 동시성 환경(동시성 64 미만)에서는 84.8%까지 향상되었습니다. TTFT 및 TPOT은 2026.1 기준과 유사하게 유지되었습니다.

모델별 버킷 설정#

적절한 버킷 구성(사전 채우기, 디코딩, 추가 버킷 크기 등)은 서비스 성능에 가장 큰 영향을 미치는 요소 중 하나이며, 수동으로 조정하기 가장 어려운 부분입니다. 2026.2에서 ArtifactBuilder는 이러한 복잡성을 해결합니다. 모든 지원되는 모델은 Furiosa 팀에서 각 모델의 아키텍처와 최대 컨텍스트를 완벽하게 커버하도록 조정된, 모델별 버킷 설정을 기본으로 제공하며, 빌드 시에 자동으로 적용됩니다.

설계 목표는 간단합니다. 기본 빌드는 일반적인 서비스 워크로드에 가장 적합한 아티팩트를 생성하며, 사용자가 버킷화에 대해 별도로 고려할 필요가 없습니다.

# Build an artifact for Qwen3-32B-FP8 and write it to ./Qwen3-32B-FP8
furiosa-llm build Qwen/Qwen3-32B-FP8 -tp 8 ./Qwen3-32B-FP8

명시적인 버킷 인수는 여전히 지원되며 우선 순위를 가지므로, 필요한 사용자에게는 워크로드에 특화된 튜닝이 가능합니다.

Prefix-Aware Routing을 지원하는 데이터 병렬 라우터#

2026.2에서 수평 확장에 적합한 첫 번째 데이터 병렬 (DP) 라우터를 도입했습니다. 이 라우터는 프론트엔드 앞에 위치하여 각 요청을 처리하기 전에 엔진 레벨의 스케줄링 전에 DP 복사본으로 전달합니다. 따라서 클라이언트는 단일 엔드포인트를 통해 서비스를 이용할 수 있으며, 각 복사본은 독립적으로 스케줄링을 수행합니다.

두 가지 라우팅 정책이 제공됩니다. round_robin은 요청을 복사본에 균등하게 분배합니다. prefix_aware는 토큰화된 접두사를 검사하고, 이미 일치하는 접두사 캐시 항목을 보유하고 있는 복사본을 선호합니다. 이는 공유된 접두사를 가진 워크로드(예: 긴 시스템 프롬프트를 사용하는 챗봇 또는 RAG 시스템)에서 중요합니다. round_robin은 공유된 접두사를 복사본에 흩뿌려 캐시 지역성을 파괴합니다. 이 정책은 --data-parallel-routing-policy를 통해 선택되며, 접두사 캐싱이 활성화된 경우 기본적으로 prefix_aware로 설정되고, 그렇지 않으면 round_robin으로 설정됩니다.

# Explicitly use prefix-aware routing
furiosa-llm serve <model> --data-parallel-size <N> \
    --data-parallel-routing-policy <policy>

접두사 캐싱이 기본적으로 활성화되었습니다.#

접두사 캐싱은 2026.1에서 선택적으로 활성화되었습니다. 여러 가지 정확성 및 성능 개선 사항이 적용된 후, 2026.2에서 기본적으로 활성화되었습니다. 이제 이 기능을 사용하려면 별도의 플래그를 지정할 필요가 없습니다.

기본 설정 변경 외에도 다음과 같은 개선 사항이 적용되었습니다:

  • 접두사 캐시 히트 지연은 캐시 히트율을 최대화하기 위해, 이미 일치하는 접두사를 처리하는 요청을 일시적으로 지연시켜, 새로운 사전 채우기를 호출하는 대신 요청을 처리합니다.

  • 디코딩된 출력에 대한 프리픽스 캐싱이 적용되므로, 다중 턴 대화는 연속적인 측면에서도 캐시를 활용할 수 있습니다.

특정 배포 환경에서 프리픽스 캐싱을 비활성화해야 하는 경우 (예: 요청 간에 프리픽스가 거의 공유되지 않거나, 캐시 히트 변동이 측정값을 왜곡할 수 있는 경우) --no-enable-prefix-caching 옵션을 사용하십시오.

furiosa-llm serve <model> --no-enable-prefix-caching

응답 API (1단계)#

2026.2에서 /v1/responses 엔드포인트에서 응답 API에 대한 초기 지원이 추가되었습니다. 응답 API는 Chat Completions보다 더 강력하고 표현력이 풍부한 OpenAI의 새로운 API이며, 이 릴리스는 간단한 요청/응답 흐름에 유용할 만큼 충분한 기능을 제공합니다.

이 엔드포인트는 의도적으로 "1단계"로 명명되었습니다. 이 엔드포인트는 요청을 수락하고 잘 정의된 응답을 생성하지만, 여전히 많은 고급 기능이 추가되고 있습니다.

OpenAI Python 클라이언트를 사용하는 최소 예제:

from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")

response = client.responses.create(
    model="Qwen/Qwen3-32B-FP8",
    input="Tell me a three-sentence bedtime story about a unicorn.",
)
print(response.output_text)

전체 엔드포인트 목록의 경우 지원되는 매개 변수, multi-turn 대화를 통해 previous_response_id, 스트리밍, 도구 호출, 및 구조 출력, 참조 답변 API.

이 릴리스의 모든 변경 사항은 아래 "전체 변경 사항" 섹션에 요약되어 있습니다.

전체 변경 사항#

주요 기능 및 개선 사항#

  • 데이터 병렬 (DP) 라우터

    • 독립적으로 DP 복제본 간의 요청을 스케줄링하는 전용 DP 라우터를 도입하여, 미세 조정된 요청 배포를 통해 추론 작업자의 수평 확장을 가능하게 합니다.

    • 접두사 기반 라우팅은 공유 접두사를 가진 요청을, 이미 일치하는 접두사 캐시 항목을 보유한 복제본으로 전달하여, 다중 임대 환경에서 요청 간 캐시 히트율을 극대화합니다.

    • DP 라우터는 프론트엔드 앞에 배치되어, 엔진 내부 스케줄링 전에 라우팅 결정을 수행하도록 하여, 복제 간의 충돌을 줄입니다.

  • 기본적으로 프리픽스 캐싱 활성화

    • 프리픽스 캐싱은 모든 배포 환경에서 기본적으로 활성화되어, 즉시 첫 번째 토큰 처리 시간을 단축합니다.

    • 추가 개선 사항으로는 프리픽스 캐시 히트 지연을 통해 캐시 히트율을 극대화하고, 디코딩된 출력에 프리픽스 캐싱을 적용하며, 하이브리드 어텐션 모델에서 안전한 프리픽스 캐시 삽입을 보장하는 등의 기능이 포함됩니다.

  • 응답 API 및 OpenAI 호환 API

    • 응답 API (/v1/responses): 상태를 유지하는 상호 작용을 가능하게 하는 응답 API 지원이 추가되었습니다.

    • 토큰화 / 역토큰화 API: 서버 측 토큰화 및 역토큰화를 위한 /tokenize 및 /detokenize 엔드포인트 추가.

    • 임베딩 dimensions 매개변수: dimensions 필드를 통해 특정 임베딩 차원을 요청할 수 있도록 지원.

  • 더 넓은 플랫폼 지원

    • ARM64 호스트 (AArch64): Furiosa SDK는 AArch64 SIMD 지원을 포함하여 ARM64 기반 서버에서 실행됩니다. 2026.1에 도입된 벡터화 최적화는 x86-64와 마찬가지로 ARM에서도 적용됩니다.

    • Red Hat Enterprise Linux (RHEL): RPM 패키지가 이제 배포되므로, Debian/Ubuntu 외에 RHEL 기반 배포판에서도 첫 번째 지원 OS를 확장합니다.

성능 및 효율성 개선#

  • 모델별 최적화:

    • Qwen3 및 Exaone4에 대해 확장되고 재조정된 prefill, decode, append 버킷을 사용하여 실제 요청 분포의 상당 부분이 잘 튜닝된 커널에 적합하도록 조정되었습니다. 또한, 낮은 배치 버킷에 최적화된 컴파일러를 사용했습니다. (실제 요청 분포가 잘 튜닝된 커널에 적합하도록 조정)

  • 로짓 복사 I/O 최적화:

    • 샘플링에 모델 출력 로딩 시 발생하는 메모리 병목 현상을 줄이기 위해, 각 디코딩 단계마다 실제로 사용되는 슬라이스만 복사하여 호스트-장치 전송량을 줄였습니다. (메모리 병목 현상을 줄이기 위해)

  • 스케줄러 최적화:

    • 프리픽스 캐시 히트 지연을 통해, 현재 실행 중인 프리픽스와 일치할 가능성이 있는 요청을 잠시 지연시켜, 요청 간 캐시 히트율을 극대화합니다. (요청 간 캐시 히트율을 극대화)

    • 접두사 기반 DP 라우터의 추가적인 최적화는 매우 긴 공유 접두사에도 빠른 라우팅 결정을 유지합니다.

API 및 사용성 개선#

  • 제공 옵션:

    • OpenAI 호환 API를 통해 노출되는 모델 ID를 사용자 정의하기 위한 --served-model-name 옵션을 추가했습니다 (별칭 설정 또는 즉시 대체에 유용).

    • 다중 부분 채팅 콘텐츠 렌더링을 위한 --chat-template-content-format 인수를 추가했습니다.

  • 샘플링 기본 설정:

    • 기본 샘플링 매개변수는 이제 모델의 generation_config.json에서 가져올 수 있으며, 서버 동작을 모델의 권장 기본 설정과 일치시킵니다.

  • 사용법 및 관찰성:

    • 사용 응답에 cached_tokens 및 프롬프트/완성 토큰 세부 정보가 추가되었습니다.

    • sampling_done 메트릭이 이제 장치 ID를 포함하여 장치별 분석을 제공합니다.

  • CLI:

    • New furiosa-llm version subcommand는 설치된 SDK 버전을 보고합니다.

  • 챗 완결 API:

    • 요청 토큰의 길이는 사용 가능한 KV 블록의 최대 길이에 대해 유효성 검사를 수행하여, 빈 캐시에 들어가지 못하는 요청을 방지합니다.

🚨 주요 변경 사항 및 기능 제거#

  • --prefill-chunk-size 옵션 제거:

    • --prefill-chunk-size CLI 옵션이 제거되었습니다. Prefill チャンキング은 이제 스케줄러에 의해 내부적으로 관리됩니다.

    • 마이그레이션: launch 스크립트에서 --prefill-chunk-size를 제거하십시오. 대체 옵션이 필요하지 않습니다.

  • PyTorch 2.10로 업그레이드:

    • PyTorch 의존성이 2.7에서 2.10으로 업그레이드되었습니다.

    • 마이그레이션: 환경이 PyTorch 2.10.x를 지원하는지 확인하십시오.

  • reasoning_content: 더 이상 사용되지 않음 (deprecated):

    • chat completions 응답의 reasoning_content 필드는 consistency를 위해 reasoning으로 이름이 변경됩니다. 두 필드는 2026.2에서 모두 채워지므로 기존 클라이언트는 변경 없이 계속 작동합니다. reasoning_content는 제거되기 전에 최소 한 번의 릴리스 사이 동안 사용할 수 있습니다.

    • 마이그레이션: 클라이언트 코드를 업데이트하여 reasoning 필드를 읽도록 변경합니다.

  • guided_decoding: 이름이 structured_output으로 변경됨:

    • guided_decoding 파라미터 그룹은 structured_output으로 이름이 변경되었습니다.

    • 마이그레이션: guided_decoding을 참조하는 모든 요청 페이로드 또는 SDK 호출을 업데이트하십시오. (이 기능을 사용하는 요청을 업데이트해야 합니다.)
