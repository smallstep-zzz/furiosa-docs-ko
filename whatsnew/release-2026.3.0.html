주요 내용#

TCL 커널 프레임 워크와 furiosa 커널#

2026.3의 정의 변화는 TCL (텐서 수축 언어) 커널 프레임 워크. 모델을 추가하는 이유를 보려면 훨씬 빨리, 그것은 우리가 하나를 설명하는 데 사용하는 방법을 살펴 봅니다.

이전 경로는 PyTorch 모델에서 시작, TorchDynamo와 Torch ATen ops의 FX 그래프로 추적. 이것은 빠르게 실행 모델을 얻기 위해 효과적이었지만 모델의 의도를 희석 : ATen을 통해 캡처는 fine-grained primitives로 그래프를 해독합니다. An aten.mm, 예를 들어, 타일링이 되고, 그 다음 요소적으로 곱하기, 그 다음 ⁇ 을 줄이고 compiler는 더 이상 ⁇ matmul ⁇ 를 보지 않고 그것을 최적화하기 전에 re-recognize을해야합니다. 그리고 축의 의미학과 오프 경계는 동일한 방식으로 흐리게됩니다. 마찬가지로 중요한 것은 모델링 단계가 compiler의 목표에 대한 RNGD의 필요성을 부착하기 위해 몇 가지 좋은 장소를 남겼습니다. 의도된 텐서 병렬화 (TP) 전략과 같은. compiler는 본질적으로 의미의 상당 부분이 이미 평평화 된 후 최적화되었습니다.

TCL 모델 의미와 구조를 보존하기 위해 설계되었습니다. 커널 저자가 high-level를 작성하는 데 설명 된 Python eDSL입니다. @tcl.kernel-장식된 함수를 사용하여 무엇을 계산하고 결과를 반환 how 그것을 실행하기 위해 - tiling, scheduling, fusion, 하드웨어 매핑 - compiler에. 그것의 중요한 아이디어는 대우하는 것입니다 전압 수축 DNN 모델이 first-class primitives로 본질적으로 의존하는 작업이므로, 모델은 그 구조의 intact와 함께 이러한 수축의 관점에서 직접 설명됩니다. 이 일치 RNGD의 언더 라이닝 텐서 수축 프로세서 (TCP) compiler가 같은 원시적 주변을 건설하고 TCL 커널은 실행 가능한 바이너리 (EDF)로 컴파일됩니다.

이러한 설계는 다음과 같은 세 가지 방식으로 유용합니다:

  • 직관적이고 compiler 친화적인 설정입니다. 저자는 스레드 레이아웃 또는 동기화보다 오히려 계산의 의미를 표현하고, TCL이 컴파일되기 때문에 도구 체인은 여러 커널을 일시 중지하고 단일 단위로 컴파일 할 수 있습니다.

  • 모듈화 및 재사용 가능. RMSNorm, 선형 또는 MLP와 같은 Kernels는 많은 모델 공유를 구축하기 때문에 새로운 아키텍처를 활성화하고 기존 블록을 구성하고 진짜로 새로운 것을 추가합니다.

  • RNGD의 원산자 패딩, 샤딩, 방송 및 multi-chip 공동은 compiler가 정정과 최적화에 대해 설명 할 수있는 언어 및 유형 수준에서 표현됩니다.

Upshot은 이제 모델 번호가 아닌 재사용 가능한 블록의 수와 스케일을 설정하는 것입니다. furiosa-핵 패키지는 콘크리트 결과입니다 - 가족 Furiosa-LLM 지원 - 가족 Furiosa-LLM 지원 - 그리고이 릴리스의 새로운 모델의 폭이 직접 따라 달라집니다. 이 라이브러리가 성장함에 따라, 우리는 미래의 릴리스에서 새로운 모델을 신속하게 가져갈 것으로 기대합니다.

새로운 모범 가정#

TCL 프레임 워크에 구축, 2026.3는 RNGD에 새로운 모델의 넓은 세트를 제공, 여러 대형 Mixture-of-Experts (MoE) 아키텍처를 포함:

  • Qwen3-VL (e.g. Qwen3-VL-32B) — 첫 번째 vision-language RNGD의 가족 : 비전 인코더와 결합 된 조밀한 변압기 (see) 멀티모달 서비스 및 Qwen3-VL 아래와 같다).

  • gpt-oss (e.g. gpt-oss-120b) - MoE 가족 MXFP4-양자화된 전문가용 가중치를 사용합니다.

  • Solar-Open (e.g. Solar-Open-100B) - 모이 가족, NVFP4- 16-bit 활성화와 KV cache (NVFP4A16)를 가진 양화된 무게.

  • Qwen3 MoE (e.g. Qwen3-30B-A3B) - MoE 가족 동적으로 FP8 활성화 quantization runtime; Instruct, Thinking 및 Coder 변형.

  • K-EXAONE (e.g. K-EXAONE-236B-A23B) - 다국어 MoE 제품군을 사용하여 하이브리드 sliding-window + 글로벌 관심 제도는 NVFP4A16입니다.

각각 FXB를 발송하므로 Hugging Face 저장소에서 직접 제공 할 수 있습니다. 정확한 저장소 ID 및 서빙 명령에 대한 per-model 카드를 참조하십시오.

FXB: Furiosa 실행 파일 묶음#

2026.3는 다음을 소개합니다 Furiosa 실행 가능한 묶음 (FXB), Furiosa-LLM의 공유 가능한 compiled-artifact 체재. An .fxb 파일은 단일 아카이브로, manifest.json 컴파일된 커널과 함께 (edfs/) NPU에 모델을 실행하는 데 필요한. 모델이 컴파일되면 .fxb, 당신은 recompiling 없이 그것을 봉사할 수 있습니다, 다른 기계에 그것을 복사하고, 또는 다른 사람을 위한 Hugging Face 허브에 그것을 재사용하기 위하여 간행하십시오.

FXB의 정의 속성은 아키텍처 지문. 나타날은 모델 아키텍처와 컴파일된 커널을 결정하는 구성 필드를 기록합니다 (숨겨진 크기, 머리 수, 구급차 크기, quantization 등), 그래서 단일 번들은 가로 건너 뛰기 any 같은 지문을 공유하는 Hugging Face 모델 - 단지 하나에서 구축되지 않았습니다. 이 연습에서 당신은 자신의 저장소 선박이 아니다 모델에 봉사 할 수 있습니다 .fxb ⁇ 포함 fine-tuned 또는 weight-updated 변종 지원 모델의 - 로컬 캐시에서 호환 번들을 재사용하여, 모든 변종을 위해 재 컴파일 대신.

헌신적인 fxb 명령은 전체 수명주기를 관리합니다. 건물, 다운로드, 캐싱, 호환성 검사 및 검사. 예를 들어, 봉사 Qwen/Qwen3-8B-FP8 (그들의 묶음이 없습니다) 출판물, fingerprint-compatible를 재사용 furiosa-ai/Qwen3-8B-FP8 묶음:

# Download a published FXB bundle into the local cache
fxb download furiosa-ai/Qwen3-8B-FP8

# Confirm it is fingerprint-compatible with the target model
fxb check Qwen/Qwen3-8B-FP8

# Serve as usual — the compatible cached bundle is found automatically
furiosa-llm serve Qwen/Qwen3-8B-FP8

서빙 시간 Furiosa-LLM는 순서에 있는 뭉치를 해결합니다: 명시된 --fxb 경로 .fxb 모형 저장소 안쪽에 발송해, 그 후에 국부적으로 시렁. FuriosaAI는 대중적인 모형을 위한 pre-compiled 뭉치를 출판합니다 Hugging Face 허브.

fingerprint-based 호환성 일치는 입니다 실험적; 지문 분야의 정확한 세트는 미래 방출에서 변화할지도 모릅니다, 그래서 일치를 가진 확인합니다 fxb check 다른 모델에 대 한 캐시 번에 의존 하기 전에. 참조 C Furiosa 실행 파일 묶음 (FXB) 번들 형식의 경우 compatibility-matching 규칙 및 전체 fxb 명령 참조.

멀티모달 서비스 및 Qwen3-VL#

2026.3는 소개합니다 vision-language (다중) 서빙 RNGD Qwen3-VL-32B 첫 번째 지원 모델로. Image-and-text 요청은 표준 OpenAI 호환 채팅 완료 API를 통해 제공됩니다. image_url 내용의 부품

다중 모드 서비스는 여전히 실험적 이 릴리스에서: 스케줄링 및 batching 멀티모드 요청의 변경은 여전히 최적화되고, 다음 릴리스에 대한 추가 개선 계획.

OpenAI Python 클라이언트를 사용하는 최소 예:

from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")

response = client.chat.completions.create(
    model="Qwen/Qwen3-VL-32B-Instruct",
    messages=[{
        "role": "user",
        "content": [
            {"type": "image_url",
             "image_url": {"url": "https://qianwen-res.oss-cn-beijing.aliyuncs.com/Qwen-VL/assets/demo.jpeg"}},
            {"type": "text", "text": "Describe this image."},
        ],
    }],
)
print(response.choices[0].message.content)

re-sending 및 re-preprocessing를 피하기 위해 요청에 따라 동일한 이미지, 다중 입력은 안정된 태그가 될 수 있습니다. UUID server-side 프로세서 캐시에서 재사용되며, 사이즈를 통해 --mm-processor-cache-gb보시다시피 Vision-Language 모델과 함께 구성됩니다. 지원되는 모형, 요구 체재 및 재사용 semantics를 위해.

오버랩 스케줄링: 앞으로 Zero-Overhead Batching#

앞으로 패스 사이, inference 엔진은 host-side 작업에 실제 CPU 시간을 소비 — 배치 스케줄링, KV-block 할당 및 레이덱 캐시에 대한 접두사. 그 작업이 실행될 때 중 NPU는 전달합니다, NPU는 준비될 다음 배치를 기다리고, 짧은 decode 단계에 이 CPU 오버 헤드는 각 반복의 뜻깊은 분수일 수 있습니다.

2026.3은 겹치는 스케줄러 이 공간을 비우는 방법 한 배트가 앞으로: NPU는 현재 배치를 실행하면서 스케줄러는 다음의 모든 메타데이터를 준비합니다. host-side 스케줄링 비용은 NPU와 중복됩니다. NPU를 지속적으로 공급하는 NPU를 유지하고 있습니다. throughput-지향적 인 작업 부하를 위해 전체적으로 전반적인 결과를 향상시킵니다. throughput 및 출력 당 시간 token (TPOT), 작의 비용에, 안으로 경계를 두는 증가 TTFT.

이 기능은 여전히 실험적, so it is 기본으로 종료 및 스케줄링 루프는 다음과 같습니다. 열망; 우리는 그것을 안정화 한 번 기본을 만들 계획. 과도한 스케줄러를 사용:

furiosa-llm serve <model> --enable-overlap-scheduling

Scoring-Based 데이터 병렬 라우팅#

prefix-aware 데이터 병렬 (DP) 라우터는 2026.2에서 2026.3로 진화 scoring-based 복제를 선택할 때 두 개의 신호를 균형시키는 정책 : 프롬프트 접두사 일치율(Prefix locality)과 토큰 부하(token footprint load)를 함께 고려합니다. 점수 프로파일로 두 지표의 상대 가중치를 조정합니다.

# Scoring-based routing (default), balanced profile (default)
furiosa-llm serve <model> --data-parallel-size <N>

# Bias toward prefix cache affinity (equivalent to the old prefix-aware behavior)
furiosa-llm serve <model> --data-parallel-size <N> \
    --data-parallel-routing-policy scoring \
    --data-parallel-scoring-profile locality

--data-parallel-routing-policy 받아들이는 scoring (전기적으로) 또는 round-robin; --data-parallel-scoring-profile 받아들이는 balanced (전기적으로) locality, or load보시다시피 Data-Parallel 라우팅 세부사항을 알려주세요.

이 릴리스의 변경의 전체 목록은 아래의 모든 변경 섹션에서 요약됩니다.

주요 기능 및 개선 사항#

  • TCL 커널 프레임 워크와 furiosa 커널

    • 도입 TCL (텐서 수축 언어) eDSL 및 furiosa-핵 모델 활성화를 위한 1차 경로로 커널 컬렉션.

    • 추가 Mixture-of-Experts (MoE) 커널(expert routing and gated expert compute), 이 릴리스에서 새로운 MoE 모델을 활성화 (gpt-oss, Solar-Open, K-EXAONE, Qwen3 MoE).

    • 추가 sliding-window 주의 전체 관심과 함께 커널, 그래서 로컬 및 글로벌 관심 interleave 모델 (K-EXAONE 및 gpt-oss와 같은) 효율적으로 실행.

    • 추가 vision-encoder 원자핵과 멀티모탈 로터리 위치 embeddings (mRoPE) Qwen3-VL vision-language 경로에 대한.

  • FXB (Furiosa 실행 파일 묶음)

    • 새로운 공유 가능, compiled-artifact 형식 번들링 manifest.json 및 컴파일된 커널 (edfs/) 를 단일으로 .fxb 파일.

    • Architecture-fingerprint 호환성 (예 : 번들은 fine-tuned 또는 weight-updated 변형을 포함하여 동일한 지문을 공유하는 Hugging Face 모델의 모든 Hugging Face 모델에 재사용 할 수 있습니다. 따라서 저장소가없는 모델 .fxb recompiling 없이 호환되는 캐시된 뭉치에서 봉사될 수 있습니다.

    • New fxb 전체 라이프사이클에 대한 명령: build, download, add, check, cache ls/rm, show, 그리고 inspect.

    • 서빙은 순서에 있는 뭉치를 해결합니다: 명시하십시오 --fxb 경로 .fxb 모형 저장소 안쪽에, 그 후에 국부적으로 시렁 ( 지문과 FuriosaIR 개정에 의해 일치하십시오).

    • Pipeline-parallelism (-pp) 선택권은 FXB 근거한 발전기에 전파됩니다.

  • 모델 지원

    • Qwen3-VL — 첫 번째 vision-language 아키텍처; 비전 인코더와 결합 된 조밀한 변압기, OpenAI 호환 API에 제공.

      • Qwen3-VL-32B-Instruct

    • gpt-oss — MXFP4-quantized 전문가와 구성 가능한 이유 노력과 함께 MoE 아키텍처.

      • gpt-oss-20b, gpt-oss-120b

    • Solar-Open — NVFP4A16 MoE 아키텍처.

      • Solar-Open-100B-NVFP4A16

    • Qwen3 밀집 - 정적 FP8 무게 및 동적 FP8 활성화 quantization와 함께 조밀한 변압기 아키텍처.

      • Qwen3-4B-FP8, Qwen3-8B-FP8

    • Qwen3 MoE - 정적 FP8 무게 및 동적 FP8 활성화 quantization와 MoE 아키텍처.

      • Qwen3-30B-A3B-FP8

      • Qwen3-30B-A3B-Instruct-2507-FP8 (설명)

      • Qwen3-30B-A3B-Thinking-2507-FP8 (생각)

      • Qwen3-Coder-30B-A3B-Instruct-FP8 (코더)

    • K-EXAONE - 하이브리드 sliding-window + 글로벌 관심과 다국어 MoE 아키텍처.

      • K-EXAONE-236B-A23B-NVFP4A16

    • Solar-Open에 대한 패서저를 호출하고 이유를 추가하십시오.

  • 멀티모달 인프라 (실험)

    • Vision-encoder runtime NPU에 대한 비전 인코더를 실행하고 새로운 text-token 시퀀스로 삽입 된 결과 이미지를 신관 generate_mm 발전기 API.

    • End-to-end OpenAI 호환용 서빙 다음을 통한 image-and-text 요청의 image_url per-request 난간과 같은 per-request 난간과 더불어 내용 부속 (레모드, base64, 또는 local-file URL), --image-limit-per-prompt and --allowed-media-domains.

    • UUID 기반 다중 모달 데이터 재사용 server-side 프로세서 캐시를 통해--mm-processor-cache-gb: 안정적인 이미지를 태그한 이미지 uuid follow-up 요청에 한 번 사전 처리하고 재사용됩니다.

엔진 코어#

  • 겹치는 스케줄링 (experimental; 기본값으로 꺼짐, 를 통해 활성화 --enable-overlap-scheduling)는 host-side 스케줄링 오버 헤드가 NPU compute로 overlapped, 작은에 throughput와 TPOT를 개량하고, TTFT 비용을 경계를 두는 1개의 배치를 실행합니다.

  • Scoring-based DP 경로 설정 data-parallel 복제를 통해 사전 설정 로컬 및 token-footprint 부하를 균형 잡힌다.

  • KV cache 개선 사항 (이 릴리스에서 가장 큰 기반 재 공장) :

    • 통일된 래딕스 캐시 global-only와 sliding-window prefix-cache 나무를 하나으로 통합하여 per-component의 트리 토폴로지를 분리하여 새로운 캐시 구성 요소 유형이 더 이상 자신의 나무가 필요 없습니다. follow-up 최적화는 long-context (~128K-token) TTFT 회귀를 복구합니다.

    • KV cache 및 offloading 인프라 (groundwork): 계층화 된 block-placement 모델 (NPU, 호스트, 또는 dual-resident) 및 전용 NPU↔host DMA 오케스트라, offloading KV 블록에 대한 기반을 놓는 NPU 메모리를 미래 릴리스에서.

    • 더욱 강력한 NPU 메모리 할당: shared-DRAM 버퍼 풀은 이제 유휴 버퍼를 다시 인용하고 I/O-buffer 스페이스는 파편 슬랙으로 예약되어 있습니다. 오버랩 스케줄링 (e.g. gpt-oss-120b long-context)에서 큰 모델에 out-of-memory 오류를 수정합니다.

  • 더 빠른 모델 로딩 비동기, 병렬화된 Hugging Face 다운로드를 통해, 과다한 무게 파일을 건너뛰기 snapshot_download.

🚨 주요 변경 사항 및 폐기#

  • /metrics는 GET-only:

    • The /metrics 엔드포인트는 이제 GET 요청만이전에는 POST to /metrics 또한 반환 200; 이제 반환 405 Method Not Allowed.

    • 이주: 모니터링 스크랩 또는 건강 검사 쿼리를 보장합니다. /metrics 과 GET.

  • Firmware 업그레이드는 이제 수동 단계입니다.:

    • 2026.3 전에 firmware 업데이트자는 firmware 이미지 패키지가 설치되었을 때 자동으로 랭크됩니다. 2026.3로 시작하여 이미지 패키지를 더 이상 트리거하지 마십시오. 업데이트자가 설치 한 후 직접 실행해야합니다.

    • 이주다음으로: apt install firmware 도구 및 이미지 패키지의 실행 sudo furiosa_rngd_updater_all 모든 RNGD 장치를 업그레이드하는 것 (또는 furiosa_rngd_updater -b <BDF> -f <firmware image> 특정 장치에 대한), 다음 감기 재부팅을 수행합니다. 참조 FuriosaAI 소프트웨어 업그레이드 전체 절차를 참조하십시오.
