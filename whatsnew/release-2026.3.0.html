Furiosa SDK 릴리스 2026.3.0#

Furiosa SDK 2026.3 출시를 발표하게 되어 기쁩니다.

이번 릴리스는 모델 커버리지에 중점을 둡니다. 핵심은 TCL (Tensor Contraction Language) 커널 프레임워크 및 furiosa-kernels 패키지, 그리고 FXB (Furiosa Executable Bundle) 패키징 형식을 도입하여 새로운 모델 아키텍처를 활성화하고 배포하는 속도를 크게 향상시키는 것입니다. 이러한 기반 위에서 2026.3은 Qwen3-VL을 통해 멀티모달 (시각-언어) 서비스를 지원하고, 여러 새로운 대규모 MoE 모델 (gpt-oss, Solar-Open, K-EXAONE, Qwen3 MoE)을 도입하며, NPU가 지속적으로 데이터를 공급받을 수 있도록 1배 빠른 오버랩 스케줄러를 소개하고, 데이터 병렬 라우터를 점수 기반 정책으로 일반화합니다.

2026.2에서 업그레이드하는 경우, 🚨 Breaking Changes & Deprecations 섹션과 FuriosaAI 소프트웨어 업그레이드를 반드시 읽어보십시오.

주요 기능#

TCL 커널 프레임워크 및 furiosa-kernels#

2026.3의 주요 변화는 TCL (Tensor Contraction Language) 커널 프레임워크입니다. 모델을 추가하는 속도가 왜 이렇게 빨라졌는지 이해하려면, 이전 방식이 어떻게 작동했는지 살펴보는 것이 도움이 됩니다.

이전 방식은 PyTorch 모델에서 시작하여 TorchDynamo를 통해 Torch ATen 연산의 FX 그래프로 추적하는 방식이었습니다. 이는 모델을 빠르게 실행하는 데 효과적이었지만, 모델의 의도를 희석시켰습니다. ATen을 통해 그래프를 세분화하면, 예를 들어 aten.mm는 타일링, 요소별 곱셈, 감소 등으로 분해됩니다. 따라서 컴파일러는 "matmul"을 인식하지 못하고 최적화하기 전에 다시 인식해야 하며, 축 및 연산 경계가 혼동됩니다. 또한, 모델링 단계에서는 컴파일러가 RNGD 대상에 필요한 힌트를 추가할 수 있는 좋은 위치가 거의 없었습니다. 컴파일러는 이미 대부분의 의미가 사라진 후에 최적화를 수행했습니다.

TCL은 모델의 의미와 구조를 보존하도록 설계되었습니다. 이는 핵심 작성자가 고수준의 @tcl.kernel 데코레이션된 Python eDSL 함수를 작성하여 어떤 연산을 수행할지 정의하고, 튜링, 스케줄링, 융합, 하드웨어 매핑 등은 컴파일러에 맡기는 방식으로 작동합니다. 핵심 아이디어는 DNN 모델이 본질적으로 의존하는 텐서 수축 연산을 1차원 원리로 취급하는 것입니다. 따라서 모델은 이러한 수축 연산에 직접적으로 표현되며, 구조가 유지됩니다. 이는 RNGD의 기본 TCP (Tensor Contraction Processor) 아키텍처와 일치하며, 이 아키텍처의 컴파일러는 동일한 원리를 기반으로 구축됩니다. TCL 커널은 이 컴파일러에 의해 실행 가능한 바이너리 (EDF)로 컴파일됩니다.

이러한 설계는 다음과 같은 이점을 제공합니다:

  • 직관적이고 컴파일러 친화적입니다. 작성자는 연산의 의미를 표현하며, 스레드 레이아웃이나 동기화에 대한 언급 없이 TCL은 컴파일을 위해 설계되었으므로, 여러 커널을 융합하고 단일 단위로 컴파일할 수 있습니다.

  • 모듈화 및 재사용 가능합니다. RMSNorm, Linear, MLP와 같은 커널은 많은 모델에서 공유되는 빌딩 블록이 됩니다. 따라서 새로운 아키텍처를 구축하는 것은 주로 기존 블록을 구성하고 진정으로 새로운 것을 추가하는 것입니다.

  • RNGD에 최적화되어 있습니다. 패딩, 샤딩, 브로드캐스트, 멀티 칩 콜렉티브는 언어 및 타입 수준에서 표현되므로, 컴파일러는 이러한 연산의 정확성과 최적화를 함께 고려할 수 있습니다.

결과적으로, 모델의 수가 아닌 재사용 가능한 블록의 수에 따라 기능 확장 규모가 결정됩니다. furiosa-kernels 패키지는 TCL 커널 (어텐션, MoE, 비전 인코더, 아키텍처별 블록)을 포함하는 Furiosa-LLM을 지원하는 커널의 집합이며, 이 패키지의 범위는 새로운 모델의 범위를 직접적으로 반영합니다. 이 라이브러리가 성장함에 따라, 향후 릴리스에서 새로운 모델을 빠르게 추가할 수 있을 것으로 예상됩니다.

새로운 모델 패밀리#

TCL 프레임워크를 기반으로, 2026.3 버전에서는 RNGD에 여러 새로운 모델을 추가합니다. 특히, 여러 개의 대규모 Mixture-of-Experts (MoE) 아키텍처를 포함합니다:

  • Qwen3-VL (예: Qwen3-VL-32B) — RNGD에 처음 등장하는 비전-언어 모델 패밀리입니다. 이는 Dense Transformer와 비전 인코더를 결합한 형태입니다 (Multimodal Serving 및 Qwen3-VL 참조).

  • gpt-oss (예: gpt-oss-120b) — MXFP4 양자화된 전문가 가중치를 사용하는 MoE 패밀리입니다.

  • Solar-Open (예: Solar-Open-100B) — NVFP4 양자화된 가중치와 16비트 활성화를 사용하고 KV 캐시 (NVFP4A16)를 지원하는 MoE 패밀리입니다.

  • Qwen3 MoE (예: Qwen3-30B-A3B) — 런타임에 동적 FP8 활성화를 양자화하는 MoE 패밀리입니다. Instruct, Thinking, Coder 등의 변형이 있습니다.

  • K-EXAONE (예: K-EXAONE-236B-A23B) — 다국어 MoE (Mixture of Experts) 패밀리, 하이브리드 슬라이딩 윈도우 + 글로벌 어텐션 방식 사용; NVFP4A16.

각 모델은 FXB (Furiosa Executable Bundle)를 제공하여 Hugging Face 저장소에서 직접 배포할 수 있습니다. 정확한 저장소 ID 및 배포 명령은 각 모델 카드에서 확인할 수 있습니다.

FXB: Furiosa 실행 파일 묶음#

2026.3에 Furiosa Executable Bundle (FXB)가 도입됩니다. FXB는 Furiosa-LLM의 공유 가능한 컴파일된 아티팩트 형식입니다. .fxb 파일은 manifest.json과 NPU에서 모델을 실행하는 데 필요한 컴파일된 커널 (edfs/)을 포함하는 단일 아카이브입니다. 모델을 .fxb로 컴파일하면 재컴파일 없이 모델을 배포하거나 다른 머신으로 복사하거나 Hugging Face Hub에 게시하여 다른 사람이 재사용할 수 있습니다.

FXB의 핵심은 아키텍처 지문입니다. manifest는 모델 아키텍처와 컴파일된 커널 (hidden size, head counts, vocabulary size, quantization 등)을 결정하는 구성 필드를 기록합니다. 따라서 동일한 지문을 공유하는 모든 Hugging Face 모델에서 단일 묶음을 재사용할 수 있습니다. 즉, 자체 저장소가 .fxb를 제공하지 않는 모델 (예: 미세 조정 또는 가중치를 업데이트한 지원 모델의 변형)을 로컬 캐시에서 호환 가능한 묶음을 재사용하여 배포할 수 있습니다. 이를 통해 각 변형에 대해 재컴파일할 필요가 없습니다.

전용 fxb 명령은 전체 라이프사이클 (빌드, 다운로드, 캐싱, 호환성 확인, 검사)을 관리합니다. 예를 들어, 자체 묶음을 제공하지 않는 Qwen/Qwen3-8B-FP8을 furiosa-ai/Qwen3-8B-FP8 묶음을 재사용하여 배포하는 방법은 다음과 같습니다:

# Download a published FXB bundle into the local cache
fxb download furiosa-ai/Qwen3-8B-FP8

# Confirm it is fingerprint-compatible with the target model
fxb check Qwen/Qwen3-8B-FP8

# Serve as usual — the compatible cached bundle is found automatically
furiosa-llm serve Qwen/Qwen3-8B-FP8

서비스 시 Furiosa-LLM은 다음 순서로 묶음을 해결합니다: 명시적인 --fxb 경로, 모델 저장소 내부에 있는 .fxb 파일, 그리고 로컬 캐시. FuriosaAI는 Hugging Face Hub에서 인기 있는 모델에 대해 미리 컴파일된 묶음을 게시합니다.

지문 기반의 호환성 매칭은 실험적인 기능입니다. 정확한 지문 필드의 세트는 향후 릴리스에서 변경될 수 있으므로, 다른 모델에 대한 캐시된 묶음을 사용하기 전에 fxb check를 사용하여 일치 여부를 확인하십시오. Furiosa 실행 가능한 묶음 (FXB)에서 묶음 형식, 호환성 매칭 규칙 및 전체 fxb 명령 참조를 확인하십시오.

멀티모달 서비스 및 Qwen3-VL#

2026.3 버전에서는 RNGD에서 비전-언어 (멀티모달) 서비스를 도입하며, Qwen3-VL-32B를 첫 번째 지원 모델로 제공합니다. 이미지와 텍스트 요청은 image_url 콘텐츠 부분을 사용하여 표준 OpenAI 호환 Chat Completions API를 통해 처리됩니다.

이 버전의 멀티모달 서비스는 여전히 실험적인 단계입니다. 멀티모달 요청의 스케줄링 및 배치 최적화가 진행 중이며, 다음 릴리스에서 추가 개선이 계획되어 있습니다.

OpenAI Python 클라이언트를 사용하는 최소 예제:

from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")

response = client.chat.completions.create(
    model="Qwen/Qwen3-VL-32B-Instruct",
    messages=[{
        "role": "user",
        "content": [
            {"type": "image_url",
             "image_url": {"url": "https://qianwen-res.oss-cn-beijing.aliyuncs.com/Qwen-VL/assets/demo.jpeg"}},
            {"type": "text", "text": "Describe this image."},
        ],
    }],
)
print(response.choices[0].message.content)

동일한 이미지를 여러 요청에서 다시 전송하고 재처리하는 것을 방지하기 위해, 멀티모달 입력은 안정적인 UUID로 태깅하여 서버 측 프로세서 캐시에서 재사용할 수 있습니다. --mm-processor-cache-gb를 사용하여 캐시 크기를 지정합니다. Vision-Language Models에서 지원되는 모델, 요청 형식 및 재사용 의미에 대한 정보를 확인하십시오.

중복 스케줄링: 제로 오버헤드 배치 처리로 향하기#

순방향 통과 사이, 추론 엔진은 호스트 측 작업에 실제 CPU 시간을 사용합니다. 여기에는 배치 스케줄링, KV-블록 할당, 그리고 라디스 캐시와의 프리픽스 매칭 등이 포함됩니다. NPU의 순방향 통과 사이에, NPU는 다음 배치를 준비하는 동안 대기하며, 짧은 디코딩 단계에서는 이러한 CPU 오버헤드가 각 반복의 상당 부분을 차지할 수 있습니다.

2026.3에 추가된 중복 스케줄러는 이러한 정체를 제거하여 한 배치를 미리 준비합니다: NPU가 현재 배치를 실행하는 동안, 스케줄러는 동시에 다음 배치의 모든 메타데이터를 준비합니다. 호스트 측 스케줄링 비용이 NPU의 컴퓨팅 작업과 병렬로 실행되므로, NPU가 지속적으로 데이터를 공급받을 수 있습니다. 처리량 중심 워크로드의 경우, 이는 전반적인 처리량과 출력 토큰당 시간(TPOT)을 향상시키지만, TTFT(전체 처리 시간)가 약간 증가합니다.

이 기능은 아직 실험 단계이므로 기본적으로 비활성화되어 있으며, 스케줄링 루프는 즉시 실행됩니다. 안정화되면 기본 설정으로 변경할 계획입니다. 중복 스케줄러를 명시적으로 활성화하려면:

furiosa-llm serve <model> --enable-overlap-scheduling

점수 기반 데이터 병렬 라우팅#

2026.2에 도입된 프리픽스 인식 데이터 병렬 (DP) 라우터는 2026.3에서 점수 기반 정책으로 진화하여, 복제본 선택 시 두 가지 신호를 균형 있게 고려합니다: 프리픽스 지역성 (이미 일치하는 프리픽스 캐시 항목을 보유한 복제본을 선호) 및 토큰 발자국 부하 (덜 혼잡한 복제본을 선호). 두 신호의 상대적인 가중치는 점수 프로필을 통해 선택됩니다.

# Scoring-based routing (default), balanced profile (default)
furiosa-llm serve <model> --data-parallel-size <N>

# Bias toward prefix cache affinity (equivalent to the old prefix-aware behavior)
furiosa-llm serve <model> --data-parallel-size <N> \
    --data-parallel-routing-policy scoring \
    --data-parallel-scoring-profile locality

--data-parallel-routing-policy 받아들이는 scoring (전기적으로) 또는 round-robin; --data-parallel-scoring-profile 받아들이는 balanced (전기적으로) locality, or load보시다시피 Data-Parallel 라우팅 세부사항을 알려주세요.

이 릴리스의 모든 변경 사항은 아래 "전체 변경 사항" 섹션에 요약되어 있습니다.

주요 기능 및 개선 사항#

  • FXB (Furiosa 실행 가능한 묶음)

    • 새로운 공유 가능한, 런타임에 컴파일된 아티팩트 형식으로, manifest.json과 컴파일된 커널(edfs/)을 하나의 .fxb 파일로 묶습니다.

    • New fxb 전체 라이프사이클에 대한 명령: build, download, add, check, cache ls/rm, show, 그리고 inspect.

    • 서빙은 묶음을 순차적으로 해결합니다: 명시적인 --fxb 경로, 모델 저장소 내의 .fxb 파일, 그리고 로컬 캐시 (핑거프린트 및 FuriosaIR 버전으로 매칭).

    • 파이프라인 병렬 처리 (-pp) 옵션은 FXB 기반 생성기에 전달됩니다.

엔진 코어#

  • 오버랩 스케줄러 (실험적; 기본적으로 비활성화, --enable-overlap-scheduling을 통해 활성화)는 1개의 배치씩 미리 실행하여, 호스트 측 스케줄링 오버헤드를 NPU 컴퓨팅과 겹치게 하여, 처리량과 TPOT을 개선하고, 작은 범위 내에서 TTFT 비용을 줄입니다.

  • 점수 기반의 DP 라우팅은 데이터 병렬 복제본 간에 프리픽스 지역성 및 토큰 풋프린트 부하를 균형 있게 분배하며, 라우팅 프로필을 통해 구성 가능합니다.

  • KV 캐시 개선 (이 릴리스의 주요 기반 변경 사항):

    • 통합 Radix 캐시는 전역만 사용되는 프리픽스 캐시 트리와 슬라이딩 윈도우 프리픽스 캐시 트리를 하나로 통합하여, 트리의 구조와 개별 구성 요소의 페이로드 간의 분리를 통해 새로운 캐시 구성 요소 유형은 자체 트리가 필요하지 않습니다. 또한, 이 작업은 장기 컨텍스트 (~128K 토큰) TTFT의 오차를 복구합니다.

    • KV 캐시 오프로딩 인프라 (기반 구축): 계층화된 블록 배치 모델 (NPU, 호스트 또는 이중 거주) 및 NPU↔호스트 DMA 오케스트레이터를 제공하여, 향후 릴리스에서 NPU 메모리 외부에 KV 블록을 오프로딩하는 기반을 마련합니다.

    • 더욱 강력한 NPU 메모리 예산: 공유 DRAM 버퍼 풀은 사용하지 않는 버퍼를 재활용하고, I/O 버퍼 공간은 분할 여유를 가지고 예약하여, 겹치는 스케줄링 (예: gpt-oss-120b 장기 컨텍스트) 하에서 대규모 모델에서 발생하는 메모리 부족 오류를 해결합니다.

  • 비동기, 병렬화된 Hugging Face 다운로드 및 snapshot_download에서 중복된 가중치 파일을 건너뛰어, 모델 로딩 속도를 향상시킵니다.

API 및 사용성 개선#

  • 제공 옵션:

  • 풀링 / 임베딩 / 로그 확률:

    • flm 인터페이스에서 풀링, 임베딩 및 로그 확률 지원을 확장하고, prompt_logprobs 누적 문제를 수정했습니다.

  • 구조화된 출력:

    • xgrammar을 0.4.0 버전으로 업그레이드했습니다.

    • 지정된 및 필수적인 도구 호출 경로가 생성된 JSON 스키마에 additionalProperties: False를 설정하여, 도구 스키마에 정의되지 않은 필드를 거부합니다. (JSON 스키마의 additionalProperties 속성을 False로 설정하여, 도구 스키마에 정의되지 않은 필드를 거부합니다.)

  • 관리/디버깅 API:

    • 테스트 및 성능 측정을 위한 /reset_prefix_cache (개발 모드에서 사용 가능) 프리픽스 캐시 재설정 엔드포인트를 추가했습니다.

    • 디버깅을 위한 RawModel 스케줄러 우회 API를 추가했습니다.

  • 신뢰성:

    • 데이터 병렬 배포의 깔끔한 종료를 위한 점진적인 DP 종료 기능.

플랫폼 및 패키징#

  • Python 3.14 지원: 지원되는 Python 버전은 3.10 ~ 3.14로, PyTorch 2.10 지원 매트릭스를 반영합니다.

  • 더 넓은 arm64 (aarch64) 지원: 네이티브 Python 패키지 (furiosa-native-llm, furiosa-tcc)는 x86_64 외에 aarch64 wheels도 함께 배포하며, 펌웨어 도구는 arm64 패키지를 제공하고, 클라우드 네이티브 구성 요소 이미지는 multi-architecture (linux/amd64 및 linux/arm64)를 지원합니다. 자세한 내용은 Released Components를 참조하세요.

  • Rocky Linux 10 지원: 드라이버 및 펌웨어는 Rocky Linux 10용 .el10 RPM 형식으로 패키징되며 (Debian 빌드 외에), 클라우드 네이티브 구성 요소 이미지는 Red Hat OpenShift 인증을 받았습니다 (Cloud-Native Components 참조).

🚨 주요 변경 사항 및 기능 제거#

  • /metrics는 GET 요청만 지원합니다:

    • /metrics 엔드포인트는 이제 GET 요청만 받습니다. 이전에는 /metrics에 대한 POST 요청도 200 응답을 반환했지만, 이제는 405 Method Not Allowed 오류를 반환합니다.

    • 마이그레이션: 모니터링 스크래퍼 또는 건강 상태 확인이 /metrics를 쿼리하는 경우, GET 요청을 사용해야 합니다.

  • 펌웨어 업그레이드는 이제 수동으로 수행해야 합니다:

    • 2026.3년 이전에는 펌웨어 이미지 패키지가 설치될 때 펌웨어 업데이트가 자동으로 실행되었습니다. 2026.3년 이후에는 이미지 패키지를 설치해도 업데이트가 자동으로 실행되지 않습니다. 설치 후에는 직접 펌웨어 업데이트 도구를 실행해야 합니다.

    • 이주다음으로: apt install firmware 도구 및 이미지 패키지의 실행 sudo furiosa_rngd_updater_all 모든 RNGD 장치를 업그레이드하는 것 (또는 furiosa_rngd_updater -b <BDF> -f <firmware image> 특정 장치에 대한), 다음 감기 재부팅을 수행합니다. 참조 FuriosaAI 소프트웨어 업그레이드 전체 절차를 참조하십시오.
